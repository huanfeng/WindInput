# 输入统计的速度模型

代码在 `wind-store/src/stats.rs`（存储与计算）与 `stat_collector.rs`（采集）。

速度 = `speed_chars × 60000 / active_millis × speed_factor`。这四个量都与「实际字数」统计分开：
上屏字数如实计（用户看的是产出），速度另有自己的分子分母。

## 旧口径为什么偏高

旧口径是「全部字符 / 整秒活跃时间」，下面四条都是单向正偏差，叠乘后偏高一倍以上：

| 偏差 | 成因 | 对策 |
|---|---|---|
| ① 整秒截断 | `num_seconds()` 向零截断，0.8s 的间隔记 0s；手越快砍得越狠 | 分母改毫秒（`active_millis`） |
| ② 口径不对称 | 间隔 ≥ 阈值时时间丢弃、字数照计 | 段首事件的字数也不进分子 |
| ③ 一次上屏 = 一个时间点 | 4 键出 7 字、1 键出一整条快捷指令 | `speed_chars_of` 按击键数封顶 |
| ④ 打错字无从感知 | 退格重打的字符计两遍、耗时算一遍 | `speed_factor` 经验修正（出厂 < 1） |

①②③ 是结构性的，必须在采集期修；只有 ④ 无法从输入法内部观测，才交给系数。不要用系数去
掩盖 ①②③。

## 封顶与「历史最快」

- `speed_chars_of`：击键数 ≤ `SPEED_SHORT_KEYSTROKES` 时按 `SPEED_SHORT_CHAR_CAP` 封顶。
  击键数为 0 表示未知，不封顶——TSF 英文批量上报一次就是几十个 1:1 击键的字符，误判会把
  英文速度砍到个位数。
- 段首那次上屏不计时，所以每天开头必然出现「字数已有几十、活跃时间才几秒」的窗口，此时外推
  速度上千字/分。`max_speed` 是永久记录，故 `qualifies_for_max_speed` 要求样本量足够；
  `recalculate_stats_meta` 从零重算，也是修正历史污染值的入口。
- 旧记录（无 `speed_v2`）没有分子分母，只能按旧口径回退，历史曲线在切换处有一道无法回补的台阶。
