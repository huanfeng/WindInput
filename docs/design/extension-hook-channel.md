# 扩展程序通道（设计）

状态：v1 已实现，只支持 Windows（范围见 §10）。日期：2026-10-22。

给扩展作者的协议说明与官方扩展（按键音等）在独立仓 WindInputExtensions（`docs/protocol.md`）。

## 1. 目标与非目标

**目标**：在不碰输入主流程的前提下，把输入过程中的若干状态（按键、组合、候选、上屏、模式）
异步投递给外部进程，满足小众的外围需求：按键音效、文本朗读、上屏特效、外部统计等。

**原则**：

1. 主流程不开放：不嵌入脚本语言、不加载第三方代码，扩展的任何行为都不能改变上屏结果。
2. 跨进程 + 异步：核心只投递，不等待；扩展宿主或扩展崩溃、卡死、慢都不影响打字。
3. 核心不联网的约束不变；扩展是用户自己安装的第三方程序，联网与否是扩展的事。
4. 不在系统里留残留：不写自启动项、计划任务、服务单元；扩展的一切都在用户目录下，删目录即卸载。

**非目标（v1）**：

- 候选注入 / 改写上屏文本。当前不接入，但协议为将来（如 AI 候选）**预留位置**，见 §7。
- 外部自行启动的进程接入。只有扩展宿主拉起的扩展能收到事件。
- Android（进程内直调形态，没有跨进程场景）。

## 2. 现状（设计依据）

- `wind-rpc` 已有事件通道（`src/events.rs`）：每订阅者一个有界 `sync_channel` + 独立 writer 线程，
  `try_send` 投递。分发与背压的写法可借鉴，帧格式（4 字节大端长度前缀 + JSON）沿用。
- **该通道不能用来推本设计的事件**：其 SDDL 为
  `D:P(A;;GA;;;WD)(A;;GA;;;SY)(A;;GA;;;BA)(A;;GA;;;AC)S:(ML;;NW;;;LW)`（`wind-rpc/src/security.rs`），
  Everyone、AppContainer、低完整性进程都能连——这是 TSF 宿主需要的。按键与上屏文本推上去，
  浏览器渲染进程这类沙箱代码也能订阅。本设计因此**不开任何具名端点**，见 §3.2。
- 密码框识别已有：DLL 在 focus_gained 上报 InputScope 掩码，`IS_PASSWORD` 位已折入
  context 级 `KEYBOARD_DISABLED`；协调器侧 `input_diag::is_password_scope(mask)`。
- 上屏出口不止一处：按键路径经返回的 `KeyAction`，命令/点击路径经 `push_commit_text` 走 push 管道。
  每日统计已解决过同样的问题：各路径调 `record_commit(text, code_len, pos, CommitSource)`，
  顶层 `record_input_stats` 兜底。扩展的 `commit` 事件挂在同一位置，复用 `CommitSource`。
- 组合矩形有 `composition_rect`（可能为 `None`，部分宿主不报）。

## 3. 架构

### 3.1 三层进程

```
 TSF/IMK/Fcitx ──按键──▶ 核心 ──KeyAction/push──▶ 应用
                          │ emit(HookEvent)  热路径：查原子标志 + try_send 小结构体
                          ▼
                        HookHub 线程：裁剪、序列化
                          │ 匿名管道（子进程 stdio）
                          ▼
                    扩展宿主 wind_input_ext             ← 核心拉起、核心监护
                          │ 匿名管道（子进程 stdio），每扩展一条
                ┌─────────┼─────────┐
                ▼         ▼         ▼
             扩展 A     扩展 B     扩展 C            ← 宿主拉起、宿主监护
```

- **核心**只认一个下游：扩展宿主。核心侧的开销与扩展个数无关。
- **扩展宿主**是我们自己写的小进程（Rust、无界面、常驻内存目标几 MB），负责扩展的启停、监护、
  权限裁剪、分发。扩展崩溃、刷屏、卡死都止于宿主，碰不到核心。
- **扩展**是第三方程序，任意语言，只需读写 stdio 上的长度前缀 JSON。

### 3.2 传输：只用继承的匿名管道

核心 → 宿主、宿主 → 扩展都用拉起子进程时建立的 stdio 管道，**不开具名管道或 socket**：

- 没有可被别人连接的端点，ACL、连接方身份校验这一整类问题都不存在。
- 对端身份由构造保证：管道另一端就是自己拉起的那个进程。
- 父进程退出，管道断开，子进程读到 EOF 即退出（与 §6 的进程绑定互为兜底）。
- 扩展实现门槛最低：读 stdin、写 stdout，不用碰平台管道 API。

扩展的 stderr 由宿主收集，写宿主自己的日志文件（按扩展分文件、限大小轮转）。

### 3.3 代码归属

- `HookEvent` 与协议 DTO 是纯数据，进纯逻辑 crate（候选：新 crate `wind-hook`）。
- 核心侧：协调器只产出 `HookEvent`；HookHub、拉起与监护宿主的代码放服务进程（`apps/service`）。
- 扩展宿主：新 app `apps/extension_host`，依赖 `wind-hook`，不依赖协调器。

## 4. 安全与权限

key 事件带具体按键，敏感度等同键盘记录器。以下全部是**必须项**。

### 4.1 安装与登记

- 扩展装在 `<userdata>/extensions/<id>/`，目录里有清单 `extension.toml`：
  `id`、名称、可执行文件（目录内相对路径）、参数、请求的档位、支持的协议版本。
- 宿主只拉起扩展目录内的可执行文件。不存 exe 哈希（扩展升级不必重新授权；先求简单）。
- **启用与授权**记在核心配置里（`features.extensions`）：总开关 + 每个扩展的启用状态与授予的档位。
  清单里的请求档位只是申请，实际以配置里的授予为准；用户在设置端明确勾选。
- 卸载 = 删目录 + 配置里残留的授权条目在下次加载时清掉。

### 4.2 授权档位

| 档位 | 内容 | 典型用途 |
|---|---|---|
| `key.class` | 按键分类（字母/数字/标点/空格/回车/退格/功能键…），无具体键 | 通用按键音 |
| `key.detail` | 具体物理键名 + 修饰键 | 按键位配音效 |
| `mode` | 中英、全半角、方案切换 | 状态提示 |
| `composition` | 当前编码串 | 特效、朗读编码 |
| `candidates` | 当前页候选文本（不含注释、不含内部权重） | 朗读候选 |
| `commit` | 上屏文本 + 来源 | 朗读、特效、外部统计 |
| `candidate.provide` | **预留**，v1 一律拒绝 | 将来的候选注入 |

裁剪分两级：

- **核心**按「所有已启用扩展的授权并集」决定发哪些事件给宿主；并集为空就不产出事件。
- **宿主**按每个扩展自己的授权再裁剪一次后分发。

### 4.3 降级规则（在核心执行）

- 焦点在密码框（`is_password_scope`）：`key.detail` 降为 `key.class`；`composition`/`candidates`/`commit` 不发。

### 4.4 日志

事件内容不入任何级别日志（核心与宿主都一样）。只记启停、崩溃、重启、熔断（扩展 id、原因）、丢弃计数。

## 5. 协议

核心 ↔ 宿主、宿主 ↔ 扩展用**同一套**消息格式；宿主转发时只做裁剪，不改结构。

### 5.1 帧与方向

- 4 字节大端长度前缀 + JSON。
- **双向**：v1 中扩展 → 宿主只有 `hello` / `subscribe` / `ping`，但帧格式从第一版起就按双向设计，
  为 §7 留路。
- 所有消息形如 `{"t": "<类型>", "v": 1, ...}`；未知类型、未知字段一律忽略（前向兼容）。

### 5.2 握手（宿主 ↔ 扩展）

```jsonc
// 扩展 → 宿主
{"t":"hello","v":1,"protocol":[1],"want":["key.detail","mode"]}
// 宿主 → 扩展
{"t":"welcome","v":1,"protocol":1,"granted":["key.detail","mode"],"core":"0.128.0"}
```

扩展身份由宿主按拉起关系确定，`hello` 不需要也不信任自报的 id。`want` 超出授权的部分降级，
`welcome` 回告实际档位。`subscribe{events:[...]}` 可随时收窄订阅。

### 5.3 事件公共字段

| 字段 | 说明 |
|---|---|
| `seq` | 每条管道单调递增；接收方据缺口发现丢包 |
| `ts` | 核心单调时钟毫秒；扩展据此丢弃过期事件（如按键音超过 50ms 不再播） |
| `sid` | 组合会话 id：一次编码输入从首键到上屏/取消共用一个，无组合时为 0。§7 依赖它 |
| `app` | 宿主应用的进程名（经 compat 同源的进程名，可为空） |

### 5.4 事件

```jsonc
{"t":"key","seq":1,"ts":123,"sid":7,"key":"a","mods":["shift"],"class":"letter","handled":true,"observed":false}
{"t":"mode","seq":2,"ts":124,"chinese":true,"full_width":false,"schema":"wubi86"}
{"t":"composition","seq":3,"ts":125,"sid":7,"code":"wq"}
{"t":"candidates","seq":4,"ts":125,"sid":7,"page":0,"selected":0,"items":["你","们"]}
{"t":"commit","seq":5,"ts":130,"sid":7,"text":"你们","source":"candidate","rect":[x,y,w,h]}
```

- `key.key` 是**物理键名**，沿用本仓小写键名风格（`a`、`1`、`space`、`semicolon`…）。
  wind-keys 的 `KEY_TABLE` 目前只覆盖标点触发键，需补成完整键名表（P1）。它不是产出字符：
  产出随中英、Shift、标点设置变化，按键位配音效要的是物理键。只有 `key.class` 档时，`key` 字段省略。
- 键名由 VK 推导：三平台前端送到核心的 `keyCode` 都已统一换算为 Windows VK，`scanCode`
  在 macOS/Linux 恒为 0，不可用。
- `key` 只表示**按下**，没有抬起事件（理由见 §8.2）。
- `key.handled`：输入法是否吃掉了这个键。
- `key.observed`：该键输入法本不处理，是前端为扩展额外上报的旁路通知（见 §8.1）。
- `commit.rect` 取组合矩形（屏幕物理像素），宿主应用不报时省略；特效扩展自行降级（如画在鼠标处）。v1 尚未填充，恒省略。

### 5.5 核心 ↔ 宿主的控制消息

除事件外，核心 → 宿主还有：`config{extensions:[{id, granted, options}]}`（启动时与配置变更时下发；
`options` 见 §6.4），
`shutdown`。宿主 → 核心：`status{extensions:[{id, state, restarts, dropped}]}`（状态变化时上报），
供设置端经 ctrl RPC 查看。

### 5.6 背压

- 协调器 → HookHub 的全局 channel 满：丢新事件，计数。
- 核心 → 宿主、宿主 → 扩展的写队列满：**丢最旧**并计数，不断开（按键高频，短暂卡顿不该被踢）。
  扩展连续 N 秒不读，按卡死处理（§6.2）。
- 下一条成功投递的事件带 `dropped` 字段告知期间丢了多少。

## 6. 生命周期

### 6.1 核心拉起并监护宿主

- 总开关打开且至少一个扩展启用时，核心拉起宿主；全部停用或关总开关时发 `shutdown`，超时则强杀。
- 宿主随核心生死，**不留孤儿**：
  - Windows：宿主放进 Job 对象，设 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`；核心退出（含崩溃）时句柄关闭，宿主连同扩展一起被系统结束。
  - Linux：宿主启动后 `prctl(PR_SET_PDEATHSIG, SIGTERM)`，并检查父进程是否已变。
  - macOS：宿主用 kqueue `EVFILT_PROC/NOTE_EXIT` 盯核心 pid。
  - 三平台都另有 stdin EOF 兜底。
- 宿主崩溃：核心按退避重启（1s、2s、4s…）；60 秒内崩 3 次即熔断，停止重启，托盘与设置端显示原因。
  核心不会因宿主的状态阻塞任何按键处理。
- 核心升级或重启：旧宿主随旧核心结束，新核心按配置重新拉起。

### 6.2 宿主拉起并监护扩展

- 按配置逐个拉起启用的扩展，工作目录为扩展目录，继承核心的会话环境。Linux 上要注意：由
  systemd 用户单元拉起的核心可能缺 `DISPLAY`/`WAYLAND_DISPLAY`，与 `wind-ui/src/linux_host.rs`
  记录的问题相同，扩展要画特效就得有它们。
- 扩展崩溃：退避重启；60 秒内崩 3 次熔断，只停这一个扩展，状态上报核心。
- 扩展卡死（写队列满持续 N 秒）：结束后按崩溃处理。
- 扩展也放进宿主的 Job 对象（Windows），随宿主一起结束。
- 配置变更（启用/停用/改授权）：宿主收到新 `config` 后增量启停，未变化的扩展不重启。

### 6.3 管理界面

- 已定：不另做带界面的管理器。扩展列表、启用、授权、运行状态放进设置端（设置端只在打开时运行，不承担常驻）。
- 落点是「高级 → 扩展程序」卡：总开关、每个扩展一行（状态 + 启用开关 + 「设置…」）。「设置…」里是授权勾选与
  按清单渲染的选项。首次启用一个扩展时默认授予它申请的档位，用户可再收窄。
- 总开关关着时，各扩展的启用开关置灰；「设置…」仍能打开，授权与选项只能看不能改。
- 第一次打开总开关先弹隐私提示：扩展能收到输入内容，输入法只转发、不审查扩展，勾选「我已了解」
  才能启用。同意记在设置端自己的 `wind_setting.toml`，之后不再提示。文档站的扩展页同样以警告标出。
- 扩展宿主 `wind_input_ext` 与核心一起签名（见 [code-signing.md](code-signing.md)）。第三方扩展由作者
  自行签名，输入法不校验。
- 设置端经 ctrl RPC 读写 `features.extensions` 配置、读取宿主上报的状态。
- 按键音示例扩展和协议说明放独立仓 WindInputExtensions，同为 GPL-3.0。

### 6.4 扩展选项

扩展自己的配置（按键音的音色、音量……）由扩展在清单里**声明**，设置端照声明渲染表单，
不为每个扩展写界面。

清单（`extension.toml`）：

```toml
[[option]]
key = "theme"
label = "音色"
type = "choice"                      # choice / bool / number
default = "keyboard"
choices = [
  { value = "keyboard", label = "键盘" },
  { value = "piano", label = "钢琴" },
]

[[option]]
key = "volume"
label = "音量"
type = "number"
default = 0.6
min = 0.0
max = 1.0
step = 0.05
```

- 值存核心配置 `[[extensions.list]]` 的 `options` 表里，只存用户改过的；没存的取清单默认值。
- 下发：核心 `config` 里每个扩展带 `options`；宿主按清单校验（未声明的键丢弃，类型不符或
  不在选项内的取默认值，数值夹到范围内），补齐默认值后发给扩展：

  ```jsonc
  {"t":"options","v":1,"values":{"theme":"piano","volume":0.6}}
  ```

  握手后立即发一次；之后只有选项变化时再发。选项、授权变化都**不重启扩展**：授权变化由宿主按新授权裁剪，不重发 `welcome`。
  不认识 `options` 的旧扩展按未知类型忽略。
- 校验在宿主而不在核心：清单在扩展目录里，宿主本来就读它；核心只转存设置端写入的值。
- 设置端经 ctrl RPC `extensions.inventory` 取扩展列表：清单（名称、申请的档位、选项声明）、
  清单错误、运行状态。写回仍走 `config.setItems` 的 `extensions.list`。
- 扩展目录里的私有文件（如 keysound.toml 的自备音效映射）照旧可用，管清单表达不了的东西；
  同一项两处都有时以 `options` 为准。

## 7. 为候选注入预留的位置（v1 不实现）

将来可能引入 AI 等候选来源。为免推翻协议，v1 先固定以下约定：

1. 授权档位 `candidate.provide` 已存在，v1 一律不授予。
2. 帧双向、消息带类型；将来新增 `suggest{sid, req, items}`（扩展 → 宿主 → 核心）不改帧格式。
3. `sid` + `seq` 让核心判定回应是否属于**当前**组合会话：会话已变或已上屏即丢弃。
   核心永不等待扩展——迟到的结果只能在下一次刷新时出现，或直接作废，不阻塞上屏。
4. 届时需重新评估：「核心不联网」的边界、注入候选的排序位置与标识、失败时的可见性。

## 8. 按键覆盖面调研结论

前提：只有本输入法是当前输入法、且应用有输入焦点时才收得到按键。下面都在这个前提下讨论。

### 8.1 哪些按键到得了协调器

| 情形 | Windows TSF | macOS IMK | Linux Fcitx5 |
|---|---|---|---|
| 中文模式普通键 | 到 | 到 | 到 |
| 英文半角字母/数字 | **不到**（DLL 本地放行） | 到（核心回 PassThrough） | 到 |
| Ctrl/Alt/Cmd 组合键 | 有输入会话或登记热键时才到 | 到 | 到 |
| 密码框 / KEYBOARD_DISABLED | **不到** | 到（核心抑制） | 到（核心抑制） |
| 无会话时的退格、回车、方向键等 | **不到** | 到 | 到 |
| 修饰键单独按下 | 不到（切换键只记标记） | 不到 | 不到 |
| 前端映射不出 VK 的键 | — | 不到（如 F 键） | 不到 |

证据：Windows 是白名单拦截，`OnTestKeyDown` 吃下的键才经 `OnKeyDown` → `_SendKeyToService`
送核心（`wind_tsf/src/KeyEventSink.cpp`，英文模式注释见 :756）；macOS/Linux 前端不做中英判定，
能映射的 keyDown 全发（`InputController.swift:469-488`、`WindEngine.cpp:827-838`）。

**结论**：Windows 上只靠协调器现有的输入，`key` 事件覆盖不全（英文模式整段缺失）。

**已定并实现：前端独立上报，不进输入流程。**核心经 `CONFIG_KEY_EXTENSION_KEY_OBSERVE` 告诉 DLL
  「有扩展订阅按键」（握手必推，扩展授权变化时广播）；开着时 DLL 在 `PassthroughNoter` 出口把放行给
  宿主的用户按键经 `CMD_KEY_OBSERVED`（0x021D，8 字节：vk + 修饰键）**异步**上报，核心转成
  `observed:true` 的按键事件，不进按键处理。未开时 DLL 每键只多一次原子读。
  - 判据同透传上报（`WindPassthrough::IsUserKeyIntoHost`：纯修饰键、自注入键不算）；Chrome/QQ 会在
    Test 判不吃后仍调 OnKeyDown，去重规则见 `wind_tsf/include/ObservedKeyGate.h`（有本机 g++ 单测）。
  - 只有 Windows 需要；macOS/Linux 现在已全发。
  - 密码框与 KEYBOARD_DISABLED 下旁路照样不发。
  - 代价：应用进程里每键多一次异步管道写；需在 DLL 加一条新的 async 命令。

即使有旁路上报，也做不到「全局按键音」：切到别的输入法或无焦点时仍收不到。要全局覆盖，扩展应自己挂
系统级键盘钩子，那就与本通道无关了。

### 8.2 键抬起

三个平台普通键的抬起**都不送核心**：

- Windows：只发切换键（Shift/Ctrl）的干净单击抬起和 CapsLock 抬起（`KeyEventSink.cpp:1782-1911`、`:2099-2154`）。
- macOS：`recognizedEvents` 只订阅 `keyDown | flagsChanged`，拿不到 keyUp（`InputController.swift:390-391`）。
- Linux：只发 CapsLock 与切换键单击的抬起，其余抬起本地吞掉或交还应用（`WindEngine.cpp:793-818`）。

**结论**：v1 的 `key` 只有按下。macOS 要拿抬起得改 `recognizedEvents` 并保证 keyUp 原样交还应用，
风险不值得为 v1 冒。以后若有需求（如按键音的「松开声」），走 §8.1 的同一条旁路补上。

### 8.3 其他发现

- 按键载荷没有「是否自动重复」字段，三平台都不传。v1 不补；以后要区分长按连发时，
  在旁路通知和现有按键帧里一并补上（Windows `lParam` 第 30 位、macOS `isARepeat`、Fcitx `isRepeat`）。
- macOS 的安全输入（secure input）：前端把它当密码框处理，核心抑制输入；「安全输入下输入法
  是否还收得到事件」代码未涉及，未实机验证。对本设计无影响——密码框本来就不发。

## 9. 已定的取舍

1. 「自动重复」标志：v1 不做。
2. `candidates` 不带注释，只给候选文本。
3. 不限制扩展行为（含联网），写进扩展说明。

**v1 只支持 Windows**：设置端在其他平台不显示「扩展程序」卡。

**开销实测**（2026-10-22，本机 release，无头协调器）：没有启用扩展时，按键路径上的扩展出口
`hook_after_key` 每次约 3ns（一次原子读），整条按键处理约 70µs，占比测不出。启用扩展（授予
`key.detail`/`commit`/`mode`，另有线程消费事件）时，出口每次 0.3–0.85µs，整条按键处理的差异
落在多次运行的波动内。

靶机（Dev 实例，按键延迟探针每轮 663 键，扩展关/开交替各两轮，开时启用按键音）：往返中位
0.52–0.54ms（关）对 0.49–0.50ms（开），p90 都在 1.55–1.65ms；核心每轮 CPU 1.03–1.13s，两种状态
无差别。宿主每轮 CPU 0.06–0.16s、私有内存 1.1MB，按键音扩展每轮 0.05–0.09s、1.9MB。
