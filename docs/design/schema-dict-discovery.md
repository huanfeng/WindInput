# 方案扩展词库的自动识别（细胞词库）

> 2026-10-09 设计稿，已定稿实施（S1–S8）。来源：rime-frost 细胞词库未使用的讨论；关联看板
> C2-1（扩展词库图形化增删，t68 / t246）、C2-36（一键挂载/启停，t177 / t214）、C2-66（一键导入热生效）。
> OpenCC 类转换（emoji / others / 中英 / 拆分）**不在本稿**，与 `${dict}` 注释的重叠另行规划。

## 1 目标与非目标

**目标**：用户把格式正确的词库文件放进方案的**指定目录**（用户目录覆盖层即可），设置端
「方案设置 → 扩展词库」里就自动出现这一项；**开启仍由用户在那里勾选**，出厂一律关。
全程不需要改方案文件或 `schema_overrides`。

**非目标**
- 不做文件监听：扫描发生在方案加载、`schema.getConfig` 时（core 本就没有 watcher）。
- 不做「导入向导」（拷文件 + 校验）：本稿先把「放进去就认」打通，向导是 C2-1 的下一步。
- 随安装包附带哪几张 rime-frost 细胞词库，单列在 §8（2026-10-10 已定）。

## 3 用户可见行为

1. 用户把 `idiom.dict.yaml` 放到 `%APPDATA%\WindInput\schemas\pinyin\ext\`。
2. 打开设置端「方案管理 → 全拼 → 方案设置 → 扩展词库」，列表里多出一项「idiom」（标题取
   词库头部的 `name:`），未勾选。全拼与双拼共用拼音主库，两个方案的列表里都会出现，各自独立开关。
3. 勾选并保存 ⇒ 该方案失效，下次使用时重建（大词库会弹「正在建立词库索引…」类提示，见 §6.3）。
4. 删掉文件 ⇒ 列表里消失；`schema_overrides` 里残留的 `{id, enabled}` 无害（被丢弃），不报错。

目录名起初沿用 rime-frost 的 `cn_dicts_cell`，S8 统一为各方案主词库目录下的 `ext`（§4）。

## 4 方案文件里声明「发现目录」

在方案文件里新增一段，声明哪个目录里的文件按什么类型自动识别：

```toml
# 拼音方案（S2 时出厂全拼 / 双拼这样声明；S8 起改走兜底，见下）
[[dictionary_dirs]]
path = "pinyin/cn_dicts_cell"   # 相对 schemas/，各层合并扫描
type = "rime_pinyin"
```

```toml
# 码表方案同样适用，例如五笔
[[dictionary_dirs]]
path = "wubi86/ext"
type = "rime_codetable"
```

- 由**方案声明**而非全局约定：方案作者决定「本方案的扩展词库放哪、按什么解析」，码表/拼音通用。
- 用户想给某个方案开发现目录，可以在 `schema_overrides` 里补这一段（需让 `merge_toml` 接受
  `dictionary_dirs`；只追加、不删除出厂声明）。——未实现，由下面的码表兜底覆盖了主要场景。

**兜底目录（2026-10-10，S7 码表、S8 拼音）**：`[engine] type` 为 `codetable` / `pinyin` 的方案没写
`dictionary_dirs` 键时，自动补一个 `<主词库所在目录>/ext`，类型同主词库（主词库取 `default = true`
那张，没有就取第一张）。出厂全拼、双拼、五笔、笔画和第三方方案不改文件就能用，目录名全部统一。
英文、混输不兜底（混输没有自己的词库）。

- 补进方案本身（不只在扫描时用），`schema.getConfig` 随之带上，设置端「打开扩展词库目录」不用另算。
- 写 `dictionary_dirs = []` 显式关掉兜底；主词库在 `schemas/` 根下时不兜底（否则会扫各方案共用的 `schemas/ext`）。
- 用子目录 `ext/` 而不是直接扫方案目录：真实用户目录里的方案目录常混着备份文件
  （如 `wubi86_addmissing（20260820_181420）.dict.yaml`）和别的方案共用的词库，平扫会把它们都列出来。
- 拼音起初按方案声明 `pinyin/cn_dicts_cell`，S8 改为同走兜底 `pinyin/ext`（维护者：统一更好）。随包细胞库
  组装到 `pinyin/ext/`；上游完整主表里的 `cn_dicts_cell/*` import 也就不会与它们重名。

## 5 识别规则（core）

注入点：`EngineManager::read_schema`，在 `merge_toml(override)` **之前**，对每个
`dictionary_dirs` 条目调用 `list_schema_resource_dir(path, ".dict.yaml")`，每个文件生成一个
`DictSpec`，追加到 `schema.dictionaries` 末尾：

| 字段 | 取值 |
|---|---|
| `id` | `dir:<相对 path 的文件主名>`，如 `dir:idiom`。带前缀，避免与方案手写的 id 撞 |
| `label` | 词库头部 `name:`（复用 `read_dict_head` / `dict_yaml_name`），空则文件主名 |
| `description` | 「自动识别：<相对路径>（用户目录/安装目录）」 |
| `path` | 相对 `schemas/` 的路径 |
| `type` | 继承 `dictionary_dirs.type` |
| `default` / `default_enabled` | `false` / `false`（出厂关） |
| `base_order` | 码表：排在全部手写扩展库之后（取已声明最大值 + 1 起递增）；拼音不读此字段 |

**跳过**：
- 方案里已有手写 `[[dictionaries]]` 指向同一路径的文件（手写声明优先）。
- 已被主库 `import_tables` 引用的文件——它们本就是主库的一部分。这条保证用户用上游完整的
  `rime_frost.dict.yaml` 覆盖主库时不会重复加载。

**扫描时机**：方案加载与 `schema.getConfig` 各扫一次，代价是一次目录列举加每个文件读头部几行；
不缓存，免得出现「放进去了设置页看不见」。

## 6 加载

### 6.1 拼音：分层，每张库各有自己的缓存

> 初稿是「把启用的细胞词库当作主表的追加 import，并进同一份 merged，缓存名带启用集合哈希」。
> 维护者问「能不能像码表一样分库，开关后不受影响」，改为分层（2026-10-09）。

`CachedDict` 新增 `Layered(Vec<CachedDict>)` 变体，首层是主库。启用的库**全是** rime_pinyin
时，`load_dictionary` 让每个库各走一遍单库合并（`load_rime_pinyin_dict`，各自的 `merged.wdat`、
音节边界与简拼段都在），组成分层视图交给 `PinyinEngine`。引擎对词库只用 6 个查询方法（精确两种、前缀、带边界前缀、
按音节截断的前缀、简拼）加 `has_longer_code`，全部在 `CachedDict` 内按层合并，**拼音引擎的调用点一处不改**。

合并语义以「与各层并成一份合并缓存逐项一致」为准（对拍测试 `layered_pinyin_dict_matches_merged_cache`）：

| 查询 | 合并方式 |
|---|---|
| 精确 | 权重降序、同权按层序、层内保持原序；`order` 重排为 0,1,2…（合并缓存的写法） |
| 前缀（含按音节截断的那个） | 每层各取 `limit` 条；每条的名次 = 层内名次 + **其他层同 code 下排在它前面的条目数**（权重更高，或同权而层更靠前，用各层精确查询去数）；再按单库的键（权重降序 → 名次 → code）排、截断 |
| 简拼 | 同码取高权重，按 (权重降序, 码字典序) 排、截断——合并缓存写简拼段正是这么排的 |
| `has_longer_code` | 任一层为真即真 |

两个容易做错的地方（各有夹具，变异验证过）：
- 名次不能跨层直接比，也**不能拿候选池重算**：按音节截断的查询在读端先取名次、再过滤，被滤掉的
  同 code 高权词（如单音节查询里的「西安」xi'an）不在池里，却照样占着合并缓存里的名次。
- 简拼同权要按码字典序，不能按层序。

**不跨层去重**：合并缓存同样保留重复项（下游引擎自己去重），保留才能逐项一致，也免得开一张细胞库就把
主库层内的重复项顺手吞掉。只有一层有结果时原样返回该层（最常见的情形，零合并代价）。

效果：
- 开关一张细胞词库只是多挂或少挂一层。方案失效重建时，主库与已建过的细胞库都直接 mmap 各自的缓存；
  只有第一次开启的那张要建一次自己的缓存。
- 全拼、双拼、混输的拼音子引擎共用同一批分层缓存（`reader_pool` 按路径共享映射），各挂各的层，互不顶掉。
- 没有「每种组合一份几十 MB 缓存」，也就不需要按组合哈希命名与清理。

`load_merged_dicts` 丢边界与简拼是独立缺陷，本稿不修；只有拼音方案混挂了别的类型才会走到它。

### 6.2 码表：直接走现有扩展层

码表扩展库已有完整机制（惰性加载、独立 wdat、热摘、影子层），发现的库就是普通扩展库，零新增。

### 6.3 实测（2026-10-09，本机 Linux，真实 rime-frost 数据，REPL）

| 场景 | 耗时 | 说明 |
|---|---:|---|
| 首次建主库合并缓存（无细胞库） | ~4 s | 一次性，之后读缓存 |
| 开 idiom（4.9 万条），首次 | 0.45 s | 主库读缓存 13 ms，idiom 建自己的缓存 |
| 开 idiom + composite（62 万条），首次 | 7.4 s，峰值 ~500 MB | composite 建自己的缓存 |
| 同上，第二次 | 0.18 s | 全部读缓存 |
| 全关 | 0.1 s | |
| 单次转换（400 条混合输入平均，含启动摊销，稳态） | 无细胞库 ~1.35 ms；开 idiom + composite ~2.0 ms | 多出约 0.65 ms，含 composite 带来的更多候选与跨层名次查询 |

探针「厚积而薄发」（只在 idiom 里）：不开时整句拼成「后继而勃发」；开了以后全拼与简拼 `hjebf`
首选都是它，`nihao` 等常用词候选不变。

大库首次开启要建缓存，期间沿用「慢才弹」的延时提示模式，不新增无条件提示。

## 7 排序

细胞词库与主库同 text 时取较高权重（现状如此，主库词不会被压低）。细胞独有的词用自身权重，
抽样分布如下（rime-frost 上游，2026-10-09 下载）：

| 词库 | 条数 | 权重中位数 | p90 | 最大 |
|---|---:|---:|---:|---:|
| idiom | 48,714 | 0 | 2 | 5,052 |
| place | 6,396 | 1 | 19 | 20,906 |
| history | 19,957 | 0 | 4 | 1,715 |
| name2 | 18,360 | 0 | 2 | 1,535 |
| food | 144,437 | 0 | 1 | 119,454 |
| exthot | 2,080 | 1 | 31 | 788 |
| composite | 622,481 | 6 | 39 | 6,577 |

主库中位数约 200（`pinyin.schema.toml` 注释），补全与整句让位的绝对阈值是 100 / 50。
所以绝大多数细胞词天然排在后面，**风险在离群值**（food 的 11.9 万、place 的 2 万会越过主库常用词）。

### 7.1 评测与决定（2026-10-09，S4）

**不设上限**（维护者定）。细胞库是用户主动开的，开了就是想打出里面的词。

评测：7 张全开（idiom / place / history / name2 / exthot / food / composite），扩展层权重临时用环境变量
封顶扫一组值（实验代码未入库）。代价看 pinyin_eval 界面序首选（样本固定取自主库文件，各档可比）；
收益看 420 个主库没有的细胞热词（每张取权重最高的 60 个，权重中位数 264）经 REPL 输入后的首选率。

| 上限 | 主库 E 短简拼首选（基线 73.6%） | 细胞热词全拼首选 | 细胞热词简拼首选 |
|---|---:|---:|---:|
| 不开细胞库 | 73.6% | 16.9% | 0.0% |
| 不设 | 72.5% | 68.6% | 18.8% |
| 1000 | 72.6% | 68.6% | 17.4% |
| 500 | 72.6% | 68.6% | 16.2% |
| 200 | 72.9% | 63.8% | 12.4% |
| 100 | 73.3% | 61.0% | 9.8% |
| 50 | 73.7% | 56.4% | 7.9% |
| 10 | 73.7% | 49.8% | 4.5% |

不设上限、全开时其余三类：A 普通词 −0.4、C 多音节 −1.0、D 混合整句 −0.4 个百分点。逐张开：idiom / place /
history / name2 / exthot 各类基本不动（idiom C −0.1），food A/C 各 −0.2，代价几乎全来自 composite。

全开时新丢的 30 条主库样本逐条看过，多为同音词竞争且细胞词合理（港中文 / 武力值 / 前脚掌 / 这张表；
「嫉恶如仇」比期望值「疾恶如仇」更标准），明显不该排前的只有少数（划船机 4833 压过「很常见」、
安室透压过「爱上他」）。上限与代价、收益是线性取舍，没有拐点；压到 200 以下要白丢 5～20 个点的热词
命中，只换回主库不到 1 个点。

随机抽的细胞词（权重多为 0～6）对上限不敏感，不能拿它评收益——被上限压住的恰是高权重热词，故收益
样本按每张库的权重取头部。

## 9 设置端（wind-setting）

列表本身不用改就会出现。小改动：
- label 为空时退回 id（现在行标题是空的）。
- 描述里显示来源层（用户目录/安装目录）。
- 本节加一个「打开扩展词库目录」按钮，打开用户目录下的发现目录（不存在就先建）。
- 设置对话框打开时重新 `getConfig` 已足够反映新文件，不另加刷新机制。

顺带修 CLI 口径不一致：`schema dict list` 在 `enabled` / `default_enabled` 都未写时按「启用」显示
（`schema_cli.rs:200`），引擎按「关闭」处理，统一成按引擎口径。
