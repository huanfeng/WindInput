# 内存占用：按用到加载、方案常驻策略与「高级 → 性能」

> 2026-10-08 设计；同日确认 §9：D1 出厂关（附启动校验缓存），D4 须用大拼音用户词库实测，D5 后续规划。
> 前置（已提交）：`1b7e36f2` 代次空提交、`a2b65c38` 推送队列有界、`aa9c6b75` 空闲时整理堆。

## 1 问题

功能越加越多，默认内存跟着涨。成因分三档，混在一起必得错结论：

| 档 | 例 | 特征 |
|---|---|---|
| 稳态常驻 | 方案引擎、反查索引、拼音表、简繁表 | 一直在 |
| 构建期峰值 | 索引重建、全表扫用户词 | 几秒后落回 |
| 高水位 | redb 读缓存 | 涨上去要等空闲回收才落 |

靶机实测（2026-10-08，19 万条拼音用户词，看 Private）：

| 场景 | 旧版 | 新版（`aa9c6b75`） |
|---|---|---|
| 启动后空闲 | 31.8 → 34.0 MB | — |
| 全表扫一次（`dict.listPaged`） | 38.3 → 61.7 MB | 32.4 → 50.5 MB |
| 空闲 60 秒回收后 | 38.6 MB | 32.1 MB |

结论：**Windows 堆自己会把大块还给系统**，「打字后不回落」在 Windows 上的成因不是分配器，
而是两件事：

1. 持续打字时数据库一直有人碰，60 秒的空闲回收永远等不到，redb 读缓存停在高位（上限 256 MiB）。
2. 一批结构**不看功能是否在用**就加载、加载后**永不释放**。

本设计处理第 2 条的全部和第 1 条的上限。

### 1.1 现状：「不看是否在用」的加载点

| 结构 | 规模 | 加载条件（现状） | 实际消费者 | 出处 |
|---|---|---|---|---|
| 方案引擎 | 每个方案一份引擎外壳 + 懒建索引 | 启动 1.5 秒后预热 `available` 全部 + 临拼目标 + english | 当前方案、临拼、临英 | `construct.rs:134-192` |
| 混输子引擎 | 与独立方案各一份 | 构建混输方案时新建，不复用表内实例 | 混输 | `manager.rs:5529/5571` |
| 反查索引（主码表） | wubi86 2.3 MB 常驻（≤3 MB 进堆） | `prewarm_indexes` **无条件** | 悬停[编码]、`${code_rev}`、联想、辅助码、自动造词 | `coordinator.rs:4699-4708` |
| `UserTextIndex` | 推断 19 万词 ≈ 5 MB/份，最多 4 份 | 悬停[编码]段按候选逐条触发；`${code_rev}` 经 `codetable_reverse_hint` 也会带上 | 同上 | `text_codes.rs:89`、`manager.rs:1273` |
| 拆字表 | 推断 ≈ 0.8 MB | 构造期 `build()` 恒加载（`sync_chaizi_assets` 只管切方案 / 重载） | `${chaizi*}`（出厂注释不含，悬停拆字段出厂关） | `coordinator.rs:2524`、`wind-reverse/lib.rs:842` |
| 简繁表 s2t + t2s | 实测约 1.6 + 0.2 MB | 启动恒加载，不看开关 | 简繁开着时上屏 | `coordinator.rs:2410-2428` |
| `CharPinyinIndex` | 约 9.2 MB | 首次加词 / `${pinyin}` 用于非拼音候选 | 加词反推拼音 | `pinyin/generate.rs:29` |
| redb 读缓存 | 实测 19 万词 ≈ 41 MB | 读到就进，空闲 60 秒才丢 | 用户词 / 词频 | `wind-store/store.rs:37` |

另有一条 CPU 成本：悬停提示**对当前页每个候选都渲染一次**（`coordinator.rs:6610-6674`），
不等鼠标悬停；出厂开着的「编码」段因此每次刷新候选都会碰反查索引和 `UserTextIndex`。

## 2 目标与非目标

**目标**

- 功能没在用，对应数据就不加载；用户关掉一个功能，下次重载配置后内存要真的降。
- 方案常驻有一个开关，在「切换零等待」和「内存随使用量」之间由用户取舍。
- 全表扫描撑高的 redb 读缓存扫完即回收，不再等 60 秒空闲（上限不动）。
- 长时间不用的懒建结构自动释放。

**非目标**

- 不做内存档位预设（「省内存 / 均衡 / 速度优先」一键切换）。`config-design-rules.md` R5 明令
  「不做预设 profile——会重新引入第三层裁决的雷区」。改为下面若干独立的项。
- 不把阈值、间隔做成配置键（R1：程序能判定的不加键）。空闲回收 60 秒、反查常驻阈值 3 MB 维持。
- 不改词库 mmap 架构（它在 Private 里本就是 0）。

## 3 原则：开关必须连着「加载」

用户反馈「用不到的功能能不能加开关」。**只隐藏显示、数据照样加载的开关，内存一分不降**，
所以每个开关都要落到「谁在决定加载」上。分两层：

1. **能从配置推出的，自动推**（不加键）：注释模板、悬停段、功能开关已经说明了要什么，
   由一处「需求汇总」算出要加载的集合（§4）。
2. **推不出的取舍，才加键**：方案是否全部常驻（§5）——它是「首次切换的等待」与「内存」的对称取舍，
   符合 R1 第 3 条。

## 4 按用到加载（不加键）

### 4.1 需求汇总 `DataNeeds`

由一个纯函数 `DataNeeds::derive(config, SchemaFacts)` 派生（实现见 `wind-coordinator/src/data_needs.rs`）。
**不放进 `ConfigBundle`**：方案级 / 模式级模板写在方案文件里，辅助码与自动造词随当前方案变，
而切方案不重建 bundle、`reload_user_config` 又是先建 bundle 后 `reload_from_config`——存进去必在
这两个时刻过期。改为在构造、配置生效、切方案、预热时现算，判据仍只在一处：

```rust
pub(crate) struct DataNeeds {
    pub reverse_index: bool,  // 悬停[编码]、code_rev、联想、辅助码、自动造词任一在用
    pub user_text: bool,      // 悬停[编码]、code_rev_all、辅助码
    pub chaizi: bool,         // 任一层注释模板或启用的悬停段引用 chaizi*
    pub pinyin_table: bool,   // ${pinyin}/${readings}、alt_commit 取拼音
    pub s2t: bool, pub t2s: bool, // 对应方向 enabled
}
```

判定要点（S1 实施时补全）：
- 方案级模板取**全部已安装方案**的并集，宁可多装一份拆字表也不要切过去才空。
- 悬停的逐字段 `${code_rev}` 走 `eval_text_var`，**不看** `code_hint_source`；`${code_source}` 单独
  出现也要查编码——两者都计入 `reverse_index`。
- 出厂结果：反查要、用户层要（全局模板含 `${code_rev}` 且临拼来源出厂 `auto`），拆字、简繁不要。
  即出厂只省拆字 + 简繁约 2.6 MB（推断）；主要收益在用户关掉功能之后。

判定材料已经现成：`Template::references`（`comment.rs:625`）、`CompiledTooltip::references`
（`tooltip.rs:150`），加上各功能的开关。**模板要覆盖三层**（全局 / 方案 / 模式级），漏一层就是
「开了功能却没数据」。

运行期才出现的格式串（cmdbar `dict.rev`、短语里的反查）无法事先判定：它们走**首次使用时
后台加载**，本次返回空、下次就有，与现有 `ensure_reverse_index_async` 同一模式。

### 4.2 各结构的改法

| 结构 | 改为 | 关掉后能省（推断） |
|---|---|---|
| 反查索引预热 | `prewarm_indexes` 第 ① 步只在 `needs.reverse_index` 时做 | 2.3 MB |
| `UserTextIndex` | 只在 `needs.user_text` 时刷新；不需要时清槽 | 每份约 5 MB |
| 拆字表 | `needs.chaizi` 才加载；变为 false 时卸载 | 0.8 MB |
| 简繁表 | 只预载 `enabled` 的方向；切换入口（热键、菜单、工具栏、命令栏）先同步加载再切 | 1.6–1.8 MB |
| 拼音表 | 维持恒加载：出厂悬停「拼音」段开着，且加词回退要用 | — |

简繁的「同步加载」已实测（S1，release，页缓存热）：s2t 1.3–3.4 ms、t2s 0.1–0.3 ms，远低于
50 ms，保持同步。下面是当初的顾虑：原注释怕的是「按键线程上做文件 I/O」。切换是一次性的用户动作，
不是逐键路径。STPhrases 1.5 MB，**实测单次加载 < 50 ms 才这么做**，否则改为后台加载并弹
「正在加载简繁数据」。顺带修一个现存缺口：菜单 / 工具栏路径（`message_handler.rs:395`）
**没有**「是否已加载」检查，热键路径有（`coordinator.rs:7974`）。

### 4.3 两个新开关（用户反馈）

R1 准入：两者都是「有用户明确不要」的真实偏好，且关掉能真正卸载数据。

| 键 | 出厂 | 关掉后 |
|---|---|---|
| `ui.tooltip.enabled` | `true` | 不再逐候选渲染悬停提示；`DataNeeds` 里悬停段的贡献全部归零 |
| `ui.candidate.comment_enabled` | `true` | 不渲染候选注释；注释模板的贡献全部归零 |

为什么不用「把模板设空」：模板是专家级字符串，普通用户找不到；而且三层裁决下全局设空会被
方案或模式级模板覆盖回来。总开关在三层之上，关就是关。

形态按 R3「开关 + 子配置」：`enabled` 与同表下的模板、段列表并列。设置端放在各自所在页
（外观 → 候选注释 / 悬停提示）卡片的首行，用 `enabled_when` 让子项随开关置灰。

## 5 方案常驻策略（加一个键）

### 5.1 键

| 键 | 类型 | 出厂 | 含义 |
|---|---|---|---|
| `schema.keep_all_loaded` | bool | 见 §9 D1 | `true`：启动预热全部方案并常驻（现状）；`false`：按需加载，长时间不用就卸载 |

一个布尔同时决定「预热」与「淘汰」：两件事是同一个取舍的两面——要么一切就绪，要么内存
随使用量走。拆成两个键会出现「不预热但永不卸载」「预热全部却又卸载」这类无意义组合。

### 5.2 `false` 时的行为

- 启动只建：当前方案、临拼目标（`input.temp_pinyin.enabled`）、english（临英开着时）、
  以及当前方案是混输时的成员所需。
- 其余方案首次切换时构建（已有 `ensure_loaded` 单飞，切换期间按现有逻辑等待）。
- **启动后台仍校验全部方案的派生缓存**（`.wdat` / `.wcmt` / `.wridx` 指纹），过期就重建，但
  建完**不留引擎**。切换耗时取决于缓存是否新鲜：缓存新鲜时只是 mmap + 建外壳，量级与 150 ms
  相当；缓存过期则要重建（雾凇 merged 实测 4 秒、峰值 491 MB）——这一步必须挪到启动后台，
  不能留给用户切换那一刻。峰值是构建期的，建完即落回，不进常驻。
- 后台每分钟检查一次，**30 分钟未用**的方案引擎从 `engines` 表摘除。不摘：当前方案、临拼目标、
  english、被已加载混输引用的。按应用记忆方案（`AppSchemaState.remembered`）里出现的方案
  **不保护**——它们本就是「最近用过」的判据，用了就会续期。
- 摘除复用 `invalidate_schema` 的扇出逻辑（它已经处理混输依赖、反查索引、单字码表），但**不
  清全部反查索引**：只清属于被摘方案的。

30 分钟不进配置（R1：「多久算不常用」程序能定，用户没有相反偏好）。

### 5.3 不做：混输复用独立子引擎

调研结论：混输的子引擎**构建参数与独立方案不同**（主码表的 `sentence_input` 取混输方案自己的、
`split_input` 恒 false；拼音侧关部分韵母、整句只出 1 条、禁全拼……，`manager.rs:5741-5780`），
不能像英文那样直接共享（英文能共享的前提是参数完全相同，`47d70cad`）。词库 mmap 本已按路径
共享，重复的只是引擎外壳。等 §8 的实测说明外壳确实可观，再单独立项。

## 6 redb 读缓存：全表扫描后回收（不加键）

> 2026-10-09 改定：上限保持 256 MiB 不动，只做「扫后回收」。

把缓存撑满的不是打字，而是**全表扫描**：读路径对缓存大小不敏感（1dead5b6 标定），打字只碰
词频与前缀所在的少数页；而下面这些操作一次就把整张用户词表的页读进缓存（19 万词 ≈ 41 MB），
之后要等「连续 60 秒没人碰库」才回收——持续打字时等不到：

| 扫描 | 触发 | 性质 |
|---|---|---|
| `UserTextIndex::build` | 悬停[编码]、`${code_rev}`，用户词代次一变就重建 | 后台、一次性 |
| `UserAssocIndex` 重建 | 联想开着、用户词 / 临时词变化 | 后台、一次性 |
| `dict.listPaged`（算 `total`）、`dict.search`、`dict.export` 等 | 设置页 | 请求驱动、可能连续 |

所以全表扫描（后台建索引与设置页请求）做完**只标记待回收**，库**空闲 3 秒**后由回收线程回收
并整理堆；60 秒的通用空闲回收不变。回收线程拍长由 10 秒改为 1 秒以支持这一档。

- **后台建索引也走这一档，不当场回收**：拼音出厂开着自动造词，打字中每学一个新词都会触发
  `UserTextIndex` 整表重建；当场回收会让按键线程陪等关库重开（本机实测 ≥7 ms，几乎全在关库刷盘），
  且每次重建都从冷缓存起扫。走短档后，持续打字（间隔 < 3 秒）期间不回收，停手 3 秒即还回去。
- 后台扫描不到 **1 万行**不标记，交给 60 秒长档——小库的缓存只有几页，回收纯属白付代价。
  设置页请求拿不到行数、且稀少，不设门槛。
- 除批量写之外，回收只在回收线程上发生。

本机实测（19 万条，库 32.6 MB）：全表扫后 RSS 19.6 MB → 标记、过短档后 4.6–4.8 MB（三次一致），
与只开库的 4.3 MB 相当。

> 另记：每学一个新词就整表重建 `UserTextIndex` 本身是 CPU 与内存抖动的源头，留给 S5 的重建节流 / 增量更新。

不做的：缓存上限下调或随数据量动态取值——小库本就碰不到上限，大库按数据量放大反而更占内存；
撑高缓存的是扫描而不是上限。

## 7 长时间后的淘汰（不加键）

| 结构 | 现状 | 改为 |
|---|---|---|
| `CharPinyinIndex`（9.2 MB） | `OnceLock`，随引擎永存 | 改 `Mutex<Option<Arc<..>>>` + 最后使用时间，30 分钟未用释放 |
| 单字全码表（`.wscc` 读回堆） | 单槽，切方案替换 | 同上，30 分钟未用释放 |
| `UserTextIndex` | 最多 4 槽 | 同上；且 `needs.user_text == false` 时立即清空 |
| 阴影缓存（wind-ui） | 32 条满了整体清，无闲置回收 | 并入图片缓存的 30 秒闲置回收 |
| 候选窗离屏表面 / 像素缓冲 | 按历史最大尺寸保留 | 窗口隐藏 30 秒后缩回 |

统一由一个「闲置清扫」驱动：协调器已有的后台线程每分钟一拍，逐项问「多久没用了」。
不为每个结构起线程。

紧凑化（与淘汰正交，单独一阶段）：`CharPinyinIndex` 两张 `HashMap<char, String/Vec<String>>`
每条单独分配，改成按字排序的数组 + 字符串池，推断 9.2 MB → 2–3 MB。改前按
`profile-peaks` 的办法先打点，**不按代码形状预判**。

## 8 「高级 → 性能」分区

按 R1 过滤后，真正进配置的只有 §5 一个键；§4.3 两个开关放在各自功能所在页。性能分区因此
做成**一个开关 + 一块只读诊断**：

```
高级
└─ 性能
   ├─ [✓] 常驻所有方案          ← schema.keep_all_loaded
   │      开着：切换方案零等待；关掉：只加载用到的方案，30 分钟不用自动卸载，省内存
   └─ 内存占用（只读）           ← 新 RPC system.memoryStats
         当前占用 32.1 MB · 已加载方案 3 个 · 用户词缓存 4.2 MB
         [复制诊断信息]
```

诊断块的用途是让用户反馈问题时能直接贴数，回答「是哪一档」：

- `system.memoryStats` 返回 Private（Windows）/ RSS（其他平台）、已加载方案列表、redb 缓存
  估计、各懒建结构是否在内存及其自报大小（复用已有 `heap_kb` 一类日志的数据源）。
- 只读，不进 REGISTRY；手写卡片，按设置端规矩补 `HANDWRITTEN` 搜索条目与锚点。

落点核对（R4 / R6）：新键三处 —— `config.rs` L1、`config_schema.rs` REGISTRY、`data/config.toml`
L2；设置端五道闸门；文档站 `settings/advanced.mdx` 新增「性能」节、`guides/config/schema.mdx`
补行；Android assets 是否跟随要问（移动端本就不预热，见 §9 D3）。新 label 的生字要过拼音检索表
守门（`pinyin_initials.txt`）。

## 10 分阶段
