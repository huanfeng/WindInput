# 连续辅助码（双拼，长句任意音节后）

状态：P0 spike 与 P1（击键坐标图、内部开关默认关、尚不含辅码）已在 `feat/aux-continuous` 实现；P2 起未开始。
2026-11-18，两轮可行性 spike 之后写成。
来源：双拼用户反馈——手心、万象 Pro 都能在长句任意位置打辅码，我们只能在串尾（`aux-code-direct.md`）。
前置：`aux-code-direct.md`（串尾直接辅助，已发布）、`aux-code-schema-source.md`（`AuxCodeLookup`）。

## 1. 问题

今天的直接辅助码每键把输入按奇偶拆成「前缀 + 末 1～2 位」，辅码只能出现在**输入串最末**。
要在长句中间限定某个字，只能先打完整句、再靠引导键后筛。用户希望像万象 Pro 一样：
每个音节后都可以直接跟 1～2 位辅码，边打边定字。

## 2. 万象 Pro 怎么做（读源码）

`wanxiang_algebra.yaml` 的「直接辅助」段用拼写运算，把每条词库编码派生出：双拼、双拼+1 位辅码、
双拼+2 位辅码、声调与辅码的各种乱序、大写变体。辅码因此是**音节拼写的一部分**，进入 librime 的
音节图，由整句打分消解「这个字母是辅码还是下一个声母」。`/` 结尾表示聚拢单字，用来避开与词组重码。
万象 Base 版只有 Lua 的两字词直接辅助，与我们现状相当。手心闭源，未能验证。

**我们不能照搬**：双拼先被 `ShuangpinConverter::convert` 按每 2 键一个音节转成全拼串，再进
DAG / 词图 / Viterbi；辅码是外挂的 `AuxCodeLookup`（字 → 码），不在词库里。串中间夹一个辅码字母，
后面所有键对整体错位。

## 3. 两轮 spike 的结论

语料：`grammar_sentence_eval` 的 189 句真实长句，转小鹤双拼，每句随机在 0～3 处音节后插入该字的
真实辅码（1～2 位），共 756 条。辅码表 `flypy_full`。（数字出自子 agent 的测量，未经第二人复跑。）

**B 路线（前端枚举多个「对齐」，各自跑现有引擎再合并）——否决**：整串合法对齐数可控（校验后均值
4～12、P95 8～30），但各对齐分别解码，引擎分数按词数平均、**跨对齐不可比**，「辅码字母读成音节」
的假对齐常赢。合并保守则辅码不起作用（1 处辅码首选率 23%），激进则不打辅码的输入也被改（86.8% → 16.4%）。

**A 路线（同一张图里加「吃掉辅码」的边 + 每个辅码字母的罚分，Viterbi 一次比较所有对齐）——有条件可行**：

| 首选率 % | 0 处 | 1 处 | 2 处 | 3 处 |
|---|---|---|---|---|
| 基线（辅码当普通键） | 86.8 | 6.9 | 0 | 0 |
| B 保守 | 86.8 | 23.3 | 47.1 | 68.8 |
| **A（罚分 λ=2）** | **86.8** | **87.8** | **89.9** | **91.0** |
| 上界（只跑正确对齐） | — | 90.5 | 93.1 | — |

- 前三命中率 95.8～97.4%；难例（不打辅码时原引擎首选错的 25 句）修复 84～88%，B 最好 56%。
- 0 处辅码整串首选与原引擎一致 100%（λ=2）。
- 每键耗时均值 0.66ms / P95 1.3ms（原引擎 0.95 / 2.4）。**只计解码本身、且是简化版，不可当成品数据。**
- **允许辅码打在词中字之后是必须的**：限定词末字时 1 处辅码首选率只有 59%。

**遗留问题（阻塞项）——逐键前缀**：奇数长度的前缀里，末键可能是残码也可能是辅码。原引擎靠词典补全
给首选（`qih` → 气候），spike 的图里只有单字残码，于是「启 + h 当辅码」赢了（`nikeyig` → 你课程、
`qiddn` → 漆雕）。0 处辅码的逐键前缀与原引擎一致率仅 89.9%；加一条「辅码后还没跟完整音节时，原引擎
首选保住第 1 位」（闸门 H2）后升到 98.7%，代价是 1 处辅码首选率掉到 81%。根因是图里缺多字残码补全节点，
**正式落地前必须补上并复测**。

spike 的近似（数字要打折看）：只有词典精确命中节点 + 单字残码节点，无模糊音 / 同键韵母 / 用户词 /
简拼 / 词典直出补全 / 重排；只测小鹤；语料切音节用最大匹配，有少量切错；位次取引擎序而非界面序。

**P0 复测（补全节点，2026-11-18）**：加上「残码 + 词典补全」节点后，0 处辅码逐键前缀（2154 个）与原引擎
首选不一致的个数（λ=2）：H 217 → 33，H2 27 → 11。H2 下 k=1 首选 81.0%（门槛 80%，余量很薄），
k=2/3 为 89.9 / 90.5；不打辅码的整串首选仍 100% 一致；每键 0.54ms / P95 1.2ms（原引擎 0.92 / 2.3）。
H2 剩下的 11 处差异逐条审视：新更对 0、新更差 9、不分优劣 2，**只有一种机制**——奇数长前缀里，
1 位辅码把键数凑成偶数后恰好拼出一个词，压过「完整词 + 残码起新词」的读法：`qiddn`（期待 → 漆雕）、
`nikeyig`（你可以 → 你课程）、`nagerfuiu`（那个人是 → 那个付出）。补全节点救不了这类（残码起的是新词），
且多是一闪而过（`qiddn` 再打一键恢复成「期待您」；`nikeyig` 持续两键）。λ 加大能压它（λ=3 剩 7 处），
但 k=1 掉到 79.9%。试过「尾部残码暂不展开」节点（罚分 1/2/3/5），前缀差异最低 8，但与辅码组合造出新的
假读法、整串首选下降，未采用。结论：**这是奇数长度下 1 位辅码与残码的固有歧义，单看键数奇偶分不开**。

**与万象 Pro 对比（2026-11-18，Docker 里跑 librime 1.13.1 + 万象 Pro + 语法模型；同一套万象辅码表、同一批 756 条输入；数据出自子 agent，未复核）**

| 首选率 % | k=0 | k=1 | k=2 | k=3 |
|---|---|---|---|---|
| Pro 直接辅助 | 93.7 | 47.6 | 33.9 | 20.6 |
| Pro，2 位辅码后补 `/` | 93.7 | 94.7 | 95.2 | 94.7 |
| 我们 H | 86.8 | 87.8 | 89.9 | 91.0 |
| 我们 H2 | 86.8 | 81.5 | 89.9 | 91.0 |

- 基线差 6.9 个百分点来自词库与语法模型，不是辅码机制。
- 1 位辅码：Pro 95.2%，我们 H2 89.3%；**2 位辅码：Pro 不加 `/` 仅 9.5%（要和下一音节抢切分，如 `vfjb` 先出「真金」，官方设计靠 `/` 聚拢），我们 75.2%**。
- 两边允许辅码打在词中字之后。Pro 对已对的字后打 1 位辅码零破坏，2 位不加 `/` 破坏 88/98（`vgqrjdgssi` → 证券等送）；我们 H 零破坏，H2 破坏 12/164，全是句尾 2 位辅码（闸门把原引擎首选放第一位所致，**待修**）。
- **逐键前缀闪动两边一致**：`qiddn` → 漆雕、`nikeyig` → 你课程、`nagerfuiu` → 那个付出、`yiruj` → 依山。区别：Pro 不打压，奇数长度前缀 833/1077 首选被辅码改掉（`qih` → 其、`vgq` → 狰），我们 H2 只有 11/2154。
- Pro 无专门闸门，靠「所有切分一起由语法模型比分」消歧；1 位辅码是无罚分的普通派生拼写。
- 上屏：辅码一并吃掉；部分选字后剩余辅码仍跟各自音节。
- 结论：方向与 Pro 同构，罚分 + H2 闸门值得保留（Pro 以大面积闪动换 1 位辅码命中率）；2 位辅码我们更强；
  可考虑提供 `/` 作为可选强制聚拢；H2 的句尾 2 位辅码破坏要在 P2 修。

## 4. 决定

| 项 | 决定 |
|---|---|
| 路线 | A：击键坐标上的联合解码（辅码边 + 罚分），否决 B |
| 范围 | 只做**双拼**；辅码 1～2 位小写字母；可打在**任一音节之后**（含词中字） |
| 不含 | 声调数字（万象的 7890）、大写辅码、`/` 聚拢——本期不做，设计不堵死（`/` 可作为 2 位辅码的可选强制聚拢，P2 后评估） |
| 与串尾直接辅助 | 串尾是连续辅助的特例，由同一套解码处理；`aux-code-direct.md` 的排序规则（§6）作为末尾辅码的闸门延续 |
| 开关 | 沿用 `direct`（出厂关），**不新增开关**（维护者已定，不做 `direct_scope`）；内部逃生口 `[engine.aux_code] continuous = false` 与编码栏分隔符 `preedit_separator` 是方案段内部项，不进设置页、无全局键 |
| 辅码罚分 λ | 内部常量，初值 2（log 概率量级），评测扫参定稿，不暴露配置；λ 与 k=1 首选率是跷跷板（λ=3 前缀更稳但 k=1 跌破 80%） |
| 闸门 | H2（辅码后未跟完整音节时原引擎首选保住第 1 位）；以 k=1 ≈ 81% 为代价压住前缀退化 |

## 5. 设计

### 5.1 击键坐标图

开启时，双拼的词图直接建在**原始击键坐标**上，不再先转全拼串：

- 音节边 = 2 个击键（现有键对规则，含零声母对、同键韵母、模糊音）；
- 音节边之后可选 **辅码边** = 1～2 个字母键；
- 节点 = 若干音节 + 在其中若干字之后吸收的辅码字母；`start / end / consumed_length` 都在击键坐标，
  打分仍用全拼码（`score_node` 同主路径）。

辅码边的合法性：它前面那个字（词内任一字，不限末字）的任一辅助码以这 1～2 位开头
（`AuxCodeLookup::any_code_starts_with`，与引导键、串尾直接辅助同口径）。不合法的辅码边不进图，
这是砍歧义的主力（校验表较松：每音节平均 11.4/26 个 1 位辅码合法，所以仍靠罚分排序）。

每个辅码**字母**扣 λ。作用：不打辅码的普通输入里，把字母当辅码的解释赢不过正常解释。

**为什么不保留全拼图、只把辅码当附注**（调研后否决）：辅码会改变后续键对的奇偶，不存在唯一的「干净击键流」或
唯一的全拼串；词内辅码也无法用「词后附注」表达。所以必须在击键坐标上建图。最小改法：边 = 击键对（带候选音节列表，
含模糊音 / 同键韵母），节点 `start/end` 为击键偏移，词典查询仍用拼出的全拼码，`LatticeNode.syl_mask` 仍与词典边界同域，
`LatticeNode` 不改。只替换 step 2/2c 的建图，step 1/3/4/5/6.x 继续吃全拼串。

### 5.2 多字残码补全节点（阻塞项）

补上原引擎「残码 + 词典补全」在击键坐标下的等价物，使「补全词被残码+辅码压过」这类系统性退化消失。
验收：逐键前缀与旧路径的差异逐条审视（spike 无补全时一致率 89.9%、H2 98.7%，仅作参考，非硬门槛）。
已知缺口：补全节点只取键对首读音、只查系统词库，不展开模糊音、不接用户词。

### 5.3 首选闸门

- **H**：联合解码首选**用了辅码**才改首选，否则原样用原引擎结果。
- **H2**：H 之上，辅码后面还没跟完整音节（末键悬空）时，原引擎首选保住第 1 位。
- 落地取舍待补全节点复测后定：补全节点到位后 H2 的代价应缩小。
- 取舍：比分闸门只比「辅码读法 vs 同终点无辅码最优路径」的分差；辅码读法拼出的是高频词时
  （`qiddn` 的「漆雕」若词频高）分差会超过裕度，挡不住这类闪动，只能靠 λ 与词频本身。
- 裕度按语法模型开 / 关分两档（关 5、开 10）：模型的转移分叠进路径分，分差尺度随之放大。
  `grammar.weight` 改变同样会改变分数尺度：模型开时裕度 = 5 + 10 × 权重（权重 0 退回 5，0.5（移动端出厂；桌面出厂不挂模型，勾上后同为 0.5）为 10，
  0.8 为 13；不暴露配置），扫参见附录「P3 界面序」。
- 落单（末键在 P1 读法里落单、被当成末字 1 位辅码）另用一档裕度 12，模型开关、权重都取同值：落单读法常是
  下一字的声母被借作辅码，假读法分差比非落单高，且不随权重放大。见附录「P3 界面序 · 落单裕度」。
- **界面序**：界面先按消费数分档。不过闸的整串整句（消费 n）压到同档对手（残码整句、补全）中最强者之下；
  有更靠前一档的候选时不动；同档一个对手都没有时不出（它在界面上必居首）。过闸的整串整句在整句池
  （`sentence_max_count > 1`）里排第 1、候选里带名次 1；不过闸的不进池。

### 5.4 协调器与上屏

- 命中的节点消费**原始击键**长度；上屏后剩余输入照常继续。
- 词频 / 学习记在**去辅码后的拼音码**下（「释读」记 `shidu`），辅码字母不进词频、不进用户词库。
- 编码栏沿用双拼击键分段，辅码附在所属音节后（形态由实现定，须让人看出哪些键被当成辅码）。
- 退格回滚、分步上屏、整句切换键（N-best）按原始击键串处理。
- **P3 交接清单**（P2 末审查结论）：
  1. 候选没有携带辅码位置：`AuxSpans` 仅在引擎内，`SentencePiece.aux` 只有个数；编码栏需新增 meta 字段。
     **P3 T2：已做。** `CandidateMeta::aux_keys`（击键坐标 `(起点, 长度)`），编码栏 `meta.preedit_split`：
     音节之间 `'`、辅码前分隔符（`ni hn'hc`、串尾 `ni'hc hn`）。分隔符是方案内部项
     `[engine.aux_code] preedit_separator`（默认空格；只认空串或由空格、`·`、`-`、`_`、`|` 组成的串，其余退回空格），
     串尾直接辅助的 `ui'du p` 同走这一项。
  2. 候选 code / 边界与消费数不一致：链断入口（`mod.rs:3595`）的整句 code 只有 P1 首音节；两处同文合并
     （`mod.rs:3773`、`3897`）只改消费数、不改 code。
     **P3 T2：已做。** 用了辅码的整句（末槽整句、链断入口、S_n、2c 残码，含不过闸的末槽辅码整句）的
     消费数、`code` / `boundary`（路径实际经过的音节去辅码，键对取首读音，末键残码取全拼残码）、
     `learn_code`（规范码，与 `code` 相同时 `None`）、辅码位置、编码栏由同一条解码路径读出；同文合并整套
     换成整句身份，只留已有候选的词库来源标记与权重。双拼边界校验对辅码候选豁免（码与双拼转换不同域）。
     记频随 `code`，T1 的临时防护已撤。分段上屏（选不带辅码的前缀候选）不吞其后的辅码字母，剩余缓冲照普通
     输入重解（待确认 #5 的现状，`partial_commit_leaves_aux_letters` 钉住）。
  3. 界面序下闸门复验（见附录「P2 评测」，消费长度排序可能使 6.5d 失效）。
     **P3 T3：已做。** 推测的机制成立但不是界面序掉点的主因：不过闸的整串整句与残码整句同处消费 n 一档时
     权重更高（6.5d 只压到末槽整句之下），在 k=0 前缀上抢首选（`womfyiqiqui` → 我们一期是）；改为压到同档
     最强对手之下（6.5e）。k≥1 界面序比引擎序低的主因是**末字 1 位辅码落单**：落单一律不放行，目标只剩
     消费 n−1 的末槽整句，界面上排在消费 n 的残码整句之后（每格 5～14 条）。见附录「P3 界面序」。
     其后落单改为按裕度 12 比分（维护者定），A 六格 k=2 全部 ≥ 88.9%，见同附录「落单裕度」。
  4. 耗时达标是开放功能的前提；批量前缀查询方案要改 `AuxCharLookup` trait。
     **P3 T0：已做首字母掩码（`letter_mask`），每键约省 75～110 µs；仍未达标，见附录「P3 耗时」。**
  5. 方案层反查索引未就绪时，trait 没有 `unready_schemas` 对应物；连续模式需照串尾直接辅助的做法当未就绪处理，

     **P3 T3：已做。** 过闸的进池排第 1（同文的末槽整句让给它），候选里带名次的整句按新池重编；不过闸的不进池
     （语料上不过闸又另成一条的 S_n 每格 0～3 条，进池收益可忽略）。
  7. 候选行为变更登记（`docs/architecture/candidate-behavior-changelog.md`）留给 P3。
     **P3 T4：已做**（2026-11-20 条目）。
  8. None 路径（击键图开、无辅码表）相对 `44ad1167` 的耗时未测。
     **P3 T0：已测**（相对旧路径整体 −14%～−18%，偶数长 +45～+81 µs、奇数长 −360～−720 µs，见附录「P3 耗时」）。
  9. `grammar.weight` 被改或模型为空时，闸门裕度仍固定为 10，无护栏。
     **P3 T3：已做。** 没挂模型 = 5；挂了 = 5 + 10 × 权重（`Grammar::weight`，不报权重的实现按 0.5）。

**串尾直接辅助在连续模式下的去留（P3 T1 盘点）**

维护者裁定：只留 `direct` 一个开关，串尾去留与万象 Pro 一致——万象没有、引擎能覆盖的并入连续模式；万象有、
引擎不覆盖的才保留最小行为。对照：万象 Pro 用 Docker 里的 librime 1.13.1 + 万象辅码；我们用 `build_dev/data`
（小鹤 + `flypy_full`，`real_data_tests::inventory_tail_vs_continuous`）。两边码表多数同码，不同的换成各自的码
（释 pl / bf，像 rn / rx）。

| 串尾行为 | 例 | 万象 Pro | 引擎（连续） | 连续模式下 |
|---|---|---|---|---|
| 词组**任一字**（非末字）1 位 | `uidu`+`p`（释）、`goqk`+`k`（国） | 无（`uidub` → 是赌…；`goqkk` → 过圊…） | 不出 | **不做**；辅码打在该字后：`gokqk` → 国情 |
| 词组 2 位跨字配对 / 任一字 2 位 | `uidupl` → 释读 | 无（`uidubf` → 试读本…） | 不出 | **不做** |
| 末字 1 位 | `uidu`+`y`（读）、`goqk`+`g`（庆） | 有（试读 侍读 识读 释读…；国庆 首位） | 出（句尾落单按裕度 12 比分，过闸时首位；不出带辅码的词） | **保留**（串尾一步只认末字） |
| 末字 2 位 | `goqk`+`gd` | 2 位是简拼级：过轻改 国庆…，补 `/` 才首位 | 出（国庆 / 6 首位） | 引擎出，串尾同文去重 |
| 单字 1 位 | `xl`+`r` → 像、`jxl`、`uip` | 有（像 儴；加 架 驾；视 失 氏） | 不出（单音节不当整句） | **保留** |
| 单字 2 位 | `xl`+`rn` → 像 | `xlrx` 不提前，`xlrx/` 才首位 | 不出 | **不做**（已定，与万象一致；`xlrn`、`jxlm` 由引擎自然序） |
| 偶数长保留前 2 个整词 / 整句 | `jxlm` → 加练 价廉 架 | 无专门规则，自然序同（价廉 首） | — | 连续模式下 2 位串尾已不做，无命中项可护；逃生口下保留 |
| 奇数长、前缀 ≥ 3 音节保首选 | `tuuugrk` | 无专门规则，自然序同（图书馆 首） | 闸门 | 保留，同上 |
| 上屏连辅码吃掉、词频记前缀码 | `uiduy` → 试读，记 `shidu` | 一并吃掉 | 整句消费整串 | 不变 |
| `max_phrase_len` | — | 无 | 不受约束 | 只约束串尾一步 |

结论：连续模式下串尾一步保留，规则由「任一字」（`DirectPhraseRule::Any`）改为「末字」（`Last`）——辅码只限定
紧挨在它前面的那个字，与词中辅码同一语义；排位护栏不变；前缀兜底解码与主转换用同一份选项。内部逃生口
`[engine.aux_code] continuous = false`（不进设置页）退回只做串尾、仍按任一字，与 0.124 起的行为相同（除退格重打时生僻命中被放行那条缺陷修复外逐字节一致）。
已发布行为的变化（T4 登记 changelog）：词组首字 / 中间字的串尾辅码不再提前（`uidup` → 释读、`goqkk` → 国庆 国情、
`uidupl` → 释读），单字 2 位也不再提前（`xlrn` → 像、`jxlm` → 架；万象要补 `/`，我们不做 `/`，维护者裁定与万象一致）。
连续模式串尾一步只做奇数长 1 位（`merge_direct_hits_into` 遇 2 位辅码直接返回）；末字 2 位由引擎出。

changelog 变化清单草案（T4 登记 `candidate-behavior-changelog.md`，连续模式下，逃生口不变）：

### 5.5 辅码表接口

`wind-engine` 目前不依赖 `wind-aux-code`。联合解码在引擎里需要字 → 码的查询，用 trait 注入

## 6. 开 / 关 与影响面

### 关（`direct = false`，出厂默认）

| 情形 | 行为 |
|---|---|
| `direct` 关、`enabled` 关、全拼、非双拼、混输 / 临时拼音、引导键态中 | **完全走现有路径**：全拼坐标图、现有 step 流程，不构击键图、不查辅码表 |
| 对拍口径 | 关闭时走旧路径，改动前后应一致；若 P1 起双拼统一到新坐标路径，则按 §9「差异审视」处理：**目标是方向正确，不要求与旧行为逐位一致**（旧行为本身可能有问题） |
| 耗时 | 无增加（入口判定走 `aux_code_settings_cached`，不读盘） |
| 持久化 | 无新增存储、无新文件格式，开关切换不留残余；已学的词频 / 用户词不受开关影响 |
| 热生效 | 开关变更沿用 `aux_settings_gen` 的失效代次，组合中途变更下一次整音节输入自愈 |

### 开（`direct = true` 且 `enabled` 生效且双拼）

- **影响面是该方案下的全部双拼输入**，不只是打了辅码的：开启后所有输入都走击键坐标联合解码。
  这是与旧串尾直接辅助的最大区别（旧版只在末尾多一次前缀解码）。
- 不打辅码的输入：整串首选与旧路径基本一致（spike 100%）；逐键前缀存在差异（spike H2 一致 98.7%）。
  差异按 §9「差异审视」逐条归类，**不以一致率为硬门槛**。
- **打字中途的闪动（须告知用户）**：奇数长度时，某一键可能让首选临时变成「词 + 辅码」的读法（`qiddn` → 漆雕），再打一键即恢复（`qiddnb` → 期待您）。这是 1 位辅码与残码的固有歧义，spike 中占逐键前缀的约 0.5%（11/2154），不影响最终上屏结果。
- **语义变化（须告知用户）**：输入串里的字母现在可能被解释为辅码。原本想打的简拼 / 残码（`nikeyig`）
  在开启后可能被当辅码解读，用 `'` 手动分隔可强制按音节切分。
- 耗时：spike 简化版每键 0.66ms；真实实现含模糊音、用户词等后需复测（基准各 ≥ 3 次）。
  **验收口径**：整体每键均值退化 ≤ 10%；分类看绝对增量（均值 ≤ 0.3 ms）；P95 与最大值的绝对增量
  ≤ 0.3 ms，其中「最大值」取逐键 3 遍最小值后的最大值。不要求每一类各自 ≤ 10%——偶数长前缀的旧路径
  本来就极便宜，比例被放大。
  这条口径是 P1 中途改的：原文是「P95 与最大值不退化」，但单遍最大值受调度尖峰支配、两个方向都会跳到
  几毫秒，P95 在偶数长上也确有几十到一百多 µs 的增量，「不退化」按字面达不到。实测见附录「P1 性能修复」。
  若分类绝对增量仍超线，增量建图（逐键复用前缀的图）另立项，作为 P2 前置。
- 已发布的串尾直接辅助用户：开启 `direct` 的人行为升级为连续辅助，串尾场景的排序规则保持（§4）。

### 已定（原「待维护者确认」）

1. 只用一个 `direct` 开关，不做 `direct_scope`：开着 `direct` 的双拼用户升级为连续辅助码（旧直接辅助用得少，
   以与主流 / 万象一致为准）。
2. 保留内部逃生口 `[engine.aux_code] continuous = false`（方案段、不进设置页、无全局键，经
   `aux_code_settings_cached` 读取、随 `aux_settings_gen` 失效）：退回 0.124 起的串尾直接辅助，逐字节不变。
   连续模式稳定后删除（未发布前改名 / 删除不做兼容）。
3. 编码栏分隔符：方案内部项 `preedit_separator`，默认空格，白名单见 §5.4 #1。

## 9. 验收

- **差异审视（取代逐位一致）**：目标是**最终方向合理正确**，不要求与旧行为百分百一致——旧行为也可能有问题。
  新旧路径有差异时，逐条（或抽样）归类为「新更对 / 新更差 / 不分优劣」，对「新更差」要么修、要么写明
  取舍理由并登记 `candidate-behavior-changelog.md`；`pinyin_eval` 看总体与分类是否不退化，而不是看逐条相同。
  仅「关闭 `direct` 时仍走旧路径」这一条保持原样，因为那时根本没动它。
- **基准语料**：沿用 spike 的 189 句 × 0～3 处辅码（扩大到更多句、更多布局：小鹤之外至少自然码、微软双拼）。
- **逐键前缀**：0 处辅码的逐键首选与旧路径的差异逐条审视，不出现系统性退化（如补全词被残码+辅码压过）。
- **难例**：不打辅码首选错的句子，辅码修复率 ≥ 80%，前三 ≥ 85%。
- **变异**：罚分置 0 → 0 辅码首选大跌；闸门关 → 前缀用例变红；辅码校验放行全部 → 1 处首选率大跌。
- **真实数据**（`build_dev/data`，缺数据跳过）：`uidupl` 一类串尾用例与改动前一致；
  长句中间辅码：`ughodvsdexnui`（`生活中的小事`，辅码打在已对的字上不得破坏）。
- 注意：worktree 里默认缺 `build_dev/data`，只能证伪不能证实；合入前在主仓复跑。

## 10. 风险

1. **双拼主路径整体换坐标**，回归面大（模糊音、用户词、屏蔽词、简拼、补全各路）。靠 P1 的对拍与并存期控制。
2. **前缀差异**依赖补全节点，是 P0 阻塞项（评判口径见 §9 差异审视，不是一致率）。
3. **语料偏小且只测小鹤**；难例仅 25 句，需扩大再下结论。
4. **辅码表较松**（每音节约 11/26 个 1 位辅码合法），依赖罚分；λ 需按布局与辅码方案扫参，
   可能不同辅码方案（自然码 / 墨奇 / 手心表）的最优值不同。
5. 两位辅码读成高频字等固有失败（见附录），不是解码方式能解决的。

### 增量建图最小方案（后续任务，不在 P3 做）

- **缓存什么**：引擎实例内按输入前缀缓存 `RawBase` 的建图中间态（`build_raw_aux` 的 `nodes` + `AuxSpans`，
  多字残码补全与用户词进图之前的那一份）；逐键输入恰是「上一键的串 + 1 键」，单槽即可，LRU 2 兼顾退格与
  翻页扩容 / 串尾直接辅助兜底解码插进来的另一条输入。
- **失效键**：方案 / 配置代次 + 辅码表代次（`aux_settings_gen` + 方案来源反查索引代次）+ 用户词代次
  （`words_generation`）+ 屏蔽词代次 + 模糊音配置；任一变即整份丢弃。辅码表由调用方逐键传入，键里要带调用方
  给的代次（`AuxCharLookup` 加 `generation()`，默认返回「不可缓存」，保持向后兼容）。
- **新一键重建什么**：起点在末 2～3 个槽（新键会改变末槽键对，或使末键落单 / 成辅码）的跨度与终点格；更早的
  起点复用旧节点，但终点落在旧串末尾附近、因新键而改变的长词跨度要按新串重算。多字残码补全、用户词进图、
  滤屏蔽词、转解码节点每键重做（量小）。
- **模型开**：S_n beam 的句尾分随终点变，整串整句解码不能复用（附录 P2 已试共用 beam，无收益），约 160 µs 留着。
- **预估**：3～5 天（同附录 P2）。
- **风险**：`convert` 从无状态变有状态（`&self` 下要内部可变 + 锁；并发调用不同输入互相踢缓存）；失效键漏一项
  就是静默的错候选；前缀判定要连 `'` 与大小写一起比。
- **对拍**：同 T0——两份导出去计时行逐字节对拍；另加「冷算 = 逐键热算」的逐字节比较（逐键前缀序列、退格序列、
  中途换辅码表 / 加用户词 / 改模糊音）。
- T4 的开关开放与否交维护者定（P3 计划待确认 #3）。

### 机制

- **附录 P2 推测的机制成立**：不过闸的整串整句（S_n，消费 n）被 6.5d 压到末槽整句（消费 e < n）之下，界面先按
  消费数分档，它与残码整句、补全同在消费 n 一档只比权重，权重是「末槽整句 − 1」，几乎恒压过残码整句。
  例：`womfyiqiqui`（k=0）S_n「我们一期是」178、残码整句「我们一起去吃」29，界面首选成了前者。
- **但它不是 k≥1 界面序掉点的主因。** 修复前后 k≥1 首选只差 0～1 条。A 上界面序比引擎序低 1～9 条（k=1 为 7～8），主因是**末字
  1 位辅码落单**：落单一律不放行，目标只剩消费 n−1 的末槽整句（引擎序首位，评测按文字算命中，但上屏会把辅码
  字母留在缓冲），界面上排在消费 n 的残码整句（`真的很不错就`、`我要校区上拉版我`）之后；串尾一步把它提到第 2 位
  的也算未命中。A 每格 k=1/2/3 各有 5～14 条属此类：把它们算上，A 六格 k=2 全部 ≥ 89.9%。
- 串尾一步（单字 / 末字 1 位，T1 保留的已发布行为）在 k=0 前缀上与旧路径差约 110 条（A）/ 103 条（B），
  与 `tail` 配置只差 0～1 条：是 0.124 起开着 `direct` 的现状，不是连续模式带来的。下文 k=0 只报引擎出处。

### 修法（6.5e）

不过闸的辅码整句按界面排序键（`candidate_display_order` 里权重之前的各键）找同档对手，压到其中最强者之下；
有更靠前一档的候选时不动（本就不居首）；一个对手都没有时不出（在界面上必居首）。放在消费数回映射之后、截断之前。
同档无对手而不出的情形少（多数时候「无同档对手」意味着闸门也没有对手、直接放行）；k≥1 样本的首选变化里见到 2 条：
`rflivpcdyrd` 人力财源（错读，去掉是对的）、`nirquyiyrkjkjubak` 你去医院看看吧（正当辅码被闸门挡住，B · 关 k=3
三布局各少 1 条）。

6.5e 只定引擎出口的初排。协调器其后的词频重排等步骤仍可让被压下的 S_n 重新居首（用户选过、词频高）：这符合
「词频可推翻先验」，不算闸门失效。

整句池：过闸的 S_n 在 `sentence_max_count > 1` 时进池排第 1（同文的末槽整句让给它），候选里带名次的整句按新池
重编（露 2 条时它原本不带名次，被整句块压到第 3）；不过闸的不进池（不过闸又另成一条的 S_n 每格只有 0～3 条）。
