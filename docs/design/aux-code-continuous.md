# 连续辅助码（双拼，长句任意音节后）

状态：**设计稿，未实施**。2026-11-18，两轮可行性 spike 之后写成。
来源：双拼用户反馈——手心、万象 Pro 都能在长句任意位置打辅码，我们只能在串尾（`aux-code-direct.md`）。
前置：`aux-code-direct.md`（串尾直接辅助，已发布）、`aux-code-schema-source.md`（`AuxCodeLookup`）。

## 1. 问题

今天的直接辅助码每键把输入按奇偶拆成「前缀 + 末 1～2 位」，辅码只能出现在**输入串最末**。
要在长句中间限定某个字，只能先打完整句、再靠引导键后筛。用户希望像万象 Pro 一样：
每个音节后都可以直接跟 1～2 位辅码，边打边定字。

## 2. 万象 Pro 怎么做（读源码）

`wanxiang_algebra.yaml` 的「直接辅助」段用拼写运算，把每条词库编码派生出：双拼、双拼+1 位辅码、
双拼+2 位辅码、声调与辅码的各种乱序、大写变体。辅码因此是**音节拼写的一部分**，进入 librime 的
音节图，由整句打分消解「这个字母是辅码还是下一个声母」。`/` 结尾表示聚拢单字，用来避开与词组重码。
万象 Base 版只有 Lua 的两字词直接辅助，与我们现状相当。手心闭源，未能验证。

**我们不能照搬**：双拼先被 `ShuangpinConverter::convert` 按每 2 键一个音节转成全拼串，再进
DAG / 词图 / Viterbi；辅码是外挂的 `AuxCodeLookup`（字 → 码），不在词库里。串中间夹一个辅码字母，
后面所有键对整体错位。

## 3. 两轮 spike 的结论

语料：`grammar_sentence_eval` 的 189 句真实长句，转小鹤双拼，每句随机在 0～3 处音节后插入该字的
真实辅码（1～2 位），共 756 条。辅码表 `flypy_full`。（数字出自子 agent 的测量，未经第二人复跑。）

**B 路线（前端枚举多个「对齐」，各自跑现有引擎再合并）——否决**：整串合法对齐数可控（校验后均值
4～12、P95 8～30），但各对齐分别解码，引擎分数按词数平均、**跨对齐不可比**，「辅码字母读成音节」
的假对齐常赢。合并保守则辅码不起作用（1 处辅码首选率 23%），激进则不打辅码的输入也被改（86.8% → 16.4%）。

**A 路线（同一张图里加「吃掉辅码」的边 + 每个辅码字母的罚分，Viterbi 一次比较所有对齐）——有条件可行**：

| 首选率 % | 0 处 | 1 处 | 2 处 | 3 处 |
|---|---|---|---|---|
| 基线（辅码当普通键） | 86.8 | 6.9 | 0 | 0 |
| B 保守 | 86.8 | 23.3 | 47.1 | 68.8 |
| **A（罚分 λ=2）** | **86.8** | **87.8** | **89.9** | **91.0** |
| 上界（只跑正确对齐） | — | 90.5 | 93.1 | — |

- 前三命中率 95.8～97.4%；难例（不打辅码时原引擎首选错的 25 句）修复 84～88%，B 最好 56%。
- 0 处辅码整串首选与原引擎一致 100%（λ=2）。
- 每键耗时均值 0.66ms / P95 1.3ms（原引擎 0.95 / 2.4）。**只计解码本身、且是简化版，不可当成品数据。**
- **允许辅码打在词中字之后是必须的**：限定词末字时 1 处辅码首选率只有 59%。

**遗留问题（阻塞项）——逐键前缀**：奇数长度的前缀里，末键可能是残码也可能是辅码。原引擎靠词典补全
给首选（`qih` → 气候），spike 的图里只有单字残码，于是「启 + h 当辅码」赢了（`nikeyig` → 你课程、
`qiddn` → 漆雕）。0 处辅码的逐键前缀与原引擎一致率仅 89.9%；加一条「辅码后还没跟完整音节时，原引擎
首选保住第 1 位」（闸门 H2）后升到 98.7%，代价是 1 处辅码首选率掉到 81%。根因是图里缺多字残码补全节点，
**正式落地前必须补上并复测**。

spike 的近似（数字要打折看）：只有词典精确命中节点 + 单字残码节点，无模糊音 / 同键韵母 / 用户词 /
简拼 / 词典直出补全 / 重排；只测小鹤；语料切音节用最大匹配，有少量切错；位次取引擎序而非界面序。

**P0 复测（补全节点，2026-11-18）**：加上「残码 + 词典补全」节点后，0 处辅码逐键前缀（2154 个）与原引擎
首选不一致的个数（λ=2）：H 217 → 33，H2 27 → 11。H2 下 k=1 首选 81.0%（门槛 80%，余量很薄），
k=2/3 为 89.9 / 90.5；不打辅码的整串首选仍 100% 一致；每键 0.54ms / P95 1.2ms（原引擎 0.92 / 2.3）。
H2 剩下的 11 处差异逐条审视：新更对 0、新更差 9、不分优劣 2，**只有一种机制**——奇数长前缀里，
1 位辅码把键数凑成偶数后恰好拼出一个词，压过「完整词 + 残码起新词」的读法：`qiddn`（期待 → 漆雕）、
`nikeyig`（你可以 → 你课程）、`nagerfuiu`（那个人是 → 那个付出）。补全节点救不了这类（残码起的是新词），
且多是一闪而过（`qiddn` 再打一键恢复成「期待您」；`nikeyig` 持续两键）。λ 加大能压它（λ=3 剩 7 处），
但 k=1 掉到 79.9%。试过「尾部残码暂不展开」节点（罚分 1/2/3/5），前缀差异最低 8，但与辅码组合造出新的
假读法、整串首选下降，未采用。结论：**这是奇数长度下 1 位辅码与残码的固有歧义，单看键数奇偶分不开**。

**与万象 Pro 对比（2026-11-18，Docker 里跑 librime 1.13.1 + 万象 Pro + 语法模型；同一套万象辅码表、同一批 756 条输入；数据出自子 agent，未复核）**

| 首选率 % | k=0 | k=1 | k=2 | k=3 |
|---|---|---|---|---|
| Pro 直接辅助 | 93.7 | 47.6 | 33.9 | 20.6 |
| Pro，2 位辅码后补 `/` | 93.7 | 94.7 | 95.2 | 94.7 |
| 我们 H | 86.8 | 87.8 | 89.9 | 91.0 |
| 我们 H2 | 86.8 | 81.5 | 89.9 | 91.0 |

- 基线差 6.9 个百分点来自词库与语法模型，不是辅码机制。
- 1 位辅码：Pro 95.2%，我们 H2 89.3%；**2 位辅码：Pro 不加 `/` 仅 9.5%（要和下一音节抢切分，如 `vfjb` 先出「真金」，官方设计靠 `/` 聚拢），我们 75.2%**。
- 两边允许辅码打在词中字之后。Pro 对已对的字后打 1 位辅码零破坏，2 位不加 `/` 破坏 88/98（`vgqrjdgssi` → 证券等送）；我们 H 零破坏，H2 破坏 12/164，全是句尾 2 位辅码（闸门把原引擎首选放第一位所致，**待修**）。
- **逐键前缀闪动两边一致**：`qiddn` → 漆雕、`nikeyig` → 你课程、`nagerfuiu` → 那个付出、`yiruj` → 依山。区别：Pro 不打压，奇数长度前缀 833/1077 首选被辅码改掉（`qih` → 其、`vgq` → 狰），我们 H2 只有 11/2154。
- Pro 无专门闸门，靠「所有切分一起由语法模型比分」消歧；1 位辅码是无罚分的普通派生拼写。
- 上屏：辅码一并吃掉；部分选字后剩余辅码仍跟各自音节。
- 结论：方向与 Pro 同构，罚分 + H2 闸门值得保留（Pro 以大面积闪动换 1 位辅码命中率）；2 位辅码我们更强；
  可考虑提供 `/` 作为可选强制聚拢；H2 的句尾 2 位辅码破坏要在 P2 修。

## 4. 决定

| 项 | 决定 |
|---|---|
| 路线 | A：击键坐标上的联合解码（辅码边 + 罚分），否决 B |
| 范围 | 只做**双拼**；辅码 1～2 位小写字母；可打在**任一音节之后**（含词中字） |
| 不含 | 声调数字（万象的 7890）、大写辅码、`/` 聚拢——本期不做，设计不堵死（`/` 可作为 2 位辅码的可选强制聚拢，P2 后评估） |
| 与串尾直接辅助 | 串尾是连续辅助的特例，由同一套解码处理；`aux-code-direct.md` 的排序规则（§6）作为末尾辅码的闸门延续 |
| 开关 | 沿用 `direct`（出厂关），**不新增开关**（见 §6「开 / 关」，待维护者确认） |
| 辅码罚分 λ | 内部常量，初值 2（log 概率量级），评测扫参定稿，不暴露配置；λ 与 k=1 首选率是跷跷板（λ=3 前缀更稳但 k=1 跌破 80%） |
| 闸门 | H2（辅码后未跟完整音节时原引擎首选保住第 1 位）；以 k=1 ≈ 81% 为代价压住前缀退化 |

## 5. 设计

### 5.1 击键坐标图

开启时，双拼的词图直接建在**原始击键坐标**上，不再先转全拼串：

- 音节边 = 2 个击键（现有键对规则，含零声母对、同键韵母、模糊音）；
- 音节边之后可选 **辅码边** = 1～2 个字母键；
- 节点 = 若干音节 + 在其中若干字之后吸收的辅码字母；`start / end / consumed_length` 都在击键坐标，
  打分仍用全拼码（`score_node` 同主路径）。

辅码边的合法性：它前面那个字（词内任一字，不限末字）的任一辅助码以这 1～2 位开头
（`AuxCodeLookup::any_code_starts_with`，与引导键、串尾直接辅助同口径）。不合法的辅码边不进图，
这是砍歧义的主力（校验表较松：每音节平均 11.4/26 个 1 位辅码合法，所以仍靠罚分排序）。

每个辅码**字母**扣 λ。作用：不打辅码的普通输入里，把字母当辅码的解释赢不过正常解释。

**为什么不保留全拼图、只把辅码当附注**（调研后否决）：辅码会改变后续键对的奇偶，不存在唯一的「干净击键流」或
唯一的全拼串；词内辅码也无法用「词后附注」表达。所以必须在击键坐标上建图。最小改法：边 = 击键对（带候选音节列表，
含模糊音 / 同键韵母），节点 `start/end` 为击键偏移，词典查询仍用拼出的全拼码，`LatticeNode.syl_mask` 仍与词典边界同域，
`LatticeNode` 不改。只替换 step 2/2c 的建图，step 1/3/4/5/6.x 继续吃全拼串。

### 5.2 多字残码补全节点（阻塞项）

补上原引擎「残码 + 词典补全」在击键坐标下的等价物，使「补全词被残码+辅码压过」这类系统性退化消失。
验收：逐键前缀与旧路径的差异逐条审视（spike 无补全时一致率 89.9%、H2 98.7%，仅作参考，非硬门槛）。

### 5.3 首选闸门

- **H**：联合解码首选**用了辅码**才改首选，否则原样用原引擎结果。
- **H2**：H 之上，辅码后面还没跟完整音节（末键悬空）时，原引擎首选保住第 1 位。
- 落地取舍待补全节点复测后定：补全节点到位后 H2 的代价应缩小。

### 5.4 协调器与上屏

- 命中的节点消费**原始击键**长度；上屏后剩余输入照常继续。
- 词频 / 学习记在**去辅码后的拼音码**下（「释读」记 `shidu`），辅码字母不进词频、不进用户词库。
- 编码栏沿用双拼击键分段，辅码附在所属音节后（形态由实现定，须让人看出哪些键被当成辅码）。
- 退格回滚、分步上屏、整句切换键（N-best）按原始击键串处理。

### 5.5 辅码表接口

`wind-engine` 目前不依赖 `wind-aux-code`。联合解码在引擎里需要字 → 码的查询，用 trait 注入
（`AuxCodeLookup` 或其只读视图），不引新依赖；输入流程**零读盘**（`no-disk-io-in-input-flow`）：
辅码表只用已在内存的来源，系统层未就绪时本键不做、候选原样、派后台构建（同现状）。

## 6. 开 / 关 与影响面

### 关（`direct = false`，出厂默认）

| 情形 | 行为 |
|---|---|
| `direct` 关、`enabled` 关、全拼、非双拼、混输 / 临时拼音、引导键态中 | **完全走现有路径**：全拼坐标图、现有 step 流程，不构击键图、不查辅码表 |
| 对拍口径 | 关闭时走旧路径，改动前后应一致；若 P1 起双拼统一到新坐标路径，则按 §9「差异审视」处理：**目标是方向正确，不要求与旧行为逐位一致**（旧行为本身可能有问题） |
| 耗时 | 无增加（入口判定走 `aux_code_settings_cached`，不读盘） |
| 持久化 | 无新增存储、无新文件格式，开关切换不留残余；已学的词频 / 用户词不受开关影响 |
| 热生效 | 开关变更沿用 `aux_settings_gen` 的失效代次，组合中途变更下一次整音节输入自愈 |

### 开（`direct = true` 且 `enabled` 生效且双拼）

- **影响面是该方案下的全部双拼输入**，不只是打了辅码的：开启后所有输入都走击键坐标联合解码。
  这是与旧串尾直接辅助的最大区别（旧版只在末尾多一次前缀解码）。
- 不打辅码的输入：整串首选与旧路径基本一致（spike 100%）；逐键前缀存在差异（spike H2 一致 98.7%）。
  差异按 §9「差异审视」逐条归类，**不以一致率为硬门槛**。
- **打字中途的闪动（须告知用户）**：奇数长度时，某一键可能让首选临时变成「词 + 辅码」的读法（`qiddn` → 漆雕），再打一键即恢复（`qiddnb` → 期待您）。这是 1 位辅码与残码的固有歧义，spike 中占逐键前缀的约 0.5%（11/2154），不影响最终上屏结果。
- **语义变化（须告知用户）**：输入串里的字母现在可能被解释为辅码。原本想打的简拼 / 残码（`nikeyig`）
  在开启后可能被当辅码解读，用 `'` 手动分隔可强制按音节切分。
- 耗时：spike 简化版每键 0.66ms；真实实现含模糊音、用户词等后需复测，**退化 > 10% 回头看**
  （基准各 ≥ 3 次）。
- 已发布的串尾直接辅助用户：开启 `direct` 的人行为升级为连续辅助，串尾场景的排序规则保持（§4）。

### 待维护者确认

1. 是否仍只用一个 `direct` 开关（我的建议）。备选：另设 `direct_scope = "tail" | "continuous"`，
   开着 `direct` 的老用户可选继续旧行为。代价是两套路径长期并存。
2. 联合解码上线初期是否保留一个内部逃生开关（不进设置页）以便出问题时退回旧串尾路径。

## 9. 验收

- **差异审视（取代逐位一致）**：目标是**最终方向合理正确**，不要求与旧行为百分百一致——旧行为也可能有问题。
  新旧路径有差异时，逐条（或抽样）归类为「新更对 / 新更差 / 不分优劣」，对「新更差」要么修、要么写明
  取舍理由并登记 `candidate-behavior-changelog.md`；`pinyin_eval` 看总体与分类是否不退化，而不是看逐条相同。
  仅「关闭 `direct` 时仍走旧路径」这一条保持原样，因为那时根本没动它。
- **基准语料**：沿用 spike 的 189 句 × 0～3 处辅码（扩大到更多句、更多布局：小鹤之外至少自然码、微软双拼）。
- **逐键前缀**：0 处辅码的逐键首选与旧路径的差异逐条审视，不出现系统性退化（如补全词被残码+辅码压过）。
- **难例**：不打辅码首选错的句子，辅码修复率 ≥ 80%，前三 ≥ 85%。
- **变异**：罚分置 0 → 0 辅码首选大跌；闸门关 → 前缀用例变红；辅码校验放行全部 → 1 处首选率大跌。
- **真实数据**（`build_dev/data`，缺数据跳过）：`uidupl` 一类串尾用例与改动前一致；
  长句中间辅码：`ughodvsdexnui`（`生活中的小事`，辅码打在已对的字上不得破坏）。
- 注意：worktree 里默认缺 `build_dev/data`，只能证伪不能证实；合入前在主仓复跑。

## 10. 风险

1. **双拼主路径整体换坐标**，回归面大（模糊音、用户词、屏蔽词、简拼、补全各路）。靠 P1 的对拍与并存期控制。
2. **前缀差异**依赖补全节点，是 P0 阻塞项（评判口径见 §9 差异审视，不是一致率）。
3. **语料偏小且只测小鹤**；难例仅 25 句，需扩大再下结论。
4. **辅码表较松**（每音节约 11/26 个 1 位辅码合法），依赖罚分；λ 需按布局与辅码方案扫参，
   可能不同辅码方案（自然码 / 墨奇 / 手心表）的最优值不同。
5. 两位辅码读成高频字等固有失败（见附录），不是解码方式能解决的。
