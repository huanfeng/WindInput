# 应用兼容性统一管理界面（设计）

状态：设计已确认，待评审 spec、待写实现计划。日期：2026-09-29。

## 1. 目标与非目标

**目标**：在设置端（`wind-setting`）新增「应用兼容性」页，统一管理 `compat.toml`，取代手改文件。

1. 区分系统默认与用户配置，可还原到系统默认（字段级 / 单条 / 全部）。
2. 后续新增兼容字段时，GUI 自动适配，不需要逐字段手写界面。
3. 用一个帮助页说明每个选项的功能与解决的问题。
4. 支持手动添加规则、导入、导出。

**范围**：`[[apps]]`（27 个字段）、`[[initial_mode_scope]]`、`[[commit_newline]]` 三段都管。

**非目标**：不做 markdown 渲染；不改变运行时的匹配维度（仍按进程名，窗口类只用于 `initial_mode_scope`）；不引入文件监听。

## 2. 现状（设计依据）

- 核心 `wind-config/src/app_compat.rs`：`AppCompatRule` 27 字段，全部容错反序列化。三层加载：`data/compat.toml` < `data_custom` < 用户层。同名进程整条覆盖，唯独 `ProtocolFields` 的 4 个字段（`composition_start_pair_guard`、`pin_anchor_when_start_drifts`、`ignore_host_ime_close`、`host_drawn_candidates`）用户未写时继承。（`ignore_host_ime_close` 0.132 起改名 `ignore_host_ime_switch`。）
- 没有「禁用 / 删除系统条目」的语法；没有 compat 的 schema（字段含义只在注释里）；`wind-rpc` 没有任何 compat 方法。
- 重载只有 `Coordinator::reload_app_compat`（`handle_menu.rs:901`），且只被右键菜单路径调用；同 pid 的 `active_compat` 缓存不会自动刷新。
- 用户层写入是 `update_user_rule` → `render_user_compat` 整份重写，非原子；TOML 语法错误时整份文件被静默跳过。
- 设置端是纯 Rust 原生 GUI（`windui`），无 Wails / 前端包。manifest 驱动只覆盖全局配置；没有帮助页组件，没有进程选择器。

## 3. 架构：核心 RPC + 字段元数据（方案 A）

合并、禁用、还原语义**只在核心实现一份**；设置端只经 `compat.*` RPC 读写，不直接碰文件，也不复制合并逻辑。字段元数据由核心提供，设置端表单与帮助页读同一份。

### 3.1 规则状态

| 状态 | 含义 |
|---|---|
| `system` | 只来自系统层，未被动过 |
| `modified` | 系统规则被用户改写 |
| `user` | 用户新增 |
| `disabled` | 系统规则被用户禁用，合并后该进程无规则 |

### 3.2 两个必须先解决的语义

> ⚠ **第 2 条「写时复制」已被第 11 节的整体原则取代**（用户层只记差异，逐字段叠加，不再拷贝系统字段）。第 1 条「禁用语法」仍然有效。

1. **禁用语法**：用户层条目允许 `disabled = true`，合并后该进程整条视为不存在。三段都加此字段。`is_empty_override` 与 `build_lookup` 需据此调整。
2. **写时复制**：现有整条覆盖会让「只改系统规则一个字段」丢掉其余字段（协议字段除外）。因此修改系统规则时，核心先把系统规则完整复制为用户条目再改。字段级还原 = 把该字段设回系统值；若整条与系统一致则删除用户条目。

### 3.3 RPC

| 方法 | 作用 |
|---|---|
| `compat.schema` | 字段元数据（见 3.4） |
| `compat.list` | 合并视图：每条带状态、有效值、系统值、用户改写字段集；参数 `section` 区分三段 |
| `compat.upsert` | 按进程名 + 字段补丁写入，内部写时复制 |
| `compat.setDisabled` | 禁用 / 启用一条系统规则 |
| `compat.reset` / `compat.resetAll` | 单条还原 / 清空用户层三段 |
| `compat.export` | 生成文本，范围：`user`（仅我的改动，默认）/ `effective`（含系统） |
| `compat.import` | `dryRun` 预览；`mode`：`merge`（同名覆盖）/ `replace`（先清空用户层） |

每次写入后核心自动 `reload_app_compat` 并使当前焦点进程的 `active_compat` 缓存失效（需处理 `pid_names` 复用，见 `revalidate_pid_name`），并广播 `compat.changed`。

### 3.4 字段元数据

核心 `wind-config` 新增 `compat_schema`（静态注册表），每字段登记：

| 项 | 说明 |
|---|---|
| `key` / `kind` | 字段名 / 控件类型：开关、三态（跟随全局·开·关）、枚举、整数、定位组 |
| `group` | 分组：候选窗定位、状态气泡、初始状态、宿主协议等 |
| `label` / `summary` | 界面名称 / 一句话功能 |
| `problem` | 解决什么问题（帮助页主体） |
| `hosts` | 已知需要它的软件 |
| `depends_on` | 联动条件，如 `candidate_x/y` 仅 `fixed` 模式有意义 |
| `protocol` / `advanced` | 是否协议字段（决定继承与还原行为）/ 是否折叠进「高级」 |

**守护测试**：对比 `AppCompatRule` 序列化字段名与注册表，漏登记即红。这补上「新增字段无兜底」的缺口（当前 `stale_probe_guard`、`password_force_english`、`schema`、`status_*` 就不在 `data/compat.toml` 顶部注释里）。

## 4. 设置端界面

- 新页「应用兼容性」，左右布局。左：规则列表，带搜索与筛选（全部 / 已修改 / 自定义 / 已禁用），状态徽章。右：所选规则详情。
- 顶部分段切换三段：应用规则 / 初始模式作用域 / 上屏换行。
- 通用渲染器：详情按 `group` 分卡片；每字段一行 = 名称 + `summary` + 控件 + 「已改写」标记 + 单字段还原按钮；复合字段按 `depends_on` 成组，条件不满足置灰。`initial_mode_scope.classes` 用列表编辑控件。
- 页头「全部还原」，条目菜单「还原 / 禁用 / 启用 / 删除（仅用户规则）」。
- 复用：`SubNav`、`section`/`setting_row`、`build_confirm_dialog_shell`、dict 页的 `CategorySpec`/`Feedback` 思路；Tab 注册改 `cli.rs` 的 `PAGES`、`pages/mod.rs` 的 `all_tabs`、`icons.rs` 的 `nav_icon` 三处，且顺序一致。

### 4.1 帮助页

页头「帮助」入口，按分组列出每字段的功能、解决的问题、已知宿主、取值说明，数据来自 `compat.schema`。字段行信息角标点击跳到对应条目。纯文本，长说明用分节对话框。

## 5. 手动添加、导入导出

**添加**：输入进程名，校验 = 去首尾空格、不含路径分隔符、不区分大小写；可「从运行中进程选择」（设置端枚举，去重，排除已有）；同名已存在则跳转到该条。新规则先是内存草稿，首次设置字段时才 `upsert` 落盘（空壳规则本就会被剔除）。

**导出**：标准 `compat.toml` 片段，可直接放进用户层；内容由核心生成，与落盘共用同一渲染函数。设置端只负责保存对话框（参考 `dict/state.rs` 的 `do_quick_export`）。

**导入**：选文件 → `dryRun` → 预览对话框（新增 N / 覆盖 M / 禁用 K / 无变化，逐条可看；列出被忽略的未知字段与被回落的错误值）→ 选 `merge` 或 `replace` → 确认写入。写入前备份原用户层为 `compat.toml.bak`。

## 6. 健壮性

- TOML 语法错误：导入与管理页路径**明确报错并给行号**；运行时加载仍容错但补 WARN 日志（现状静默）。
- 落盘改为临时文件 + rename。
- 设置端与右键菜单统一走核心同一入口，核心内一把锁串行化。
- 容错回落的错误值收集为 `warnings`，随 `compat.list` / `compat.import` 返回。

## 9. 已定决策与风险

- **禁用 / 启用**：禁用时用户条目保留已有的改写字段并加 `disabled = true`；启用只去掉 `disabled`，恢复到禁用前的状态（可逆）。要回到系统原貌用「还原」。`ProtocolFields` 继承只对未禁用的条目生效。
- **`data_custom` 层**：在视图里与系统层同等对待，只读，状态记为 `system`。
- **`active_compat` 缓存失效**：写入后清掉缓存的 pid 并对已连接 pid 走现有的 `Connected-pid compat refresh` 路径重算，不依赖焦点切换。实现时用靶机日志（`Compat rule for process=` 行）验证。
- **`[[initial_mode_scope]]` / `[[commit_newline]]`**：目前只透传、无写入 API，P1 补齐，同样支持 `disabled`、写时复制与还原。
- **风险**：核心合并语义变化会影响右键菜单的既有写入路径（共用 `update_user_rule`），P1 必须保持其行为不变，并用既有测试兜底。

## 10. P1 实现中的修正与补充（2026-09-29，独立审查后）

> 本节中与「协议字段 `InheritBool`」「写时复制」「导入按字段合并到系统拷贝上」有关的条目，已被第 11 节取代；其余仍然有效。

实现后经独立审查，下列语义与第 3~6 节初稿不同，以本节为准：

- **协议字段用「出厂 / 开 / 关」**（`Kind::InheritBool`），不是「跟随全局 / 开 / 关」：`null` 表示继承系统层，
  与全局设置无关。冗余判定（用户条目是否与系统一致）必须**先按运行时同一套规则做协议字段继承**再比较，
  否则「把协议字段置空」会留下一条视图里看不见的空壳，把以后出厂新增的修复整条挡掉。
- **导入按字段合并**，不是整条覆盖：底子是用户条目，其次是系统条目的完整拷贝，导入里写了的键覆盖、没写的保留。
  分享片段常只有一两个字段，整条覆盖会让系统规则的其余字段（出厂宿主修复）静默丢失。要整条替换用 replace 模式。
  导入保留原始键值：`caret_use_top = false` 序列化时会被省略，只看结构体就丢了「显式覆盖出厂 true」的意思。
- **补丁严格校验**：键必须是登记字段、不得含 `process`/`comment`/`disabled`、JSON 类型要与控件类型相符、
  值域外取值（容错反序列化只会记一条「回落」）一律拒绝；别名（`en`/`zh`）和带空白的文本不算无效。
- **data_custom 层禁用的规则不出现在视图里**（运行时本来就没有）。
- **写锁真实存在**：进程内 `lock_user_compat()`，`update_user_rule`（右键菜单）与 `compat.*` 写方法在读到写完的
  全程持有。落盘为 唯一临时名 → 写满 → `fsync` → rename。
- **损坏的用户层**：`list` 与合并导入等要保留现有内容的方法报错（带行号）；`resetAll` 与 replace 导入本来就要丢弃
  现有内容，不被它拦住（原文件先备份）；右键菜单路径遇到损坏文件仍重建，但先把原文件留作 `compat.toml.bad`。
- **备份**：`compat.toml.bak-<unix 秒>[-<序号>]`，只留最近 5 份，新备份的排序键严格大于现存所有备份。
- **视图新增** `has_user_entry` / `user`，界面据此判断「还原」有没有东西可还原、禁用前用户改过什么。
- **`compat.changed` 只覆盖 RPC 写入**，右键菜单的写入不广播，设置页在窗口重获焦点时重新拉取。
- 仍未做（留给 P2 开工前定接口契约）：`warnings`/`fallbacks` 带上「段·进程·字段」上下文、错误结构化
  `{code, field}`、camelCase/snake_case 统一、守护测试改用 `value_domain_guard` 的种子键集以覆盖 `rename`。

## 11. 整体原则：用户层只记差异，逐字段叠加（2026-09-29）

**动机**：此前同一套系统里并存四种语义——运行时合并是「同名进程整条替换」（仅 4 个协议字段例外地继承）、
右键菜单写「只带被点那一项」的稀疏条目、设置端写时复制整条快照、导入按字段合并。菜单的稀疏条目撞上
运行时的整条替换，在靶机上让微信丢了出厂的 `caret_use_top` 与 `stale_probe_guard`（见记忆
`compat-menu-sparse-rule-drops-factory-fields`）。设置端的写时复制是在为一个不一致的底层打补丁。

**原则**：层序 `data/compat.toml` < `data_custom` < 用户层，**每一层都是相对下一层的差异**，同名进程内逐字段叠加：

| 语法 | 含义 |
|---|---|
| 写了字段 | 覆盖下层的值（含显式 `false` / `0`，那是有意义的覆盖） |
| 没写字段 | 继承下层 |
| `unset = ["字段", …]` | 取消下层设定的字段，回到「没设置 / 跟随全局」 |
| `disabled = true` / `false` | 禁用 / 重新启用整条规则；它也只是一个普通的叠加字段 |
| （不存在） | 「整条替换」。只有导入的 replace 模式（先清空用户层）才有这个效果 |

同一条里既写了字段又 `unset` 了它，写了的赢。`unset` 向上累积，更高层重新设置该字段时自动从清单里拿掉。
列表字段（`classes`）按整个字段替换，不做元素级合并。

**为什么在原始键值上叠加**：结构体的裸 `bool` / `i32` 序列化时省略默认值，「没写」与「显式写了 false」在
结构体里是同一个东西，而叠加必须区分它们。所以先在原始表上叠加，最后才一次性反序列化成运行时结构体
（`compat_overlay`）。副作用是**认不出的键原样保留**：新版本写下的字段被旧版本读写时不会被悄悄丢掉。

**落地**：
- 运行时 `load_layered`：三层原始键值逐层叠加 → 跳过禁用行、剥 `unset` → 逐行容错反序列化（一行结构错只丢这一行）。
  `merge_rules` / `ProtocolFields` 整套特例删除；「每个登记字段都能穿过叠加」由一条遍历全部登记字段的测试守住。
- 写入统一走 `apply_edits`：`Set` / `Clear`（清除：系统层设了它就写 `unset`）/ `Inherit`（还原：删掉用户层关于它的
  一切痕迹）三种编辑，最后过 `normalize`——按**运行时效果**判断冗余（去掉某个键后叠加结果不变的键与 `unset` 都删，
  整行没内容就删整行）。「已修改」因此永远意味着有真正的差异，不会有视图里看不见的空壳。
- 右键菜单：包装函数签名不变，内部改为字段编辑。菜单第一档「跟随全局」= `Clear`；`ignore_host_ime_close` 的第一档曾是
  「跟随内置规则」= `Inherit`（当时没有全局设置项，下层就是出厂）。它改名 `ignore_host_ime_switch`、有了全局项
  `input.ignore_host_ime_switch` 之后，第一档同样是「跟随全局」= `Clear`。菜单读不到系统层（数据目录解析不出来）时，
  清除字段保守地写 `unset`，不凭「系统里没有」去省。
- 设置端：`compat.upsert` 的补丁 `null` = 清除（`Clear`），`compat.resetField` = `Inherit`——界面上每个系统设了值的字段，
  在「跟随全局」之外多一个「出厂」状态。`Kind::InheritBool` 取消（不再有特殊三态），`protocol` 标记仅作提示。
- 导入：每条规则叠加到用户层同名**差异行**上（不是整条替换，也不是拷贝系统字段），支持 `unset`；无效取值只丢这一个键并报告，
  绝不原样落进用户层文件。导出用户层 = 差异，体积小、可移植；导出生效 = 叠加后的全貌。

**迁移**：已有用户文件不用改。原来的稀疏条目语义从「整条替换」变成「叠加」——靶机微信的
`first_show_mode = "instant"` 会自动拿回出厂的 `caret_use_top` 与 `stale_probe_guard`，这正是想要的。
唯一受影响的是曾靠「整条替换」间接取消系统设定的用户（例如让 Excel 回到跟随全局的旧写法），需要显式 `unset`；
右键菜单与设置端的写入路径已经这样写。

### 11.1 独立审查后的补充（2026-09-29）

叠加重构提交后又经一轮独立审查，修了以下几处，语义以此为准：

- **写错的值 = 没写，且必须在叠加之前剔掉**（`sanitize`）。若错值先参与叠加、事后才被容错回落成 `None`，
  它会把下层的好值一起盖没：布尔写成 `"yes"` 丢出厂的协议字段，`classes` 里混进非字符串甚至让出厂的
  explorer 作用域整行丢失（explorer 变成不受限制，闪英问题会回来）。清理只作用于**参与叠加的副本**，
  要写回文件的原始行不动。没有 `classes` 的作用域规则作废（不是「全挡」；全挡要显式写 `classes = []`）。
- **用户层里不认识的东西原样保留**：认不出的键、认不出的值（新版本写下的枚举值）、认不出的顶层段，
  写回时都不删；规范化只修剪「已登记且值有效」的字段。视图里它们不算差异（`state` / `overridden` 不受影响），
  单独列在 `unknown_keys`。
- **读不进来的内容按损坏处理**：`[apps]` 写成单括号、数组里有非表元素等，`parse_raw` 会记进 `skipped`。
  菜单路径重建前先留 `.bad`；设置端 `list` / 写方法报错，`resetAll` 与 replace 导入照常能恢复。
- **写回自检**：渲染后重新解析并与内存比对，不一致就拒绝落盘。非 ASCII / 含点 / 含空格的键写回时加引号
  （否则一个手写的 `"备注" = "x"` 就能让整个用户层失效）；日期时间读入时转成文本，保住内容。
- 同一层里同名进程的多行，读入时按顺序叠成一行；进程名读入时 trim（运行时查表因此能匹配）。
- `unset` 接受单个字符串；`unset = ["disabled"]` 可解除下层的禁用。
- 菜单给「被下层禁用」的进程选了一项时，写入附带 `disabled = false`（用户自己在设置页禁用的不动）。
- 用户目录与系统预置目录相同（拿不到用户配置目录时的兜底）时，菜单与设置端都拒绝写入。
- `compat.list` 的 `warnings` 现在真的有内容（各层被忽略的无效值，带段与进程）。生效导出保留 `unset` 记号，
  同一套系统层上重新导入结果一致。

**迁移提示（发布说明要点名）**：旧语义下，用户层某条规则只要还有别的字段，删掉某个字段就等于「跟随全局」
（整条替换）。新语义下删掉字段 = 继承出厂。受影响的是出厂配了值的进程：`EXCEL.EXE` / `et.exe` 的
`first_show_mode`（会回到 `wait`），`SearchHost.exe` / `searchapp.exe` / `startmenuexperiencehost.exe`
的 `host_render`（旧菜单写 `false` 等于不写，靠整条替换才关掉，现在会重新打开）。文件里无法区分「有意跟随全局」
与「稀疏条目意外盖掉出厂值」，做不了自动迁移；这几类需要用户重新设置一次（菜单与设置端已写成显式 `unset` / `false`）。

**已知取舍（不改）**：用户层是相对**当前**出厂层的差异。用户设的值恰好等于出厂值时被当成冗余删掉，
以后出厂改了这个值，用户的选择跟着没了；用户清除了一个出厂当时没设的字段不会留 `unset`，以后出厂加上这个字段，
用户的「跟随全局」会被覆盖。换来的是「已修改」永远意味着真正的差异、没有隐形空壳。

## 12. 设置端界面设计（P2～P4）

核心侧（P1）已完成并上靶机验证；本节定设置端（`wind-setting`，纯 Rust + `windui`）怎么做。
设计依据是对设置端现状的两轮调研，下面凡标「调研」的都有代码出处。

### 12.1 先纠正的几个假设

- `backup.rs` / `integration.rs` 不是页面，是「高级」页里的**卡片**；整页手写的先例只有 `stats`，master-detail 的先例是
  词库页（`dict/`，目前在独立窗里）。master-detail 页**不能套 `page()`**（它是无限高的滚动容器，里面放 `weight` 会塌），
  要自己返回 `Element::row().fill()`。
- windui **没有**带徽章的可选列表、也没有三态控件；控件**没有变更回调**（只写绑定的 `Signal`，靠 `reactive_effect` 监听
  版本号）；没有「窗口重新获得焦点」的公开回调；`compat.*` 在设置端 `rpc.rs` 里连 mock 都没有（落到 `Value::Null`）。
- 设置端所有 manifest 控件都走「保存时统一 diff」（`FieldRegistry`）。**compat 页不走这条路**：每次改动立即 `compat.*`
  落盘，所以不调 `manifest::field`，只借它的控件构造；底栏的「恢复本页 / 应用设置」对本页无意义，要隐藏。

### 12.2 位置与整体布局

新增一个侧栏 Tab「应用兼容」，放在「高级」之前（`cli.rs` 的 `PAGES` 插 `"compat"`，与 `all_tabs` 逐格一致）。
选 Tab 而不是词库那样的独立窗：规则数量是几十条量级，是日常会回来调的东西，独立窗多一层入口；侧栏 Tab 也天然接入搜索与深链。

```
┌ 应用兼容 ──────────────────────────────────────────────────────────────┐
│ ┌ 左栏 240 ──────────┐ ┌ 右栏（滚动）────────────────────────────────┐ │
│ │ [应用规则|作用域|换行]│ │ Weixin.exe   [已修改]        [禁用][还原此规则]│ │
│ │ 🔍 搜索  [＋添加][⋯]│ │ ─ 候选窗定位 ─────────────────────────────── │ │
│ │ 全部 已修改 自定义 已禁用│ │ 候选窗首显策略  说明…      [跟随全局 ▾]   │ │
│ │ ▌Weixin.exe  已修改 │ │   出厂: —                    [已改·还原]     │ │
│ │  QQ.exe      系统   │ │ 按光标上沿定位  说明…          [开]           │ │
│ │  Feishu.exe  系统   │ │   出厂: 开                    [出厂]         │ │
│ │  mine.exe    自定义 │ │ ─ 宿主兼容（高级，默认折叠）──────────────────── │ │
│ └────────────────────┘ └──────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────────┘
```

- 顶部分段切换三段：应用规则 / 窗口作用域（`initial_mode_scope`）/ 上屏换行（`commit_newline`）。
  作用域段与换行段字段很少（各一个），复用同一套渲染器，不另写页面。
- 左栏：搜索（进程名）、状态筛选（全部 / 已修改 / 自定义 / 已禁用）、规则行（进程名 + 状态徽章）。
  状态徽章语义色：系统 = `TextMuted`，已修改 = `Accent`，自定义 = `Success`，已禁用 = `Warning`。
- 右栏：头部（进程名、状态徽章、`禁用/启用`、`还原此规则`、用户新增的规则还有`删除`），下面按 `compat.schema` 的
  `group` 分卡片，`advanced` 字段收进默认折叠的「高级」卡片。
- 页面级操作放左栏工具栏的「⋯」：导入、导出、全部还原、帮助。

### 12.3 每个字段的四种显示状态（决定了要补的核心契约）

字段行要让用户一眼分清「这个值是谁定的」，共四种：

| 状态 | 含义 | 显示 | 操作 |
|---|---|---|---|
| `default` | 系统和用户都没设，走全局 / 默认 | 灰色「跟随全局」 | 直接改 |
| `system` | 出厂设了，用户没动 | 正文色 + 「出厂：值」 | 直接改 |
| `user` | 用户改写了 | `Accent`「已改写」+ 出厂值提示 | 「还原为出厂」 |
| `cleared` | 出厂设了、用户取消（`unset`） | 「已取消出厂设定（出厂：值）」 | 「还原为出厂」 |

如果让界面自己从 `system` / `user` / `effective` 三份数据推导，极易写错（`effective` 会省略裸 bool 的 `false` 与 `0`，
「用户设为关」与「用户清除」在 `effective` 里长得一样）。所以**核心补一个现成的逐字段视图**，界面只渲染：

```jsonc
// compat.list 的 RuleView 新增
"fields": {
  "first_show_mode": { "source": "user", "value": "wait", "systemValue": null, "userValue": "wait" },
  "caret_use_top":   { "source": "system", "value": true, "systemValue": true, "userValue": null },
  "stale_probe_guard": { "source": "cleared", "value": null, "systemValue": true, "userValue": null }
}
```

- `value` 按控件类型给**类型化的默认值**：Bool → `false`，TriBool / Enum / Text → `null`，Int → `0`，TextList → `[]`，
  界面不必知道「省略默认值」这回事。
- `source` 只看**有效**的差异：写错的值、与系统一致的冗余、认不出的键都不算 `user`。
- 这一步是设置端的**前置**（P2-0），放核心做、核心测：契约在一处、可测、不随界面漂移。

### 12.4 交互与写入

- **每次改动立即落盘**，不设「应用」按钮：开关 / 下拉 / 分段控件变化 → `compat.upsert`（补丁 `{key: value}`，
  选「跟随全局」发 `null`）；「还原为出厂」→ `compat.resetField`；整条 → `compat.reset`；禁用 → `compat.setDisabled`。
- **不能出现写回循环**：控件只写 `Signal`、靠版本轮询触发请求，而请求成功后的重拉又会回写 `Signal`。每个字段控件持有
  「上次同步值」与全局「正在回填」标志：回填期间的信号变化不发请求；变化后的值与上次同步值相同也不发。
- **文本 / 数字不能每个键都落盘**：`text_input` 只有 `on_submit`（回车），`stepper` 没有提交事件。首选回车提交 + 旁边一个
  「✓」按钮；先做一个小 spike 确认 windui 有没有失焦事件，有则加上失焦提交。
- **调用同步 `call_core`**：与现有页面一致（`compat.*` 是本地读写，毫秒级，最坏卡 5 秒且与别的页同级）。同步还让页面测试能用
  `take_mock_calls()`（thread_local）直接断言请求形状；改成后台线程 + channel 会失去这一点，不划算。
- **失败一律 toast 核心给的中文报错**（补丁被拒、用户层读不进来、目录相同拒写等）。`compat.list` 本身报错（用户层损坏）时，
  右栏显示醒目的横幅：原因 + 「全部还原（会先备份）」按钮，其余操作置灰。
- **刷新时机**：进入本页、收到 `compat.changed` 事件（核心在 RPC 写成功后广播；自己写的也会收到回声，回填标志防冲）、
  手动刷新按钮。右键菜单的写入**不广播**，所以还要靠「回到设置窗」刷新——windui 没有公开回调，先用
  `caret::window_active()` 边沿轮询，**未实测**，列为 spike，不行就给 windui 加一个 `on_window_activated`。

### 12.5 添加、导入导出、还原、帮助

- **添加规则**：对话框里输入进程名（trim、拒绝路径分隔符，与核心同规则），旁边「从运行中进程选择」下拉（排除已有规则）。
  已存在同名则跳到那一条。新规则先是**草稿**（左栏置顶显示「未保存」），第一次设置字段才 `compat.upsert`；
  没设置就离开则丢弃草稿——空壳规则本来就不落盘。
- **进程枚举放设置端**：`CreateToolhelp32Snapshot`（`windows` crate 加 `Win32_System_Diagnostics_ToolHelp`），
  `#[cfg(windows)]` 实现 + 非 Windows 返回空的桩（本机 Linux 要能跑单测与截图）。放核心会让 `wind-webdata`（要给 Android
  闭包用）背上 Windows 依赖，不划算。
- **导出**：对话框选范围（仅我的改动 / 全部生效规则，前者默认）→ 保存对话框 → `compat.export` 拿文本，设置端自己写文件。
- **导入**：选文件 → `compat.import` `dryRun` → **预览对话框**（`RichDoc` 分节：新增 / 覆盖 / 禁用 / 无变化 / 将被移除，
  以及忽略的键、被丢弃的无效值、被拒绝的规则）→ 选「合并 / 替换」→ 确认 → 真正导入，toast 报备份文件名。
- **全部还原**：确认对话框（说明会先备份）→ `compat.resetAll`。
- **帮助**：大对话框，按 `compat.schema` 的分组列出每个字段的功能、解决的问题、已知宿主、取值。字段行的信息角标点开时只看该字段
  （带「查看全部」），省掉「滚动到某个锚点」这个 windui 里不好做的事。全部文案来自核心，设置端不自己写字段说明。

### 12.6 复用与缺口

复用：`SubNav` 之外的页面骨架照 `dict/view.rs`（`host_signal` + epoch、`reactive_effect`、`toast_sink`、
`Feedback`）；选中态照 `dict/sidebar.rs` 的「选中 / 未选中 / 指示条三元素 + `visible_when`」（windui 没有响应式样式）；
徽章照 `dict/view.rs` 的手画徽章；对话框用 `build_confirm_dialog_shell` / `build_group_dialog_shell_large`；
导入预览用 `RichDoc`（先例 `schema_manager.rs` 的导入报告）；文件对话框照 `backup.rs`。
缺口：带徽章的规则列表（自己拼）、三态控件（`segmented` 拼）、文本列表编辑（多行文本框，一行一项）、
窗口激活刷新（spike）、进程枚举（新依赖）。

### 12.8 风险

1. **写回循环**（12.4）是最容易出隐蔽 bug 的地方，必须有专门的测试：程序化回填不发请求、同值不发请求。
2. **窗口激活刷新**无公开回调，方案未实测（12.4 spike）。
3. **文本 / 数字提交语义**取决于 windui 有无失焦事件（12.4 spike）。
4. **列表性能**：选中态每行三元素，几十条没问题，上百条需评估；规则数量级不会到那里，先不做虚拟列表。
5. **拼音首字母表**：新页标题带新汉字会让 `table_covers_every_title_char` 变红，而本机没有 pwsh，需按记忆里的等价流程重算。
6. **`PAGES` 插入会让 `advanced` / `about` 的下标后移**，`cli.rs` 里有单测硬编码了下标；`PAGES` 与 `all_tabs` 错位不会报错，只会让深链与二级导航错一格。
7. **进程枚举只能真机验证**。

### 12.9 P2～P4 落地时与设计不同的地方（2026-09-29）

- **写回循环用「重建」而不是「回填标志」消解**：写入成功后整体重拉 `compat.list`，选中项的视图变了就**整体重建详情**
  （`host_signal`），新控件以新值为基线、effect 以构建时的版本为基线，构建帧不触发，所以不存在「回填期间的信号变化」这回事。
  `apply_list` 只在内容真的变化时才动信号——核心对自己写入的回声广播不会造成重建、丢焦点。
- **窗口激活刷新**：给 windui 加了 `App::on_window_activated` / `Window::on_window_activated`（只在真实的激活边沿触发，
  初始视为已激活），不再用 `caret::window_active()` 轮询；右键菜单的写入也已经会广播 `compat.changed`。
- **文本 / 数字提交**：`text_input` 只有回车回调、`stepper` 没有提交事件，结论是文本类字段 = 输入框 + 「应用」按钮
  （回车同效），数字字段用 stepper + 「应用」（审查后改：stepper 的输入框逐字回写信号，按信号写盘会在首位数字后
  重建详情丢焦点）。没有做失焦提交。
- **进程选择器暂未做**（12.5 的「从运行中进程选择」）：新增对话框目前只收手填的进程名，说明里指路到任务管理器。
  这条只能真机验证，单列为后续。
- **导出范围**：只导用户层（`scope: user`），没有「全部生效规则」的选项，界面上不提供以免与「分享我的改动」混淆。
- **帮助**：做成当前段全部字段的说明对话框（含高级项），没有做「字段行角标 → 只看该字段」；字段行的悬停提示里有
  `problem` 全文。
- **全局搜索**只收页级入口（应用兼容 / 新增 / 导入 / 导出 / 还原），规则字段来自运行时元数据，不进静态索引。
- **审查后补的护栏（2026-09-29）**：写后选中 / 草稿有变化而规则集没变时由 `reload_after_write` 自行 bump 两个 epoch；
  草稿仅在核心里确有该规则后才转正（normalize 成空的补丁不落行）；写失败按核心的值重建详情；「还原」按钮在依赖置灰
  包裹之外；导入预览重算失败即禁用「导入」；页面重建时已加载则重拉（主窗关闭期间漏掉的广播）。

### 12.10 改为独立窗口与「只列被覆盖的项」（2026-09-29，使用反馈后）

- **独立窗口，不再是主窗的一页**：规则多、三栏，放进主窗一页显得乱。入口在「高级」页新增的「应用兼容」卡片
  （排在「游戏兼容」上方）；主窗侧栏没有这一格，`cli::PAGES` 里也没有 `compat`。全局搜索的应用兼容条目改落在
  这张卡上（`advanced:compat` 锚点）。`--page compat` / `--compat` 冷启动由 `App` 的窗口直接承载（同 `--page dict`）。
  窗口与词库窗同构：`compat_window.rs`，单例键 `compat_manager`，窗口激活时刷新（`on_window_activated`）。
- **三栏**：左栏分类（应用规则 / 窗口作用域 / 上屏换行）、新增 / 导入 / 导出、「显示高级选项」开关、说明 / 全部还原 /
  刷新 / 返回设置；中栏进程列表（搜索 + 状态筛选）；右栏配置信息。
- **右栏只列被设置过的字段**：出厂设了的、用户改了的、用户取消了出厂值的，以及用户刚挑出来等着给值的。
  其余字段经「添加覆盖项」对话框（按分组列出、带一句说明）挑选。候选 = 还没被任何一层设置的字段；高级字段仅在打开
  「显示高级选项」时提供，已设置过的高级字段照常列出。
  - 开关类挑选即写 `true`（写「关」等于没写，没有更自然的初值）；其余类型先在界面里占一行（`pending`，不进核心、
    不跨段），给了值才落盘。待设置的字段选回「跟随全局」不会让这一行消失。
  - 字段行右侧的按钮：用户新增的规则与待设置项叫「移除」，出厂规则上的叫「还原」（还原为出厂设置）。
- **规则被清空时先问**：用户新增的规则去掉最后一项后核心里整条消失，界面不直接让它凭空没了——保留成一段空白
  草稿并弹窗问「删除 / 保留空白规则」；选保留可继续添加覆盖项，不设置任何项就离开则不会被保存。出厂规则怎么还原
  都不会消失，不提问。整条「删除 / 还原」与全部还原是明确的用户意图，同样不提问。
- 草稿不再限于「应用规则」一段（其它两段也有用户新增规则，清空提示需要草稿承接）。

### 12.11 第二轮使用反馈后的调整（2026-09-29）

- **生效时机**：没有「保存」环节，每个动作立即 `compat.*` 落盘；核心写成功后 `reload_compat_and_refresh`
  重载规则表并让当前前台进程的缓存立即按新表重算，所以改完即生效（不必重启软件 / 输入法）。窗口关闭与否无关。
- **选中效果统一**：分类与进程列表用 `dict::sidebar::selectable`（accent 淡底 + 左缘指示条 + 文字转强调色），
  与词库窗左栏、主窗侧栏同源；选中态由信号直接驱动，点选不再重建列表。进程列表的横向内缩放在滚动内容上
  （≥ 滚动条占宽），滚动条不再压住条目。
- **分段控件一律改下拉**（状态筛选、三态开关、导入方式）：多段时占位太宽，与其它页保持一致。
- **移除 / 还原改图标按钮**（× / ↺，悬停出说明）。
- **枚举只显示中文**：核心 `compat.schema` 每个枚举字段带 `optionLabels`（与 `options` 同序），名称登记在
  `compat_schema::OPTION_LABELS`，漏登记有测试拦；取值原文（配置文件里的写法）只在「选项说明」的「可选值」里交代。
- **改回默认值不让行消失**：字段各有「没设置」这一档——枚举 / 文本 = 没写即跟随全局（下拉第一项），
  三态开关 = 跟随全局 / 开 / 关，纯开关与数字没有第三态（关 / 0 与没写等价，核心会丢掉）。用户主动改成这些值时
  行保留（界面里的「待设置」占位），要去掉走「移除」。
- **「显示高级选项」挪进「添加覆盖项」对话框**：它只影响能挑到哪些字段。
- **右键菜单增加整条规则开关**：「应用独立配置」子菜单第一项「启用此应用规则」（勾选 = 生效；
  该应用没有任何规则时置灰），与设置端「禁用 / 启用」同一件事，方便快速判断问题是不是兼容规则引起的。
- **文案与右键菜单对齐（同日）**：字段名 / 选项名统一取菜单用词——候选窗首显、候选窗定位、初始输入模式、初始标点模式、
  方案、状态提示位置（分组也叫「状态提示」）、坐标不可用时的状态提示位置、符号自动配对、宿主关闭输入法、密码框强制英文；
  锚点名带「角」（屏幕左上角…）、兜底位置「上次位置 / 不显示」。同一个取值在不同字段说法不同时用
  `FIELD_OPTION_LABELS` 覆盖（状态提示位置的 `fixed` = 「固定（取当前位置）」）；三态开关三档说法由核心 `triLabels` 给出
  （自动配对「启用 / 禁用」、宿主关闭输入法「跟随内置规则 / 忽略 / 采纳」，其余「跟随全局 / 开 / 关」）。
  协调器里有测试锁住菜单标题、锚点名与元数据一致。
- **列表排序与草稿（同日）**：进程列表「用户层动过的在前」（已修改 / 自定义 / 用户禁用的，含草稿），纯出厂的在后，组内保持核心
  顺序；草稿当作「自定义」规则同样过筛选与搜索，被挡住时不再占着选中。入口统一称「应用兼容性与独立配置」。
