# 字词范围（只出单字 / 只出词组）

## 1. 背景

五笔系输入法的传统功能，各家都叫「字词模式 / 单字模式 / 词组模式」（极点、万能、QQ 五笔）。
本仓叫**字词范围**（`word_scope`），三档：

| 档位 | 候选内容 |
|---|---|
| `all` | 字与词都出（出厂） |
| `char` | 只出单字 |
| `phrase` | 只出词组 |

### 1.1 单字档的价值不止「练习拆字」

三层用途，第三层决定了本功能的实现要求：

1. **练习五笔**——强迫拆字，不靠词组蒙；
2. **打人名 / 古文 / 生僻文本**——词组是干扰项，永远抢首选；
3. **★ 定长盲打**——五笔单字恒 ≤ 全码长。只出单字时同码的词被滤掉，
   「满码唯一即上屏」的成立率大幅提高，用户可以不看候选窗连续敲。

第 3 条是它与拼音的分水岭：**拼音没有定长**，单字档对拼音只剩用途 2。故拼音默认不开，
但配得了（值域与归属对所有引擎一视同仁）。

⇒ 实现上第 3 条意味着本功能**不是纯粹的候选过滤**：它会改变满码自动上屏的口径。
那是想要的结果，但必须被测试钉住（`char_scope_enables_auto_commit_at_full_code`），
不能是过滤的意外后果。

## 2. 配置：三层，顺序不可换

| 层 | 位置 | 归属判据 |
|---|---|---|
| ① 临时态 | `State::word_scope_override`（热键切的） | 无——压过一切 |
| ② 方案级 | `[candidate] word_scope`（三态，多一个 `follow`） | `effective_data_schema` |
| ③ 全局 | `input.word_scope` | — |

取值的唯一入口是 `Coordinator::effective_word_scope`。

### 2.1 ★ ① 与 ② 的判据刻意不同

②「这个码位出字还是出词」问的是**词库该交出什么** ＝ 数据属性，与同段的 `font_family`、
`text_orientation` 以及 `[phrases]`、`[punct] custom_mappings` 同源。可见后果：

> 五笔方案配了单字档，按反引号进**临时拼音**，那里照常出词。

这是刻意的——临拼正是为了打主方案打不出的东西，在那里再砍掉一半候选只会让人无路可走。

而 ① 是「用户此刻按下热键的意图」，无条件生效，**包括临拼里**。他刚按了键，不该再问一遍
「你现在打的算哪个方案的数据」。

同一个功能的两层用两种判据，`[punct]` 段的 `mode`（跟活跃方案）与 `custom_mappings`
（跟数据方案）已经是同一个形状。

### 2.2 为什么住在 `[candidate]` 段而不是 `[engine.codetable]`

与 `[key_actions]` 同一条论证：**它与引擎类型无关**。放进 `[engine.codetable]` 就得在
`[engine.pinyin]` 再写一份，两处必然分叉。

### 2.3 ⛔ 内置方案一项都不声明

出厂是**全局 `all` + 所有内置方案 `follow`**。「五笔常开、拼音不开」靠文档与设置页引导，
不靠出厂值。

理由：方案级非 `follow` 的取值恒覆盖全局 ⇒ 给 wubi86 预置 `char` 的话，五笔用户在**全局页**
把这一项调成任何值都纹丝不动，而「方案自带」那个标记藏在方案设置里，他不会去找。
从他的角度这就是「设置项坏了」。`short_code_yield_level` 在 0.119 恰好这么栽过一次并当天
撤回，判据已成文：**用户在全局页做的事，必须能作用到出厂方案上。**

守门在 `factory_schemas_do_not_declare_word_scope`（遍历全部出厂方案，走真实反序列化）。

⚠️ 这条只约束**内置**方案。第三方方案作者写这一项完全正当。

## 3. 判据：什么算「一个字」，谁豁免

实现在 `wind_candidate::word_scope_admits`。

### 3.1 按字素簇算，不按码位

走 `single_markable_char`（UAX #29），故 `⚽️`(2 码位)、`👨‍👩‍👧`(5 码位)、`🇨🇳`、`1️⃣` 都算
一个字。⛔ 别退回 `chars().count() == 1` ——issue #83 的教训是逐条列举 Unicode 规则必随版本
静默漏一类。

### 3.2 豁免：短语 / 命令 / 分组

字词范围管的是**词库**出什么，而这三类是用户自己配出来的快捷方式（`fj` → 一整段文本），
不该因为开了单字档就整个消失。

### 3.3 ★★★ 豁免判据是 `is_user_authored`，**不是** `is_common_like`

`is_common_like`（检索范围过滤用的那个）＝ `is_common || 那三项`。带上 `is_common` 的话，
常用**词**（「中国」「时候」——`mark_common` 对逐字皆常用的词同样置 `is_common = true`）
会一并豁免，**单字档就只剩生僻词被滤掉，整个功能失效**，而候选窗看着还挺正常。

两个过滤器问的是不同的问题（「这条算不算常用」 vs 「这条是不是用户自己配的」），只是答案
在那三项上碰巧一致。守门在 `common_words_are_not_exempt`（变异验证：把豁免换成
`is_common_like`，只有这一条红）。

### 3.4 两档互补是刻意的

豁免项之外，`char` 放行的与 `phrase` 放行的**恰好互补**（同一个 `is_some()` 的正反两面）。
于是用户在两档间来回切换时，不会有候选两边都不出现——那种「切过去没有、切回来也没有」的洞
最难被报告。

## 4. 落点与次序

主候选链（`handle_candidate.rs`）：

```
mark_common → sort → dedup → apply_filter → **apply_word_scope** → apply_freq_rerank
  → apply_shadow → 空码补全收口 → short_code_yield → 英文头部候选 → emoji 扩展
  → state.candidates 定稿 → 满码自动上屏「显示态」复评
```

### 4.1 必须早于 `apply_shadow`

`ShadowPin.position` 是**绝对下标**，记的是用户右键当时**所见的那个列表**——单字档下所见
列表就是滤过的，滤在 shadow 之后位次就对不上了。出简让全踩过同一个坑（「置顶写得进去、
下次打同一个码毫无变化」）。

守门 `word_scope_filter_runs_before_shadow`（源码顺序断言——端到端造 shadow 规则要真实的
`store`，headless 里是 `None`，行为断言写不出来）。

### 4.2 补全池走同一条链

主列表被滤空之后才会从补全池取一条；那一条若不过字词范围，用户看到的就是「开了单字模式
还是冒出一个词」。守门 `completion_pool_goes_through_the_same_filter`。

### 4.3 被滤集直接丢弃，不留 `FilterOutcome`

检索范围要留被滤集是因为有「末页翻页放宽」这条出路。字词范围没有，也刻意不给一个：用户开
单字档就是不想看见词，「翻到底还能翻出词来」与这个意图相反。要看词就切档位。

## 5. 与既有机制的交互（三条都是**不用动手**的）

### 5.1 ★ 满码自动上屏：既有的「显示态复评」已经解决

`decide_auto_commit`（`wind-engine` 的 `codetable/engine.rs`）数的是**引擎自己**那份候选里
`code == input` 的条数，而本过滤做在协调器侧 ⇒ 引擎看见的列表里那个词还在，按它判恒是
「不唯一、不上屏」。

救回来的是 `handle_candidate.rs` 里既有的**显示态复评**：引擎没给出上屏意向时，按
**最终显示列表**再判一次。它当初是为智能过滤加的（滤掉同码生僻字后复评放行，见
`recheck_auto_commit_unique_after_filter`），而判据落在「用户看见的是哪些候选」上、
与过滤的成因无关，于是字词范围天然搭上了同一趟车。

实测（五笔 `dddd`，`auto_commit_at_full = true`）：

| 档位 | 结局 |
|---|---|
| `char` | 自动上屏「大」，候选清空 |
| `all` | 停在候选态（大 / 大厦 / 硕大 / 磕磕碰碰） |

⇒ `char_scope_enables_auto_commit_at_full_code` 同时是那条复评的**第二个消费者**的守门：
将来谁把复评改成只认智能过滤（比如加一个 `filter_mode` 判据），这里会红。

### 5.2 出简让全天然停手

`short_code_yield::apply` 找接位者要求 `chars().count() > 1`，找不到直接返回；首选判据又要求
是单字。⇒ `char` 档（无多字接位者）与 `phrase` 档（首选不是单字）**各被一条判据挡住**，
两档都不动手。无需接线。

### 5.3 emoji 扩展不会留下孤儿

emoji 插在整条加工链的**最后**（注释写明「放进过滤链里它会被静默滤光」），故它看到的已是
滤过的列表，`char` 档下多字宿主早已消失。无需特判。

## 6. 运行时切换：临时态，不写盘

按键动词 `word_scope:<载荷>`，载荷 `char` / `phrase` / `all` / `cycle` / `follow`
（`follow` = 清掉临时态、回落配置层）。

**两张按键表都有它**，动词与载荷逐字一致：

- `keys.key_actions` / 方案 `[key_actions]`（`BoundAction`）——符号键、字母 z、组合键；
- `keys.session_actions` / 方案 `[session_actions]`（`SessionAction`）——Tab、翻页键那一批。

只在一张表里加是错的：另一张表里写同一个动词会落 `None`，表现成「这个键没绑上」，
而用户只是把配置从一张表挪到了另一张。

### 6.1 不写配置（用户 2026-09-07 拍板）

`set_filter_mode` 切一次就写回 `input.filter_mode`；本项只改内存。直接好处是**不必碰
`schema_overrides/{id}.toml` 那条写盘链**（本项是方案级配置，持久化就得往那儿写，还要登记
`SideCommitter` 并处理「设置页正开着时被后台改写」）。

形态上它与 `State::scope_relaxed` 同构：纯内存、一个失效点、一条不写配置的切换路径。
⛔ 实现时别照 `set_filter_mode` 抄——那是持久化路径。

### 6.2 失效点：切方案时清空

收口在 `sync_schema_scope`（代际驱动，与 `punct_before_schema` 同批）——本仓唯一能覆盖全部
五条切方案路径的地方。

★ 这里**不需要** `punct_before_schema` 那种「保存原值」的配套：临时态本身就是 `Option`，
清成 `None` 即回落配置层。那条真机教训（`Follow` 退化成「保持上一个方案强加的值」）在此
天然不成立——它的成因是 `state.chinese_punct` 既是当前值又是唯一存储，本项两者是分开的。

### 6.3 消费点的结局：`Consumed`，不顶字

与**辅助码同族**：切的是「这一码出什么」，正在打的那串码要原样留着。
⛔ 别按临拼 / mix 那样顶字重开——顶字会把用户想换个档位再看的那串码上屏，而他要的恰恰是
换个档位重看这一码。

换档后候选可能整个变空（单字档下该码无单字），那时**只剩状态泡这一个反馈**，故三个消费点
都弹泡（持锁，走 `show_tip_locked`）。

## 7. 已知边界

### 7.1 「截断 → 过滤」在拼音上仍在（未做引擎下推）

引擎是「产生 N 条 → 排序 → `truncate(max_candidates)`」，本过滤在其后 ⇒ 理论上单字档可能
不足一页。码表方案基本无影响（一个码位候选本就不多）；拼音高频音节的前 N 条里单字占多数，
实测也未见不足。

真要做，路径是现成的：`ConvertOptions::admit` 把准入下推进引擎（生僻字模式的先例），
调用方仍需「不足则加大重取」（`refill_rare_if_short`）。⚠️ 那时还要处理 Viterbi 整句——
它走 `insert(0)` 绕过 `push_unique`，不受 `admit` 约束，只能在调用方侧再滤一次。

本轮只做内核。设置页（`wind-setting` 仓）、工具栏格子、文档站待后续。
