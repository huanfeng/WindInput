# 自动造词模型重做：滑窗草稿层

**状态**：设计稿，**未实施**。对应看板 C2-22 / C1-2 的 S5。
**前置阅读**：`codetable-auto-phrase.md`（现状模型与它的 flush 闸门）、`cross-engine-auto-phrase.md`（S3）。

## 0. 范围（2026-09-21 定）

**只重做码表那条造词路径，不是新功能。**

- **复用现有开关** `[schema.codetable.auto_phrase].enabled`，不新增配置段。
- **出厂仍是关的**，与现状一致——码表用户一般不习惯自动造词。
- **替换**码表的连续单字路径（`feed_auto_phrase`），不与它并存。
- 拼音那条 `learn_phrase_on_commit` **不动**。C2-22 原文设想的「拼音输入的也要算进来」
  本轮不做，留待后续。

★ 这两条决定同时定死了本设计的**风险上限**：受众是主动开启该开关的用户，
不是全体。滑窗必然带来的杂词，影响面因此是可控的——这是「先记一堆、用过的才留」
这个模型能被接受的前提。

⚠️ 但它也意味着**老用户的行为会变**：开着这个开关的人，造词逻辑从「连续单字」
换成了「滑窗草稿」。不是新增一个可选项，是就地换掉。

## 1. 要解决什么

用户侧的话是「开了自动造词，等了很久只造出 3 个词」（[t82](https://forum.windinput.com/topic/82)）、
「正常打字不容易进入造词」。

拆开看有六道闸，但**主因只有一道，而且它是设计写死的**：

**造词只收「连续单字」，而正常打字里大多数词是选词组上屏的。**
`auto_phrase.rs:72-75`——多字词上屏 = 终止，且该词本身不入缓冲。一句话里只要选中一次词组，
前面攒的字当场被结算、词组不参与、之后从零开始。正常打字词组占大头 ⇒ 缓冲几乎攒不到
2 个以上的连续单字。当初的理由是「选了词组说明这不是一串散字」——对**当时那个模型**是对的。

其余五道是放大器，不是主因：

| # | 闸 | 位置 |
|---|---|---|
| 1 | 长度须落在 2–5，**超长整体丢弃**（打 6 个单字才敲空格就全没） | `auto_phrase.rs:122` |
| 2 | 只有终止信号到来才 flush，一段话没碰上信号就白打 | `handle_addword.rs:320` |
| 3 | 打完立刻敲空格落进 200ms 自提交回声窗 ⇒ 那次终止丢失 ⇒ 与下句粘连 ⇒ 多半超长被丢 | `coordinator.rs:287` |
| 4 | 查重命中即跳过（**这条是对的，保留**） | `handle_addword.rs:377/394` |
| 5 | 索引未就绪整次跳过（已被 `.wscc` 缓存大幅缓解，见 `codetable-auto-phrase.md`） | `handle_addword.rs:354` |

★ **判据：只放宽长度、只补终止信号，治不了主因。** 用户抱怨的「正常打字不容易造词」，
根子在「正常打字本来就不是连续单字」。

## 2. 核心判断：换缓冲的对象，不是调参数

现状缓冲的是**连续单字序列**；本设计改为缓冲**最近上屏的文本流**，再对流做滑窗切分。

```
现状：  单字 → 单字 → [词组：终止，前面结算，词组不入] → 单字 …
本设计：凡真落屏的文字都进流 → 滑窗切 2–5 字 → 全部记下
```

「我今天去上班」不论是逐字打的、还是「我」+「今天」+「去」+「上班」选词组拼出来的，
进流之后都切成 `我今天 / 今天去 / 天去上 / 去上班 / …`。**主因那道闸是在换对象这一步顺带消失的**，
不是被调松的。

**杂词会非常多，这是预期而非缺陷**（C2-22 原文）。整个设计的重心因此从「猜一个词」
转移到「先记一堆，用过的才留」——过滤发生在使用端，不在产生端。
这个模型之所以敢用，前提是 §0 那两条：出厂关闭、受众是主动开启的用户。

### 2.1 流从哪里取

挂 `Coordinator::note_commit_action`（`handle_addword.rs:172`），**不是** `feed_auto_phrase`。

前者是**一切真落屏文字的收口点**：它覆盖 40+ 个返回点、五种 `KeyAction` 变体
（`InsertText` / `InsertTextWithCursor` / `ReplaceBackward` / `CommitAndHoldComposition` /
`CommitThenDeferComposition`），注释里记着散点打点漏一条的真实事故（2026-09-02 五笔长按 d）。
后者刻意只取前两种，因为旧模型只关心「新起的一段输入」。

⚠️ `ReplaceBackward` 进流要**先回退再追加**：它是回改已上屏内容（智能标点二次按键替换、
cmdbar 撤销上屏），直接追加会让被替换掉的字留在流里，制造与退格幽灵字同源的脏数据。
回退量取 `count`（UTF-16 单元，与流的量纲对齐）。

### 2.2 流在哪里断开

滑窗**不跨句**。断流信号沿用现有那套终止信号（`codetable-auto-phrase.md` §3），
但语义从「flush 造词」变成「流到此为止，下一段重新起」：

- 非汉字上屏（标点 / 英文 / 数字 / 空格）
- 焦点丢失、IME 停用、中英切换、切换方案
- 光标移动（`SelectionChanged`，经 `SELF_COMMIT_GRACE` 过滤回声后）
- idle 超时

不断流的话，「上班。今天」会切出「班今天」这种跨句杂词——杂词多是预期，跨句杂词是纯噪声，
两者要分开看待。

## 3. 架构

```
落屏文本流 ──滑窗切 2–5 字──► 草稿层（专用表，带有效期）
                                   │ 用户真的用它上屏了一次
                                   ▼
                              临时词库 temp_words（现有）
                                   │ count 累到 promote_count
                                   ▼
                              用户词库 user_words（现有）
```

**下游两级完全复用现状**，本设计只新增最上面那一级和它到临时词库的那一步跃迁。
「用过即转正」不必新写：`maybe_promote_temp` 的 `count ≥ promote_count`
（`handle_addword.rs:696-713`）就是该语义。

## 4. 存储：专用表，不是内存

草稿进 redb 的**专用表**，不是进程内存。

初稿曾选内存（`DictLayer` 是干净的 trait，省一次 redb 往返）。**否决**，理由不是内存占用而是
**草稿的价值恰恰在跨时间**：用户今天滑窗记下「盖伦」，明天再打时能直接出、进而转正。
服务重启（升级、崩溃、切用户）一清空，这个功能的核心收益就打了折，而重启频率完全不受我们控制。

### 4.1 三个跟着来的约束

**① redb 是单写者，草稿会和别人抢写锁。** 草稿表与 `TEMP_WORDS`/`USER_WORDS`/`FREQ`
共处同一个 `Database`。按 §7 的估算约 4 条/秒，若每条一个写事务，它就是这个库里最高频的写入方，
会顶到选词写词频（`record_freq`）那条路上。
⇒ **异步不只是「不挡按键」，还必须是批量**：攒够 N 条或 T 毫秒合并成一个写事务。
C2-22 原文只说了「异步」，这一层是本设计补的。

**② 崩溃丢失最近一批未 flush 的草稿，直接接受**，不做 WAL 之类的补偿。草稿是机会性产物，
丢几条的后果只是「那几个词这次没记住」，与造词前的状态一致，没有引入损坏。
判据同 `cross-engine-auto-phrase.md` §2 的「部分失败静默接受，不做原子回滚」。

**③ 草稿表不建简拼索引。** `TEMP_WORDS` 有一张 `TEMP_ABBREV` 伴随索引，每条写入都要同步
维护（`abbrev_index::shift`）。草稿写入量高一两个数量级，配索引等于把写放大也翻上去。
代价是草稿**只支持精确码召回、不支持简拼**——而草稿的定位就是「你刚打过的，用同样的码再打
一次就出来」，简拼召回等它转正进 `temp_words` 之后自然就有。
★ 这条在 trait 层面是免费的：`DictLayer::search_abbrev` 的默认实现就是返回空，
且文档注明「不回退全表扫」（`wind-dict/src/layer.rs:46`）。

### 4.2 表结构

新表 `DRAFT_WORDS`，key 沿用 `enc_key(schema, code, text)`（与 `TEMP_WORDS`/`FREQ` 同一套，
`user_words.rs`），value 至少含 `created_at`（定有效期与淘汰序）。
**不存 weight**：草稿在候选里恒沉底（§5），weight 不参与任何比较，存了就是一个永远读不到
却要维护的字段。

## 5. 召回：只精确，且沉底

草稿要「有效期内能用编码打出来」就得参与候选召回，而滑窗杂词极多。两道闸解决：

**① 只响应精确查询。** 新层实现 `DictLayer::search`（精确命中才返回），
**`search_prefix` 返回空**。码表打字是前缀式的（w → wq → wqv…），前缀阶段根本不召出草稿，
只有打满那个词的完整码时才命中——这恰好就是「用同样的码再打一次就出来」的语义，
把杂词整个挡在前缀阶段之外。

**② 沉底键兜底。** 仿 `is_split_composed`（`handle_candidate.rs:159`）——它是插在
`candidate_display_order` 链里的布尔全序键，语义是「排在所有普通候选之后，无论 weight 多高」，
位置在 `by_consumed` 之后、`cmp_match_layers` 之前。草稿加一个同形态的 `is_draft` 键。
⚠️ 该键**必须是全序**（对每一对候选都表态），这是 `place_english_after_common_exact`
那条注释反复提醒过的坑。

**层的挂载**：新增 `LayerType`，数值排在 `Temp = 2` 之后（现有 `Logic=0 / User=1 / Temp=2 /
Cell=3 / System=4`，`wind-dict/src/layer.rs:12`），经 `DictManager::register_layer` 挂进引擎的
`CompositeDict`。⚠️ `merge_search` 跨层同 `(code,text)` 会**继承更高的 weight**
（`composite.rs:121`）——草稿不存 weight，此处要确认它不会把别层的词意外抬权。

## 6. 转正：草稿 → 临时词库

用户选中一条草稿候选上屏 ⇒ 把它从 `DRAFT_WORDS` 删除、写进 `TEMP_WORDS`（`learn_temp_word`）。
单写事务内完成，形态同 `promote_temp_word`（`temp_words.rs:378`，那里已有一个事务同时开四张表
的先例）。

此后它就是一条普通临时词：再被用到就 `count++`，累到 `promote_count` 晋升进用户词库，
容量超限时按 `(count, created_at, weight)` 淘汰（`b43c73c5`）。

★ **A2-16 搁置的出厂 `promote_count` 改动在这一步一并结掉**：只有到这里「用过即转正」
才是完整语义，现在单改那个出厂值是半截。

## 7. 有效期与容量

**⚠️ 仓内没有任何「按墙钟时间过期」的先例**（已核实：`temp_words` 那套是「计数晋升 + 容量淘汰」，
临时拼音是输入模式不是候选，剪贴板反查求值即用不落库）。TTL 是本设计引入的新机制，
清理路径要自己写全，别指望有现成的。

- **有效期**：初值 1 天（C2-22 设想）。查询时过滤过期条目，**不能只靠定期清理**——
  否则清理线程没跑到的窗口里，过期草稿照样被召回。
- **清理时机（已实施，两条通路，缺一不可）**：
  - **落库之后**（`maybe_evict_drafts`，后台 flush 线程内）：清过期 + 超上限淘汰，
    **只对当前写入的那个方案**。
  - **启动时一次**（`purge_drafts_on_start`，`construct.rs` 的预热线程里、eager 闸之前）：
    **全表跨方案**，只清过期、不做容量淘汰。
    - 为什么必须跨方案：落库那条带的是当前方案前缀，够不着两类草稿——**开关被关掉之后**
      （此后再没有落库，旧草稿永远没人收）与**用户已经不用的方案**。两类都会永久躺在库里。
    - 为什么不在这里做容量淘汰：上限是**按方案**定义的（`evict_drafts` 的语义是「这个方案
      保留 N 条」），全表跨方案套同一个上限会把小方案连坐清空。
    - 不看开关是刻意的：关掉功能的用户更需要它，且因为没有新写入，表会在一个 TTL 内自行排空。
    - 它顺带数出**剩余条数**打进 debug 日志——见下面量级估算的「未实测」警告，那是真机
      重定上限唯一的观测出口。
- **容量上限**：超出按 `created_at` 升序淘汰（草稿没有 count 可比，最早的先走）。

### 量级估算（**纸面推算，未实测**）

按 60 字/分钟（1 字/秒）、滑窗 2–5 字，每新增一个字最多产生 4 个新窗口 ⇒ **约 4 条/秒**。
每条按「词 + 码 + 时间戳」约 50 字节：

| 场景 | 条数 | 体量 |
|---|---|---|
| 连续打字 1 小时 | ~14,400 | ~720 KB |
| 一天打 8 小时（有效期 1 天） | ~115,000 | ~5.7 MB |

对比反查索引 95.4 MB，这个量级站得住。但**必须配容量上限**，否则重度用户一天就能把它顶到
几十 MB。上限初值待实测调参（C2-22 原文也要求「按性能与易用度实测调参」）。

⚠️ 真实打字有大量停顿、断流与重复窗口（同一个词反复打会命中同一条 key），实际条数应显著
低于上表。**上表是上界，不是预期值**——实施时先量一版真机数据再定上限，别拿这张表当依据。

## 8. 配置

**沿用 `[schema.codetable.auto_phrase]`，不新增配置段**（§0）。老用户的配置文件不必迁移，
设置页那两个已暴露的控件（「启用自动造词」「转入用户词库次数」）语义不变。

| 键 | 现状 | 本设计 |
|---|---|---|
| `enabled` | `false` | **不变**，仍是这一个总开关 |
| `promote_count` | `0` | 见 §6 —— 出厂值改动在「用过即转正」落地时一并结掉 |
| `min_phrase_len` / `max_phrase_len` | 2 / 5 | **复用为滑窗长度上下界**，值不变 |
| `idle_timeout_ms` | `0`→5000 | 复用为断流的 idle 超时 |
| `temp_max_entries` | 5000 | 不变，管的仍是**临时词库** |
| `draft_ttl_hours` | — | 新增，草稿有效期，初值 24 |
| `draft_max_entries` | — | 新增，草稿表容量上限，**待实测** |
| `draft_flush_batch` / `draft_flush_interval_ms` | — | 新增，异步批量写入，**待实测** |

★ `max_phrase_len` 复用成滑窗上界之后，「**超长整体丢弃**」那道闸（§1 放大器 1）自然消失
——滑窗本来就只切 2–5 字，不存在「整条序列超长」这回事。这是换缓冲对象带来的连锁简化，
不是另外去掉了一道判断。

⚠️ 四个新键都只在**码表段**下，因为本轮范围限码表（§0）。将来若扩到拼音，
届时再决定是共用还是各配一份——**别现在就为那一天预留**，本仓在配置分层上吃过
「预留了却与实际演进对不上」的亏。

## 9. 与现状造词路径的关系：就地替换

现状两条路径（`handle_addword.rs:233/561` 按引擎类型分流）：码表的 `feed_auto_phrase`
（连续单字）、拼音的 `learn_phrase_on_commit`（分步/整句）。

**码表那条被本设计就地替换**（§0 已定）。判据：它的全部产出都是草稿层的**子集**——
连续单字序列本身就是落屏文本流的一段，滑窗会把它切出来的每个 2–5 字组合都覆盖到。
并存只会多一条写入路径和多一份杂词，还会让「这个词是怎么进来的」变得无法回答。

**拼音那条保留不动**：它学的是拼音码词，与草稿层的码表码不同域（`pinyin-code-domains.md`），
两者从主键起就活在不同编码域里，不是重复。

退役 `feed_auto_phrase` 时要一并处理的：
- `AutoPhraseBuf` 及其打断语义单测——滑窗状态机取而代之，**旧测试不要直接删**，
  逐条对照新模型该有什么行为（那里面沉淀着「多字词终止」「idle 分段」这些判据的来由）。
- `flush_auto_phrase` 的八道闸里，**查重两道（系统词库 / 用户词库）必须原样保留**到新路径，
  它们不是旧模型的包袱。索引就绪闸同理（取码一样要用）。
- `AutoPhraseBuf::discard()` 这个「零生产调用点」的语义随旧状态机一起退场，别顺手继承。

## 10. 未决

> §0 已结掉原列表的前两条（复用现有开关、出厂仍关闭）。剩下三条：

1. **草稿候选要不要显示得与众不同**（如注释标记）：用户看到一堆没见过的词沉在候选底部，
   不知道它是什么、也不知道选了会怎样。可发现性与干扰的权衡未定。
   ⚠️ 与「出厂关闭」叠加后这条的紧迫度下降了——看到它的都是主动开启的用户。
2. **混输下草稿归属哪个方案**：`write_data_schema_id` 现有逻辑按 `CandidateSource` 分流，
   而落屏文本流**不携带来源**（这正是 §2 想要的）。
   ⇒ 本轮范围限码表，产出恒是码表词，归属可直接取**主码表成员方案**
   （同现状 `flush_auto_phrase` 的 `mixed_primary_schema`，`handle_addword.rs:330`），
   问题因此大幅简化，但仍需在实施时确认这条捷径对所有混输配置都成立。
   ⚠️ 取码必须传成员方案 id，传混输方案自身会得到空表（`cross-engine-auto-phrase.md` §6.2）。
3. **与 S3（跨引擎补写）的叠加**：两者都会放大写入量，先后顺序与叠加效果未评估。

## 11. 验证

- 纯逻辑单测：滑窗切分（含断流、`ReplaceBackward` 回退、长度边界）——状态机保持
  `auto_phrase.rs` 那样的**纯逻辑零 IO**形态，打断语义全部单测覆盖。
- 存储层单测：TTL 过滤、容量淘汰、草稿→临时词的跃迁事务。
- **召回层护栏（本设计最容易出错的一处）**：草稿**不得**出现在前缀候选里；
  草稿在完整码命中时**必须**排在所有普通候选之后。两条都要能被变异验证打红——
  ⚠️ 本仓踩过「护栏全钉在纯函数上、绕开消费点」，这两条必须钉在候选装配的消费点上。
- 端到端：走 `handle_key_event_policed`（**不是**裸 `handle_key_event`，后者不经过打点与投喂，
  见 `codetable-auto-phrase.md` §3 的警告）。
- 启动清理：跨方案全表扫（按方案清只收得掉当前方案那条，是本条护栏的对照面），
  以及配置的**量纲**（小时 → 秒）——漏掉 ×3600 不会报错，只会让草稿 24 **秒**就过期，
  功能看着开着而用户永远等不到一条被用上。
- **自动化测不到的三处**（只能真机验，见 `.omc/IMPLEMENTATION_PLAN.md` 同名小节）：
  启动清理的**调用点**、过期后的端到端行为（集成测试造不出「隔天的草稿」）、
  删方案时的级联清库。
- **待真机**：草稿表的真实增长曲线与词条质量；flush 批量参数；容量上限。
