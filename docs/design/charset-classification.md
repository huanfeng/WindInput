# 字符集分类 `charsets/` 设计

> **范围**（2026-09-04 拍板）：把散在代码里的「字符集」定义收拢成一套配置驱动的
> **字符类**系统，供四个消费者共用：常用性默认值、免词频、生僻字模式准入、
> 常用字列表的类型列与整类批量。
>
> **拍板的三条边界**：
> - **不做方案级覆盖**——字符类是全局的语言学属性，与五笔/拼音无关。
> - **GB18030 不动**——它是 `FilterMode` 的档位名（意为「不过滤」），不是字符集。
> - **老的逐条覆盖原样留着**，不迁移、不清理（代价见 §7.2）。
>
> **状态：已完整落地**（2026-09-04）。配置层、判定层、四个消费者接线、设置页读写与
> 「字符集分类」两层视图均已完成，182 条回归复验通过。进度与提交号见 §9。

## 1. 现状：五套各自为政的机制

| # | 机制 | 形态 | 职责 | 消费者 |
|---|---|---|---|---|
| 1 | `charblock::BLOCKS` | 硬编码 50 条 `(名, start, end)` | **显示域**：类型列标签 | 类型列、整类批量 |
| 2 | `common::is_common_scope` = `is_han ∪ is_pua` | 硬编码区间 | **判定域**：默认字表管不管得着 | 常用性判定、批量准入 |
| 3 | `charclass::PRESET_EMOJI` | 5 个块名的别名 | 近似 emoji（⚠️ **两个方向都不准**，见 §5.5） | 免词频、生僻准入 |
| 4 | `charclass::PRESET_SYMBOLS` | 15 个块名的别名 | 分组便利 | 配置取值 |
| 5 | `common_chars.txt` + redb 稀疏覆盖 | **字符列表** 8104 字 | 常用/生僻判定 | 检索范围过滤 |

前四套喂 `BlockMask(u64)`，接 `exclude_blocks` / `include_blocks`。第五套独立，接 `filter_mode`。

### ⛔ 1 和 2 永远不要合并

`charblock.rs` 模块头已有此禁令，理由不是职责洁癖而是**失效方向不同**：

| | 漏一块的后果 | 方向 |
|---|---|---|
| `is_han`（判定域） | 那批字**恒判常用**、过滤静默失效 | **不安全** |
| `BLOCKS`（显示域） | 类型列显示「其它」 | 安全 |

issue #83 正是前者：`is_han` 列举到扩展 H 末尾 `0x323AF`，Unicode 17 的扩展 J 从
`0x323B0` 起，**差一个码位**落到域外，用户候选里冒出一批无字形的生僻字。

⇒ **配置化会天然诱使这两者合并**（都是码位区间，看着该用同一套语法）。这是本次改造
最危险的一步：合并后一切照常工作，只有 Unicode 出新版时才炸，且表现为「过滤静默失效」
而不是报错。防线见 §2.4。

## 2. 数据模型：类 = 字符集 + 属性

### 2.1 ⛔「常用字 / 生僻字」不是并列的类

需求初稿把 `常用字`、`生僻字` 与 `emoji`、`符号` 并列。它们不是一个东西：

- `emoji` / `符号` / 自定义段 = **字符集**，外延由码位/列表定义，一个字符可同时属于多个；
- `常用字` / `生僻字` = **判定结果**，由「字符集 → 默认值 → 用户覆盖」三层算出来，二值互斥。

并列会立刻产生无定义状态：`龘` 既在「生僻字」类又在「基本汉字」类，谁说了算？更硬的
障碍是**「生僻字」本质是补集**（汉字域 ∧ 不在常用表里），列举不出来，写不成码位段。

⇒ 分类只定义**字符集**，常用性降为叠加其上的**属性**。

### 2.2 ★★★ 两种性质，两种合成规则

一个类会被几个消费者同时问到，但它们要的答案形状不同：

| 性质 | 合成规则 | 为什么 |
|---|---|---|
| `default`（常用性） | **仲裁**：`order` 最小且表态的类赢 | 二值判定，只能有一个答案 |
| `no_freq`（免词频）<br>`in_rare`（生僻模式准入） | **并集**：任一命中的类为真即真 | 布尔能力，多给一个是**安全方向** |

⚠️ 这条不能含糊。`▶` 同时命中 emoji 类与「符号」类；若 emoji 配 `no_freq = true`
而符号配 `false`——按并集它免词频（与现状一致），按仲裁则取决于 `order`（**行为变更**）。
`exclude_blocks` 现在就是并集语义，多免一个字符无害，不得因属性化而悄悄改成仲裁。

⇒ 外部引用写法 `exclude_blocks = ["emoji", "my_symbols"]` **保留**（已出厂，且同为并集）。
它与类上的 `no_freq` 是同一件事的两个入口，装载期合并成同一个掩码。

### 2.3 ★★ 作用域：「生僻字是补集」这个问题只是换了位置

`common_han` 若只写 `file = "common_chars.txt"`，「在文件里 → 常用」能表达，
但**「是汉字、却不在文件里 → 生僻」表达不了**——那个字压根不是这个类的成员。

这正是现在 `is_common_scope`（作用域）与 `base`（名单）分两层的原因，必须保留：

```yaml
key: common_han
scope: han                   # 作用域：这个类「管得着」谁
file: common_chars.txt       # 名单：作用域内的白名单
default: common              # 名单内
outside: rare                # 作用域内、名单外  ← 缺了它「换一本常用字表」就做不到
```

纯段类不写 `scope` / `outside`（≡ 作用域=成员，域外不表态），行为与现状一致。

### 2.4 ⛔ `scope` 只接受内置属性名，不接受用户写的 ranges

`scope` 背后是判定域（§1 的机制 2），漏一段 = 过滤静默失效。`ranges` 背后是显示域，
漏一段无害。**判定域的完整性必须由代码保证**，不能交给配置。

⇒ `scope` 的值域是**闭集**：`"Han"` / `"PUA"`。用户能自定义的只有 `ranges`。
（初稿还列了 `"Emoji"`，已随 §5.2 一并删除——emoji 不是判定域。）

## 3. 配置落点：为什么是独立的 `charsets/` 目录

### 3.1 ⛔ 不能进 `config.toml`——`is_known_key` 是静态登记表

`config_schema.rs` 的 `is_known_key(key) = field(key).is_some()`，每个键要在代码里逐条
登记。`charset.my_symbols.default` 这种**用户起名的键登记不了**。连锁后果：

- `prune_redundant` 用 `is_known_key` 把未登记键整体排除 ⇒ 自定义类不参与「等于默认就剔除」；
- 设置页配置项列表、来源可见性 `OriginSnapshot`、方案覆盖登记 `SCHEMA_OVERRIDES`
  **全都基于这张表** ⇒ 自定义类在这些机制里等于不存在。

⇒ 把动态键塞进为静态键设计的系统，不是跑不起来，是**跑起来后一半配置基础设施对它
静默失效**。「键名是我定的还是用户定的」应当是决定配置落点的第一个问题。

另两条次要理由：`ranges` 几十段 + 增删几百字符会淹掉一个供用户通读的文件；
`config.toml` 的四层合并 + `prune_redundant` 一整套，对 charset 是杀鸡用牛刀。

### 3.2 沿用 `compat.toml` 的层序，偏离两处

`app_compat.rs` 已经把「三层同名资源」这条路趟平：

| `compat.toml` 现成的 | charset 复用 |
|---|---|
| 三层 `data/` → `data_custom/` → `user_config/` | ✅ 出厂 / 定制版 / 用户 |
| 用户层 GUI 整份重写 + 固定头注释声明「手写注释不保留」 | ✅（GUI 只重写它自己那一份） |
| **系统层程序绝不改写**，字段文档留系统层 | ✅ 出厂更新通路 |
| 省略默认值（`skip_serializing_if`） | ✅ 全字段 `Option`，`None` = 不表态 |
| **剔除空壳规则**（`update_user_rule`） | ✅ |
| 解析失败按空处理、宁可重建不卡死菜单 | ✅ 但**按文件**降级，见下 |

**⚠️ 偏离一：字段级合并，不是整条覆盖。** compat 是「同进程名整条覆盖靠前层」。charset
**必须字段级**——用户只想改 emoji 的 `default`，整条覆盖会连带丢掉系统层的 `ranges` 与
`name`。实现是一个 `take!` 宏：`overlay` 里 `Some` 的字段才写下去。

**⚠️ 偏离二：一层是一个目录，不是一个文件。** 见 §3.4。

### 3.3 ⛔ 不入 redb

| 判据 | charset 定义 | 常用性逐条覆盖（保持现状） |
|---|---|---|
| 写入频率 | 低（设置页） | 高（候选右键） |
| 量级 | 几十个类 | 上千条 |
| 用户要手写/看 | **是** | 否 |
| 要分享/换机器 | **是** | 否 |
| 服务在线时可读 | **必须** | 无所谓 |

最后一条是实锤：服务运行时 redb 上着锁，查真实条目得跑 `dict export` CLI。用户配的
字符集定义，他会期望随时打开看一眼。

⇒ **分界线：「定义」进配置文件，「记账」进 redb。**

### 3.4 ★ 一层 = 一个目录，一个类 = 一个文件

初稿是每层一个 `charset.toml`。改成目录扫描的三条理由：

1. **类会变多**（50 个内置块 + emoji + 常用汉字 + 用户自定义），单文件会长到没法通读；
2. **定义与内容分居两处**是初稿最别扭的地方——`charset.toml` 里写 `file = "emoji_chars.txt"`，
   要改一个类得同时开两个文件，而其中一个是没有任何自述的裸字符列表；
3. **加一个类不该要求改动别处**。固定文件名意味着新类得先在某个索引里登记；扫描目录则
   「放进去就生效」，这是配置系统里少见的能真正做到**零登记**的形态。

⇒ 形态取自 `.dict.yaml`：meta 头 + `...` + 列表体，一个文件自我完备。

```
data/charsets/                     ← 出厂层，程序绝不改写
  emoji.yaml                       ← meta 头 + 1427 条内嵌列表（生成物）
  common_han.yaml                  ← meta 头 + file: 引用外部字表
data_custom/charsets/              ← 定制版层
{user_config}/charsets/            ← 用户层，文件名任意
```

### 3.5 ⛔ 覆盖按内部 `key`，不按文件名

用户方案是「同名文件覆盖同名文件」。⛔ **不采用**，因为它让「改一个字段」和「接管整个
定义」在语法上无法区分：用户想把 emoji 改成默认生僻，就得整份复制 1427 行过来，从此
脱离出厂更新——正是 §4.1 那个坑换了个容器复现。

⇒ 三条规则：

| | 规则 |
|---|---|
| **匹配** | 按文件里的 `key` 字段，文件名只影响同层内的加载顺序 |
| **meta 字段** | 字段级合并，`Some` 才覆盖（`take!` 宏） |
| **列表体** | 默认**增量**：裸行追加、`-` 前缀删除；`replace: true` 才整份替换 |

用户层最常见的写法因此只有四行：

```yaml
---
key: emoji                # 按 key 匹配，不看文件名
default: rare
...
-☯                        # 这个不算 emoji，从类里去掉
```

### 3.6 一个坏文件不拖垮一层

解析失败**按文件降级**：warn 出文件名与原因，跳过它，继续加载同层其余文件。
⛔ 不做「一层解析失败就整层按空处理」——那会让一个手滑的缩进静默关掉 50 个内置类。

## 4. 出厂内容与安全边界

### 4.1 ⛔ 承载出厂值的列表不能整体替换（论证保留，容器已换）

初稿讨论的是 `[[charset]]` **数组表**：数组在深合并里是整体替换，用户只改一个 `default`
却要回写整个数组 ⇒ 内置类的完整定义被固化进用户层 ⇒ **Unicode 升版时新的 emoji 这个
用户永远拿不到**。

同一个坑本仓已踩过三次：`key_actions` 物化、扩展词库 override、`compat.toml` 空壳规则。
共同判据：**稀疏 diff 的合并算子里，「删除」和「顺序」有没有表达**。数组两样都没有。

⇒ 换成目录 + yaml 后论证不变，只是解法换了位置：

| 要表达的 | 数组表 | 现在 |
|---|---|---|
| 只改一个字段 | ⛔ 得重写整个数组 | 文件里只写那一个字段 |
| 删除一个成员 | ⛔ 表达不了 | 列表体 `-☯` |
| 删除整个类 | ⛔ 表达不了 | `enabled: false` |
| 顺序 | ⛔ 靠数组下标，覆盖即固化 | `order`，一个可稀疏覆盖的数 |

### 4.2 ★ 出厂文件一个判定字段都不写

`data/charsets/emoji.yaml` 只有 `key` / `name` / `order`，`default`、`no_freq`、`in_rare`
**全部留空**。留空 = 不表态 = 行为与本类出现之前完全一致。

写上 `default: rare` 的后果是：升级到这一版的用户**突然发现 emoji 从候选里消失了**，
而他什么都没改。新增一个判定机制时，出厂值必须是「这个机制不存在」那一档。

⇒ `charsets_factory_files.rs` 钉住这条，且读的是**仓里真实的出厂文件**而非夹具——
夹具只能证明解析器自洽，证明不了我们实际发出去的文件是对的。

### 4.3 GUI 的可写边界

| 字段 | GUI | 理由 |
|---|---|---|
| `default` / `order` / `enabled` / `no_freq` / `in_rare` | ✅ 可写 | 纯用户意图，无出厂值可固化 |
| 列表体的增删（`星` / `-☯`） | ✅ 可写 | 纯用户数据 |
| `ranges` / `file` / `replace` | ⛔ 只读 | 承载出厂值，写了就固化 |

要改范围：新建一个自定义类，别覆盖内置类的 `ranges`。

## 5. ★★ emoji 用**字表文件**，不用 ranges、也不内置

### 5.1 ⛔ 先否掉 ranges

1. **keycap 基字符**（`0-9 # *`）在 `Emoji` 属性里为真，独立时却不算 emoji。区间只能
   表达「包含」，表达不了「包含但不算独立」。
2. **`text_has_emoji` 是序列级判定**（基字符 + `U+20E3` 才算），区间是字符级的，表达不了。

### 5.2 ⛔ 但「不能用 ranges」推不出「必须内置」——那一步曾经是错的

初稿据上面两条把 emoji 定成了**内置属性函数**（`property = "Emoji"`，用户不可改）。
2026-09-04 用户指出还有第三种形态：**像 `common_chars.txt` 那样的字表文件**。
上面两条对它都不成立：

| 反对 | 对 `ranges` | 对**列表** |
|---|---|---|
| keycap 基字符 | ⛔ 区间扣不掉 | ✅ **不列就是不列**，逐条列举天然能做例外 |
| 序列级判定 | ⛔ 字符级表达不了 | ✅ 列表的键是**字素簇**（覆盖表早就支持多码位簇） |

区间的表达力是「一段连续码位，全要或全不要」；列表的表达力是「这些，逐个」。
用针对前者的论证去否定后者，是一步无效推理。

而列表在本次改造的**核心诉求**上明显更好：

| | 内置属性函数 | 列表文件 |
|---|---|---|
| **用户可改** | ⛔ 不可能 | ✅ 整份覆盖 + `add`/`remove` |
| 查询成本 | 二分 151 段 ≈ 7 次比较 | **HashSet O(1)** |
| 体积 | 1.2KB 常量 | ~7KB 文件（`common_chars.txt` 8104 字，同量级） |

★★★ 第一行即结论：**本次改造的全部目的就是让判据可自定义**，而内置属性函数是唯一一个
用户碰不到的形态——在一个可配置系统里给最该配置的那一项开后门，自相矛盾。

### 5.3 生成 `data/charsets/emoji.yaml` 时的三个决定

⚠️ 必须写在生成器里并注释，否则下次重新生成就丢：

1. **不列 `0-9 # *`**——keycap 基字符，独立时不是 emoji。这条从代码里的
   `is_keycap_base` 变成生成器的一条排除规则，须有测试钉住「列表里恰好没有 ASCII 数字」。
2. **列 `U+20E3`**（组合键帽符）——让 `1️⃣` 在逐字符存在性判定里能命中。副作用是它单独
   也算 emoji，但组合符号不会单独成为候选，无害。
3. **不列 ZWJ 序列与肤色组合**——`👨‍👩‍👧` 逐 char 查表时首码位 `👨` 已命中；列全 RGI 的
   5225 条会让文件大 6 倍，换不来任何判定差异。

   ⚠️ **这一条的前提是「消费方会逐 `char` 回落」**，它是一条跨模块的约定，而不是字表
   自身的性质。判定层若只按字素簇查表，`⚽️`（`⚽` + `U+FE0F`）这类**裸基字符 + 变体
   选择符**全都漏判——而上游词库存的恰恰多是这种形态。防线见 §6.6。

### 5.4 判定来源只剩两支

`property` 字段整个删掉。一个类的成员由两支来源**并集**构成，两支都可缺省：

| 来源 | 字段 | 装载期产物 |
|---|---|---|
| 区间 | `ranges` | 不相交分段表，一次二分 |
| 离散 | `file` + 内嵌列表体 | `HashSet<String>`，O(1) |

⇒ 内嵌列表体与 `file:` 是同一支的两种写法，可并存：`emoji.yaml` 用内嵌（生成物，
自我完备），`common_han.yaml` 用 `file:`（§ 见下）。用户自建类两种都能用。

**⚠️ `common_chars.txt` 刻意不搬进 yaml**：那个文件早就支持整份覆盖（放一份同名文件到
用户配置目录的 `schemas/` 下即可），搬家会让**已经这么做的用户静默失效**，而他完全看不
出原因。已出厂的覆盖点，改造时只能新增、不能移动。

`scope`（`han` / `pua`）**仍内置**——那是**判定域**（§2.4），漏一段 = 过滤静默失效，
与 emoji 无关；emoji 从来不是判定域。

样本：`wubi86_hgwb_emoji.dict.yaml`，4132 条目 / 1404 簇；两套判据一致的 1321 簇。

⚠️ **「182」是条目数不是簇数**——去重后是 79 个字素簇。两个数都记下来，免得下次复验
按簇数比对时以为对不上。

★ 复验中踩到两次**「参照实现凭记忆重建」**：

1. 按「第一列即文本」读码表 ⇒ 两套判据都认 0 条，看着像判据全错。那本码表头部显式
   声明了 `columns: [code, text, weight]`，**第一列是编码**。
2. 「表情符号」块的区间按记忆写成 `1F300-1F5FF` + `1F600-1F64F`，真值是 `1F300-1FAFF`
   整片 ⇒ 差异数翻了一倍（326 vs 79）。

⇒ 复验的参照实现必须从代码/数据里抄真值。凭记忆重建的参照物，错了也是一片绿或一片红，
两种都会把人引到错误的结论上。

代码已不在仓里，以下结论只存于本节，P2/P3 直接照此实现：

#### 数据源与属性选择

- 来源：`https://www.unicode.org/Public/UCD/latest/ucd/emoji/emoji-data.txt`（Unicode 17.0）
- 用 **`Emoji`** 属性：**1438** 个码位。
- ⛔ **绝不用 `Extended_Pictographic`**（2848）：它含**未分配码位**，是给 UAX #29
  断簇用的，不是「是不是 emoji」的判据。
- ⛔ **不用 `Emoji_Presentation`**（1219）：实测会**误伤 201 个**（`❤ ☀ ✈ ♠ 🕵 🖥`）
  ——因为上游词库存的是**裸码位**，1404 簇里只有 10 个带 `FE0F`。
- Unicode 官方立场：`© ® ™ ↔ ▶` **都是** emoji（RGI fully-qualified，只是归在
  `Symbols` 组）。「这是符号不算 emoji」那条线属性表里没有，只在 `emoji-test.txt` 的
  group 里，需要它得引入 5225 条 RGI 全表——已否决（会连 `✅ ❌ ⭕` 一起摘走）。

#### 为什么不能按 Unicode 块判（这是整件事的起点）

实测一本五笔 emoji 码表（4132 条 / 1404 簇），旧的「五个块并集」口径**两个方向同时不准**：

- **漏 182 条**：`⬅ ⬛ ⭐ ⭕ 🀄 🃏 🅰 🆚 🈚 🉐 ⤴ ⤵` 所在的块根本不在块表里；
  `▶ ◀ ↔ ↩ ‼ ™ ℹ ㊗ Ⓜ 〰 © ®` 所在的块大部分是非 emoji，整块搬进来会连
  `← → ▲ ◆` 一起搬；
- **多收**：「杂项符号」块内的 `☰`、「杂项技术符号」块内的 `⌘ ⌥`。

⚠️ 早期记录把 `♠ ☯` 也列进「多收」，**是错的**——`2660`/`262F` 在 `emoji-data.txt` 里
明确带 `Emoji` 属性，收进来是对的。2026-09-04 拿生成出的字表实证后更正。
★ 教训：结论转存文档后，**第一次有能力实证时就该验一遍**，否则错误会在转述中固化。

⇒ **补块补不齐**：块是显示域的划分、emoji 是字符属性，两者正交。

#### keycap 陷阱（生成列表时最容易漏的一条）

`Emoji=Yes` 收了 **12 个 ASCII 字符**：`0`-`9`、`#`、`*`（keycap 序列 `[0-9#*] FE0F? 20E3`
的基字符）。它们独立时**不是** emoji。不排除的后果**全部静默**：数字候选免词频、
`0-9` 挤进生僻字候选、一次整类批量把十个数字判掉。

⇒ 生成 `emoji.yaml` 时排除这 12 个（§5.3 第 1 条），并用一条测试钉住
「ASCII 区恰好排除了这 12 个」——它同时防住上游属性变化时的静默漂移。

#### 保留未撤的部分

设置仓 `b3c5e10`（`format!("U+{}", block_range)` 在范围为空时渲染出孤零零的 `U+`）
**不撤**：`OTHER`（「其它」）的 `range_text()` 早在本次改动前就返回空串，任何归到
「其它」的字符都会触发，那是一个独立的既有 bug。

## 6. 实现要点

### 6.1 ★★ 仲裁在装载期做完，热路径不遍历类列表

判定发生在每次按键 × 每个候选 × 每个字符（五笔单字母下 78+ 候选）。

| 类型 | 装载期产物 | 热路径 |
|---|---|---|
| 区间型（`ranges`） | 各类段边界取并集切成**不相交段**（约 200 段），每段预存该段内
`order` 最小的表态类 | 一次二分 |
| 离散型（`file` / 内嵌列表体） | HashSet | O(1) |

⛔ 朴素实现（遍历 N 类、每类二分）是 O(N·log M)，改完就卡，且不报错只是变慢。

### ⛔ 6.1.1 离散型**不要**切进分段表

初稿写的是「所有类的段边界切成不相交段」。对离散型的类这条不成立：`common_han` 的
8104 字是离散点集，切进去会把 Han 域打成约 16000 段，二分要 14 次比较——而现在是
「几次区间比较 + 一次 HashSet 查询」。**热路径反而变慢**。

⇒ 混合结构，且用 `order` 短路：段结果已预存「该段 order 最小的表态类」，
**仅当某个离散类的 `order` 更小时才需要查它的 HashSet**。常见情形（离散类 order 较大）
连 HashSet 都不查，比现状更快；最坏情形与现状持平。

### 6.2 `BlockMask` 换 `u128`

现已用 52/62 位（50 块 + 「其它」+ emoji），自定义类一多就溢出。表示层改一处，
判定仍是两条指令。`charclass.rs` 的位宽断言注释里已记着这条出路。

### 6.3 列表增删零热路径成本

因为它们落在 `charsets/*.yaml`（而非 redb），装载期即可并进成员集：追加行进
HashSet、`-` 前缀行进 `excluded`（**优先于 `ranges` 与成员表**，否则从段表里扣不掉）。
**不需要** `has_member_overrides` 这类热路径闸门。

### 6.4 解析容错

⛔ `ranges` 语法错**不得整类丢弃**（`.ok().unwrap_or(空)` = 丢数据），须 warn 并保留
其余段。参照 `config.rs` 的容错解析纪律。

### 6.5 校验：类被完全遮住

某类若被 `order` 更小的类完全覆盖，它永不命中——这是「配了没反应」的经典来源。
装载期检出并 warn。

### ★★ 6.6 并集查询必须「先整簇、不中再逐 char」

这是接口两侧各自合理的假设失配出来的洞，2026-09-04 接线时由一条既有测试
（`both_freq_ends_share_one_verdict` 的 `⚽️` 样本）抓住：

| | 假设 | 合理性 |
|---|---|---|
| 生成器（§5.3 决定 3） | 消费方**逐 `char`**，故省略组合序列 | ✅ 旧的 `BlockMask::contains_text` 正是逐 char |
| 判定层 `any_char_in` | 按**字素簇**查，故 `👨‍👩‍👧` 能整条命中 | ✅ 字表里那是一整条 |

接在一起就漏了两种输入：

| 输入 | 只查整簇 | 只逐 `char` |
|---|---|---|
| `👨‍👩‍👧`（字表里是一整条） | ✅ | ✅ 首码位也在表里 |
| `⚽️` = `⚽` + `U+FE0F` | ⛔ **漏** | ✅ |
| `1️⃣` = `1` + `FE0F` + `20E3` | ⛔ 漏 | ✅ `U+20E3` 在表里 |

⇒ 两步都要：先整簇、不中再逐 `char`。单 `char` 的簇上两步等价，直接跳过第二步。
`excluded` 对两步都优先（删掉 `⚽` 之后 `⚽️` 也不再命中）。

★ 教训：**一个模块省略的东西，是另一个模块补上的**——这种约定不写进类型，就只能靠
两边的注释同时正确。§5.3 那三条决定现在各自注明了前提。

### ★★ 6.7 安全阀：补集类的名单为空时撤销表态

`common_han` 的形态是「作用域 = 汉字，名单 = `common_chars.txt`，名单内常用、**域内
名单外生僻**」。字表读不到时（路径变了、文件被删、定制包漏打），名单为空而作用域还在
⇒ **每个汉字都落进「域内、名单外」⇒ 全部判生僻**，候选被过滤到几乎不剩，全程只有一条
warn。

⇒ 装配期检出「有 `scope` + `outside` 却一个成员都没有」的类，**撤销它的表态**
（回到没有这个类的样子），而不是拿空名单去判。

★ 失效方向必须是「这个类不表态」，不是「反过来判」。同款防线是 `CommonChars::is_empty()`
——那里也是拿「出厂表没装进来」当作**退化为不过滤**的信号。

⚠️ 只对**同时有 `scope` 和 `outside`** 的类生效。纯段类成员为空只是它不命中任何字符，
没有「补集」那一半，本来就无害。

## 7. 迁移与已知代价

### 7.1 零配置迁移

内置类的 key 沿用 `exclude_blocks` / `include_blocks` 现有取值（`"emoji"` / `"符号"`
及 50 个块的中文名），**已出厂的配置一个字不用改**。`name` 缺省 = key。

★ 这是 §3.5「按 key 匹配而非按文件名」的另一半收益：key 是配置里早就存在的标识，
文件名是新引入的——用文件名当主键，等于给一套已出厂的取值凭空加一层映射。

### 7.2 ⚠️ 「老覆盖原样留着」的代价：改了 `default` 会显得没反应

用户曾点过「整类设为生僻」，库里躺着上千条 emoji 覆盖。他现在把 emoji 类的 `default`
改成 `common`——**一点反应都没有**，因为逐条覆盖优先级更高，全压着。

这是「配了没反应」的标准形态，且是本次改造自己造的。**不迁移数据，就必须在界面上解释**：

```
表情符号                     默认: 生僻 ▾
⚠️ 该类有 1204 条逐条覆盖优先于此设置   [查看] [清理冗余]
```

「清理冗余」复用写端已有判据（`is_cluster_common_by_default(key) != common` 才留记录），
不需新写。

### 7.3 ★★ 整类批量应改为「改 `default`」

现在 `handle_common_chars.rs` 的整类批量是：扫描**词库里出现过的**该类字符 → 写上千条
redb 覆盖。三个毛病：

1. **只覆盖词库里已出现的字符**——用户装一本新 emoji 词库，新出现的又冒出来，
   而他记得自己处理过；
2. 改主意要再来一次反向批量；
3. 备份包按条膨胀。

根因是**把一个关于字符集的断言，实现成了对当前数据的一次遍历**，有效期悄悄绑在了数据
快照上。改 `default` 是对整个类说的，不问词库里有没有。

⇒ 两种操作都保留，界面须说清差别：改 `default`（整类、跟随出厂 ranges 更新、可逆）
vs 逐条覆盖（精确、用于例外）。

### ⚠️ 7.4 `emoji` 这个 key 依赖出厂文件在场

`exclude_blocks = ["emoji"]` 里的 `emoji` **不是**内置区块组（§6 的 `builtin_block_specs`
刻意不造它），它的成员由 `data/charsets/emoji.yaml` 给出。文件不在 ⇒ 名字解析不出来
⇒ 那一行被当成「未识别」跳过 ⇒ 功能静默失效。

已核过两条部署路径都是**整目录**复制，新目录自动带上：

| 路径 | 语句 |
|---|---|
| `scripts/dev.ps1` | `Copy-Item "$ProductRoot\data" -Recurse -Force` |
| `scripts/pack-installer.sh` | `cp -rf "$BUILD_DIR/data" "$STAGE/"` |

⇒ 无需改打包。但**测试夹具不会自动获得它**——`freq_learn_tests` 的临时 data_dir 因此
显式复制 `data/charsets/`，且找不到时 panic 而非跳过（跳过的话测试会以「开关没生效」
这个形态失败，与真实故障长得一模一样）。

### 7.5 跨仓契约

JSON 字段 `block` / `blockRange` / `blockBulkEditable` 被 wind-setting 的 `spec.rs` /
`view.rs` 直接读，**不改名**，只换取值来源。设置页的「字符集分类」两层视图需要**新增**
一个列类的 RPC。
