# 单字输入

## 1. 背景

五笔系输入法的传统功能，各家都叫「字词模式 / 单字模式 / 词组模式」（极点、万能、QQ 五笔）。
本仓叫**单字输入**（`single_char`），**一个开关**：关（出厂）＝字词都出，开＝只出单字。

### 1.0 ⛔ 曾有第三档「只出词组」，已删（2026-09-09）

初版对齐了各家的三档形态（`all` / `char` / `phrase`）。用户实测后判定「只出词组」的表现
**非常奇怪**：单字被整批滤掉后，大量码位只剩零星几条甚至空列表，而五笔用户按码取字的
肌肉记忆全部落空。

它与「只出单字」看似对称（判据恰是同一个 `is_some()` 的正反两面，写起来几乎免费），
**实际价值完全不对等**——留着只是徒增一个没人用、却处处要考虑的状态：每个消费点、每条
测试、每份文档都要多带一档。⇒ 整档删除，类型从三值枚举退化成 `bool`。

★ 教训：**判据对称不等于产品对称**。「反正实现只要一行」不是保留一个档位的理由。

### 1.1 单字模式的价值不止「练习拆字」

三层用途，第三层决定了本功能的实现要求：

1. **练习五笔**——强迫拆字，不靠词组蒙；
2. **打人名 / 古文 / 生僻文本**——词组是干扰项，永远抢首选；
3. **★ 定长盲打**——五笔单字恒 ≤ 全码长。只出单字时同码的词被滤掉，
   「满码唯一即上屏」的成立率大幅提高，用户可以不看候选窗连续敲。

第 3 条是它与拼音的分水岭：**拼音没有定长**，开了对拼音只剩用途 2。这条分水岭直接决定了
配置的形状——全局那一层**按引擎分成两份**，见 §2.1。

⇒ 实现上第 3 条意味着本功能**不是纯粹的候选过滤**：它会改变满码自动上屏的口径。
那是想要的结果，但必须被测试钉住（`single_char_enables_auto_commit_at_full_code`），
不能是过滤的意外后果。

## 2. 配置：临时态 + 按引擎分流的两份

| 层 | 位置 |
|---|---|
| ⓪ 引擎不变量 | 英文/未知引擎恒关，**压过临时态**（见 §2.6） |
| ① 临时态 | `State::single_char_override`（热键切的），压过配置层 |
| ② 配置层 | **按当前引擎分流**，见下表 |

| 引擎 | 全局 | 方案级覆盖 |
|---|---|---|
| 码表 | `schema.codetable.single_char` | `[engine.codetable] single_char`（`Option<bool>`，不写＝跟随） |
| 混输 | 同上 | **继承主码表方案**（`codetable_settings` 自己解析到 `primary_schema`） |
| 拼音 | `schema.pinyin.single_char` | 无（刻意） |
| 英文等 | — | 恒关 |

取值的唯一入口是 `Coordinator::effective_single_char`。

⛔ **方案级那个 `Option<bool>` 别挂 `tolerant_de::tolerant`**（本字段一度挂过，测试当场红）。
那个适配器第一行就是 `String::deserialize`，只治「字符串枚举写错了值」；布尔字段挂上去，
连**正确**的 `single_char = true` 都会解析失败，表现成「方案级配了完全没反应」。
类型写错走段级降级，与同段其它 `Option` 同一条路。

### 2.1 ★ 全局那一层按引擎分成两份，不是一份

两种引擎对这件事的诉求本就不同：

- **码表**用户开它是为了**定长盲打**（单字恒 ≤ 全码长 ⇒ 满码唯一即上屏的成立率大增）；
- **拼音**没有定长，开了只是「不出词」，用途只剩「找一个字」。

分成两份之后，**「五笔只出单字、拼音照常出词」在全局层就表达得了**，不必逐方案配
（用户 2026-09-08 拍板）。先例是 `english_merge`——码表侧与拼音侧各有一份、刻意不共享取值。

### 2.6 ⚠️ 英文引擎恒关是**不变量**，问在临时态之前

英文候选是单词，开了会把它们全滤光，而英文方案下用户要的从来不是「只出单字母」。

★ 正因为它是不变量而非默认值，这道判据必须问在 `single_char_override` **之前**——写在
后面就被临时态绕过去了：英文方案下按一次 `single_char:on`（或 `toggle`），词库候选整批
消失，只剩 `english_head_candidates` 追加的输入原文（那批插在过滤之后）。
守门 `english_engine_ignores_the_runtime_override`。

### 2.2 方案级覆盖只给码表

一台机器上常有多张码表（五笔 / 虎码 / 快符），简码体系深浅不同，逐方案配是真实需求；
而拼音方案通常只有一张，全局那一份就够了。混输方案也不单独配——它继承主码表方案。

⇒ 与同段的 `short_code_yield_level` 是同一条论证，两者也因此住在同一个段里
（`[engine.codetable]`）、在设置页里挨着显示。

### 2.3 ⛔ 内置方案一项都不声明

出厂是**全局两侧都关 + 所有内置方案不写这一项**。「五笔常开、拼音不开」靠文档与设置页
引导，不靠出厂值。

理由：方案级 `Some(_)` 恒覆盖全局 ⇒ 给 wubi86 预置 `true` 的话，五笔用户在**全局页**
把这一项关掉纹丝不动，而「方案自带」那个标记藏在方案设置里，他不会去找。
从他的角度这就是「设置项坏了」。`short_code_yield_level` 在 0.119 恰好这么栽过一次并当天
撤回，判据已成文：**用户在全局页做的事，必须能作用到出厂方案上。**

守门在 `factory_schemas_do_not_declare_single_char`（遍历全部出厂方案，走真实反序列化）。

⚠️ 这条只约束**内置**方案。第三方方案作者写这一项完全正当。

### 2.4 ⚠️ 当前只有主输入路受管辖

过滤只接在 `update_candidates`（主输入路）上。**临拼 / 临英 / mix / 特殊模式各有各的候选
装配函数，都不经过这里**，故都不受本项管辖。

⇒ 别照着 §2 那张表推断「临拼会跟着 `schema.pinyin` 那一份走」——它压根走不到。要让它们
也受管辖，得在各自的装配函数里接同一个 `apply_single_char`，那是另一轮的事。

### 2.5 主输入路自己的三个漏点（2026-09-09 冷读审查所得）

即便在主输入路内，也有三处候选**产在过滤之后**，故不受管辖。都不是崩溃级，但都是
「开了单字还是看见词」这类用户报得出来的表现，列在这里以免下次当成新 bug 重查：

| 漏点 | 落点 | 表现 | 评估 |
|---|---|---|---|
| 联想候选 | `handle_assoc.rs` 直接 `state.candidates = hits`，不经 `build_candidates` | 上屏一个字后照样弹一列联想词 | **最值得先修的一个**；联想本就是独立通路，接线成本是一行。用户 2026-09-09 定：暂不动 |
| 多级溢出顶码 | `coordinator.rs` 的 `engine_top` 取引擎裸 `convert(&prefix, 1)` | 该罕见路径下可能顶出一个词 | 低。**主路径是对的**：`prefix == pre_buf` 时取的是已过滤的显示首选 |
| 「重复上屏」候选 | `handle_candidate.rs` 把上次上屏文本 `insert(0, …)` | 上次上的若是词，按引导键会看见它 | 低 |

共同成因是同一个：**`apply_single_char` 接在候选链内，而这三处都在链外往 `state.candidates`
里塞东西**。真要根治得给「往最终列表塞候选」立一个统一出口，那是比本功能大得多的一轮。

📌 原本还有第四个漏点「词组档的 emoji」，随「只出词组」一并消失：emoji 依附宿主追加，
而 `min_word_chars` 出厂为 2 ⇒ 单字宿主达不到门槛、emoji 根本不出现；就算用户改成 1，
emoji 是单字素、本就算「单字」，受不受管辖结果一样。**删掉一个档位顺手消掉了一个漏点。**

## 3. 判据：什么算「一个字」，谁豁免

实现在 `wind_candidate::single_char_admits`。

### 3.1 按字素簇算，不按码位

走 `single_markable_char`（UAX #29），故 `⚽️`(2 码位)、`👨‍👩‍👧`(5 码位)、`🇨🇳`、`1️⃣` 都算
一个字。⛔ 别退回 `chars().count() == 1` ——issue #83 的教训是逐条列举 Unicode 规则必随版本
静默漏一类。

### 3.2 豁免：短语 / 命令 / 分组

本项管的是**词库**出什么，而这三类是用户自己配出来的快捷方式（`fj` → 一整段文本），
不该因为开了单字模式就整个消失。

### 3.3 ★★★ 豁免判据是 `is_user_authored`，**不是** `is_common_like`

`is_common_like`（检索范围过滤用的那个）＝ `is_common || 那三项`。带上 `is_common` 的话，
常用**词**（「中国」「时候」——`mark_common` 对逐字皆常用的词同样置 `is_common = true`）
会一并豁免，**就只剩生僻词被滤掉，整个功能失效**，而候选窗看着还挺正常。

两个过滤器问的是不同的问题（「这条算不算常用」 vs 「这条是不是用户自己配的」），只是答案
在那三项上碰巧一致。守门在 `common_words_are_not_exempt`（变异验证：把豁免换成
`is_common_like`，只有这一条红）。

## 4. 落点与次序

主候选链（`handle_candidate.rs`）：

```
mark_common → sort → dedup → apply_filter → **apply_single_char** → apply_freq_rerank
  → apply_shadow → 空码补全收口 → short_code_yield → 英文头部候选 → emoji 扩展
  → state.candidates 定稿 → 满码自动上屏「显示态」复评
```

### 4.1 必须早于 `apply_shadow`

`ShadowPin.position` 是**绝对下标**，记的是用户右键当时**所见的那个列表**——开着的时候所见
列表就是滤过的，滤在 shadow 之后位次就对不上了。出简让全踩过同一个坑（「置顶写得进去、
下次打同一个码毫无变化」）。

守门 `single_char_filter_runs_before_shadow`（源码顺序断言——端到端造 shadow 规则要真实的
`store`，headless 里是 `None`，行为断言写不出来）。⚠️ 它钉的是**文本位置**而非执行顺序，
把调用挪进「定义靠前、调用靠后」的辅助函数会假绿；今天可靠是因为两个锚点同在
`build_candidates` 函数体内。

### 4.2 补全池走同一条链

主列表被滤空之后才会从补全池取一条；那一条若不过本项过滤，用户看到的就是「开了单字模式
还是冒出一个词」。守门 `completion_pool_goes_through_the_same_filter`。

### 4.3 被滤集直接丢弃，不留 `FilterOutcome`

检索范围要留被滤集是因为有「末页翻页放宽」这条出路。本项没有，也刻意不给一个：用户开
单字输入就是不想看见词，「翻到底还能翻出词来」与这个意图相反。要看词就关掉它。

## 5. 与既有机制的交互（三条都是**不用动手**的）

### 5.1 ★ 满码自动上屏：既有的「显示态复评」已经解决

`decide_auto_commit`（`wind-engine` 的 `codetable/engine.rs`）数的是**引擎自己**那份候选里
`code == input` 的条数，而本过滤做在协调器侧 ⇒ 引擎看见的列表里那个词还在，按它判恒是
「不唯一、不上屏」。

救回来的是 `handle_candidate.rs` 里既有的**显示态复评**：引擎没给出上屏意向时，按
**最终显示列表**再判一次。它当初是为智能过滤加的（滤掉同码生僻字后复评放行，见
`recheck_auto_commit_unique_after_filter`），而判据落在「用户看见的是哪些候选」上、
与过滤的成因无关，于是本项天然搭上了同一趟车。

实测（五笔 `dddd`，`auto_commit_at_full = true`）：

| 状态 | 结局 |
|---|---|
| 开 | 自动上屏「大」，候选清空 |
| 关 | 停在候选态（大 / 大厦 / 硕大 / 磕磕碰碰） |

⇒ `single_char_enables_auto_commit_at_full_code` 同时是那条复评的**第二个消费者**的守门：
将来谁把复评改成只认智能过滤（比如加一个 `filter_mode` 判据），这里会红。

### 5.2 出简让全天然停手

`short_code_yield::apply` 找接位者要求 `chars().count() > 1`，找不到直接返回。⇒ 开着的时候
列表里没有多字接位者，它在判据处就停手了。无需接线。

### 5.3 emoji 扩展不会留下孤儿

emoji 插在整条加工链的**最后**（注释写明「放进过滤链里它会被静默滤光」），故它看到的已是
滤过的列表，开着的时候多字宿主早已消失。无需特判。

⚠️ emoji 自己**逃出了本项管辖**（它产在过滤之后），但这不构成问题：它依附宿主追加，而
`min_word_chars` 出厂为 2 ⇒ 单字宿主达不到门槛、emoji 根本不出现；就算用户改成 1，
emoji 是单字素、本就算「单字」，受不受管辖结果一样。见 §2.5 末尾。

### 5.4 简繁转换不改变「是不是单字」——但这是**数据性质**，没有代码守着

转换发生在**出口层**（`handle_mode.rs` 的 `maybe_convert` / `cand_convert_text`），而
`apply_single_char` 跑在候选装配中段 ⇒ **判据看的是词库原文，转换在它之后**。所以要问：
繁简转换会不会把单字变成多字（或反过来）？

实测 OpenCC 四张表（逐行按**码位数**判）：`TSCharacters` / `STCharacters` 零条
「单字键 → 含多字值」；`TSPhrases` / `STPhrases` 零条「多字键 → 单字值」。⇒ 判定不会
被转换改变，落在转换前文本上是安全的。

⚠️ **但这条靠的是数据，不是不变量，且没有任何测试或断言守着**——破坏了不会红。
`T2SConfig` 自己的文档写着「要加台/港变体时同时补 `chain_for` 的分支」；真接了
`TWPhrases` / `HKVariants` 一类表进转换链，或换 OpenCC 数据源，**这条必须重验**。

### 5.5 两处「单字」口径不同（今天无差异）

`single_char_admits` 用字素簇（`single_markable_char`），`expand_s2t_variants` 用
`chars().count() == 1`（码位数）。两个函数在同一条链上一前一后。对 CJK 没有差别，故
今天不产生分歧；但口径分叉本身值得记——将来任一侧要处理非 BMP 或组合序列时会显形。

## 6. 运行时切换：临时态，不写盘

按键动词 `single_char`（裸写 = 切换），或带载荷 `single_char:on` / `:off` / `:toggle` /
`:follow`（`follow` = 清掉临时态、回落配置层）。裸形式有先例：`aux_code` 与
`aux_code:page_next`。

**两张按键表都有它**，动词、裸形式与载荷逐字一致：

- `keys.key_actions` / 方案 `[key_actions]`（`BoundAction`）——符号键、字母 z、组合键；
- `keys.session_actions` / 方案 `[session_actions]`（`SessionAction`）——Tab、翻页键那一批。

只在一张表里加是错的：另一张表里写同一个动词会落 `None`，表现成「这个键没绑上」，
而用户只是把配置从一张表挪到了另一张。

### 6.1 不写配置（用户 2026-09-07 拍板）

`set_filter_mode` 切一次就写回 `input.filter_mode`；本项只改内存。直接好处是**不必碰
`schema_overrides/{id}.toml` 那条写盘链**（本项是方案级配置，持久化就得往那儿写，还要登记
`SideCommitter` 并处理「设置页正开着时被后台改写」）。

形态上它与 `State::scope_relaxed` 同构：纯内存、一个失效点、一条不写配置的切换路径。
⛔ 实现时别照 `set_filter_mode` 抄——那是持久化路径。

### 6.2 失效点：切方案时清空

收口在 `sync_schema_scope`（代际驱动，与 `punct_before_schema` 同批）——本仓唯一能覆盖全部
五条切方案路径的地方。

★ 这里**不需要** `punct_before_schema` 那种「保存原值」的配套：临时态本身就是 `Option`，
清成 `None` 即回落配置层。那条真机教训（`Follow` 退化成「保持上一个方案强加的值」）在此
天然不成立——它的成因是 `state.chinese_punct` 既是当前值又是唯一存储，本项两者是分开的。

### 6.3 消费点的结局：`Consumed`，不顶字

与**辅助码同族**：切的是「这一码出什么」，正在打的那串码要原样留着。
⛔ 别按临拼 / mix 那样顶字重开——顶字会把用户想换个模式再看的那串码上屏，而他要的恰恰是
换个模式重看这一码。

开启后候选可能整个变空（该码一个单字都没有），那时**只剩状态泡这一个反馈**，故三个消费点
都弹泡（持锁，走 `show_tip_locked`）。

### 6.4 ⚠️ `session_actions` 侧空闲不吞键

那张表收的是 Tab / 翻页键那一批**宿主另有原义**的键。执行臂若无条件 `Consumed`，用户照
`data/config.toml` 的示例写下 `tab = "single_char"` 之后，Tab 在所有程序里当场失效——
不只是「无候选时」，完全空闲时也吞。判据取「有会话」而非「有候选」（单字模式下某个码本来
就可能一条候选都不剩，那时若按「无候选」放行，用户就再也关不掉它了），与 `Cancel` 同侧。

⇒ 想空闲时也能切 → 绑到 `key_actions`：那张表收符号键 / z / 组合键，没有宿主原义要让，
故那边恒吞键。守门 `session_bound_single_char_releases_the_key_when_idle`。

## 7. 已知边界

### 7.1 「截断 → 过滤」在拼音上仍在（未做引擎下推）

引擎是「产生 N 条 → 排序 → `truncate(max_candidates)`」，本过滤在其后 ⇒ 理论上开启后可能
不足一页。码表方案基本无影响（一个码位候选本就不多）；拼音高频音节的前 N 条里单字占多数，
实测也未见不足。

真要做，路径是现成的：`ConvertOptions::admit` 把准入下推进引擎（生僻字模式的先例），
调用方仍需「不足则加大重取」（`refill_rare_if_short`）。⚠️ 那时还要处理 Viterbi 整句——
它走 `insert(0)` 绕过 `push_unique`，不受 `admit` 约束，只能在调用方侧再滤一次。
