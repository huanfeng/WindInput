# 混合简拼：同一串里混用声母与全拼音节

> 状态：**已实施**（2026-07-30）。走的是 §4 之外的第四条路，见 §4.5。
> 由真机反馈引出：全拼下 `nhao` 候选为空，用户期望 `n`(简) + `hao`(全) → 「你好」。
> 属**功能缺失**，不是缺陷——这种形态从未被支持过。
>
> 实现：`wind-engine/src/pinyin/mixed_abbrev.rs`（模式表示与枚举）+ `mod.rs` step 5b（系统词
> 召回）+ step 6 内的用户词分支。测试：`tests/pinyin_mixed_abbrev.rs`、
> `tests/pinyin_user_word_boundary.rs::shuangpin_mixed_abbrev_survives_boundary_check`。
>
> 前置阅读：`pinyin-code-domains.md`（三编码域、简拼索引 v5、边界贯通）。本文只讲混合简拼。

## 1. 用户期望与现状

多数输入法支持在一串里混用两种音节表示：

| 形态 | 例 | 含义 |
|---|---|---|
| 全简拼 | `nh` | n·h 两个声母 |
| 全拼 | `nihao` | ni·hao 两个完整音节 |
| **混合（声母在前）** | `nhao` | n(声母) + hao(全音节) |
| **混合（全拼在前）** | `nih` | ni(全音节) + h(声母) |

现在只支持前两种。后两种候选为空或只出前半截。

## 2. 实测：两种混合形态卡在**不同**的地方

`AbbrevMatcher::is_abbreviation`（`scorer.rs:24`）的判据是两条：
① 每个字母都得是某音节的首字母（`trie.is_prefix(单字母)`）；
② 整串**不能**是完整音节序列（`maximum_match` 覆盖长度 < 串长）。

实测（`SyllableTrie::new()`）：

| 输入 | `is_abbreviation` | 卡在哪 |
|---|---|---|
| `nh` | true | —（正常工作） |
| `nihao` | false | 判据②：完整音节序列 → 走全拼，**正确** |
| **`nhao`** | **true** | 判据都过、**进了简拼分支**，但索引里只有整串简拼 `nh`，查 `nhao` 无果 |
| **`nih`** | **false** | 判据①：`i` 不是任何音节的首字母 → **压根不进简拼分支**；DAG 切出 `ni`、`h` 成残码 |
| **`nihm`** | **false** | 同上，且 `nihm` 不是任何全拼码的前缀 ⇒ 真正候选为空 |
| `xan` | true | —（正常工作） |
| `dblg` | true | —（正常工作） |
| `woain` | false | 判据① |

**结论：这不是一处改动能解决的。**
- `nhao` 要改的是**召回**（索引/投影只认整串简拼）
- `nih` 要改的是**判据**（逐字母检查排斥全拼音节的中间字母）

两者都还要求切分层能表达「这一段是声母、那一段是完整音节」。

### 2.1 更正：`nih` 那一半其实早就有候选

> 实施期实测发现，上表对 `nih` 的描述**不完整**。把 `enable_abbrev` 关掉，`nih` 照样出
> 「你好」——它来自 **step4 前缀补全**：`nih` 恰好是全拼码 `nihao` 的字符串前缀。

推广开来，混合形态要按**声母段的位置**分三类，收益完全不同：

| 形态 | 例 | 改动前 | 混合简拼带来什么 |
|---|---|---|---|
| 声母在**开头** | `nhao` | 候选为空（不是任何码的前缀） | **新增召回**，核心价值 |
| 声母在**中间** | `nihm` | 候选为空 | **新增召回** |
| 声母在**末尾** | `nih` | 前缀补全已命中 | 只是收紧到精确音节数（`nihaoma` 这类更长的词会被排除） |

⚠️ 因此 **`nih` 不能用作混合简拼的验收用例**——那是一条改动前后都成立的恒绿断言。
验收要用 `nhao`（声母在前）和 `nihm`（声母在中间）。
`tests/pinyin_mixed_abbrev.rs::trailing_initial_form_is_already_covered_by_prefix_completion`
把这个事实锁成了断言，防止后人再拿 `nih` 当证据。

## 3. 为什么召回改不动 —— 两处语义都是「整串」

**系统词侧**（`mod.rs` step 5）：查 wdat 的 `AbbrevSection`，v5 起存 `abbrev → 全拼码`。
索引键是**完整简拼串**（`nh`、`dblg`），没有「前 k 个字母是声母、其余是全拼」这种键。

**用户词侧**（`mod.rs` step 6）：枚举全部用户/临时词，用 `abbrev_of_code(code, boundary)`
把每个词投影成简拼串再比对。投影也是**整串**（`xianning` → `xan`），同样表达不了混合。

**切分层**（`dag.rs`）：`Dag` 的节点是**完整音节**。声母（`n`、`h`）不是音节，
进不了词图，所以「`n` + `hao`」这条路径根本构造不出来。

## 4. 方案候选

### 方案 A：切分层引入「声母节点」

给 `Dag` 增加一类节点：单字母声母，只在无法切出完整音节时作为候选边。切分结果因此可能是
`[声母 n][音节 hao]` 的混合序列，再由词图按「声母只约束首字母」的规则匹配词条。

- ✅ 一处改动同时解决两种形态；与 `SylSpan` 的三域表示天然相容（声母节点 flat 长度为 1）
- ⚠️ **直接改逐键候选生成热路径**，且会让路径数显著膨胀（每个位置多一种解释）
- ⚠️ 需要新的匹配规则：词图查询不再是「码相等」，而是「按位约束」

### 方案 B：查询扩展（把混合串展开成候选码集合）

在召回前把 `nhao` 展开成若干可能的全拼码（`nihao`/`nuhao`/`nvhao`…），逐个走主表精确查。

- ✅ 不动切分层与索引，改动局部
- ⚠️ 组合爆炸：每个声母位可对应几十个音节，多个声母位相乘不可控（需要按位剪枝 + 上限）
- ⚠️ 本质是「猜」，与 `pinyin-code-domains.md` 反复强调的「能取回真值就不要推断」相悖

### 方案 C：索引侧支持前缀简拼

`AbbrevSection` 额外存「前 k 个音节的声母 + 剩余全拼码」形式的键。

- ✅ 查询侧简单（仍是一次点查）
- ⚠️ 索引体积按 k 膨胀；wdat 又要 bump（刚从 v4→v5）
- ⚠️ 只解决 `nhao` 那一半，`nih`（声母在后）仍需判据改造

**倾向 A**，但它是热路径改动，必须先有评测对账（见 §6）。B 可作为 A 的兜底或过渡。

### 4.5 实际采用：方案 D —— 模式匹配（切分只产模式，召回复用现有索引）

三个候选方案的代价都集中在「要么改切分、要么改索引、要么靠猜」。第四条路把混合信息
从**切分**挪到**模式**上，三样都不动：

```text
  nhao ──切分──> [Initial('n'), Syllable("hao")]   ← 模式（mixed_abbrev.rs）
       ──投影──> "nh"                              ← 各段取首字母 = 纯简拼串
       ──点查──> "nihao"                           ← AbbrevSection 现有的键，真值码非推断
       ──校验──> ni|hao 逐段比对：n? ✓ / ==hao ✓   ← 模式在这里第二次发挥作用
```

关键在于**投影键退化成纯简拼**，正好是 `AbbrevSection` 已有的键形状。于是：

- 不动 `Dag`（避开 A 的热路径改动与路径膨胀）——切分只在混合模块内部做，且有短路（见下）；
- 不猜音节（避开 B 的组合爆炸）——码是从索引点查取回的真值；
- 不改索引（避开 C 的 wdat bump）——一个字节都没动；
- 两种形态由**同一套模式**表达，§2 说的「卡在不同环节」合成一处。

代价与边界：

1. **必须短路**。`nihao` 这类完整全拼串同样有混合解释（`ni`+`h`+`ao`），不挡住就是每次
   击键白跑一趟枚举与索引。`mod.rs` step 5b 用「整串已被音节完整覆盖」短路——评测三类
   样本全是完整全拼串，实测四项指标逐位持平，即短路 100% 命中（§6）。
   双拼下判据换成「转换结果覆盖了整串击键」，因为 `completed_len` 说的是转换后的全拼域。
2. **索引取码上限要放宽**。混合路径拿到的码还要过逐段校验，绝大多数会被滤掉，
   故取 64。
   > **2026-09-22 更新**：`MIXED_ABBREV_INDEX_LIMIT` 已更名 `ABBREV_INDEX_LIMIT`，
   > **纯简拼也用同一个值**。原先纯简拼单独取 10，理由是「键即答案」——该前提只在
   > 键下词条少于 10 时成立：真实词库 `bcx` 有 48 条，取 10 意味着 w=1 的「拜城县」
   > 在 `bcx` 下永不产生，却在 `baicx`（混合、64）下出得来。**打得更省事的写法反而
   > 查得更少**。且截断在召回层，候选窗与调频都够不着。
3. **boundary 缺失即不参与**（不是放行）。模式比对的是「第 k 个音节长什么样」，没有真值
   切分就没有判据，放行等于不校验。这与全仓「任一侧为 0 即降级放行」的惯例方向相反，
   `syllables_from_boundary` 的文档注释里写明了理由。
4. 枚举有三道成本闸门：段数 ≤ 6、模式数 ≤ 24、输入长度 ≤ 16，另有可达性预筛避免 DFS
   遍历死胡同。截断按 DFS 顺序（长音节 > 短音节 > **双字母声母** > 单字母声母），
   故是确定性的。
   > **2026-09-22 更新**：模式数上限从 16 提到 24 —— 双字母声母（见 §4.7）在 zh/ch/sh
   > 的位置上多出一条边，深层分支互相挤，`chengshizhong` 实测丢掉了 3 条**改动前就有**
   > 的解释。新增维度不给额度等于拿新解释换旧解释，
   > `retroflex_edges_do_not_evict_pre_existing_interpretations` 钉住了这条。

### 4.6 preedit 显示：必须与**击键**同域（实施当天的真机回归）

召回接好、候选正确，但预编辑区没有分隔显示：`nhao` 原样显示 `nhao`，`nh` 显示 `nh`。

根因在「预编辑区跟随首选候选」那一支的条件：

```rust
if top.boundary != 0 && top.code == completed && !completed.is_empty()
```

简拼/混合候选的 `code` 是词的**全拼码**（`nihao`），与击键不同域；而 `nhao` 一个完整音节
都切不出来，`completed` 是空串 —— 两边永远对不上，于是这一支从来没被简拼走过。
**纯简拼此前也一直没有分隔显示**，不是混合简拼引入的新问题。

★ 修法的关键不是"把 code 渲染出来"。直接复用 `render_preedit(code, boundary, …)` 会显示成
`ni'hao`：用户只敲了 4 键却看到 5 个字母，**退格与光标编辑立刻错位**。正确做法是拿候选的
真值音节序列去切**击键串**：

```text
  击键 nhao  +  真值 ni|hao
    ni  ← "nhao" 整段对不上 ⇒ 声母段，吃 1 字节 'n'
    hao ← "hao"  整段对上   ⇒ 音节段，吃 3 字节
  ⇒ n'hao        （去掉 ' 恰好还原击键串，这是不变量）
```

实现 `mixed_abbrev::render_keystroke_preedit`。逐音节贪心、音节段优先（声母段是信息更少的
解释，只在整段对不上时成立）；任何一步对不上或没有恰好覆盖整串就返回 `None`，保持原显示
——preedit 是显示层，宁可少一个分隔符，也不能给出与击键长度不符的串。

⚠️ **写这条的测试要同时钉住「有分隔符」和「与击键同长」两件事。** 只断言含 `'`
的话，`ni'hao` 也能过，而那才是更糟的错。

**已知边界（未处理）**：双拼下 preedit 由 `build_raw_preedit` 无条件接管（按双拼击键的
音节边界分段），故双拼下的简拼/混合简拼显示仍走双拼语义、不走本节这套。双拼每 2 键 1 音节，
`xan` 究竟是「3 个声母」还是「xa + 残码 n」本身就有歧义，插一手会与双拼自身的分段自相矛盾。

### 4.7 简拼族「全串或无」——前缀回退（第二轮真机回归）

真机连打 `bzdnihaobuhao`（想打「不知道」+「好不好」），**输到 `bzdha` 整串空码**。
`bzd` 明明能出「不知道」。

根因：简拼族的召回一直是**全串或无**——`AbbrevSection` 按完整简拼串点查，混合模式又要求
覆盖整串。于是简拼一旦长过任何单个词，候选就彻底为空。全拼下有 step3 子短语与 step4
前缀补全兜着（`nihaobu` 照样出「你好」且只消费 5 字节），简拼下此前没有任何对应机制。
**这不是混合简拼引入的，纯简拼一直如此。**

修法（`mod.rs` step 6.2 + `recall_abbrev_prefix`）：整串一无所获时，从最长前缀往下试、
**一有产出即停**（最长匹配语义；否则每次击键会拖出一串越来越短的简拼候选淹掉候选窗）。
产出的候选 `is_partial=true` 沉在完整匹配之后，并**自带击键域的 `consumed_length`**。

⚠️ **`consumed_length` 必须绕开统一计算。** 下方那个循环按 `code`/`query` 关系算消费数，
而简拼的 code 是词的全拼码（`buzhidao`）、不以 `bzdha` 开头 ⇒ 会落到「消费整串」，
选中「不知道」后余下的 `ha` 被一起吃掉，分步上屏当场失效。判据用
`c.is_abbrev && c.consumed_length != 0`（整串简拼候选的该值保持 0，照旧走统一计算）。

### 4.7.1 ★★ 回退门槛：两次写错，方向相反 ⇒ 判据切错了维度

| 版本 | 门槛 | 病症 |
|---|---|---|
| 一 | `!abbrev_full_hit`（简拼族没命中） | **太宽**：纯全拼被拖进降级 |
| 二 | `stroke_is_plain_abbrev \|\| !mixed_pats.is_empty()`（整串是合法简拼模式） | **太窄**：长串被挡在门外、彻底空码 |
| 三 ✅ | `!mixed_covered`（整串**有成不了音节的部分**） | — |

- **一太宽**：`meiyou` 的 `is_abbreviation` 因 `i` 判假、整串又被音节完整覆盖使混合模式为空
  ⇒「简拼族一无所获」成立 ⇒ 退到 `meiy` 后 `[mei][y]` 命中「没有」，凭空多出 `is_abbrev`
  候选、破坏「前缀补全排在精确匹配之后」的层级
  （`engine_manager::test_pinyin_trailing_partial_prefix_floats_above_exact` 当场变红）。
- **二太窄**：`bzdnihaobuh` 最少需要 `[b][z][d][ni][hao][bu][h]` **七段**、超过
  `MAX_SEGMENTS=6` ⇒ 整串模式为空，`is_abbreviation` 又判假 ⇒ 两头不沾、回退不启动 ⇒
  **连打到第 11 键彻底空码**（真机第三轮报的正是这个）。串越长越容易触发。

★★ **「同一个判据连续两次修正且方向相反」是判据切错维度的指纹**（同款现场见
`project_common_chars_pua_leak` 的「常用字」作用域）。这里错的维度是**「像不像简拼」**——
它既依赖词库有没有那个词（版本一的偏差来源），又依赖模式段数上限（版本二的偏差来源），
两者都与「该不该允许简拼解释」无关。正确的维度是**「输入里有没有成不了音节的字母」**：
有 ⇒ 全拼解释不完整 ⇒ 允许简拼族接手；没有 ⇒ 纯全拼，不许降级。它不受词库与段数影响。

分工也随之清晰：**门槛只负责挡掉纯全拼，逐前缀的严格判定在 `recall_abbrev_prefix` 内部**
（每个 stroke 各自过 `is_abbreviation` / `mixed_patterns`）。门槛不该替前缀把关。

两条红线已锁成 `full_pinyin_never_enters_prefix_fallback`（挡住版本一）与
`long_stroke_is_not_blocked_by_fallback_gate`（挡住版本二）。

### 4.7.2 部分匹配的 preedit：余下击键要**自己再切一遍**

`bzdnihaob` 选中「不知道」（消费 `bzd`）后尾巴是 `nihaob`，其中 `ni`/`hao` 是完整音节、
`b` 是残码。整段追加会显示成 `b'z'd'nihaob` —— 该切的地方没切。故
`render_keystroke_preedit` 返回 `(渲染串, 已消费字节数)`，由调用方对尾巴走
`compose_segment` 再拼接，得 `b'z'd'ni'hao'b`。锁成
`partial_preedit_segments_the_remainder_too`。

### 4.7.3 ★★ 切点竞争：别把「切点长短」做成硬闸门

真机第四轮：`bzdhaobuhao`（想要「不知道」+「好不好」）**首候选是「表彰大会」**。

`bzdh` 恰好是「表彰大会」（biao·zhang·da·hui）的简拼，首版的「最长匹配、一有产出即停」
就把 `h` 判给了它，于是：

| 切点 | 命中 | 真实词库权重 |
|---|---|---|
| `bzdh` (4) | 表彰大会 | 93 |
| `bzd` (3) | 不知道 | **62492（高 672 倍）** |

`break` 让更短的切点**一条都进不来**，剩下的 `aobuhao` 成了垃圾。一个结构性偏好压过了
三个数量级的词频差异。

★★ **切点长短是「来源」差异，不是结构质量差异 ⇒ 只配走 weight，不配做布尔式硬排除。**
布尔排除等价于惩罚 ∞ —— 这与模糊拼音 `is_fuzzy` 从层级键改回权重折扣是同一条教训
（`project_fuzzy_pinyin_layer_vs_penalty`）。改为**多切点候选共存、同层按词频竞争**后，
「不知道」拿回首选，「表彰大会」沉到第 7 位但**仍在候选里**（用户真想要也选得到）。

但**完全不管切点长短也不对**：一路试到 `bz` 时，「标准/帮助/保证」会凭 ~5 万的词频挤进
前几位，而它们只解释了 11 键里的 2 键。软偏好的落点选在**「是否入场」**而非「入场后打
折扣」——`MAX_FALLBACK_CUTS = 2`（最长 + 次长）。理由：折扣要按未解释字母数调一个乘性
系数，量纲难定且依赖本轮最大消费长度、不稳定；而相邻切点的竞争才是真实场景。
每切点再限 `MAX_FALLBACK_PER_CUT = 6`，保证短切点挤得进来（否则长切点占满配额，
词频高 672 倍的那个照样进不来）。

### 4.7.4 评测基线：D 类「简拼+全拼混合整句」

`pinyin_eval` 新增 D 类，专门度量「智能组句」：取 W1 的**简拼** + W2 的**全拼**拼成击键串
（`bzd` + `haobuhao`），期望整句 = W1+W2。入池条件里最关键的一条是**整串不能被完整切成
音节序列**，否则它会走纯全拼路径（`mixed_covered` 短路），测的就不是简拼。

第四列（A/B/C 是「切分正确」）对 D 类改为**首词命中**——击键串与真值音节不同域
（`bzd` 压根不是音节），切分判据无从成立。另有 `first_word_recall`（W1 出现在候选里，
任意位次）用于区分两种完全不同的失败：**召回率低 = 前缀回退没退到那个切点（缺陷）；
召回高而命中低 = 简拼固有的同音歧义**（`bzd` 下 12 个词按词频竞争，采样到的低频 W1
本就不该在首位）。缺了这个区分，光看命中率会把后者误读成前者。

**基线（seed=20260721，n=1000）**：

| 指标 | 立基线时 | §4.8 实施后 |
|---|---|---|
| top-1 / top-5 / MRR | **0.00% / 0.00% / 0.0000** | **12.10% / 12.10% / 0.1210** |
| 首词命中（首选） | 2.30% | 0.00%（整句占首选，部分候选退到第 2、3 位） |
| 首词召回（任意位次） | **40.30%** | 40.30% |

⚠️ **采样口径中途收紧过一次**：立基线时从全词库分层抽样配对，产出「达拉特旗」+「半道儿」
这种没人会打的串；调闸门阈值时发现它会把参数带偏——被度量的场景与样本分布不匹配时，
指标越精确越误导。现改为只用 unigram 词频前 1/3 的常用词配对（用户打简拼正是为了少敲
**熟词**）。两个口径下「立基线」那一列都是 0（整句压根不出），故上表的对比仍然成立。

★★ **「放宽切点数」方案已被这条基线否决，勿再尝试**：`MAX_FALLBACK_CUTS` 取 8 时
召回率**从 40.30% 掉到 14.60%**、首词命中掉到 0.00%。短切点的高频词会占据首选并把长切点
的正确候选挤出 top-10（`dltqbandaoer` 首选变成 `dl`→「到了」，`dqsmayou` 变成
`dq`→「地球」）。这条实验的价值在于它证明了**启发式有天花板**：先到先得占配额的机制下，
放宽只会让噪音更早占满配额。要越过 40%，必须让所有切点**同时**参与并由语言模型仲裁。

### 4.8 混合整句解码（「智能组句」）—— **已实施**

用户第四轮问「是没有激活智能组句吗」，判断准确。现已实施：简拼段作为词图节点与全拼节点
混排，由 Viterbi 选最优路径。`bzdhaobuhao` 直接出「不知道好不好」。

落点：`lattice::add_abbrev_nodes` + `mod.rs` step 2b。

**架构上比预想顺** —— `LatticeNode` 的 `start`/`end` 本就是**字节跨度**、Viterbi 的 dp 也按
字节位置推进，故简拼节点与全拼节点天然可串，**解码器一行都没改**。真正的工作在三处：

1. **简拼跨度不在音节图上**。`build` 的跨度来自 `graph.ends_within(p, ..)` 且开头有
   `graph.is_reachable(p)` 守卫，而 `bzd` 的 b/z/d 都不成音节 ⇒ 位置 0 不可达、也给不出
   终点。故简拼节点独立枚举 `(p,q)`，且 `build` 新增 `require_reachable` 参数——混合路径
   传 `false`，因为 `[3,6) hao` 这些边其实都在图里、只是被那道守卫挡住了。
2. **step 2 无法复用**。它的入口是 `syllables.len() >= 2`，而 `syllables` 是从 0 起连续的
   完整音节覆盖：`bzdhaobuhao` 的 `syllables` 为空、`completed` 为空串 ⇒ 整句解码压根不
   启动。step 2 依赖 `completed` 处理残码（`nihaom` 只在 `nihao` 上跑整句），不能改成整串，
   故另起 step 2b 在**整串**上建图。
3. **三道闸门**，逐条都由实测定出（见下）。

#### 三道闸门

| 闸门 | 值 | 挡什么 |
|---|---|---|
| 质量 `MIXED_SENTENCE_MIN_LOGP_PER_CHAR` | -8.0 | 路径平均每字 log_prob 过低的拼凑整句 |
| 节点数 | ≥ 2 | 单节点路径（那是简拼候选，不是句） |
| 未覆盖长度 | ≥ 2 字母 | 尾部单字母残码（「还没打完」不是简拼段） |

★ **节点数 ≥ 2 是词频记账的红线**：单节点路径（`dblg` → 只有「夺不了冠」）包装成整句会让
它的 `code` 变成击键串 `dblg`，而简拼候选的 `code` 是全拼码 `duobuliaoguan` —— 同一个词的
词频记到两个互不相认的键上，正是 wdat v5 改「索引存码」时修掉的坑，不能从新路径重新引进来。

★ **未覆盖长度 ≥ 2 只加在 step 2b**：`zhongguorenm` 的尾部残码 `m` 也让 `!mixed_covered`
成立，整句便插到首位、把「中国人民解放军」挤后一格
（`pinyin_completion::test_useful_completions_still_float` 当场抓到）。step 5b 的混合召回
不加这道闸——`nihaom` → 「你好吗」正该走混合模式。

#### 质量闸门的取值：受控对比，不是估算

| 阈值 | 整句 top-1 | 首词命中 |
|---|---|---|
| 不设闸门 | 12.10% | 0.00% |
| **-8.0（采用）** | **12.10%** | 0.00% |
| -6.5 | 10.30% | 0.50% |
| -5.0 | 1.10% | 3.30% |

-8.0 是**零代价点**：整句命中与不设闸门相同，却挡掉最离谱的那批（`nhaoma` 原本出
「你会熬吗」每字 -11.01，闸掉后正确的「你好吗」上位）。

★ 收紧到 -5.0 曾看似合理——用户真会打的组合每字落在 -3.7 ~ -4.8，而错误整句多在 -4.9 以下。
但受控对比显示它**砍掉 91% 的正确整句**只换来 3.3% 的首词命中。且整句占首位时部分候选
就在第 2、3 位，按一下数字键即可选到，**「首词命中 0%」不等于分步上屏那条路断了**。

⚠️ 另需注意 `ABBREV_NODE_PENALTY`（简拼节点每音节惩罚）**调不动首选**：实测 1.2 / 2.5 / 4.0
三档 D 类指标几乎不动，因为整句靠 `SENTENCE_WEIGHT_BASE`(3e7) 无条件置顶，`log_offset`
那点差异撼动不了。要改首选行为得动闸门，不是动惩罚。

#### 成效与限制

D 类 top-1 **0% → 12.10%**，A/B/C 三类逐位不变。

★★ **12.10% 不能当体验读**。D 类是随机词对配出来的（虽已收紧到常用词），而真实输入是有
语义的搭配。实测用户真会打的串**全部正确**：

```text
bzdhaobuhao → 不知道好不好 ✓    bzdzenmeban → 不知道怎么办 ✓
wmyiqizou   → 我们一起走   ✓    nhaoma      → 你好吗     ✓
```

⚠️ 剩余限制：`lm.rs` **只有 unigram**（bigram 插值已实现、缺语料）。靠词频差能分开的情形
没问题，更微妙的切点选择需要上下文概率。正确与错误整句的每字 log_prob 分布在 -5 ~ -6.5
区间大幅重叠，**任何阈值都必然既误伤正解又放行错解**——这是 unigram-only 的固有上限，
不是闸门没调好。要再上一个台阶得先有语料。

双拼下不启用（`input` 是转换后的全拼、与击键不同域，简拼判据会全部失配）。

### 4.9 双字母声母 `zh`/`ch`/`sh` 作为一个段（2026-09-22 实施）

本文前面所有模型图里的「声母段，吃 1 字节」是**改动前**的形状。整条简拼链路曾建立在
「简拼域里一个音节恰好占一个 ASCII 字母」这条硬假设上，于是 `zh` 只能被解释成 `z`+`h`
两段——这一点在**组合区里对用户直接可见**（打 `zhge` 显示 `z'h'ge`）。后果：

| 击键 | 改动前的唯一解释 | 投影键 | 段数要求 | 用户想要的 |
|---|---|---|---|---|
| `zhge` | z\|h\|ge | `zhg` | 3 音节 | 「这个」= zhe\|ge，挂在 `zg` |
| `zhy` | z\|h\|y（纯简拼） | `zhy` | 3 音节 | 「这样」= zhe\|yang，挂在 `zy` |
| `baichx` | bai\|c\|h\|x | `bchx` | 4 音节 | 「拜城县」= bai\|cheng\|xian，挂在 `bcx` |

新增 `AbbrevSeg::Retroflex(char)`，载荷是 z/c/s 那一位——**投影键取的正是它**，故三者
都落到已有的键上，索引仍然一个字节都不用动（与 §4.5 的第三条不变量一致）。

四处配套，少一处就只修好一半：

1. `edges()` 返回**带类型的** `Edge` 而非裸长度：`zh` 与 `ba` 都是 2 字节，靠长度分不出
   声母段和音节段，而 `walk` 原本正是用 `len == 1` 判的——那条判据在新维度下必错且不报错。
2. `walk` 收口守卫为「含 `Retroflex`」放行，**即使全是声母段**（`zhy` 正是这种形态，
   纯简拼路径逐字母切、表达不了「zh 是一个声母」）；但仍要求**段数 ≥ 2**，否则单段模式
   （`zh` → 键 `z`）会绕过 `MIN_ABBREV_STROKE` 立的「单字母不构成简拼」那条规矩，
   在 step 6.2 的切点上把键 `z` 下所有 zh 开头的单音节词连同单字的巨大权重灌进候选。
3. `render_keystroke_preedit` **两遍贪心**（先双字母优先、失败再单字母）。单遍会让老写法
   `zh`→中华 的显示从 `z'h` 退化成无分隔符的 `zh`：贪心无回溯，第一步吃掉 2 字节后第二个
   音节没键可分，整个函数返回 `None`。候选侧两种解释并存，**显示侧也必须并存**。
4. `seg_matches_fuzzy` 的 `Retroflex` 分支走 `fuzzy::retroflex_relaxed`：放宽成「只比首字母」
   仅在 `zh_z`/`ch_c`/`sh_s` 开着时成立。⚠️ **不能复用 `initials_fuzzy_equal`**——`zh` 与 `z`
   首字母相同，它会走 `a == b` 短路恒返回 true，等于把这个段降级回单字母声母、开关形同虚设。

判据是**收紧**而非放宽：`zhy` 只召回首音节以 `zh` 开头的词（只有/专业/这样），`zuo|yong`
这类进不来；老写法 `z|h|y` 照常并存。真实词库实测（limit=300）：「这个」300+ 条内无 →
第 2 位，「这样」无 → 第 3 位，「拜城县」(`baichx`) 无 → 第 74 位。

> `zh`/`ch`/`sh` 的**模糊音开关救不了这条**：在简拼键空间里它们是恒等变换（首字母相同），
> 解决的是「打 `z` 匹配 `zhe`」，不是「把 `zh` 算成一个声母」。

## 5. 必须保住的约束（上一轮踩过的坑，逐条都有代价）

1. **简拼候选的 `boundary` 与双拼校验的豁免关系。**
   `boundary_compatible` 靠「任一侧为 0 即放行」豁免简拼；wdat v5 给简拼候选填上真实
   boundary 后，那条隐式豁免失效，双拼下简拼**整批被误杀**（`ae2df59` 已显式豁免
   `is_abbrev`）。混合简拼候选的 boundary 同样与击键不同域，**必须确认走在豁免侧**。
   ★ 推而广之：**给一个原本恒为 0 的字段填真值前，先查谁在依赖它是 0**。
   模糊变体至今仍靠 `boundary=0` 豁免同一道校验。

2. **层级键两侧必须一致。** `cmp_match_layers` 第一键是 `is_abbrev`（`false < true`）。
   系统词简拼曾借 `is_prefix=true` 沉底、用户词简拼用 `is_abbrev=true`，两类同质候选
   分属两层 ⇒ 用户词被整层压住、**词频永远翻不过硬闸门**（`ae2df59` 已统一）。
   混合简拼候选要么并入 `is_abbrev` 层，要么明确定义新层级——**不能借用别的层级键**。

3. **音节数过滤不能丢。** 扁平码有损：`xian` 既是「西安」的 `xi|an` 也是「先」的 `xian`。
   简拼按「字母数 == `boundary.count_ones()`」过滤，否则 `xa` 会捞出「先/线/弦」一串单字
   且权重高得多、排在最前。混合形态下这条规则要重新定义（声母段与音节段的计数口径）。

4. **简拼判据须用原始击键 `raw_input`，不是 `query`。** 双拼下 `query` 已是转换结果，
   拿它判简拼永远匹配不到用户敲的串。全拼下两者相等，故对全拼零影响。

5. **`consumed_length` 的域。** 简拼候选消费整串 raw；混合形态下若只消费前半段（分步上屏），
   必须用 `interp::map_fp_to_raw` 那套 `SylSpan` 映射回击键域，不要另造字节扫描。
