# 双拼下的手动音节分隔符

状态：已实施，未真机。

## 1. 为什么双拼也需要分隔符

「双拼每 2 键一音节、边界免费且精确」是对的，但只在**整串都用全码**时成立。一旦用户
中途打一个简拼声母，其后**所有**键的配对都会错位一位：

| 击键 | 用户想打 | 实际读成 |
|---|---|---|
| `nhc` | 你(简 `n`) + 好(`hc`) | `nh` → `nang`，`c` 落成残码 ⇒ `nangc` |

两种读法都是合法击键序列，打分无从区分——`pinyin-mixed-abbrev.md` 记过这件事：
「双拼下 `xan` 是三声母还是 `xa`+残码，本身歧义，**故意未处理**」。本功能就是补上
那个手段：`'` 把段结构定死，歧义消失。

`n'hc` ⇒ 段 `n`（落单，作声母）+ 段 `hc`（→ `hao`）⇒ 全拼域得 `nhao`，
正是混合简拼（声母段 + 完整音节）认得的形状。

## 2. 落点：`'` 由 `ShuangpinConverter::convert` 自己消化

改造前 `convert_with_opts` 在入口处**整体剥除** `'` 再送进双拼转换，全拼路径的
`has_sep` 分支因此永远轮不到双拼。现在改为把原串直接交给 `convert`，由它把 `'`
当作**配对的硬边界**：遇到就重置配对起点，自身不进 `full_pinyin`、不占 `position_map`。

到 `convert_with_opts` 后半段时 `input` 已是纯全拼域，全拼那套 `has_sep` 逻辑
对双拼输入恒不成立——两条路不交叉，全拼行为一字未动。

### 2.1 段尾落单键 ≠ 末尾落单键

| | 语义 | `has_partial` |
|---|---|---|
| 末尾落单（`nih`） | 还没打完，下一键可能与它成对 | **置位** |
| 段尾落单（`n'hc` 的 `n`） | 用户已用 `'` 宣告「它就到此为止」 | **不置** |

置错了下游会把已定案的简拼段当成待续输入。两者写进 `full_pinyin` 的内容相同
（都取 `initial_of`），区别只在这个位和要不要继续扫描。

### 2.2 段尾落单键刻意不进 `syllables`

它不是音节。这样 `sp_boundary_mask` 会把它当作「回写段」自动标出段起点
（那里本就有 `s.fp_start > cursor` 的空隙分支），**手动边界无需在 mask 里另开一路**。

### 2.3 偏移域

`raw_start` / `raw_end` / `position_map` 一律取**含 `'` 的击键偏移**，于是
`map_consumed_length` 回算出的键数天然把分隔符算在内——用户确实按了那一下。
少算会让分步上屏后残留一个孤立的 `'`。

## 3. 顺带修掉的两处：判据的隐含假设被分隔符打破

分隔符是**第一个**让「双拼音节连续铺满击键串」不再成立的场景。两处依赖那个假设的
判据因此暴露：

### 3.1 `mixed_covered` 只看末尾（会误短路）

```rust
// 旧：最后一个音节到达末尾 ⇒ 认为整串已覆盖
r.syllables.last().is_some_and(|s| s.raw_end >= raw_input.len())
```

`n'hc` 里 `n` 段（raw 0..1）没被任何音节覆盖，但最后一个音节延伸到了末尾 ⇒ 判据为真
⇒ 混合简拼整条路被短路 ⇒ **候选一条不剩**。

改为问「**有没有**击键没被音节覆盖」，逐段检查空洞（`'` 自身不算待解释的击键）。
★ 同一个洞出现在开头时（`omni` 的回写段 `om`）旧判据一样漏，只是此前没有场景踩到。

### 3.2 混合模式枚举的域（双拼下击键域里没有音节）

`mixed_patterns` 要找的是「声母段 + 音节段」，而**双拼击键域里根本没有音节**：
`n'hc` 的击键 `nhc` 只能读成三个声母，`[n][hao]` 永远出不来。

此前双拼下混合简拼之所以能work，靠的是击键串**碰巧在全拼域也读得通**
（`xanning` = `x`+`an`+`ning`）——那是巧合，不是机制。

⇒ 新增 `use_fp_for_mixed`：**双拼且用户打了分隔符**时，模式改从 `full_pinyin` 枚举。
那时段结构由 `'` 定死，`full_pinyin` 是唯一解释，不存在拿它去猜的风险。

★ 这不违反 `pinyin-mixed-abbrev.md` §5 约束 4（判据用 `raw_input` 非 `query`）：
那条管的是**纯简拼**——「这串击键是不是一串声母」只有击键域答得了（`xan` 靠它才命中
「西安宁」）。两个判据问的是不同的问题，故 `abbr_query` 与 `mixed_pattern_source`
刻意分家，没有分隔符时后者恒等于前者，双拼既有行为一字不动。

## 4. preedit：手动的一撇与自动的一撇合流

双拼 preedit 显示**原始击键**并按音节边界自动插 `'`（`build_raw_preedit`）。
手动 `'` 已经在击键串里，若仍按段 `join("'")`，就会在它旁边再插一个：
`n'hc` → `n''hc`，用户看到自己没按过的第二撇，退格还得按两次。

改为**逐字节重建**，判据是「这一位输出前，前面是不是已经有分隔符了」——手动的和
自动的都算，于是两者天然合流，连续 `''` 与首尾 `'` 也都原样留住。

不变量：**去掉所有 `'` 后必须恰好还原击键串**（同 `render_keystroke_preedit` 那条）。

## 5. 键位：`auto` 改成避让**已占用**的键

协调器原先在 `manual_separator_key_of` 里对双拼早退，已撤销。但直接放行会出事：
`auto` 的旧语义只避让选词键，双拼下 `'` 是选词键 ⇒ 它转而选反引号 ⇒ 而反引号正是
双拼出厂的辅助码触发键（`shuangpin.schema.toml` 的 `backtick = "aux_code"`），
夺走后那条绑定**只剩一条 warn 日志**，用户看到的是「配了没反应」。

⇒ `auto` 现在避让两类占用：选词键 + **本方案 `[key_actions]` 已绑的键**。
两个都不空闲时退化成「不启用」。双拼正是这种情况，于是行为与改造前逐位一致，
而全拼（没绑反引号）照旧选反引号。

★ **判据的维度是「这个键空不空闲」，不是「这是什么引擎」。** 曾试过在出厂
`shuangpin.schema.toml` 里写 `separator = "none"` 来达到同样效果，被
`builtin_pinyin_schemas_do_not_declare_separator` 拦下——出厂方案自带该项会让
**全局设置页那一项对该方案静默失效**，用户改了没反应且界面上看不出为什么。
按引擎类型硬判则会把用户显式配的 `quote` 也一并否掉。两条错路都指向同一件事：
差异属于**键位预算**，就该在键位层面表达。

## 6. 全拼侧：手动分隔符曾与简拼族**全面互斥**

打了分隔符就用不了简拼，这在全拼下比双拼更明显，且是三层原因叠加：

| 输入 | 改前 | 改后 |
|---|---|---|
| `n'hao`（混合简拼） | 首选「好」，「你好」在第 **146** 位 | 「你好」@0 |
| `b'z'd`（纯简拼） | **一条候选都没有** | 「不知道」@0 |

三处根因，缺一条都修不好：

1. **`abbr_query` 带着 `'`** ⇒ `is_abbreviation` 见非字母即判假，纯简拼整条路不走。
   改为剥掉 `'`——剥完**仍在击键域**，`pinyin-mixed-abbrev.md` §5 约束 4
   （判据用击键不用 query）照旧成立，双拼靠击键判简拼那条（`xan` → 西安宁）不受影响。
2. **`mixed_patterns` 吃的也是它** ⇒ 模式枚举同样判假。改用 `query`（见 §3.2）。
3. ★★ **`syllables` 照单全收 `sep_spans`**。`completed` 的契约是「从 0 开始的连续
   音节覆盖」，而手动分隔符第一次让**开头的段可以不是音节**（`n'hao` 的 `n`）。
   不接在起点上的 `hao` 被当成 completed 之后，`lookup_with_fuzzy("hao")` 让
   「好」「号」「薅」以**精确匹配**身份占满前排——它们根本没解释前半段。
   改为只收从起点连续的段。

★ 第 3 条与 §3.1 是**同一个隐含假设**（音节从起点连续铺开）在两处的实例。
分隔符是第一个打破它的输入形态，一次暴露三处。

### 撤掉的一条豁免

曾在「手动分隔符边界过滤」里加 `is_abbrev` 豁免（简拼族的 code 是全拼码、与击键
不同域）。**撤了**：`syllables` 改成只收起点连续段之后，简拼族出场的前提恰恰是
「起点那段成不了音节」⇒ 那时 `syllables` 为空，`syllable_span` 一律返回 None 自然放行。
变异验证去掉它 9 条用例全绿——没有可达路径能证明它必要。
