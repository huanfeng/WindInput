# 蒙古文纵向候选：字体分层 + 候选项旋转 90° + 文字竖排

蒙古文用户定制了自己的输入方案。两处与既有能力不匹配：

1. **蒙文纵向书写**——候选需要旋转 90° 呈现（列内自上而下读，列自左向右推进）；
2. **蒙文字体常不含英文字形**，或英文字形难看，而候选字体每个节点只能配一个字族，
   缺字时由系统随意回退，无从控制。

三个交付：**C**（字体回退链 + 按脚本指派）、**A**（候选项旋转）、**B**（方案级候选字体）。
本文只记「不打开代码就该知道」的判据与已否决方向，细节看源码注释。

---

## C. 字体：回退链与按脚本指派是**两种机制**

| | 语义 | 触发条件 |
|---|---|---|
| 回退链 `ui.font.fallback` | 「本字体**没有**这个字 → 依次试下一个」 | 仅当当前字体缺字 |
| 脚本指派 `ui.font.scripts` | 「拉丁字符**一律**用 X」 | 无条件，字符落在该类即生效 |

★ **只做回退链解决不了问题的一半**：绝大多数字体都带 ASCII 字形（Mongolian Baiti 也有），
一旦字体自己「有」英文，回退链永远不触发，想换也换不掉。反过来指派也替代不了回退链——
用户指派的英文字体总有覆盖不到的字符。合成顺序：**指派决定这一段的 base family →
该段再走自己的回退链**。

### 配置形态：刻意不把 `family` 改成数组

改类型要配一层 Value 迁移，漏了就让老用户整份配置静默回落出厂值。
拆成 `family`（不动）+ `fallback`（新数组）则**零迁移**，设置页现有字体控件也不用动。
最终链 = `[family] + fallback`。

```toml
[ui.font]
family = "Mongolian Baiti"
fallback = ["Noto Sans Mongolian"]
[ui.font.scripts]
latin = ["Segoe UI"]
```

### ⛔ 已否决 / 已踩过

- **给两个新键加 `skip_serializing_if`**——本仓用它表达「这个键**退出**配置体系」
  （见 `keys.key_actions_materialized`）。加上之后 `registry_covers_every_config_key`
  的差集为空、**守门测试静默放行**，而该键在 CLI、配置片段导入、设置页里全都够不着。
  ⇒ 面向用户的新键一律不加。修复要**三处同动**：去标记 + 补 REGISTRY + 补 `data/config.toml`
  （只补注册表会让闸门从「缺失」翻成「多余」）。
- ~~**「`AddMapping` 不问 base font，每个字符都会被映射到 target」**~~ ——**这条是错的，
  已被实测推翻**（一度写进两处代码注释与本文档）。真实语义：**base font 先被问，
  映射的 target 列表是「base 缺这个字时」的接续**。
  ⚠️ 按那条错误前提推导，会得出「默认链的兜底映射会把脚本指派与方案级字体整个吃掉」
  这个吓人但**不存在**的结论——终审时正是这么推的。三条实测互相印证：
  `fallback_chain_is_applied`（base 缺字时链尾决定字形）、
  `default_chain_fallback_does_not_swallow_a_script_assignment`（拉丁段不被兜底吃掉）、
  `leaf_family_survives_a_non_empty_default_chain`（叶子级字族同理）。
  **改 `ensure_fallback` 前先跑这三条。**
- **拿 `charblock` 那张表切段**——它是显示域、没有蒙古文块，且自己写明「新块落进『其它』
  可以接受」。判定域必须另建一张，且按大段/平面兜底而非逐块（issue #83 的教训）。

### ★★ 切段的两条硬判据

1. **分类轴必须是「脚本」不能是「字符功能」**。把「数字」当一类指派给英文字体，会把
   蒙古文数字 `U+1810..1819` 从蒙文词里切走——而切段边界就是 shaping 边界，
   蒙古文是上下文相关成形，切错即字形断裂。故 `digits` 类只含 ASCII 数字。
2. **表外一律强归属只对「脚本」成立**。Common 符号块（`U+2070..20CF` 货币、
   `U+20F1..25FF` ℃™№Ⅰ→∑①■、`U+27C0..2AFF`、`U+2E00..2E7F`）必须**显式列成中性**，
   否则 `abc→def` 被切成三段、`第①条` 被切成三段，中间那段掉回默认链。
   ⚠️ 这个 bug 在「只声明 latin」的最小用例下**看不见**，必须声明 `cjk` 或 `emoji` 才暴露。

### 中性字符继承上下文

空格 / ASCII 数字 / 西文标点默认中性、归属继承相邻强脚本；只有用户**显式声明**
`digits` / `punct` 才提升为强归属。否则中文候选里的半角数字会跳字体——而混用字体会改行高
（DirectWrite 取该行所有字体中最大的 line metrics），表现是「带数字的那几项行高和别人不一样」。

### 平台差异（已知、已标注）

macOS 的 CoreText 后端**只实现了回退链**（进 cascade list），按脚本指派未实现，
`set_font_plan` 会 warn 一次。另有一处相反：叶子级字族覆盖 base 时，
Windows 侧靠一条 `baseFamilyName = None` 的兜底映射让默认链仍生效，
CoreText 的 cascade list 是字体级属性、本就恒生效。

## A. 旋转：**不是一种排列**，而是「横排时文字怎么写」

### ★★ 两根轴，不是一个四值枚举

`ui.candidate.layout` 只有 **horizontal / vertical** 两个值，面向所有用户；
旋转 90° 与文字竖排住在**方案**里：`[candidate] text_orientation = normal | rotated | upright`。

```rust
Orientation { vertical: bool, text: TextOrientation }
```

曾按「LayoutIntent 的第三、第四个取值」实现过一版并合并，随后推翻。三条理由，每条单独都够：

1. **注释模板只认横竖。** 它在全局/方案/overlay/模式**四层**各有一对
   `_vertical`/`_horizontal`，窗口尺寸下限有四个字段，`flip_when_above` 只对竖排成立。
   把旋转塞进同一个枚举，这些对子要么变四元组（组合级代价），要么被迫「旋转态走横排
   那一支」——后者能跑，但它恰恰证明**旋转本来就不是一种排列**。
2. **值域挤在同一个下拉里。** 外观页那个控件面向所有用户，而旋转是极少数方案才用的；
   四个平铺选项既难选，也在暗示它们是同一类东西。
3. ★ **合成一根就切不开了。** 蒙古文用户想在自己的方案里临时切竖排时，
   `ime.toggle("layout")` 只能把方向整个换掉、连旋转一起丢。拆开之后切换只动 `vertical`，
   `text_orientation` 纹丝不动。**这是拆轴的主要收益**，由
   `toggling_direction_never_touches_text_orientation` 钉住。

### 归属：文字排列跟**数据方案**，与候选字体同源

| 字段 | 归属 | 判据 |
|---|---|---|
| `[candidate] layout` | `active_behavior` | 用户对**呈现**的偏好 |
| `[candidate] font_family` | `effective_data_schema` | 这些字**用什么渲染** |
| `[candidate] text_orientation` | `effective_data_schema` | 这些字**怎么排** |

「怎么排」与「用什么字体」是同一个问题的两面 ⇒ 判据必须一致。收益是具体的：
临英期间候选是英文、归 `english` 桶，字体和排列一起跟着归它，
**不会出现「打英文却还按蒙古文方案转 90°」**。同段两字段判据不同这件事，
`[punct]` 的 `mode` 与 `custom_mappings` 已经是同一个形状。

⇒ 它随输入语境**逐次按键**变化，不能挂到 `sync_schema_scope` 那条代际驱动的路上
（临英进出不改代际）；取值点在 `desired_orientation`，每次显示都重算。

### 决策链：两根轴各走各的，最后合流

```
vertical:  加词 > 独占模式 > 手动值 > 方案 layout > 全局基线   （orientation_for）
text:      方案（按 effective_data_schema 取）                （candidate_text_orientation_of）
                              ↓
                    Orientation::normalized()
```

`orientation_for` 返回的 `of()` 是 `Option<bool>` 而不是 `Option<Orientation>`——
返回整个结构会让人以为它也管文字排列，而各层的常量里那一位恒是 `Normal`，
一路 `or` 下来就把 baseline 带的方案意图冲掉了。**本轮正是这么写错的**，
且只有「手动切一下方向」这一条路径测得出来。

唯一的耦合是**竖排时 `text` 归零**（竖排再转 90° 就是横排）。归一化只在
`Orientation::normalized` 一处做；读侧一律走 `rotated()` / `upright()` 两个派生方法，
自己判 `!vertical && text != Normal` 等于把归一化复制到第二处。

### 渲染端一位不改：仍是「竖排的排版 + 转 90°」

拆轴只动了配置与决策层。渲染端收到的仍是 `SetCandidateLayout { vertical, rotated, upright }`
三个**已归一化**的布尔：

| 判据 | 旋转态取值 | 收益 |
|---|---|---|
| `vertical` | **false** | 尺寸下限、注释模板、`flip_when_above` 自动走横排支，一处不改 |
| `list_vertical`（局部空间） | **true** | 行距、宽度预算、文字截断、分隔方向沿用竖排实现，一行不改 |
| `reversed` | **true** | 局部列首经顺时针落到屏幕最右，逆序后候选 1 才在最左 |

### 渲染：临时缓冲双向旋转

把屏幕上那块底子**逆向**搬进局部缓冲 → 子树照常画进去 → **正向**搬回。
子树全程在未旋转的局部空间排版，这是整个能力的支点。

- ⛔ **不走 DirectWrite 的 `SetCurrentTransform`**：只转文字，转不了背景/边框/序号圆圈；
  且差分法回写的包围盒要在旋转空间重算，等于把已稳定的合成路径再撬一遍。
  临时缓冲是纯像素操作，macOS 后端与 HostRender 的 SHM 帧路径自动跟上。
- ★ 第一步「搬底子」**不能用填透明代替**：文本后端的差分法合成要拿目标像素当背景做
  抗锯齿混合，底子不对文字边缘就带错误混色；窗口圆角/渐变/九宫格背景也在那块底子里。
- ★ 两次像素搬运**共用同一个映射函数**。各写一个双重循环的话，「搬进来的底子」与
  「搬回去的结果」会错开一个像素——表现是文字边缘发虚且整体偏移一格，而两段各自看都对。
- 命中矩形必须跟着转。漏掉这步画面完全正常、只有鼠标点错候选。

映射约定（只此一处）：屏幕内偏移 `(sx, sy)` ← 局部 `(lx, ly)`，`lx = sy`、`ly = ch-1-sx`。
直觉校验：局部左上角落到屏幕右上角 —— 这正是「顺时针」。

### 与拆字字根（PUA）的编排次序

`create_layout` 是四层叠加、**后写覆盖前写**：
TextFormat 全局字族 → 全文 base family → 脚本段 → `pua_runs` 的私用区段。
脚本段必须夹在中间，且 `class == None` 的段**不得**再调 `SetFontFamilyName`——
顺序搞反或对 `None` 段也下发，都会把字根段的字族盖回主字体、字根变方框。
判据上两者不冲突：三段私用区在脚本表里全部落表外 ⇒ 强归属 ⇒ 永远自成一段。

### 已知边界（刻意不做）

- `vertical_max_width`（主题的竖排宽度上限）在旋转态**不生效**——它钳的是屏幕宽度，
  而旋转态该钳的是列长。屏幕安全钳制那条已按轴翻转（`local_text_extent_px`）。
- `flip_when_above` 旋转态不参与：列序已由 `reversed` 决定。
- 注释模板走**横排**那一份。要给旋转态单独的模板，用方案级 `[candidate]` 的两个键。
- 手动切方向（命令栏 `ime.toggle("layout")`）**不改文字排列**：它只翻竖排位那一根轴。
  切到竖排时旋转按 `normalized()` 归零（竖排再转 90° 就是横排，没有定义），切回横排时
  原样回来——蒙古文方案因此照样能用横/竖切换，方案意图不被这个二值开关吃掉。

## A2. 文字竖排（对联式）：`text_orientation` 的第三个取值

同一根轴上，与 `rotated` 的差别只有一处：字不跟着转，逐字直立下行，像中文对联。
术语取自 CSS `text-orientation: sideways | upright`——`rotated` 是 sideways，
两者的关系正是那一对。

### 复用面：只有「叶子怎么搭」不同

`upright` **蕴含** `rotated`，于是 `list_vertical`、`reversed`、阴影轴、尺寸下限、
分隔方向、翻页栏位置、tooltip 侧边定位**全部原样复用**，`build_tree` 里 14 处
`list_vertical` 一处不改。本位只在拼叶子时读一次。

### 数学：外层顺时针 ∘ 每格逆时针 ≡ 恒等

文字拆成逐格单元，每格套 `View::rotated_ccw`；外层的 `rotated_cw` 把它们转回正的。
局部空间里逐格单元是个 Row（左→右），转完就是屏幕上的一列（上→下）。

`view.rs` 的旋转位因此从 `rotate_cw: bool` 改成 `rot: Rot { None, Cw, Ccw }`——
两个 bool 表达得出 `cw && ccw` 这种无意义状态，枚举压根表达不出来。
两向共用同一份映射表与同一个 `for_each_mapped`，理由与「两次搬运共用」同源。

`cw_around_ccw_is_the_identity` 一条钉住三件事：两向映射互为逆、嵌套时内层拿到的底子
是对的（差分法合成要用）、宽高交换两次回到原值。用**左右异色**两块而不是单色——
单色块转 180° 也一样，测不出方向。

### 三处消费点，各由一条测试守住

| 消费点 | 取舍 | 守门测试 |
|---|---|---|
| 文字叶子 | 逐格切、每格扶正；装饰留在外层容器上（否则每个字各画一个药丸） | `upright_advances_by_line_height_rotated_by_glyph_width` |
| 序号叶子 | **整块**扶正，不逐格切 | `upright_index_is_one_block_not_stacked_digits` |
| 截断 | 量**沿列方向**（行高累加），不是横向宽度 | `upright_truncation_measures_the_stacking_axis` |

序号整块扶正 ⇒「10」横着读、位于列首，正是纵排里数字的常规排法（日文排版称
tate-chu-yoko）；逐格切会排成竖着的 1、0，看着像两个候选。

截断这条尤其阴：拉丁字母横向前进约 0.5em、竖着占一个行高约 1.2em，**差两倍以上**；
汉字两轴只差两成。按横向宽度估容量的话，表现是「英文候选戳出屏幕」而中文候选看着
完全正常。⚠️ 判据**不能**塞进 `truncate_text_for_width` 本身——编码栏与模式徽标也调它，
而它们没有被切成格。

### 切格：`upright_cells`，不是 `chars()`

每格单独排版一次，切错的表现是**记号掉到下一格去**：组合音调符号、日文浊点、
汉字异体字选择符会各自单独成格，渲染成一个孤立的点或直接不显示。

⛔ 与脚本表里的 `Raw::Sticky` 是**两张表，不要合并**。那张表的文档写明它只列**跨脚本**
的那几个，因为同脚本的组合符与基字符落在同一区间、按脚本分段天然就在一起；
本函数没有那层保护。两张表的取舍方向相反——同 `charblock` 与本脚本表的关系。

### 已知边界

- ⚠️ 按格切分**必然切断连写脚本的字形连接**（阿拉伯文、蒙古文）。那些脚本要的是
  `rotated`。判据不在切格函数里，而在「谁会选这个布局」，故只记不拦。
- 注释**不**扶正，跟着项一起转（sideways）。它是拉丁编码，横着读反而对，
  且扶正会让整列跟着编码变宽。这与 CSS 默认的 `text-orientation: mixed` 同向。
- 切格不是完整的字素簇算法（那需要一张 Unicode 属性表）。覆盖 CJK ＋拉丁＋数字
  ＋标点＋常见 emoji；天城文那类需要重排序的元音符号不在其列。

### 包裹层内**一切**文本逐格扶正，拉丁不例外

⛔ 曾按「注释是拉丁编码、横着读反而对」（CSS 默认的 `text-orientation: mixed`）
留它跟着项转。**真机推翻**：旋转态是「一切都转」故自洽，直立态里只有候选文字立着、
注释躺着，同一列里出现两种阅读方向 —— 原话是「看不懂」。

⇒ 判据改为：**落在旋转包裹层内部的文本节点一律逐格扶正**。共三处，
走同一个 `CandidateWindow::upright_text`：注释、模式徽标、**内联**编码。
内联编码的 caret 由该函数按字节位分派到它落进的那一格，转完是格间的一条横线，
正是纵排里插入符该有的样子。

⚠️ 独立编码栏（`preedit_display = "candidate_top"`）**不**走它：那一栏在包裹层
**外面**，本就没转过。这是 `preedit_view` 要带一个 `upright` 参数的唯一理由。

⚠️ 序号是唯一例外且刻意如此：整块扶正（「10」横着读、位于列首，日文排版称
tate-chu-yoko）。单位数下两种做法完全相同；逐格切会把多位数排成竖着的 1、0，
看着像两个候选。

代价照单接受：一个 4 字编码吃掉 4 个行高，列会变长。不想要注释的人有现成逃生口——
方案级 `comment_template_horizontal = ""`。

## C2. 类别名值域进 capability

`ui.font.scripts` 的键名（`latin`/`cjk`/…）此前只在 core 里有。设置端要给用户**预填**
这些类别就得手抄一份，而抄本会滞后——`ui.candidate.layout` 已经踩过这个形状
（值域从 3 变 4，设置端滞后，方案里手写的第 4 个值被静默改写回默认）。

故 `FieldType::Map` 改成携带键名值域 `Map(&'static [&'static str])`：

- 非空 ⇒ capability 的该项带 `values`（对 `enum` 是合法**取值**，对 `map` 是合法**键名**，
  由 `type` 决定读法）；空 ⇒ 不带，设置端据此区分「类别固定的表」与「自由命名的表」
  （自定义标点若也被预填一堆行就荒唐了）。
- ⚠️ 改的是**已有变体**而不是新加一个 `KeyedMap`：`FieldType::Map` 有约十处 match，
  其中 `patch.rs` 的 `is_map_key` 与 `config_schema` 的 flatten 边界是**语义闸门**，
  漏一处是静默行为改变。改已有变体 ⇒ 编译器逐个报错，一个都漏不掉。
- 真相源仍只有一份：`FONT_SCRIPT_KEYS` 在 wind-config，`ScriptClass::ALL` 在 wind-ui，
  由 wind-ui 侧的 `script_class_keys_match_config_registry` 比对（含**顺序**——
  设置端按这个顺序铺行，顺序漂了用户每次打开对话框都看到行序变化）。
  只能在 wind-ui 侧测：wind-config 依赖不到 wind-ui。

## B. 方案级候选字体：`[candidate] font_family`

「切到蒙文方案就换字体」此前表达不出来——字体是全局的、主题也是全局的。

### ★★ 归属取**数据方案**，与同段的 `layout` 刻意不同

| 字段 | 归属 | 因为它回答的是 |
|---|---|---|
| `layout` | `active_behavior()` | 「此刻候选怎么排」＝用户可见的**呈现态** |
| `font_family` | `effective_data_schema()` | 「**这些字**用什么渲染」＝数据属性，与 `[phrases]`、`[punct] custom_mappings` 同源 |

⇒ **看见同一个段就统一判据是错的**。`[punct]` 的 `mode` 与 `custom_mappings` 已经踩过
一模一样的形状。取错的表现：临英期间候选归 `english` 桶、字体却还跟着五笔走，两边看各自都对。

### ⇒ 下发通路也随之不同

`effective_data_schema` 随**输入语境**逐次按键变化（临英/快符叠加），不随方案代际变化。
挂到 `sync_schema_scope` 那条代际驱动的路上会整个失效——`schema_scope_gen == generation`
直接 return，临英进出根本不改代际。故它与布局同处：**在 `UpdateCandidates` 的两个发送点
之前重算**（`notify_ui_update` + `show_add_word_preview`，漏一处的表现是加词面板字体变回默认）。

命令也因此是独立的一条：`SetCandidateFont`（来自 `ui.font`、随配置重载推一次）与
`SetCandidateTextFamily`（随候选更新重算）节奏不同，合成一条会让配置重载那条路每次按键
都重推整份字体方案。

### 作用域只到 text 节点

序号 / 编码栏 / 注释 / 翻页栏**不**跟着换：它们是拉丁与数字，换成蒙文字体反而更差。
要按脚本换字体用全局 `ui.font.scripts`——那是按**字符**分的，比按节点分更贴合真实问题。

★ 渲染端把解析结果算一次、四个消费点（两处测量 + 候选叶子 + 占位行叶子）共用同一个值。
各自去取必然漂移，且两种表现都不报错：测量与渲染不同源 ⇒ 预算按一种字体算、排版按另一种走；
占位行漏掉 ⇒ 它与真实行行高不等。

## 测试纪律（本轮踩到的两类假绿）

1. **样本必须跨越被测的那条边界**。「纯蒙文串」证明不了蒙文不会被拉丁指派抢走——
   整串同类时无论分类对错，输出都是单段。要 `"abc" + 蒙文` 才测得到。
2. **断言要落在「这个改动能影响的那个量」上**。旋转态各列「等宽」恒真
   （宽对应局部行高），要断言的是**等高**（对应局部宽度）；
   「又窄又高」拿横排当对照也测不出来，因为竖排本来就窄而高——对照必须选竖排。

⚠️ 变异验证本身也有个静默失败：本仓 `.rs` 有 LF 也有 CRLF，`perl -0` 里带 `\n` 的模式
在 CRLF 文件上不匹配、静默 no-op。**「变异后测试没红」要先确认变异真的改到了文件**，
否则会把「没变异」误读成「测试有洞」。
