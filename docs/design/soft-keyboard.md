# 软键盘

> 一块持续常驻的符号面板。开启后接管主键区按键，敲什么、点什么，都按当前面的映射表
> 转换后上屏——与自定义标点是同一种语义，只是范围扩大到整个键盘。
>
> 相关：[key-resolver-unification.md](key-resolver-unification.md)（按键解析两张表）、
> [overlay-mode-config.md](../redesign/overlay-mode-config.md)（实例身份判据的来源）。
>
> 状态：P0–P3 已实施（数据层 / 运行时接管 / 面板 / 入口）。
> 实施期新增的判据与偏离已并入本文，见 §4.5、§7.3、§8.3、§9。

## 1. 定位：它不是方案，是配置文件

设计过程中走过一段弯路，记在这里防止重走。

最初想把软键盘做成 `kf` 快符方案的一种呈现（`[overlay].presentation = "keyboard"`），
再进一步做成 `kind = "keyboard"` 的容器方案 + 每面一个 overlay 方案。两条都被否掉：

- **`presentation` 挂在 kf 上**——一旦有多个面，面就有了自己的名字、图标、码表，
  身份不再来自 kf，挂错了地方。
- **一面一方案**——能力上最强（每面可单独直达、可第三方分发），但十几个面就是二十多个文件，
  对这个体量的功能过重。

⇒ **最终形态：单个配置文件 `system.softkeyboard.toml`，完全独立于方案体系。**

这个决定有一个重要的连带效果：**软键盘脱离引擎**。没有方案加载、没有码表查询、没有候选生成，
按键直接查配置展开的内存表 → 上屏或执行。链路比方案路线短得多。

代价（已接受）：面不能被单独直达、不能被第三方单独分发。整个文件可以被用户整份替换，
但没法「装一个面进已有键盘」。

### 1.1 与「合集直通车」的关系

`kf` 那种「引导键进入某个符号合集」的能力不受影响——软键盘自己可以绑热键，
也可以直通到指定面（见 §7）。丢的只是**面作为独立实例**的那部分能力。

## 2. 数据模型：三层，各有唯一写入者

```
rows / rows_shift（整面画布，位置对位）
        ↓ 加载展开
   KeyMap: (page, 键位, 层) → 输出      ← 唯一的运行时真相
        ↑ keys 单键补丁（同文件内，按键名）
        ↑ 用户文件稀疏覆盖（同格式）
```

### 2.1 文件形态

```toml
# system.softkeyboard.toml

[[pages]]
id   = "math"
name = "数学"
rows = [
  "∵ ＋ － × ÷ ＝ ≠ ≈ ≡ ＜ ＞ ° ‰",   # ` 1 2 3 4 5 6 7 8 9 0 - =
  "√ ∛ ∜ ∑ ∏ ∫ ∮ ∂ ∇ ∆ ⌈ ⌉ ∕",      # q w e r t y u i o p [ ] \
  "∈ ∉ ⊂ ⊃ ⊆ ⊇ ∪ ∩ ∖ ∧ ∨",          # a s d f g h j k l ; '
  "∞ ∝ ∠ ⊥ ∥ ≌ ≅ ≪ ≫ ⊙",            # z x c v b n m , . /
]
rows_shift = [ … ]                      # 可省，省则第二层整层为空
keys = { q = "√", "shift+q" = "∛" }     # 单键补丁，压在画布之上
```

**画布用空格分隔的 token 按位置对位**，第 n 个 token 落到该行第 n 个键位。选它而不是
逐字符画布，是因为逐字符放不下多字符 token（`(（`、`::`）；选它而不是逐键
`q = "√"` 映射表，是因为画布在编辑器里**看着就是键盘的样子**，改起来不用对照键位表。

- 行长不必写满，缺的尾部即空键位。
- 占位符 `.` 表示该键位空。要输出字面 `.` 用 `\.`。
  ⚠️ 转义按**字符**边界推进，不能按字节——本仓在短语转义上踩过按字节推进贴中文即 panic。
- 行数固定为 4（数字行 / QWERTY / ASDF / ZXCV），多余的行忽略并 warn。

### 2.2 ★ 写侧纪律：只有一个整表写入者

读侧三层合并，**写侧只允许写覆盖层**。

> `rows` / `rows_shift` 只有一个写入者（作者，或用户整份替换文件）；
> **补丁层只做稀疏 diff，永不整表回写。**

本仓所有覆盖类事故（方案级配置、引导键物化、扩展词库开关）都是同一个根因：
两个写入者对同一份整表各写各的。将来若做键盘编辑器，它只能往补丁层写单键，
**绝不允许把展开后的内存表倒灌回 `rows`**——那就是「整体替换 ⊕ 稀疏 diff」的数据丢失。

P0 阶段该文件**只读**：出厂一份，用户可整份拷到 `%APPDATA%\WindInput\` 修改，
GUI 不回写（同 `system.quick.toml`）。将来真要编辑器，按 `SideCommitter` 接
（本仓已定：非 config.toml 落点一律登记 SideCommitter，禁止再加独立保存按钮）。

### 2.3 用户覆盖的三态语义

用户文件里出现一个 `[[pages]]`，按 `id` 匹配出厂面：

| 用户文件写了什么 | 语义 |
|---|---|
| `rows` **缺失** | 不动基础画布，只应用 `keys` 补丁 |
| `rows` **存在** | 整面画布替换（`keys` 仍在其上叠加） |
| `id` 不匹配任何出厂面 | 新增一个面，追加在末尾 |

面序 = 出厂面序 + 用户新增面追加。**P0 不做面序重排**，别预支。

### 2.4 ★★★ 补丁键名必须复用已有的按键名体系

`keys` 里的 `q` / `shift+q` / `bracketleft` 这些键名，**必须走
`keys.key_actions` 已经在用的那套拼写**，不能另起一套。

本仓已经因为两仓键名拼写不一致吃过亏：触发键配了完全没反应，**不报错、不告警、
静默不匹配**。软键盘一旦引入第三套键名，同样的指纹会立刻重现，而且这次是用户手写配置、
出错率更高。认不出的键名要 warn 后跳过（同快符格式表对未知 `kind` 的处置），不要静默丢弃。

## 4. 运行时：谁被接管

### 4.1 按键处置（可推导，不维护第二份清单）

| 键 | 处置 |
|---|---|
| 布局里的**符号键位** | 接管 → 查映射表；无映射则**吃掉忽略**（不透传） |
| 布局里的**特殊键** | 透传（封闭集，不可映射，见 §4.2） |
| 布局**之外**的一切 | 透传（F1–F12、小键盘、Ctrl/Alt 组合） |
| Shift / Esc / 翻页键 | 面板自己的控制键 |

### 4.2 特殊键是封闭集，硬编码透传

**不接受映射。** 放开可配会带来一族判据（映射了的退格还能不能长按连删？映射了的回车
还换不换行？），而它买到的灵活性没人要。这条一开始就关死，比事后收窄便宜。

★ 封闭集的**定义来源直接取** `wind-keys/src/key_inject.rs` 的 `parse_key` 键名表：
`enter / tab / esc / space / backspace / del / ins / home / end / pgup / pgdn / 方向键`。
它正好覆盖软键盘需要的全部特殊键，拿它当唯一来源就不会漂移。

### 4.3 Shift 是临时切层，不是 toggle

按住 Shift 期间面板整面切显第二层，松开还原。

⛔ **CapsLock 一律不碰**——本仓已有禁令：修饰键作功能键只走 keyup 轻敲，
「翻转再回敲复原」的做法已被删除、勿再实现。

但 CapsLock 在键盘上占着一个 1.75u 的显眼宽键位。取舍是：**那个键位改画成「当前面」按钮**,
显示面名、鼠标点击切下一面；**物理 CapsLock 键不接管**，行为完全交给系统。
键位被利用了，禁令也没破。

### 4.4 切面

走翻页键。软键盘态下没有候选窗，翻页键（PgUp/PgDn 及各组翻页键）正好闲置，
语义上也是「翻页」，用户不用记新键。面板底部另有可点的 PgUp/PgDn 键位与顶部标签行，
三个入口同一个动作。

### 4.5 ★ 吃键门控

软键盘态要吃掉大批键（含无映射的空键位）。本仓不变量：

> **C++ 吃键集必须 ⊆ Rust 出字集**

C++ 侧必须知道当前处于软键盘态，否则症状是「改了没生效」，而这类问题的排查链很长。
**软键盘态一开始就接进那条判据链，不要事后补。**

### 4.6 上屏出口

符号上屏必须走**已收口的上屏出口**，不要新开路径。简繁转换出口曾经七处全漏、事后才收口，
新增快捷路径正是那类缺陷的典型来源。长按重复产生的输出同样走这条出口，不抄近路。

## 5. 长按重复

### 5.1 两条路径成本不对称

| 路径 | 要做的事 |
|---|---|
| **物理键长按** | **什么都不用做。** 系统 auto-repeat 本来就连发 keydown——只要别误加去抖、别写成「只处理首次 keydown」 |
| **鼠标按住键帽** | 自己起定时器：首延迟后转入匀速重复。键帽保持按下态，不是每次重复闪一下 |

特殊键既然是透传的，它们的**物理长按由宿主自己处理，我们完全不参与**——按住退格连删，
是宿主收到系统 auto-repeat 的结果。只有**鼠标**按住面板上的退格时，才轮到我们重复。

### 5.2 参数读系统设置，不要自定常数

| 参数 | 来源 |
|---|---|
| 首次延迟 | `SPI_GETKEYBOARDDELAY`（0–3 → 250/500/750/1000 ms） |
| 重复间隔 | `SPI_GETKEYBOARDSPEED`（0–31 → 约 400 至 33 ms） |

自定两个常数一定会和物理键手感对不上。

### 5.3 重复与否的判据

> **产生输出的键重复，改变状态的键不重复。**

- 重复：符号键、Backspace、Del、Space、Enter、Tab、方向键
- 不重复：Shift、Esc、PgUp/PgDn、面名键、关闭按钮

切面键若重复，按住一下面就飞速乱切。

### 5.4 ⚠️ 鼠标长按撞 SetCapture

鼠标按住键帽后移出键帽、或在窗口外抬起，都必须能停下来。常规做法是 `SetCapture`——
但本仓已有记录：**后台窗口的 SetCapture 是按线程失效的**，而软键盘正是 NOACTIVATE 的后台窗口。

兜底代码已经写好了：`popup_menu.rs` 的 `any_mouse_button_down()` 就是为这个问题写的轮询兜底。
拖动面板与长按重复两处都走它，别再走一遍 SetCapture 的弯路。

## 6. 生命周期

### 6.1 ★★★ 焦点契约：面板永远不拿焦点

窗口样式沿用现有浮层那一组——`WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW | WS_EX_LAYERED |
WS_EX_TOPMOST`（候选窗与工具栏已在用，`wind-ui/src/window.rs`）。
`WM_MOUSEACTIVATE` 必须回 `MA_NOACTIVATE`。点击照样收得到 `WM_LBUTTONDOWN`，
交互不受影响，只是窗口不被激活、宿主焦点原地不动。

> **「切换焦点自动关闭」这条行为完全依赖面板不抢焦点。**
> 面板一旦可激活，用户点它上面任何一个键都是在改变焦点——它会把自己关掉。
> 将来若有人想把面板挪进可激活窗口，这条行为会立刻塌掉。**这个依赖写进注释，不要靠记。**

### 6.2 开启入口

- 热键（`key_actions` / `session_actions`，见 §7）
- 工具栏图标（键盘图标，toggle）
- 右键菜单（开启 + 子菜单直接选面）

### 6.3 关闭路径

| 触发 | 语义 |
|---|---|
| Esc | 手动关闭。软键盘态吃掉，不透传给宿主 |
| 面板关闭按钮 | 手动关闭 |
| 工具栏图标 / 右键菜单再点 | 手动关闭（与开启同一入口） |
| **切换焦点** | 自动关闭 |

### 6.4 ⚠️ 失焦判据复用工具栏那套，但后果不同

「焦点变化」在 TSF 里不是一件事，是三层，且本仓纪律是**三层焦点判据不可跨层复用**。
工具栏——同样是跟随焦点的浮层——为这件事踩了五轮，最后收敛出一张失焦语义后果矩阵，
其中「给 `OnKillThreadFocus` 补对称预判」已被明确否决。

> **复用工具栏那套「什么算失焦」的判定，不要自己写一套。**

⚠️ 但有一处语义差异要显式处理：工具栏是**隐藏**（失焦藏起、回来再显示），
软键盘是**关闭**（不可逆，切回来不自动恢复）。同一套判据、两种后果——
复用的是判定，不是动作。这个分界不划清，很容易写成「切回应用软键盘自己弹出来」。

同宿主内的焦点抖动（点工具栏、宿主内部换输入框）**不算切换焦点**，按宿主窗口粒度判。

### 6.5 工具栏交互

⚠️ 三个已知坑：

- 工具栏图标主字按**显示宽度**截断（`d8aa2e20`）；加内置按钮要同步显示排序配置。
- 设置页控件**分派有两处，漏一处静默降级且测试全绿** ⇒ 改设置页 UI 必须 `--screenshot` 自查。
- 工具栏 `auto_hide` 的 `is_active` 守卫 `on_shown` 会导致永不重新起表。

**决定：软键盘显示期间不抑制工具栏自动隐藏。**

判据是「工具栏藏起来会不会让用户失去关闭软键盘的途径」——不会：面板自带关闭按钮，
Esc 也能关。而抑制要动 `auto_hide` 的 `is_active` 守卫，那里踩过「抑制之后永不重新起表」
的坑，为一个并不缺失的途径去碰它不划算。

## 7. 接线

### 7.1 action 值域用现成形态

`BoundAction` 已经是「动词 + 携带 id」的枚举，冒号分隔：

```
"mix:<id>"             进指定融合模式
"special:<id>"         进指定特殊模式
"toggle_schema:<id>"   切到指定方案，再按回来
```

⇒ 软键盘同构：

```
"softkeyboard"          开 / 关
"softkeyboard:<page>"   直通某一面
```

⚠️ **必须进白名单，不是「解析得动就收」**。写错的动词若静默通过，按下时分发端匹配不上、
什么都不发生，**与「没绑上」完全同形**，用户无从分辨。面 id 不存在则由消费端门卫拦下并在
加载期 warn，动作本身解析成 `BoundAction::None`，不静默变成别的功能。

### 7.2 两张表都合法——但理由要论证

全局 `keys.key_actions` 与方案级 `[session_actions]` **都可以绑**。

判据是：**这个动作会不会把「配了它的那张表」本身换掉。**

- 反例 `switch_schema`：明确标了只在全局表合法——方案级按活跃方案查表，单向切走之后
  目标方案没有这条绑定，这个键就再也按不动了。
- 软键盘是浮层、**不改变活跃方案** ⇒ 方案级表还是那一张 ⇒ 关闭键仍然按得动 ⇒ 两张表都合法。

这个论证要留在代码注释里，否则下一个人只看到「两张表都行」而不知道边界在哪。

### 7.3 ★ 开启动作不进 `DISPATCH_ACTIONS`

`BoundAction::DISPATCH_ACTIONS` 那份白名单的注释写着：

> `add_word` / `open_add_word_dialog` **不在此列**：它们要返回占位 composition 来激活
> C++ 转发全部按键，不符 `dispatch_hotkey` 的 `bool` 契约……**混进来会变成「按了没反应」**。

软键盘开启后正是要接管全部主键区按键 ⇒ 它与 `add_word` 同类，**不是**与 `toggle_toolbar` 同类。

> 判据：**开启后是否需要接管后续按键。** 不接管的进 `DISPATCH_ACTIONS`；
> 接管的走 `coordinator.rs` 的特判分支。

### 7.4 鼠标点特殊键走 `key.tap`

面板上的特殊键被鼠标点击时，焦点在宿主、我们不能插文本，只能让那个键发生一次。

本仓「勿用按键模拟实现 `type()`」的禁令**不适用**——那条禁的是把待上屏文本降级成按键序列
（会绕开 CR 规范化与跟打统计）。功能键点击走的是 `key.tap` 那条正路，实现现成：
`wind-keys/src/key_inject.rs` 的 `SysKeys`（`KeyInjector` trait，wind-cmdbar 在用）。

## 8. 呈现

### 8.1 布局零配置

**软键盘的布局就是键盘的布局。** 编码字符即键位坐标（`q` → Q 键），不需要任何行列定义。

标准 ANSI 主键区，五行等宽 15u：

| 行 | 构成 | 加宽键 |
|---|---|---|
| 1 | ` 1…= + Backspace | Backspace 2u |
| 2 | Tab + q…\ | Tab 1.5u，`\` 1.5u |
| 3 | 面名键 + a…' + Enter | 面名键 1.75u，Enter 2.25u |
| 4 | Shift + z…/ + Shift | 左 2.25u，右 2.75u |
| 5 | Ins Del Space PgUp PgDn Esc | Space 8u，其余 1.5/1.25u |

### 8.2 键帽承载两条信息

- **原键标识**（角标，等宽小字）：告诉用户敲哪个物理键。没有它，软键盘就退化成纯鼠标面板。
- **输出符号**（主体）：当前面、当前层的映射结果。多字符 token 字号自动收窄。

### 8.3 绘制成本：实测够用，**没有**做单键重绘

设计阶段判断「面板内容几乎恒定，应当底板烘焙 + 单键重绘」。实施时发现前提变了：
`wind-ui` 已有 View 树 + flex 布局，且 `TextRenderer` 有文本测量缓存（2026-08-13 加的）。
47 个键帽全是 `fixed_w`/`fixed_h`，重排只是算矩形，真正贵的字形测量走缓存。

⇒ 当前实现是**每次重建整棵 View 树再整块重绘**，没有底板烘焙。

⚠️ 这条够用有前提，写进代码注释了：**若把键帽改成按内容自适应宽度，或去掉测量缓存，
前提就不成立**，鼠标划过面板会明显发烫。那时再上单键重绘，不要提前优化。

### 8.5 遮挡

面板是 layered 浮层，软阴影自绘、**计入窗口矩形**。候选窗因此挤掉过 QQ 的弹出输入框。
软键盘面积更大，但**位置由用户固定、不跟随光标**，天然避开了那条路径。

### 8.6 主题

键帽、面板、高亮、角标各需要一个主题键。角标色是最容易忽略的一个——它要比正文更淡，
又要在深色底上仍然可读，直接沿用 `dim` 会偏亮。

## 10. 实施期定下的判据

设计阶段没写、实现时才浮现，都属于「漏了会静默出错」那一类。

### 10.1 软键盘状态放 `Coordinator` 的 atomic，不放 `State`

状态推送（`push_state_update` → `build_status`）内部要 `state.lock()`，而开关软键盘发生在
**已经持有 `&mut State`** 的按键路径里。放进 `State` 就意味着「改完必须先还锁再推送」——
一条只能靠注释维持的不变量，漏一处的症状还极隐蔽：Rust 认为软键盘开着并接管按键，
C++ 仍按「没开」判定而不吃数字键，于是数字行整行失效、别的键都正常。

放在 atomic 上，两条路径互不相干。语义上它也确实与输入状态正交。

### 10.2 状态推送用 RAII guard 挂在按键入口最开头

`handle_key_event` 有几十个 return 点，逐个补推送必漏。改为在函数**最开头**声明一个
`SoftKeyboardPushOnDrop`：局部变量逆序析构 ⇒ 它最后走 ⇒ 那时 `state` 的 `MutexGuard`
已经还了，推送里的 `state.lock()` 不会撞上自己。

### 10.3 ★ 工具栏的「值域」与「默认显示」必须是两份

加软键盘格时顺手把它写进了 `DEFAULT_TOOLBAR_ITEMS`，被一条守门测试当场拦下——
那条测试的注释写着：

> 留空必须渲染出与本功能落地前**逐格相同**的序列。这条红了就意味着给所有老用户改了
> 工具栏外观——那是本次改动最不能有的后果。

它拦住的不是一个笔误，是一个**没意识到自己在做的决定**：往值域里加一格，顺带改了所有
老用户的工具栏。两件事被 `default_toolbar_items()` 从 `TOOLBAR_ITEM_KEYS` 直接生成这一
行代码焊死了。

⇒ 拆成两份：`TOOLBAR_ITEM_KEYS` 是**合法值域**，`DEFAULT_TOOLBAR_SHOWN` 是**默认显示**。
软键盘格属于前者不属于后者——它已有热键与主菜单两个入口，不必再占一格。

配套地，那条「每个登记的键都必须被解析认识」的守门要保留（它防的是「配了没反应」），
但「值域解析结果 == 默认项」这半条要改成子序列断言，否则往值域加格又会与改外观焊在一起。

### 10.4 ★★★ 动词值域散在三处，只加解析层等于没加

出厂热键 `ctrl+shift+k = "softkeyboard"` 写好、`BoundAction::parse` 认得、协调器分派
也接好了，部署到真机按下去**什么都不发生**。唯一线索是日志里一行：

```
WARN keys.key_actions: 组合键不支持动词 "softkeyboard"（键 "ctrl+shift+k"），忽略
```

组合键另有一份白名单 `hotkey::hotkey_action_entry`——它才决定一个动词能不能编译进
key_down 热键表。三处缺一不可：

| 处 | 管什么 | 漏了的症状 |
|---|---|---|
| `BoundAction::parse` | 引导键链 / 方案级表 | 单键绑定不生效 |
| `hotkey_action_entry` | **组合键**能否进热键表 | **组合键按下无反应**（本次踩的） |
| 协调器分派臂 | 收到动作后做什么 | 热键转发到了但没人处理 |

★ 这正是设计 §7.1 写的那条判据的现场：「与『没绑上』完全同形，用户无从分辨」——
只不过当时想的是解析层，实际漏的是编译层。

**守门已补**：`config_schema.rs` 的
`factory_combo_key_actions_are_accepted_by_the_hotkey_compiler` 遍历出厂 `key_actions`，
凡走组合键通路的动词都必须被白名单接受。

策略位按动词分。软键盘**不带 `CHINESE_ONLY`**——初稿按 `special:` 照抄了那一位，理由是
「面板的按键接管建立在中文模式下 C++ 吃字母/标点之上」；真机上这条推理反了：正因为
英文模式吃不到键，才要在 C++ 侧**专设软键盘总闸**（§10.7），而不是把面板也限制成
只能在中文模式打开。面板画的是键位→符号的映射，跟中英文没有关系。

### 10.5 ⚠️ 菜单有两处构建，加项要选对

`build_menu_items_macos`（macOS 简化菜单）与 `build_main_menu_items`（Windows 主菜单）
各建各的。软键盘项一开始加进了前者——编译过、测试绿，而 Windows 上的主菜单里根本没有
这一项，macOS 上倒是多了一个点了没反应的项（面板是 `LayeredWindow` 的 Windows 实现，
非 Windows 分支是空壳）。

与「设置页控件两处分派，漏一处静默降级且测试全绿」是同构的坑：**同一个 UI 概念有两个
构建者时，编译器不会提醒你漏了哪个**。加菜单项前先确认自己在哪个函数里。

### 10.6 面板只收当前面，键位名是两侧唯一的共同标识

`UiCommand::ShowSoftKeyboard` 只带当前面的 47 个键位；切面重发一次，而那一刻本就要重排。
一次性发全部 13 面要搬一千多个键位，其中 92% 当场用不上。

点击回送的是**键位名**而不是下标：下标依赖「面板与协调器对键位顺序的理解一致」，
错了会静默错位；键位名是两侧共同的那套拼写，错了当场告警。

### 10.7 ★★★ C++ 的「吃键」与「转发」是两个函数，判据必须成对

软键盘总闸写进 `OnTestKeyDown` 后，物理 Esc 关不掉面板，连查两轮。根因是
`OnKeyDown` 里**没有对称的放行**：

```cpp
// OnKeyDown，门内
else if (keyType == Backspace || Enter || Escape || CursorKey)
    isInputKey = hasInputSession;   // 软键盘不组码 ⇒ 恒 FALSE
```

于是 Escape 在 `OnTestKeyDown` 被吃、在 `OnKeyDown` 被判成非输入键 —— **吃了不发**，
协调器根本收不到这个键。用户看到的是「按 Esc 毫无反应」，而日志里两边都各自「正常」。

这个坑在同一个文件里已经有两条现成的教训（`pair_jumpout_forward` 与
`english_custom_punct`），注释都写着同一句话：那边吃了、这边不发，键就凭空消失。

⇒ **判据**：往 `OnTestKeyDown` 加任何一条 `*pfEaten = TRUE` 的分支，都必须在
`OnKeyDown` 找到（或建立）与之逐条对应的 `isInputKey = TRUE`。两处的条件表达式应当
能逐字对照——本次两边用的是同一个 `IsSoftKeyboard() && !(Ctrl|Alt)` + 同一张
`ClassifyInputKey` 白名单。

还有第二层：`OnKeyDown` 门内那条判定链**有先后**，软键盘键必须与 `isPairJumpOut`
并列在**首位**，否则中文模式下会被后面的 `isInputKey = hasInputSession` 覆盖回 FALSE。
「加在链里」不等于「加对了位置」——这与 §10.5「菜单有两处构建」是同一类错误：
代码进去了、编译过了、测试绿了，运行时走的是另一条路。

### 10.8 「左固定 + 中间自由 + 右固定」不需要新的布局原语

标签行的关闭按钮、底行的翻页键都出现过「位置随内容浮动」。第一反应是给 `View` 加一套
定位能力，实际上现有两件就够：

- `fill_cross()` 把行撑到父列的内容宽（= 最宽那行键盘的宽度）
- `View::spacer().grow()` 吃掉富余，把后续子节点顶到末端

少了前者，行宽只等于自身内容宽，spacer 分不到一个像素 —— **而这在窄面板上看起来还挺
对**，面越多、面板越宽，错得越明显。守门测试
`view.rs::fill_cross_row_lets_spacer_pin_the_last_child_right` 钉住了这个组合。

### 10.9 「当前项可见」的校正要收口在渲染前，不要挂在每个改动点

标签行按项滚动后，用热键切到靠右的面，标签行不跟过去，当前面的高亮落在可见范围外，
看上去像是没切成功。初版只在 `show()` 里挡了左边界。

`current` 有四条来路（热键、直通车、点标签、底行 ◀▶），逐条接线迟早漏一条。改为在
`render()` 里统一 `ensure_current_visible()` —— 不管谁改的、改成什么，画之前必然校正一次。

配套地，「放得下几个」的算术抽成纯函数 `tab_window`，渲染与自动滚动**共用同一份判据**：
两边各算一遍宽度，迟早分叉成「滚过去了但画出来还是看不见」。抽成纯函数也让它能被单测
直接喂宽度覆盖到（本仓的 UI 代码大多因为依赖 `TextRenderer` 而测不到）。

### 10.10 ★★★ 面分两种：符号面出符号，键盘面出按键

真机反馈：「其它输入法的标准 PC 键盘，点击时是把按键发给输入法自己，用这个软键盘也能
正常打中文，而不是直接上屏。」初版所有面一律查表上屏，于是在 PC 键盘面上点 n-i-h-a-o
得到的是五个字母，而不是「你好」。

⇒ 面加一个属性 `send_keys`：

| | 符号面（默认） | 键盘面（`send_keys = true`） |
|---|---|---|
| 画的是 | 键盘打不出的字符 | 键盘本来就有的键 |
| 点键帽 | 查表 → 上屏那个字符 | **合成一次真实按键** |
| 敲物理键 | 查表 → 上屏 | **完全不接管**，落回常规输入链路 |

这不是「PC 面特殊」的硬编码——用户自制的键盘面同样可以打开它。

**三处必须同时知道当前面是哪种**：

1. **UI 点击**（`ui_softkeyboard_key`）：键盘面合成 `tap("shift+q")`。发的是**键位**不是
   画布上那个字——画布只管显示。面板 `WS_EX_NOACTIVATE` 不抢焦点，合成的键落在真正的
   焦点窗口上，经宿主 → TSF → 常规链路回到我们自己。
2. **Rust 按键**（`handle_softkeyboard_key`）：键盘面只画一下按下的样子然后 `None` 放行。
3. **★ C++ 吃键**（`STATUS_SOFT_KEYBOARD_KEYS`）：键盘面不启用软键盘总闸。
   **少了这一位，键盘面在英文模式下会「吃了不发」**——总闸吃掉键，而常规链路在英文态
   返回 PassThrough，键彻底消失。这正是 §10.7 那条不变量的又一个现场。

配套：`_IsSoftKeyboardEatenKey` 收成**一个**判据函数，`OnTestKeyDown` 与 `OnKeyDown`
都调它。§10.7 的教训是「两边必须一致」，这一步让一致由编译器保证而不是靠纪律。

**正在打字时面板的控制键要让位**：键盘面上有编码或有候选时，Esc 是「清空这串码」、
翻页是「翻候选页」，都比「关面板 / 切面」更贴近用户当下在做的事。只有键盘面会出现
这种局面——符号面根本不组码。

**切面要重推状态**：面的类型变了，`STATUS_SOFT_KEYBOARD_KEYS` 随之改变，C++ 的吃键
判定必须跟上。四条改面路径（热键、直通车、点标签、底行 ◀▶）都要置 dirty 或直接推送；
UI 事件那条不在按键路径上，没有 RAII guard 兜底，得自己推。

**用户覆盖是三态**：不写 `send_keys` 沿用出厂值。只想换 PC 面画布的用户不该顺带把它
降级成符号面——那会让整面突然打不出中文，而配置里一个字都没提到这件事。

### 10.11 CapsLock：只管字母、与 Shift 异或、两种面一视同仁

「大写时应该切换为 Shift 档」听起来是一句话，实际有三条判据，每一条错了都只在特定
组合下暴露：

1. **只管字母**。真实键盘上 Caps 开着按 `1` 出的仍是 `1`，不是 `!`。数字行与符号键
   必须完全不受影响。
2. **与 Shift 异或，不是或**。Caps 开 + Shift 按下出的是**小写**。写成「或」在
   「只按 Shift」「只开 Caps」两种单独情形下都表现正常——最难发现的那种错。
3. **两种面都生效**。初版把它限制成「只在键盘面」，理由是「符号面的按键处理只认
   `MOD_SHIFT`，显示跟着 Caps 变会造成显示与实际不符」——**这是把自己的实现缺口
   当成了设计理由**。真机上用户在标点面按 CapsLock 毫无反应，日志一行
   `show page=1 send_keys=false` 当场点破。正解是让符号面的**输出也跟着显示档走**：
   那一面是查表直接上屏，「画着什么就出什么」本来就做得到。

★ **回送的 `shift` 在两种面上语义不同**，这正是「显示与输出不分叉」的落点：

| | 回送什么 | 为什么 |
|---|---|---|
| 符号面 | **显示档**（含 Caps） | 查表直接上屏，画着什么就出什么 |
| 键盘面 | **物理 Shift**（不含 Caps） | 合成真实按键，CapsLock 由系统自己应用 |

键盘面那条若混进 caps：Caps 开时合成的 `shift+q` 在真实键盘上恰好出小写，
表现为「Caps 开着点字母，出来的正好是反的」。

判据抽成 `wind-ui-types::slot_layer` 并单测覆盖——**它住在 types crate 而不是面板里，
因为协调器的物理键取档必须用同一份**。各写一份的症状是「面板画着 A，敲下去出 a」。

### 10.12 ★ 标签行：`View` 补上 clip 之后才谈得上「滚动」

标签行折腾了三轮，前两轮都在没有裁剪能力的前提下凑合：

1. 折行 → 面板高度随内容长，自定义面一多就往下长几层
2. 按项取舍（放得下几个画几个）→ 项宽不一时**永远对不齐容器边缘**，右侧箭头会随着
   当前显示了哪几项左右跳

第三轮给 `View` 加了真正的 `clipped()`，问题才消失。实现是「画完把界外像素还原」而不是
给每个绘制函数加 clip 参数——底层十来个 `fill_*` 与 `TextRenderer::draw` 各自逐像素写
缓冲，逐个开洞既繁琐、漏一个就前功尽弃；还原法只碰一次缓冲，且对**以后新加的绘制方式**
一样有效。命中收集同步裁剪：被裁掉的部分不能点，否则鼠标会在容器外的空白处点到不可见
的控件。

有了它，标签行是「`‹` │ 视口(clip) │ `›` │ `✕`」，视口 `fixed_w(0) + grow`：
**measure 时宽度为 0，整行宽度与内容彻底无关**，右侧控件的位置只由键盘宽度决定。

### 10.13 「把当前项滚进视野」只能在换项时做

§10.9 把这条收口在 `render()` 里每帧执行——**那让用户根本滚不动标签行**，手一松就被
拽回当前面。滚动是用户的意图，换面才是我们的：记住上次已经滚过去的面，只在它变了的
时候拉一次。

### 10.14 不可撤销的按钮在**抬起**时才触发

关闭按钮按下即关，手感上像「还没点就没了」，而且中途反悔（按住挪开）也来不及。
普通键位则必须按下即出字——打字要跟手，长按重复也建立在按下就开始之上。
故只给「关掉整块面板」这一类动作用 `fires_on_release`，抬起时还要求鼠标**仍停在原控件上**。

### 10.15 主题：复用已有的「键盘域」语义色，不另立一套

初版给面板起了一整套 `softkb_*`，而**任何主题文件里都没有定义它们**，于是永远落到硬编码
兜底——换成橙色主题，软键盘还是蓝的，而且没有任何报错。

主题里早有一组键盘域语义色（`key_bg` / `key_text` / `key_hint` / `key_special_bg` /
`key_pressed_bg` / `keyboard_bg`），本是给 Android 软键盘定的，注释还写着「桌面没有这些
控件」。它们描述的与桌面面板是同一件事：一块键盘长什么样。更要紧的是那些值一律以
