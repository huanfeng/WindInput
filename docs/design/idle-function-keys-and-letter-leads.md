# 空闲态功能键与字母引导键（规划）

> 来源：维护者提出两条按键需求——① 空闲态裸 F1（及其它功能键）可绑功能；② 拼音下 u / v / i 等字母空闲时可作引导键（进快捷输入之类的模式）。
> 看板：C2-116（空闲态 F 键）、C2-117（字母引导键）。前置已完成的部分见 [session-key-extensions.md](session-key-extensions.md)。
> 本文只做规划，**尚未实施**；§5 列出需维护者拍板的点。

## 1. 现状摸底

### 1.1 空闲态裸功能键

| 平台 | 现状 |
|---|---|
| Windows TSF | `ClassifyInputKey` 对 F1–F12 返回 `None`：无会话时既不吃也不发 IPC，宿主独占。要让服务端看到，只能进 key_down 热键表（`_keyDownHotkeys`），由 `OnTestKeyDown` 在 IPC 之前决定「吃不吃」 |
| 引擎侧 | `key_actions` 里单键走 `LeadingKey` 通路（引导键链，仅对有字符的键成立）；裸 `f1` 被 `route_of_key_action` 归为 `LeadingKey`，但 TSF 永远不会把空闲的 F1 送过来，等于配了不生效 |
| Linux / macOS | 键事件本就整体交给服务端（无 TSF 那种热键表预筛），引擎侧放行后应可用，**待实测**确认 |

旧结论「单键不能进热键表」的真正含义是：进表后 TSF 在 IPC 前就吞掉，宿主的 F1 帮助等全部失效；对字符键（`backtick`）更是直接打不出字。对**不产出字符的功能键**，代价只是「中文模式下该键归输入法」，且是用户显式绑定的结果。

### 1.2 字母引导键

- 方案级 `[key_actions]` 与 `bound_action_for` **已接受任意字母**，让位由 `bound_action_yield_reason` 裁决：码表引擎看「是否活码前缀」；**非码表引擎一律让位**（拼音 / 混输里字母全是有效输入，借作功能键会丢首字母）。所以拼音下配 `u = "mix:quick_mix"` 当前会被让位、不生效。
- 全局 `keys.key_actions` 的字母：旧版接受，`migrate_letter_trigger_keys` 把 z 折进 `z_key_action`、其余字母摘除并 warn；解析端现仍能解析字母，但设置端下拉只留 z。
- 拼音引擎没有「某字母能否作为一个码的开头」的查询接口。

## 2. 方案一：空闲态功能键

**做法**：裸功能键 `f1`…`f12` 在 `keys.key_actions` 里走 key_down 热键表，策略位用 `CHINESE_ONLY`（中文模式吃、英文模式透传），不带 `FORWARD_ONLY`（真动作热键，任何时候都吃）。

1. `route_of_key_action`：新增判定——无修饰的 F1–F12（及 `shift+f1` 之类已是组合，本就走 Hotkey）归 `KeyActionRoute::Hotkey`。仍**不收**字符键、`enter` / `space` / `backspace` / 方向键等（它们各有专属路径或会话语义）。
2. `Compiler::compile`（`hotkey.rs` ~573）的 Hotkey 分支为这类键生成 `CHINESE_ONLY` 策略；`compile_global_lead` 不再收它们（避免两条通路同键）。
3. TSF：热键表命中后现有逻辑已会「中文模式吃、转发服务端」，应无需改 C++；**只需验证**无会话 + 无 Ctrl/Alt 的裸键是否被 `FORWARD_ONLY` 闸门之类误放行（该闸门只认标记，真动作热键不带标记，预期无碍）。
4. 动词：沿用 `command:` / `comment_state` / `toggle_*` 等已有动词。服务端返回必须是**确定 Consumed**（`command:` 本就恒吞）；不要做「吃了又吐」——会触发 TSF 的 `OnTestKeyDown(TRUE)+OnKeyDown(FALSE)` 翻转问题（见记忆：产物不变的标点别吃）。
5. 设置端：按键总览 / 全局自定义按键的键名下拉加 F1–F12（仅 key_actions 表；注意与注释切换键默认 F1 在**会话态**的关系，二者不同表，不冲突，但按键总览应并排提示）。
6. 文档：写清代价——中文模式下该 F 键不再到达宿主；英文模式不受影响。

**风险与取舍**
- 笔记本 Fn 键、截图工具常占 F1 / F 键（commit fd295420 已提到），故**出厂不绑**，维持现状。
- 游戏 / 全屏应用靠现有应用兼容的「默认英文」机制规避，不新增机制。
- Linux / macOS 先实测；若 fcitx5 / IMK 对裸 F 键不转发，另议，不阻塞 Windows。

**测试**：`hotkey.rs` 编译用例（裸 `f1` → Hotkey 路 + CHINESE_ONLY）；协调器用例（空闲态 F1 → 命令执行、Consumed）；`route_of_key_action` 对 `backtick` 等字符键保持 `LeadingKey`（回归）；真机：Win 记事本中文模式按 F1 触发、英文模式仍弹宿主帮助。

## 3. 方案二：字母引导键（方案级，仅空缓冲）——已按下述简化口径实施

维护者拍板：**不做 `can_lead_with` 之类的合理性判断**，字母键只在方案级 `[key_actions]` 支持，用户自己配置、自己负责；设置端只提示。

1. `bound_action_yield_reason`：非码表引擎（拼音 / 混输）对字母绑定**不再让位**，绑了就当引导键；码表引擎的活码前缀 / z repeat 让位判据不变。
2. **仅空缓冲生效**：字母走 `VK_A..=VK_Z` 臂，不经「缓冲非空时顶字 + 进模式」的 `_ =>` 臂，`nv` / `lv` 中间的 `v` 不受影响（测试 `pinyin_letter_lead_enters_only_on_empty_buffer` 钉住，变异验证过）。
3. 全局 `keys.key_actions` 仍不收字母（跨方案无从判断）。
4. 设置端：方案级入口的键下拉开放 a–z（不列 F 键）；选了字母的行显示「仅空缓冲生效」。
5. 出厂不绑。拼音文档示例：`u = "mix:quick_mix"`。

## 5. 已拍板

1. 空闲态只开 F1–F12。
2. 字母引导键只限空缓冲，同 z。
3. 字母只在方案级配置，不做额外判定。
4. 设置端选了字母只提示。
