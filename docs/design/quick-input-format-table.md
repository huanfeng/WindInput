# 快捷输入格式表（system.quick.toml）

快捷输入（`;` 模式）的日期 / 数字 / 金额 / 计算候选，此前格式与顺序全部硬编码在
`wind-quick-input` 里。本设计把「渲染成什么样」外置为一张格式表，随程序发布，
用户可在配置目录放同名文件整份覆盖。

**定位：出厂行为与改造前逐条等价，普通用户完全无感。**

分工随后长成两层：**手写整份文件**仍是高级特性（模板与出厂顺序，本文档主体），
而**调序 / 停用 / 单条恢复**有 GUI 入口——右键候选菜单（§11）与设置页（§11.1）。
两层各写各的落点，GUI 绝不回写 `system.quick.toml`。

---

## 1. 唯一的地基：解析归代码，渲染归配置

| | 归属 | 例 |
|---|---|---|
| **解析** | 代码，不可配置 | `2025.12.25` → `(y=2025,m=12,d=25)`；`1+2*3` → `7`；`123.45` → 整数部分/小数部分 |
| **渲染** | 配置 | `(2025,12,25)` → `2025年12月25日` / `二〇二五年十二月二十五日` / `2025-12-25` … |

配置里不能新增 `kind`——那意味着要在 TOML 里描述文法。用户拿到的是「同一批解析结果的另一种写法」，
不是插件机制。这条线一旦模糊，格式表就会长成一门半吊子的语言。

## 2. 文件形态

```toml
[[formats]]
id = "date.cn"            # 稳定 id：日志、将来的候选身份都按它认人；同 kind 内唯一
kind = "date"             # 白名单：date / month_day / year_month / number / calc
text = "$Y年$M月$D日"      # 模板，双路径见 §4
position = 1              # 组内顺序（升序）；缺省按文件出现序
```

解析入口 `Config::resolve_data_file(data_dir, "system.quick.toml")`，
即[用户覆盖机制](../architecture/user-override.md)的**模型 A（整份替换）**，kind 标签 `data`。
与 `system.phrases.toml` 同规格：用户目录那份存在即整份胜出，不做键级合并。

代价（与 `config.toml` 的取舍相反，此处刻意选了简单）：**用户覆盖后，出厂新增的格式对他永久失效**。
故出厂文件头必须写明「拷贝本文件再改」，让用户从完整副本出发而不是从零写。

## 3. kind 与各自的变量

`kind` 恰好对应五个已有解析器，不多不少：

| kind | 触发输入 | 解析器 |
|---|---|---|
| `date` | `2025.12.25`（三段） | `parse_date_parts` |
| `month_day` | `12.25`（两段，年补当年） | `parse_date_parts`（`year == 0` 分支） |
| `year_month` | `2025.12` | `generate_year_month_candidates` 的前半 |
| `number` | `123.45`、或算式求值结果 | `number_subject` |
| `calc` | `1+2*3` | `evaluate_expression` |

`date` 与 `month_day` 是**同一个解析器的两种输入形态**，分成两个 kind 只为让出厂条目各自不同：
两段输入里的年份是代码替用户补的，首选就不该带年（`12月25日`），而三段输入里的年是他自己打的。
变量集两者完全相同（`month_day` 的 `$Y` 系列 = 当前年，农历可用），用户调整也各自记账——
对「打两段」和「打三段」的排序偏好本来就不是一回事。

日期类变量与 `system.phrases.toml` **同名同义**（`$Y $MM $D $YC $MC $DC …`），
差别只在数据源：短语层绑当前时间，快捷输入绑用户打进去的数字。用户学一次。

数字类变量是现有函数的一一映射（`$AMT` `$CNL` `$CNU` `$DIG` `$THOU` `$N`），
计算类两个（`$EXPR` `$RESULT`）。完整表见文档站的「自定义格式」页。

农历变量（`$LMD` `$LM` `$LD` `$LY` `$LYN` `$LZ` `$LF`）**只给 `date` 与 `month_day`**
（两者都有确定的年月日），`year_month` 不给，见 §10。

**渲染为空串的条目自动丢弃**——这是「条件」的唯一表达方式，配置里不写 if。
`$AMT` 对负数或三位小数本就返回空串（`decimal_to_amount` 的既有语义），那条候选自然不出现。

## 4. 双路径：变量替换 与 表达式求值

一条模板要么全是变量、要么全是表达式，**不得混用**（混用在加载期被拒绝）。
分流判据是「含裸 `{`」——`${Y}` 的花括号属于变量语法，`{year()}` 的才是表达式。

```toml
text = "$Y年$M月$D日"                      # 日常：变量替换
text = "{amt(unit='圆', zheng='false')}"   # 偏离出厂时：函数 + 命名参数
```

### 命名参数即「偏离出厂的那一点」

每个 quick 函数的**默认参数就是出厂行为**，与对应的 `$` 变量逐字等价
（`{month()}` ≡ `$M`，`{month(pad=2)}` ≡ `$MM`，`{month(cn='true')}` ≡ `$MC`）。
用户只为想改的那一处写参数，而不是把整个格式拆成函数去拼——
`{replace(amt(),'整','')}` 这种拼法能work但不该是推荐写法，能力应当长在函数自己身上。

布尔参数必须加引号（`cn='true'`）：裸 `true` 会被表达式解析器当成函数调用。
参数值非法（`zheng='nope'`）**报错而非当 false**，否则用户会以为开关坏了。

### 依赖方向（硬约束，不可违反）

```
wind-quick-input（零 wind-* 依赖：解析 + 基础转换 + $ 模板引擎 + QuickValues）
        ↑                                        ↑
   wind-phrase（$ 模板引擎的另一个消费者）        │
        ↑                                        │
        └──── wind-coordinator（分发 + QuickCtx）─┘
                     ↓
               wind-cmdbar（quick 函数族，经 EvalContext::quick_var 取值）
```

两条关键约束：

- `wind-quick-input` **绝不反向调用 cmdbar**（会成环）。表达式求值由宿主经
  `ExprEval` 回调注入，分发点在 coordinator——它本来就同时依赖两者。
- `wind-cmdbar` **也不依赖 wind-quick-input**。quick 函数不做解析，只经
  `EvalContext::quick_var(name)` 取宿主已解析好的量，再做纯字符串加工（补零、
  换分隔符、替换单位）。`quick_var` 有默认实现（返回 `None`），故加这个方法
  不惊动任何既有实现者。

`$` 模板引擎（`$name` / `${name}` / `$$` 转义）从 `wind-phrase` 下沉到
`wind-quick-input::template`，两处共用同一份解析：变量名解析规则若在两个文件里不一致，
「用户学一次」的前提就不成立。phrase 侧只保留自己的变量 resolver（时间源）。

### 注册表与作用域

表达式用 `Registry::quick()`（纯函数 + quick 函数族），**刻意不并入 `Registry::full()`**：

- `year()` / `amt()` 只在「有一次输入被解析成日期或数字」的上下文里有意义，
  混进全局表会让它们出现在短语的函数手册里，而在那里调用只能得到空串；
- 不含动作函数——格式表描述的是候选长什么样，不该能改剪贴板、按键或配置。
  `$CC`（带动作）与 `$SS`/`$AA`（多候选）的求值结果一律拒绝。

⚠️ **`s2t()` / `pinyin()` 目前是 stub**（`fn_passthrough`，原样返回）。繁体金额、
数字读音这类需求要等 cmdbar 补上实现，文档里不要承诺。

### 诊断

表达式的函数名/参数在**求值期**才校验（`$` 变量的 kind 白名单是加载期，两者不同）。
故 `Coordinator::new` 加载完表后跑一次 `quick_eval::precheck`：用一组样本值 dry-run
每条表达式，把未知函数、未登记参数名、非法参数值一次性报到启动日志。

没有这道预检，写错的表达式在运行期只表现为「那条候选不出现」，而热路径不能每次按键
都告警（那会刷爆日志），用户将完全没有线索。

## 5. 顺序：组内归格式表，跨来源归 members

`schema.mix_modes.members` 决定**来源之间**的顺序（先算式还是先日期），
格式表的 `position` 只决定**组内**顺序。

这条边界不能破。`members` 就是快捷输入的开关与优先级机制，上一轮改造刚把
「`enable_english` 与 members 双真相源」消灭掉；格式表若再表达跨来源顺序，
就是把那个坑重新挖开。

## 6. 三层兜底

配置文件坏掉不能导致「打不出字」：

| 情形 | 行为 | 日志 |
|---|---|---|
| 用户/安装两处都没有 | 回落**代码内置默认表** | `warn`（部署损坏） |
| 整份 TOML 解析失败 | 回落内置默认表 | `warn` 带 TOML 报错 |
| 单条模板含未知变量 | 跳过**该条**，其余照常 | `warn` 带 id |
| 未知 `kind` | 跳过该条 | `warn` 带 id |

内置默认表是代码里的 `const`，与出厂 `system.quick.toml` 内容一致。两者会漂移，
因此需要一道测试钉住（见 §7）。

## 7. 状态

已落地：格式表加载与兜底、`$` 变量路径、coordinator 接线与部署验证、
cmdbar `quick` 函数族与表达式路径、启动预检、农历（§10）。出厂表全部是变量模板
（表达式是给用户的，出厂不用），故零回归闸门覆盖的就是全部出厂行为。

设置页已落地（见 §11.1）：core 侧 `quick.*` 十二个 RPC + 视图口径 + 导入导出编解码，
GUI 在 `wind-setting` 仓（词库页第二个全局域）。能调序、启停、单条/整表恢复、导入导出，
以及新增/编辑/删除**自己的**格式条目（出厂条目的模板不可改，只能停用）。

未做：`s2t`/`pinyin` 依赖 cmdbar 补实现；24 节气（需第二套数据，与农历表同量级）。

## 8. 零回归闸门

「普通用户完全无感」必须是可验证的，不是声明：

1. **内置默认表的渲染输出 == 改造前的硬编码输出**，逐条逐序相等。改造前的期望值直接
   写进测试（date/year_month/number/calc 各若干输入）。

   农历两条是**有意新增**的，故这道闸门比较的是日期候选的**前 5 条**——把新值直接抄进
   期望值，闸门就从「公历行为永不变」退化成「当前实现等于当前实现」。农历那两条
   由单独的测试把关（位置在公历之后、超范围时消失、年月类不出）。

   同一条纪律适用于后来分出的 `month_day`：两段输入（`12.25`）的首选由「替用户补年的
   完整日期」改成不带年的 `12月25日`，是**有意变更**，故两段形态整个移出这道闸门，
   由 `test_month_day_forms_prefer_short_writing` 正面覆盖（短写法在前、补年条目仍在、
   三段输入不受影响）。
2. **出厂 `data/system.quick.toml` 解析出的表 == 内置默认表**。防止两者漂移——
   出厂文件改了而 const 没改（或反之），用户与兜底路径就会看到不同的候选。

## 9. 候选身份（留口，本期不接）

`generate()` 目前返回 `Vec<String>`，候选没有身份。格式表引入 `id` 后，可以给候选带上
`quick:date.cn` 这类稳定标识。本期不接消费点，只把 id 留在结构里——将来要支持
「某条格式置顶 / 记词频」时，按 id 匹配是唯一可靠的方式（求值型候选每次文本都可能不同，
按文本匹配必然失效）。

## 10. 农历

`wind-quick-input::lunar`。出厂在日期候选后追加两条（`农历四月廿九` / `丙午年四月廿九`），
另供短语层的 `$L*` 使用（绑当前时间）。

### 算不查表

1900–2100 的农历数据表流传很广，但来源与许可大多不可考，更要命的是**抄错了不会编译失败**，
只会让某一年整年错位。这里改用 Meeus《天文算法》的截断级数直接算：

| 量 | 出处 | 精度 |
|---|---|---|
| 朔（新月）时刻 | 第 49 章，含 A1–A14 附加项 | 数秒 |
| 太阳视黄经 | 第 25 章低精度公式 | 0.01°（≈15 分钟） |
| ΔT = TT − UT | Espenak & Meeus 分段多项式 | 分段拟合 |

系数可逐条对照原书核验，范围也不受表的两端限制。规则用时宪历三条：朔日为月首；
冬至所在月恒为十一月；两个十一月之间有 13 个月时，第一个**不含中气**的月为闰月。

三处容易被忽略、错了就整月错位的地方：

- **日界是东经 120° 的午夜**，不是 UTC——朔落在 UTC 16:00 之后就会算到前一天；
- **ΔT 不能省**。朔时刻算出来是力学时而日界是世界时，两者在本区间差 20~200 秒，
  朔落在午夜附近时这点差直接决定初一是哪天；
- **判「含中气」不必逐个中气求时刻**。一个朔望月约 29.5 天、太阳走约 29°，至多跨一个
  30° 边界，故比较月首与月末的 30° 区间号即可——省掉一个数量级的二分求解。

### 范围与失败

支持公历 **1900-01-01 ~ 2100-12-31**（上限受 ΔT 外推精度限制）。超范围、
或公历日期本身非法（`2026.2.31`），一律返回 `None`。

⚠️ 非法日期必须在换算入口挡住：儒略日会把 `2026-02-31` 照算成 3 月 3 日，
于是农历候选给出一个「看起来很对」的错值。合法性交给 `chrono::NaiveDate::from_ymd_opt`。

### 两种「没有值」：算不出来 vs 这天没有

★ 这是农历部分最容易搞错的一条，两者的后果必须不同：

| 情形 | 返回 | 后果 | 例 |
|---|---|---|---|
| **算不出来** | `None` | 整条模板作废 | 超出 1900–2100、`2026.2.31` 这类非法公历日 |
| **算得出，但这天没有值** | `Some("")` | 渲染成空串，整条照常出 | `$LF` 在非节日 |
| **不认识这个变量** | `None` | 整条模板作废 | `$NOPE` 拼错 |

「算不出来」必须是 `None`：农历模板通常带字面前缀，`农历$LMD` 若把空串填进去会把
「农历」二字单独上屏。表达式路径同理——`lunar()` 换算不出时**报错**而非返回空串。

而 `$LF` 属于第二类，走空串。用户写 `$LY年$LMD$LF` 要的是「节日当天追加节日名」：
平常日子给出「丙午年四月廿九」，端午当天给出「丙午年四月廿九端午节」。与 `$AMT`
「小数超两位返回空串」是同一条约定。

> **历史**：`$LF` 起初也返回 `None`，理由是让 `今天是$LF` 在平常日子整条消失。
> 那个理由只覆盖了「`$LF` 独占一条模板」的写法，而用户的实际写法是**追加式**，
> 于是含 `$LF` 的短语一年有 355 天打不出来。连带代价是启动预检的样本日期被迫挑节日。
> 改为空串后两者一并消失，预检样本反而改用平常日子当守门（见 `quick_eval::date_sample`）。

⚠️ 改这里时别把三类合并成一类：让 `None` 一律变空串，`$NOPE` 这种拼错就会静默产出
半截文本，`unknown_variable_kills_whole_template` 的保护全丢。

### 年月类不给农历

农历月与公历月不一一对应（有闰月，且月首不在公历月初），`2026.12` 推不出唯一的农历月。
`FormatKind::YearMonth` 的白名单不放行 `$L*`，放行了只会让用户拿到看似合理的错值。

### 干支按农历年

农历年**以正月初一为界**：公历 2026-01-01 属农历 2025 年（乙巳），2026-02-17 才转丙午。
干支与生肖都据此推——用公历年推是农历实现最常见的错。`$LYN`（农历年数字）与 `$Y` 因此可能差 1。

### 验证

锚点测试是这套算法的总闸门（任一系数写错都会大面积飘红，而不是等用户某天发现差一天）：

- **春节 30 个锚点**，跨 1900–2028；
- **闰月分布**（2020 闰四月 / 2023 闰二月 / 2025 闰六月），外加「平年不得出现闰月」
  ——只测前者会漏掉「多算一个闰月」这一半；
- **除夕**随腊月大小浮动（2024 是三十，2025–2028 连续四年廿九），写死会连错四年；
- **全范围连续性**：1900–2100 抽样每一天都能换算，2020–2030 逐日检查日号连续。

实现期用一份独立的 Python 实现交叉验证过同一批锚点，两者结论一致。

## 11. 用户调整（右键菜单）

格式表文件是给高级用户的。普通用户在候选窗右键即可调序与停用，落点**独立于文件**。

### 三个落点

| 落点 | 内容 | 谁写 |
|---|---|---|
| `data/system.quick.toml` | 格式模板与出厂顺序 | 出厂 / 高级用户手写 |
| `<userdata>/data/quick_format.toml` | 用户的调序、停用与自加条目 | 右键菜单 / 设置页（可手改） |
| `Coordinator::quick_adjust` | 上一行的运行时镜像 | 写入时同步 |

**GUI 调整绝不回写 `system.quick.toml`。** 两个理由，第二个是要命的：抢走高级用户
手写文件的所有权（重写丢注释与排版）；更糟的是让普通用户点两下右键就永久脱离出厂更新，
而他毫不知情——整份覆盖的代价（§2）必须是知情选择，不能是右键的副作用。

### 不能复用 shadow

shadow（候选调整）的键是 `(方案, 输入码)`。快捷输入的「输入码」是 `2026.6.19` 这种具体值，
把格式调整存进去，用户调完换个日期就失效。症状是「当时有效、隔天失效」，间歇发作且日志干净。

| | 作用域 | 键 |
|---|---|---|
| 候选调整 | 一次输入（这个码下的这些字） | `(方案, 输入码)` |
| 格式调整 | 一类输入（所有日期） | `格式类别` |

同理**不能复用 `candidate_op_scope`**：那个判据问的是「有没有词库落点」，混输确实没有，
它对混输返回 `None` 是对的（注释里写着「新增模式时先补落点、再放行」）。格式调整另起
`quick_format_scope`，判据是「这条候选是不是某条格式渲染出来的」。

### 存稀疏的 (id, position)，不是完整顺序

```
moved  = [{ id: "date.lunar", position: 0 }]   # LIFO，index 0 = 最新
disabled = ["date.basic"]
```

应用算法与 shadow 同构：基表 → 剔除 `disabled` → **逆序**遍历 `moved` 逐条取出重插。
逆序即 LIFO，最新的操作优先级最高。

关键收益是**没被碰过的条目不出现在存储里**：将来出厂新增一条格式，它不在两个列表里，
自然落在出厂位置。存完整 id 序列的话，就得再定一条「新增格式排哪」的规则，怎么定都会让人意外。

孤儿 id（高级用户改文件时删掉了那条）静默忽略，不清理——他可能过会儿又加回来。

### 为什么能放行上移/下移

`handle_menu.rs` 有条现成纪律：拼音普通候选只放行置顶，前移/后移禁，因为
「`position=N` 在候选集变动后失去意义」。

格式表不受此限：**同一类的格式条目集合是稳定的**，永远是那 5–7 条，不随输入变化。
拼音候选每次输入都是不同的集合，`position=3` 下次指向完全不同的字。

### disabled 而不是 hidden

设置页的既有能力是 `set_enabled`（启用开关），被停用的行**在管理界面里仍然可见**、能再打开。
若语义定成「隐藏」，那一行就该从列表消失，用户便再也点不到它。

在没有设置页之前，「恢复本类默认」是停用之后的**唯一出口**（被停用的格式不出候选、右键点不到），
所以它是必需项而非可选项。粒度是整类，单条恢复要等设置页。

### 候选身份

`Candidate::id` 填 `quick:{kind}:{格式 id}`，与短语的 `phrase:{code}:{原文}` 同域不同前缀。
候选文本逐次输入都不同，右键要认的是**格式**，按文本认人必然失配——与短语 `date` 候选
需要 `cand_id` 是同一个理由（§9 留的口子在此兑现）。

### 立即生效

写库后必须**回灌运行时镜像**并重建候选。只写库不回灌，症状就是「调了没反应、重启才生效」。
重建走 `update_mix_candidates`（快捷输入的候选在 `mix_buffer` 上），走主路径的
`update_candidates` 会读到空的 `input_buffer`，后果不是「不刷新」而是候选窗被清空。

## 11.1 设置页（词库管理 → 快捷输入）

格式表是**全局**的（键只到 kind，不带方案），故在 `wind-setting` 的词库管理里与「命令短语」
并列为第二个全局域，而不是挂在某个方案下。

### 两种口径：候选看到什么 vs 用户能管什么

| | 函数 | 停用项 |
|---|---|---|
| 候选生成 | `FormatTable::entries_of_adjusted` | **剔除** |
| 设置页 | `FormatTable::entries_of_view` | **保留**（否则再也开不回来） |

`entries_of_view` 的启用段**直接取 `entries_of_adjusted` 的输出**，不重算顺序。两处各算一遍
「第几位」迟早漂移，症状是「设置页点了上移，列表动了、候选没动」，且两边都不报错。
有测试 `view_enabled_order_equals_candidate_order` 拿候选那条路径当基准钉住这件事。

停用项**留在原位**。它们不在候选里，看似「没有正确位置」，最初因此沉到该类末尾——
**实测被否**：停用是可逆、反复试的动作，沉底会让同一行在停用/启用之间来回跳，
而管理界面里「行不乱动」比「位置反映候选顺序」重要得多。

做法是给每个停用项找一个锚点（它前面最近的那个启用条目），插在锚点之后。

**锚点的参照系是「假设全部启用」的顺序，不是基表**——这一点决定了「先调序、再停用同一条」
会不会跳。位置信息其实一直都在：**停用不清 `moved` 规则**（两者是 `FormatAdjust` 的独立
字段），丢失只发生在计算环节——`entries_of_adjusted` 先剔除停用项，那条 `moved` 便找不到
目标、成了孤儿规则被跳过。所以锚点改查「把 `disabled` 清空后重算一遍」的顺序，那里每条的
`moved` 都生效：

```text
基表 [A,B,C]、moved=[(C,0)]、C 停用
  假设全启用  [C,A,B]   ← C 的 moved 生效
  真实候选    [A,B]     ← C 的 moved 成了孤儿
  C 的前驱: 无 → 插最前 ⇒ 视图 [C,A,B]，与停用前一致
```

**零新增状态**（不必持久化视图位置），代价是每类多算一次排序（至多七条）。两条测试各管一面：
`disabling_a_row_does_not_move_it`（未调序的条目，五个类别每一行各验一遍）与
`disabling_a_reordered_row_keeps_its_new_position`（调序到每个可能位置后再停用）。

⚠️ 不能图省事写成「不剔除停用项、直接对全表应用 `moved`」：`moved` 的下标是「剔除停用项
之后」的位置，把停用项留在列表里再套同一个下标，启用项之间的相对顺序就会与候选不一致。
举例——基表 `[A,B,C,D]`、A 停用、`moved=[(D,1)]`：候选是 `[B,D,C]`，直接套下标却得到
`[A,D,B,C]`（启用项成了 `[D,B,C]`）。守护见
`enabled_order_still_matches_candidates_with_disabled_in_between`。

### ⚠️ 三个「位置」不是一回事

| 名字 | 含义 | 谁用 |
|---|---|---|
| `position`（TOML / store） | 组内序号 | 基表与移动规则 |
| `displayPos` | 列表行号，1-based，**含停用项** | 只给人看 |
| `moveIndex` | 该条在**候选**里的 0-based 下标 | `quick.move` 唯一认的口径 |

停用项占着行号却不在候选里，拿行号去写移动规则，用户会看到「上移一位跳过好几条」——
与右键菜单里 `index_in_kind` 防的是同一个错。停用项的 `moveIndex` 为 `null`，
这同时表达了「不能移动，得先启用」。

### RPC 契约

读写都在 `quick.*`（全局流，与 `phrase.*` 同族；**不并进方案级的 `dict.*`**——那些按
`schemaId` 取数据，格式表没有 schemaId）。

| 方法 | 参数 | 返回 |
|---|---|---|
| `quick.list` | — | `[{kind,id,text,displayPos,moveIndex,enabled,adjusted,user,sample}]` |
| `quick.move` | `kind,id,index` | `{ok}` |
| `quick.setEnabled` | `kind,id,enabled` | `{ok}` |
| `quick.resetEntry` | `kind,id` | `{ok}` |
| `quick.resetKind` | `kind` | `{ok}` |
| `quick.add` | `kind,text` | `{ok,id}` |
| `quick.setText` | `kind,id,text` | `{ok}` |
| `quick.delete` | `kind,id` | `{ok}` |
| `quick.vars` | — | `[{kind,vars:[{name,desc}]}]` |
| `quick.export` | — | `{content}` |
| `quick.previewImport` | `content` | `{moved,disabled,formats,skipped,kinds}` |
| `quick.import` | `content,strategy?` | `{moved,disabled,formats,skipped}` |

`kind` 一律收字符串并在 `WebDataHost` 的实现里解析（未知类别报「未知的快捷输入类别: xxx」），
这样 `wind-webdata` 不必为一个枚举去依赖 `wind-quick-input`。

★ `user` 与 `adjusted` **不是一回事**，设置页按前者分流行级权限：出厂条目被调序过也是
`adjusted`，但它只能停用、能「恢复默认」；用户条目反过来——能改模板、能真删，而它没有
「默认」可回到。

`setText` 而非 `update`：改的是**模板**，且只对用户条目有效（出厂条目返回错误，
约束由 store 的数据结构兜住——模板只存在 `added` 里）。没有「改出厂条目模板」的 RPC，
那条路径被刻意否决（见本节末）。

写操作全部经 `Coordinator::edit_quick_format` 一个入口，**写库与回灌镜像合成一步**——
分成两个方法迟早有人只调一半，而那个 bug 的症状是「设置页改了不生效、重启才生效」，
没有任何报错。

### 示例列（`sample`）

设置页列表里全是 `$YC年$MC月$DC日` 这样的模板，光看认不出哪条是哪条，故每行带一个示例。

★ 实现上**不新增渲染路径**：用示例输入串跑一遍真实的候选生成（`generate_adjusted`），
所以示例与用户实际打出来的东西必然一致。另写一套「设置页专用渲染」漂移了也没人会发现，
两边看着都对、只是不一样。

日期样本用**今天**（用户脑子里知道今天几号，一眼能对上号），数字用 `1234.5`，算式用 `1+2*3`。
`QuickSource::Date` 按输入形态分派到三个类别，故三段/两段/年月各跑一次。

生成时的调整**只清 `moved`/`disabled`、保留 `added`**：清掉前两者是因为停用条目也要有示例
（候选路径会把它们剔掉），保留 `added` 是因为用户条目**住在调整里**。P1 这里传的是空 map，
那时是对的；加了自定义条目之后再传空，等于渲染一张没有用户条目的表——症状是自己加的那几行
示例恒为空、其它行都好，看着像模板写错了。

⚠️ 「示例为空」**不等于**「这条永远不出」——只说明这组样本值渲染不出来（农历超出
1900–2100、表达式写错都会这样）。

### 导入导出：只导用户改动

导出的是**改动**（调序 / 停用 / 将来的自定义条目），不是完整生效表。理由与「存稀疏
`(id, position)`」同源：换机导入后，出厂新增的格式仍会自然生效；导出完整表则把当前版本的
出厂内容固化进文件，日后升级新增的写法**在导入后永远不出现**，而用户完全无从察觉。

文件是 `[[formats]]` + `[[adjust]]` 的 TOML（编解码在 `wind_quick_input::user_file`），
序列化手写以便带头部注释、解析走 serde。两个易漏点：

- **含单引号的模板必须改用双引号**：`{amt(unit='圆')}` 是出厂就有的写法，而 TOML 单引号
  字面量里无法转义单引号。少了这道分支，导出时不报错、导入时才炸。
- ★★ **`moved` 重放必须逆序**（`.rev()`）：它是 LIFO 列表（index 0 = 最新 = 优先级最高），
  而 `move_quick_format` 每次调用都把规则插到队首。顺着遍历的话最老的规则反而占队首，
  症状是「导入后顺序和导出前不一样」。与 shadow 的 pin 规则导入是同一个陷阱。
  注意单条移动时顺序反转**不可观测**，测试夹具必须造出两条互相竞争位置的规则。

导入不静默丢东西：解析期与写入期跳过的条目连原因一起进 `skipped`（未知类别、模板非法、
模板与已有条目逐字相同），实际写入的自定义条目数进 `formats`。

⚠️ 该字段 P1 时叫 `ignoredFormats`（当时没有存储落点，如实报「已忽略 N 条」）。P2 起真的
导入，故连**名字一起改**——留着旧名字会让设置页的摘要文案与实际行为对不上，而那种偏差
没人会发现（两边看着都对）。

`strategy = "replace"` 先清空既有数据，缺省为合并。★ replace 走的是
`clear_quick_format_kind`（**含**自定义条目）而不是 `reset_quick_format_kind`：
它的语义是「用文件里的状态覆盖现状」，留着旧条目会得到「文件里的 + 我原有的」。

### 自定义条目（P2，已落地）

存储落点是 `QuickFormatRecord` 的 `added` 字段（与 `moved`/`disabled` 同域同事务），
**不改 `Coordinator::quick_formats`**（那是启动加载的不可变字段）——用户条目走
`quick_adjust` 这条 RwLock 路径即时生效，也不需要文件监视器。

RPC 新增四个：`quick.add`（返回分配到的 id）/ `quick.setText` / `quick.delete` /
`quick.vars`（模板变量提示清单）。

**已定：不做「编辑出厂条目的模板」**（含一切形式的 `overrides: (id, 新模板)`）。
出厂条目只能停用与调序；想要别的写法就**停用出厂那条、自己加一条**，加出来的一律是独立
条目（独立 id），不与任何出厂条目建立「变体」关联。

唯一的例外是**模板逐字相同**：同 kind 下已存在同样的模板（无论出厂还是用户的）就拒绝保存
并指出是哪一条，因为两条完全一样的候选除了占位没有任何作用，还会让「候选里怎么有两个一样的」
变成一个查不出原因的报障。不一致的一律放行、各算一条。

判据是这张表的顺序**由用户直接指定**，不像命令短语那样由权重算出来——短语改权重才能影响
排序，所以「编辑」在那边有不可替代的作用；这边「停用 + 新增 + 摆到想要的位置」已经完全覆盖
了「想改出厂那条」这个需求，`overrides` 只是同一件事的第二条路径。

★ 顺带消掉的是**出厂表升级时的三方合并**：若有 `overrides`，出厂改了某条模板而用户又
override 过它，就必须选一个——留用户的旧值（用户永远看不到新出厂模板，且无从得知）还是
采用新值（丢用户改动）。两条路都得给 UI 加解释性提示。而「停用 + 新增」天然无此问题：
出厂那条照常随版本更新、只是被停用着，用户随时开回来就能看到新版写法，自己那条独立存在。

#### 实现要点

- **id 命名空间由加载期守门，不靠约定**：用户条目取 `{kind}.u{n}`，而 `FormatTable::parse`
  **拒绝**匹配 `{kind}.u\d+` 的出厂 id（沿用既有「剔除 + warn」策略）。否则某天出厂表加一条
  `date.u1` 就与用户条目静默撞车，行为取决于遍历顺序。
  序号取「已有最大 + 1」而非「条数 + 1」——删掉中间一条后条数会回退，新条目撞上仍然存在的
  那个 id（`u1,u2,u3` 删 `u2` 后条数 2 ⇒ 又生成 `u3`）。
- **删除语义按 `added` 分流**：出厂条目「停用」（真删要回写文件，§3 已排除），用户条目
  **真删**并连带清掉它的 `moved`/`disabled`（留下孤儿规则本身无害，但重加同 id 条目时那条
  旧规则会突然复活、把它挪到意外的位置）。
- ⚠️ **两种「清理」必须分开**：`moved`/`disabled` 是对基表的**调整**（清掉即回到出厂，可逆），
  `added` 是用户**自己的内容**（清掉就没了）。故 store 有两个方法：
  `reset_quick_format_kind`（面向用户的「恢复默认」，**保留** `added`）与
  `clear_quick_format_kind`（导入 replace 的语义，连 `added` 一起清）。
  前者原先是 `t.remove(kind)`，`added` 落进同一条记录后那个写法会让右键点一下「恢复默认」
  就永久丢掉手写模板。同理 `QuickFormatRecord::is_empty` 必须算上 `added`，否则
  `modify_quick_format` 的「空记录即删键」收尾会让新加的条目当场消失。
- **「恢复此条」对用户条目无意义**：它没有「默认」可回到，按行禁用该菜单项（`spec::row_ops`），
  而不是让它变成隐式的删除。
- ★★ **导入时 id 冲突必须连 `moved` 一起改写**：导出文件里 `[[formats]]` 带 `date.u1`、
  `[adjust.date]` 的 `moved` 也引用 `date.u1`。导入到一台已有 `date.u1`（内容不同）的机器
  上时要重新分配 id，若只改 `[[formats]]` 侧不改 `moved` 侧，规则就悄悄指向了本机原有那条。
  症状与漏 `.rev()` 一样是「导入后顺序不对」，同属导入重放的引用完整性。已由
  `quick_import_remaps_conflicting_id_and_its_move_rule` 钉住（反向对照确认：去掉改写后，
  本机原有条目被挪到首位，导入的那条留在原位）。
- **模板逐字相同则跳过并如实报数**，故重复导入同一份文件是幂等的。

#### 两个「加了 added 之后才成立」的陷阱

★ `entries_of_adjusted` 的两个入参**必须共用生命周期**：条目现在可能住在表里、也可能住在
`adjust` 里。而 `entries_of_view` 需要「`moved`/`added` 照常、`disabled` 当空」的一趟计算，
现造临时 `FormatAdjust` 就编译不过（局部变量里的 `added` 活不到返回值需要的 `'a`）。
故内部拆出 `entries_with` 收三个切片，让调用方能对同一个 `adjust` 做**部分借用**。
漏把 `added` 传进那一趟的后果是：被停用的用户条目在参照系里根本不存在，锚点算法找不到它、
只能垫到末尾（`disabled_user_entry_keeps_its_moved_position` 守门）。

★ **示例列的调整不能再传空 map**。P1 传空是对的（那时只有出厂条目），用户条目住在
`adjust.added` 里之后，空 map 等于「渲染一张没有用户条目的表」——症状是自己加的那几行示例
恒为空、其它行都好，看着像模板写错了。改为「只清 `moved`/`disabled`、保留 `added`」。

#### 变量提示清单

`FormatKind::var_hints()` 给出每类的 `(变量名, 说明含示例值)`，经 `quick.vars` 供设置页的
模板输入框提示。**真相源必须在 core**：变量白名单是 `supports_var` 的知识，设置仓硬编码一份
会在加新变量时静默过时（用户照提示写不出新变量，或提示里的变量已被删，两种都看不出是提示
的错）。它与 `supports_var` 是两份数据（多了说明文字），故三道测试钉住：名字必须都能通过
`supports_var`、每类条数写死（加变量时会红，提醒同步文档站变量表）、`year_month` 的提示里
不得出现农历变量。

设置页把它按类别分节一次列全，**变量集相同的类别合并成一节**（`date` 与 `month_day` 完全
相同，不合并要把同样的 17 行出两遍）。一次列全而不是只列当前选中的那类，另一个好处是用户
能直接看到「年月那类没有农历变量」这种最容易写错的地方。

#### 设置页的两处 windui 陷阱（均由 `io_dialogs_build_and_layout` 抓住）

- **类别选项不能在构建期算好**：对话框只构建一次，而那一刻列表数据还没加载，选项会被永久
  冻结成空的。`Element::segmented` 的 `debug_assert!(!opts.is_empty())` 当场炸；换成容忍空
  列表的控件则会潜伏到真机，症状是「类别下拉里什么都没有」。改用 `dropdown_signal` 绑信号，
  在开对话框时填充。
- **`label` 上不能用 `.wrap()`**（text_input 专用，会 panic），限行用 `max_lines`。

#### 行级权限：`spec::row_ops`

快捷输入是词库页第一个「同一类别里两种行有不同权限」的域。`CategorySpec::ops` 是**类别级**
声明（这一类有没有这个功能），到了行级还要再过一道 `row_ops`——否则出厂条目上会亮着「删除」，
点下去收一句 core 的报错，而用户完全不明白为什么。菜单与操作列共读它，判据只此一处。

`save_calls` 对本类别在**解析权重之前**分流：快捷输入没有权重维度，`edit_weight` 从来不被
设置，让它先跑那个 parse 会得到「权重需为整数」——一个与用户所做之事毫无关系的报错。

## 12. 生效时机

与 `system.phrases.toml` 一致：**没有文件监视器，改完必须重启服务**。
路径在启动时一次解析定死。
