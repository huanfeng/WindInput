## 0. 结论摘要

**可以做，但真正的难点不是切分算法，而是三件与本仓现状冲突的事：**

| # | 难点 | 现状 | 结论 |
|---|---|---|---|
| 1 | 简码在切分中制造海量假边 | 一简 50 条 / 二简 655 条**几乎全部是简码**，且权重被人为置顶 | **必须按「简码 vs 全码」二分处置**，见 §5 |
| 2 | 词库 weight 不是词频，是层级带 | 一简 9999 / 二简 9950 / 三简 9000 / 全码均值 851 | **整句解码不能用码表 weight**，须另立词频轴，见 §6 |
| 3 | 全仓硬约定「码表候选 `consumed_length` 恒 0」 | 多处代码以此为前提做分支 | 整句必然打破，需逐处清点，见 §7 |

**切分算法本身是已解决问题**：`LatticeBuilder` + `ViterbiDecoder` 是按**字节跨度**工作的，
不含任何拼音专属假设；把音节图 `SegGraph` 换成「定长码段图」即可直接复用，Viterbi 一行不用改。

**建议路线**：`P0` 数据侧标记简码/全码 + 独立整句词频 → `P1` 码表 Lattice + 复用 Viterbi
→ `P2` 协调器接线（`consumed_length` 分段上屏）→ `P3` 配置开关与混输共存。
默认**关闭**，per-schema 开启。

**已定的交互路线**（2026-08-24）：简码字**照常直接打**（智能容忍，靠惩罚 + 整句整体最优压），
**显式分隔符**作为消歧手段把该边惩罚归零。两者是同一根轴上的两档、不是两个开关，见 §5.3。

## 1. 问题定义：与拼音整句差在哪

拼音整句能成立，靠的是一层**切分先验**：417 个合法音节构成 `SyllableTrie`，
`Dag::maximum_match` 求「覆盖最多字符」的切分，`nihao` 只有 `ni|hao` 一条主路径，
`nih|ao` 因 `nih` 不是音节被直接排除。切分空间在查词典之前就已大幅剪枝。

**码表没有这层先验。** 五笔码是 a–y 的任意串，任何位置切开都「合法」。于是：

- `aaw`（本意 `aawt` →「工作」的前缀）可以读成 `a|a|w`，也可以读成 `aa|w`；
- `ggg` 可以读成 `g|g|g` =「一一一」，而这三个 `g` 都是权重 9999 的一级简码。

这正是本仓**已经踩过的坑** —— `mixed/engine.rs` 里 `in_code_len_opts()` 的注释：

> `allow_partial_final: Some(false)` —— 这一段的击键串同时是码表码，让尾部残码参与整句
> 解码会抢走码表首位（真机 `aaw`，本意五笔 `aawt`→「工作」，首选变成「啊啊我」）。

当时的处置是把拼音侧的残码整句在码长内整体关掉。做码表整句等于**主动把这个歧义请回来**，
所以必须先有一套明确的抑制规则，而不是先写解码器。

## 2. 本仓现状盘点

### 2.1 码表引擎（无任何切分能力）

`wind-engine/src/codetable/engine.rs::convert()` 是单段查询：

```
输入码 → ① 精确 dm.search(input) → ② 前缀 dm.search_prefix(input) → ③ 空码补全
       → cmp_exact_first + base_sort 排序 → truncate → 编码提示 → 自动上屏判定
```

全程把 `input` 当一个不可分割的整体。`ConvertResult` 里 `consumed_length` 字段从不填，
即全仓约定的「码表候选 `consumed_length` 恒 0（= 消费整串）」。

### 2.2 可直接复用的基建

| 组件 | 位置 | 复用性 |
|---|---|---|
| `ViterbiDecoder::decode(nodes, input_len)` | `pinyin/viterbi.rs` | **完全通用**。输入是 `Vec<Vec<WordNode>>`（按结束位置分桶的字节跨度节点），不含拼音语义。Beam 宽 7、可挂 `Grammar` |
| `LatticeBuilder::build()` | `pinyin/lattice.rs` | **结构可用**。它枚举的是字节跨度 `(p,q)` 而非音节路径，跨度来源是传入的 `SegGraph`。打分函数 `score_node` 是拼音语料调过的，需另立码表版 |
| `SegGraph` | `pinyin/dag.rs` | **可用**。`edges[p] = 从 p 出发的终点集合`，纯字节位置图。已有 `from_dag`（多路径）/ `from_syllables`（真值链）两个构造器，码表只需加一个 `from_fixed_len(len, max_code_len)` |
| `consumed_length` 分段上屏 | 协调器 `handle_candidate.rs` + `coordinator.rs` | 机制现成，但见 §7 的约定冲突 |
| `Candidate::is_sentence` | `wind-candidate` | 现成标志，`freq_rerank` 的整句锚定按它判定 |
| DAT 精确查询 | `wind-dict/datformat.rs::search()` | 够用。每个跨度一次精确查（复杂度见 §4.3） |

**关键判断**：`LatticeNode` / `WordNode` 的 `start` / `end` 是**字节位置**，Viterbi 的 DP 也按
字节位置推进。这正是混合简拼（`add_abbrev_nodes`）能与全拼节点同图共存而「Viterbi 一行都不用改」
的原因 —— 码表节点同理，是**第三类节点**，不是第二套解码器。

### 2.3 五笔编码的结构性事实（本仓极点词库实测）

`build_dev/data/schemas/wubi86/wubi86_jidian.dict.yaml`，88543 行：

| 码长 | 条目数 | 其中多字词 | 权重均值 | 权重最大 |
|---:|---:|---:|---:|---:|
| 1 | 50 | 0 | 9998 | 9999 |
| 2 | 655 | 0 | 9950 | 9950 |
| 3 | 5352 | 2 | 8997 | 9000 |
| 4 | 82469 | 62650 | 851 | 8060 |

**简码 vs 全码**（判据：该条目的码是否就是该字的最长码）：

| 码长 | 条目 | 「该码即全码」 | 简码 |
|---:|---:|---:|---:|
| 1 | 50 | **0** | 50 |
| 2 | 655 | 1 | 654 |
| 3 | 5352 | **1604** | 3748 |

三条硬事实：

1. **一简、二简几乎 100% 是简码** —— 该字必有更长的码。它们在整句里是纯噪声边。
2. **三码条目里 30%（1604 条）是全码**，含「皮 hci」「线 xgt」「纹 xyy」这类常用字
   （字根不足 4 个、识别码凑不满 4 码）。**所以「整句只认 4 码单元」这条捷径走不通** ——
   这也正是 rime-wubi-sentence 要专门声明「已兼容 3 码全码」的原因（§3.2）。
3. **多字词几乎恒 4 码**（62650 / 62652）。五笔词组规则（2 字取前二码 + 后二码，3 字及以上取
   前三字首码 + 末字首码）保证了这点。⇒ 整句的绝大多数边长度恒为 4，切分歧义主要来自
   短码字，不来自词组。

## 3. 外部实现调研

### 3.1 librime `table_translator`：整句是**兜底**，不是主路径

`src/rime/gear/table_translator.cc`。三个关键设计：

**① 触发条件是「整串查不到任何词条」**（`Query()`）：

```cpp
if (enable_sentence_ && !translation) {
  translation = MakeSentence(input, segment.start, /* include_prefix_phrases = */ true);
} else if (sentence_over_completion_ && starts_with_completion(translation)) {
  if (auto sentence = MakeSentence(input, segment.start)) {
    translation = sentence + translation;      // 整句插到补全候选之前
  }
}
```

即：`aawt` 在码表里有词 → **根本不进整句路径**；只有整串无解时才拆。
`sentence_over_completion` 是次强档：整串只有补全候选（码更长的词）时，整句插到前面。

**② 建图：可达顶点集 + 逐长度试查**（`MakeSentence()`）：

```cpp
hash_set<int> vertices = {0};
for (size_t start_pos = 0; start_pos < input.length(); ++start_pos) {
  if (vertices.find(start_pos) == vertices.end()) continue;   // 不可达即跳过
  // 用户词典 / encoder：for len = 1..剩余长度，逐个查
  // 系统词典：prism->CommonPrefixSearch() 一次拿全部前缀命中
  //   命中则 vertices.insert(end_pos)，同时 graph[start][end] 存同码词条列表
}
if (auto sentence = poet_->MakeSentence(graph, input.length(), GetPrecedingText(start))) { ... }
```

`max_homographs_`（默认 1，墨奇配 2）限制每条边保留几条同码词条 —— **边上不是全部候选，
只有权重最高的 N 条**。这是控制 DP 规模的关键旋钮。

**③ 打分与 tie-break**（`poet.cc`）：

- 无 grammar 走 `DynamicProgramming`（每位置单状态），有 grammar 走 `BeamSearch`（每位置
  按「最后一个词」分桶，`kMaxLineCandidates = 7`）。**本仓 `ViterbiDecoder` 与之逐条对应**。
- `weight = candidate.weight + Grammar::Evaluate(context, text, entry->weight, is_rear, grammar)`。
  无语言模型时就是**词条权重累加**。
- `Poet::LeftAssociateCompare`：权重相等时，**词数少的优先**；词数也相等时按各词长度
  字典序比较（即前面的词更长者胜）。**形码词条权重常常同档，这条 tie-break 才是
  「尽可能长的前缀优先」的实际执行者。**
- `if (start_pos == 0 && end_pos == total_length) continue;` —— **整句结果里排除「单个词覆盖全串」**，
  那种情况由普通 translator 负责。

> ⚠️ librime **没有对简码做任何特殊处理**。它能用，是因为使用它的形码方案自己在数据侧
> 把编码定长化了（见 §3.2）。直接照抄 `MakeSentence` 而不动数据，在本仓词库上会满屏
> 「一一一」。

### 3.2 rime-wubi-sentence（墨奇五笔整句）：改用 `script_translator` + 数据侧定长化

<https://github.com/gaboolic/rime-wubi-sentence>。这是目前最成熟的形码整句方案，
覆盖五笔 86/98、虎码、宇浩、字源。**它的做法与直觉相反：不用 `table_translator`，
而是把形码当拼音喂给 `script_translator`。**

`moqi.yaml` 的 `translators` 段（形码方案共用）：

```yaml
translators:
  - table_translator@custom_phrase      # 1、2 码置顶（短语表，走 table）
  - table_translator@big_char_set
  - script_translator                    # ← 主翻译器：整句
  - script_translator@user_dict_set
  - script_translator@add_user_dict
```

`script_translator` 天然是「拼写 + 切分 + Poet」的整句翻译器，代价是要给它一套
**可切分的拼写规则**。数据侧因此做了两件事：

**① 编码写成定长「双拼式」二元组**（`cn_dicts_wb/8105.dict.yaml`）：

```
地	fb,n0;f0,00	130314
不	gi,i0;dh,i0;i0,00	162600
要	sv,f0;s0,00	262570
```

`fb,n0` = 五笔码 `fbn` 补位成定长 4；`;` 分隔同一字的多种打法；`f0,00` 是一级简码 `f`。
`0` 是补位符。

**② `speller/algebra` 把它还原成实际击键，并给短码补终止符 `/`**：

```yaml
- derive/^(\w)(\w),(\w)(.+)$/$1$2$3/      # fb,n0  → fbn      （3 码，无终止符）
- derive|^(\w)(\w),(\w)0.+$|$1$2$3/|      # fb,n0  → fbn/     （3 码全码，加 /）
- derive|^(\w)(\w),00.+$|$1$2/|           # 2 码字 → xx/
- derive|^(\w)0,00.+$|$1/|                # 1 码字 → x/
```

`speller/alphabet` 里因此包含 `/`：`alphabet: zyxwvu...ZYXWVU...[/|`。

**⇒ 核心手法：把「不足满码的编码」在整句词典里改写成「码 + 显式终止符」，
让它在切分器眼里恢复成一个不会与其它编码前缀混淆的定长单元。**
README 的措辞是「已兼容同一个字不同的编码打法，已兼容 3 码全码。全码后跟 `/` 可以只出单字」。

代价：用户在整句中打简码字**必须多敲一个 `/`**。社区讨论里的原话是「五笔全码不足 4 码的字
（如『不』对应 i、『有』对应 e），需在输入完后补一个逗号作为分界符」
（<https://emacs-china.org/t/rime/29460>）。

### 3.3 虎码 Rime-tiger_code：整句作为**引导键模式**

<https://github.com/tsaoshuang/Rime-tiger_code> 的方案说明：「单字方案同时集成单字、
打词 `[D][G]`、整句 `[H][F]` 输入」。即整句不是默认行为，而是用引导前缀显式进入。

**这条路对本仓最省事**：本仓已有引导键特殊模式基建
（`docs/design/special-mode-entry-hotkey.md`），整句可以先做成一个特殊模式验证效果，
再考虑是否升为常规路径。

### 3.4 三家做法对照

| | librime table_translator | rime-wubi-sentence | 虎码 tiger_code |
|---|---|---|---|
| 触发 | 整串无解时兜底 | 默认（主翻译器） | 引导键 `H`/`F` |
| 切分 | 顶点集 + CommonPrefixSearch | speller 拼写切分（prism） | 同左 |
| 简码处理 | **无**（靠数据侧） | 数据侧补 `/` 终止符 | 同左 |
| 词频 | 词条 weight 累加 + 可选 grammar | 白霜词库真实词频 + octagram | 同左 |
| 打分 tie-break | `LeftAssociateCompare`（词少优先） | 同左 | 同左 |

**共同结论：三家都没有在算法里解决简码歧义，全都在数据 / 交互层解决。**

## 4. 建议的算法设计

### 4.1 总体：复用拼音的解码器，换一张图

```
输入码串
 └─ CodeSegGraph::build(len, max_code_length)                  新增：定长码段图
      └─ CodeLatticeBuilder::build(input, graph, dict, policy) 新增：码表节点
           │  逐跨度 (p,q)，q-p ∈ [1, max_code_length]
           │  dict.search(&input[p..q]) → 按 §5 的简码策略过滤 → 按 §6 的词频打分
           └─ ViterbiDecoder::decode(nodes, input.len())       复用，零改动
                └─ ViterbiResult { words, log_prob, boundary }
                     └─ 整句候选 Candidate { is_sentence: true, consumed_length: ... }
```

~~`SegGraph` 新增构造器 `from_fixed_len`~~ —— **实现时发现用不上**，见 §11.1。
码表直接在 `CodeLatticeBuilder` 内枚举跨度，`dag.rs` 一行未改。

### 4.2 边的产生规则（这是全部难点所在）

对跨度 `(p, q)`、码 `c = input[p..q]`、命中词条 `e`：

| 条件 | 处置 |
|---|---|
| `q - p == max_code_length`（满码） | **无条件入图** |
| `e` 是全码（该 text 无更长码） | **无条件入图**（覆盖 1604 个 3 码全码字） |
| `e` 是简码，且**下一位是显式分隔符** | 入图，**免罚**（用户已明确表态，见 §5.3 路线 B） |
| `e` 是简码，且 `q == input.len()`（串尾） | 入图，轻罚（用户打到末尾还没打完是常态，见 §5.4） |
| `e` 是简码，其它位置 | 入图，**重罚 `SHORT_CODE_PENALTY`**（智能容忍档，见 §5.3 路线 C） |
| 每条边保留的同码词条数 | 上限 `MAX_HOMOGRAPHS`（对齐 librime，建议 2） |

> ★ 简码边**始终入图**，只是带惩罚 —— 这不是「B 或 C 二选一」，而是同一条策略的两档：
> 显式分隔符把惩罚归零，没打分隔符时靠惩罚 + 整句整体最优去压。⇒ 实现上只有一个
> 惩罚量 `SHORT_CODE_PENALTY`，没有第二个开关。**不要把它拆成两个正交布尔** ——
> 那是 `project_empty_code_terminal_keys` 记过的老毛病（认出轴之后别再拆成正交布尔）。

### 4.3 复杂度

跨度数 = `input_len × max_code_length`（≤ 4n），每跨度一次 DAT 精确查询（walk ≤ 4 步）。
20 码输入 ⇒ ≤ 80 次查询，每次 O(4)。Viterbi DP 状态数 ≤ `n × BEAM_WIDTH(7)`。
**与拼音整句同量级，无需新增词典 API**（`dict.search()` 已够用）。

> 优化项（非必须）：DAT 一次 walk 即可拿到从 `p` 出发的全部前缀命中，把 4 次查询降为 1 次。
> 对应 librime 的 `prism->CommonPrefixSearch`。留到有实测性能问题时再做。

### 4.4 排除「单个词覆盖全串」

对齐 librime 的 `if (start_pos == 0 && end_pos == total_length) continue;`：
整串本身若在码表里有词，那条候选由现有的精确 / 前缀路径产出，整句不重复产。
否则会出现「同一个词以两种身份进候选列表、再被去重逻辑合并」的混乱。

## 5. 一简二简：核心难点专章

### 5.1 为什么它是核心难点

三个性质叠加：

1. **短** —— 1~2 码的边可以插在任意位置，边数 ≈ 位置数，是切分歧义的主要来源；
2. **高频字** —— 一简 25 个键位对应「一地在要工上是中国同民」等最常用字，
   语言模型不会排斥它们组成的串（「一一一」在字频上并不离谱）；
3. **权重被人为置顶** —— 9999 / 9950，见 §6。

⇒ 不处理的话，**任何长串都会被切成一串简码字**，整句功能等于不可用。

### 5.2 判据：简码 vs 全码，可离线预计算

```
is_short_code(entry) := len(entry.code) < max{ len(c) : c 是 entry.text 的任一编码 }
```

这个判据**不需要 text→code 反查索引**（`docs/design/codetable-short-code-yields-full.md` §2
已论证过同款性质：五笔简码恒是全码前缀），可以在 `gen_dict` 生成词库时逐条算好，
或在 `.wdat` 构建时扫一遍全表标记。

实测规模（§2.3）：一简 50 / 50 是简码、二简 654 / 655 是简码、三简 3748 / 5352 是简码。
**排除简码边后，1~3 码的边只剩 1605 条全码字**，切分歧义规模下降一个数量级。

### 5.3 三条交互路线（**已定：B + C 并存**）

| 路线 | 用户怎么打「不」(i) | 优点 | 缺点 |
|---|---|---|---|
| **A. 打全码** | 打 `gii`（「不」的全码） | 零新语法，切分最干净 | 五笔用户肌肉记忆是简码，反直觉；且 30% 的字全码就是 3 码，A 并不能把单元长度统一成 4 |
| **B. 显式分隔符**（rime 路线） | 打 `i` + 分隔键 | 与 rime 生态一致、切分完全无歧义 | 多敲一键；需要新键位语义 |
| **C. 智能容忍** | 直接打 `i`，靠重罚 + 语言模型 | 体验最顺 | 准确率取决于语言模型；本仓 bigram 默认关闭且已评估「收益不显著」 |

**决策（用户 2026-08-24 拍板）：C 智能容忍为默认路径 + B 显式分隔符作为消歧手段，两者并存。**
A 被排除 —— 它与 30% 的 3 码全码字直接冲突（「皮」根本没有 4 码全码可打），且违反五笔用户习惯。

落到实现上**只有一个惩罚量**（§4.2）：

```
简码边惩罚 = 0                    下一位是显式分隔符（B：用户已表态）
           = SHORT_CODE_PENALTY_TAIL   位于串尾（未打完，轻罚）
           = SHORT_CODE_PENALTY        其它位置（C：智能容忍，靠整句整体最优压）
```

两条路线的关系是**同一根轴上的两档**，不是两个开关。分隔符不是「另一种输入模式」，
只是把这条边的惩罚归零。

**由此产生的两项工程约束：**

1. **分隔键位须先清点**。本仓拼音侧已有分隔符基建可直接沿用：`'` 是硬边界，
   `segment_with_separators()` 按 `'` 分段独立切分，`map_consumed_over_separators()`
   把 `consumed_length` 补偿回原始输入空间。但须先查该键在码表方案下有没有被
   `key_actions` 或标点占用，判据见 `docs/design/key-resolver-unification.md`
   的「进哪张表」一节。rime 生态用 `/`，本仓 `/` 可能已用于快捷输入引导。
2. **`SHORT_CODE_PENALTY` 的标定必须靠实测，不能拍脑袋**。选了 C 就意味着准确率
   成为主要风险 —— 没有上下文语言模型时（bigram 已实测收益不显著、默认关闭），
   压住 25 个最高频简码字的全部力量就来自这一个常量。⇒ §8 的「离线正确率验证」
   从建议项**升为 P1 的准入门槛**，且须做惩罚量的参数扫描，而不是只跑一次。

### 5.4 串尾例外

用户打「我是中国人」的过程中，任意时刻的击键串尾部都是**未打完的编码**。串尾的简码 / 前缀
必须放行，否则整句候选会在每次按键时闪断。这与拼音侧 `add_partial_final_nodes`（残码整句，
step ②c）是同一件事，且拼音侧已经踩过一次教训：**残码位不能享受「词性优待」**
（`score_node_partial_final` 不给虚词加成），因为「用户打到一半的那个音节」与
「整句内部已成形的搭配」前提不同。码表侧同理 —— **串尾简码边要放行，但不能给它简码的高权重**。

## 6. 词频量纲：比切分更致命的问题

### 6.1 极点词库的 weight 是「层级带」，不是词频

| 码长 | 权重带 | 含义 |
|---|---|---|
| 1 | 9999 / 9998 | 一简，人为置顶（第二条是字根字） |
| 2 | 9950 / 9949 | 二简 |
| 3 | 9000 附近 | 三简 |
| 4 | 8000–8060 | `protected_codes` 保护带（上游键位约定） |
| 4 | 120–7999 | 主库普通带（真实 unigram 词频折算） |
| 4 | 1–119 | 扩展库带 |

Viterbi 的节点分是 `ln(weight / TOTAL)`。`ln(9999) − ln(851) ≈ 2.46`，而
`WORD_PENALTY = 3.0`、多字词加成 `+3.0 × √字数`。⇒ **三个一简字（3 × 2.46 的优势）足以
压过一个 4 码词组**。任何输入都会被切成简码串。

### 6.2 必须另立整句词频轴

三条路：

| 方案 | 做法 | 评价 |
|---|---|---|
| ① 归一化映射 | 简码条目的整句分取「该 text 全码条目的权重」 | 简单，无新数据。但 30% 的短码字没有更长码，且保护带 8000+ 同样不是词频 |
| **② gen_dict 增列** | 词库增加一列真实词频（`text` 的 unigram / 词组频） | 干净。`gen_dict` **本来就有 unigram 数据源**（词库头部注释：「按 unigram 真实词频重新排序」），只是折算后被层级带覆盖了 |
| ③ 借道拼音库 | 整句分查拼音词库的 `text → weight` | 需要 text 为键的索引；`.wridx` 是 text→code，text 为键的 wdat 已实测否决 |

**建议 ②**：在 `.wdat` 的 `EntryRecord` 增加 `sentence_weight`（或旁挂一张
`text → freq` 小表），`VERSION` 升级即可自动重建缓存。整句解码**只读这一列**，
展示排序继续读原 `weight` —— 两个轴各管各的，互不干扰。

> ★ 这与 `docs/design/sentence-weight-same-axis.md` 记录的拼音侧教训同源：整句权重与
> 普通候选权重必须能在同一根轴上比较，否则排序层会互相推翻。码表侧要提前把这件事想清楚：
> **整句候选进入协调器后，它的 `weight` 用哪个轴表达**。

### 6.3 简码的展示权重与整句权重方向相反

注意一个反直觉的点：出简让全（`short_code_yield`）**把简码字往下压**，
调频的简码位保护（`codetable-freq-short-code-protection.md`）**把简码字往上抬**，
而整句需要的是**第三种排序** —— 两者都不是。三套逻辑的作用域必须写清楚，
否则会重演「同一条加成在两个位置前提不同」的老问题。

## 7. 与现有硬约定的冲突清单

### 7.1 ⚠️「码表候选 `consumed_length` 恒 0」

这条约定被多处代码当前提：

| 位置 | 依赖形式 |
|---|---|
| `handle_candidate.rs:120,169-175` | 清空守护：`consumed_length == 0` 视为整串匹配 |
| `handle_candidate.rs:320-351` | 词频记账：只给「消费整串」的候选记频 |
| `auto_phrase.rs` 模块注释 | 码表自动造词之所以要自建缓冲，就是因为码表恒 0、`committed_segs` 走不到 |
| `freq_learn_tests.rs:624` | 已记录：混输超码长回捞的前缀候选开始如实标注 `consumed_length`，此前那个分支「现实中不可达」 |

**码表整句必然产生 `consumed_length < input_len` 的候选**（整句上屏一段、余码继续打）。
上述四处都要重新判定，且 `freq_learn_tests.rs:624` 的注释说明**混输侧已经打破过一次** ——
可以照着那次的处理方式清点。

### 7.2 自动上屏 / 顶码 / 满码空码清空

`decide_auto_commit` / `handle_top_code` / `should_clear` 都基于「输入是一个完整编码」
的假设。整句模式下输入长度会远超 `max_code_length`，这几条判据要么关掉、要么改判据。
参考「简拼开时顶码不生效是有意取舍」那次的权衡方式 —— 同一族问题。

> **已定口径**：整句开启时**顶码、满码上屏（`auto_commit_at_full`，含唯一全码那条）、
> 满码空码清空（`clear_on_empty_max`）三者一律让位**，判据统一为「功能开没开」，见 §11.6。

### 7.3 混输方案下的双整句冲突

`wubi86_pinyin` 混输方案里，同一串击键会被**拼音整句**和**码表整句**同时解释。
现有的 `pinyin_claims_overflow` / `pinyin_has_any` / 截断优先级档是为「码表 vs 拼音候选」
设计的，再加一路整句需要新的档位判据。**建议 P1 阶段先只支持纯码表方案，混输留到 P3。**

### 7.4 编码提示与 preedit 显示

`show_code_hint` 标注「剩余编码」的逻辑假设候选码是输入的前缀。整句候选的 code 是
整串、text 是多字，标注逻辑要单独处理。preedit 也需要显示切分形态
（类似拼音的 `ni'hao`），三种切法的落点见 `project_preedit_split_forms` 记录的现状。

### 7.5 超码长时补全候选让位

开整句且超码长时，整句一旦解出，**不再显示更长词条的补全**——整句是超码长那一格的主角，
补全混进来只会把它挤下首位。（另一分支去掉了补全的码长闸门，合并时要按这条核对。）

## 11. 实现纪要

> 本章记录**实现与上面设计的差异**，以及实测推翻的假设。上面各章保留原样（那是当时的
> 判断），差异集中在这里，避免读者分不清「设计怎么想」与「代码怎么做」。
>
> 代码：`wind-engine/src/codetable/sentence.rs`（新）、`codetable/engine.rs`（接线）、
> `wind-dict` 的 `DictLayer::for_each_entry`（新，供索引构建）。
> 测试：同文件 9 条单测 + `codetable/engine.rs` 7 条集成测试 +
> `tests/codetable_sentence_probe.rs` 2 条真实词库探针（`#[ignore]`）。

### 11.1 `SegGraph::from_fixed_len` 没有加 —— 用不上

设计里想给 `SegGraph` 加一个「定长码段图」构造器再喂给 `LatticeBuilder`。实现时发现
**`SegGraph` 对码表没有任何价值**：它提供的两样东西——`reachable` 剪枝与歧义接缝惩罚
（`ambiguous`）——在码表下一个都不成立。全位置恒可达；而「同一段又能拆成两段」在音节学里
是消歧信号，在码表里只是普通的切分歧义，没有额外含义。

⇒ 码表在自己的 `build_nodes` 里直接双层循环枚举跨度，`dag.rs` **一行未改**。
拼音侧完全不受影响。

### 11.2 P0 的数据侧改动换成了运行时索引

设计里 P0 要改 `gen_dict` + `.wdat` 格式（加 `is_short_code` 标记与整句词频列）。
实现改为**运行时懒构建的 `ShortCodeIndex`**（`OnceLock` 守着，全表扫两遍）：

- 真实五笔词库实测：**4452 条简码，构建 65 ms**，与 §2.3 的预测（50+654+3748=4452）
  **逐条吻合**；
- 不动缓存格式 ⇒ 不必 bump `VERSION`、不触发全量重建，也避开了「由缓存派生的缓存」
  那一族失效问题；
- 代价：每个开启整句的方案首次超码长输入时多 65 ms。

⇒ **P0 因此不再是 P1 的前置**。但 §11.4 说明它并没有完全解决词频问题。

### 11.3 打分函数：拼音的三条调整**逐条都不适用**，照搬会实测出错

这是实现阶段最大的发现。`pinyin::lattice::score_node` 有三项调整，起初照搬，
真实词库探针立刻打脸：

| 调整 | 拼音里补偿什么 | 码表里为何不成立 | 实测后果 |
|---|---|---|---|
| 多字词加成 `+3.0×√字数` | n 字词占 **n 个音节**，unigram 独立性假设对路径上每个词各扣一次 `ln(TOTAL)`，整词只扣一次 ⇒ 需要补 | **4 码词组与 4 码单字占同一条边**，都只扣一次，过度惩罚不存在 ⇒ 加成没有补偿对象，退化成「凡词组白送」 | `ggll` 上「一」(2831) 输给「来来回回」(1298)；`trnt` 上「我」(3371) 输给「特性」(1812) |
| 单字惩罚 `−3.0` | 阻止把词拆成单字 | 跨度相同就无所谓拆不拆；跨度不同已由每边固定罚承担 | 同上 |
| 单字虚词优待 `+2.0` 且豁免每词罚 | 虚词随内容词出现是语法黏着 | 五笔一简 25 键里「是/在/要/不/了/有/我」**全在虚词表内**，合计 5.0 的优势恰好把最危险的那批简码字整体提权 | 有单测 `function_words_get_no_bonus` 锁住 |

⇒ 码表版打分是 **`ln(w/T) − WORD_PENALTY`**，没有任何按词性/字数的调整。
去掉后全码打法的还原率 9/12 → 10/12。

**这三条是同一句话**：同一条加成，在两套编码结构里前提不同 —— 与拼音侧
`score_node_partial_final` 为残码位去掉虚词优待，是同一条判据的又一次应用。

### 11.4 ★ 新发现：`gen_dict` 按**码长**发权重带，3 码全码字的词频被覆盖

§6.1 说「全码带 120–7999 是真实词频量纲」——**这句话对 3 码全码字不成立**。
`gen_dict` 的分带是按码长的，而 3 码条目里有 1604 条其实是全码（字根不足 4 个的字），
它们跟三级简码一起拿到了 9000 带。后果实测可见：

- 「八」最长码 `wty`(3 码) = 9000，「人」最长码 `wwww`(四叠保护带) = 8010
  ⇒ 「八」压过「人」，`khlgw` 解成「中国八」；
- 「个」最长码 `whj`(3 码) = 9000 ⇒ 被当作带、落回中性值 851，
  而「修」有 4 码全码 `whte` = 2135（普通带、可信）⇒ **低频字压过极高频字**。

> ✅ **本节描述的问题已由 §11.9 解决**（整句词频改从拼音词库取）。下面这套止血
> 只在**退化路径**（拿不到拼音词库）上还生效，留档说明那条路径为什么准确率更低。

止血措施：`trusted_weight()` 把 `> 7999` 的权重视为「带」而非词频，落回中性值
`NEUTRAL_WEIGHT = 851`（普通带实测均值）。分界 7999 不是魔法数，就是 `gen_dict`
`regular_weight_max=8999` 之下那一档普通带的上沿。加上它之后简码打法 9/12 → 10/12。

⚠️ **这只是止血**。落回中性值等于承认「这个字的真实频率，这份词库里没有」。
真正的修法有两级：

1. **小而具体**（新增，建议优先）：`gen_dict` 分带时区分「3 码简码」与「3 码全码」，
   后者不该发 9000 带 —— 这是一个 1604 条的定点修正，不动格式；
2. **彻底**（原 §6.2 方案②）：给词库增列真实词频。

### 11.5 整句恒消费整串 ⇒ §7.1 的四处依赖点**一处都没动**

`CodeSentenceDecoder::decode` 只接受**覆盖整串**的解（判据是
`ViterbiResult::log_prob.is_finite()`，不是 `words.is_empty()` —— decode 在终点不可达时
会从最远可达位置回溯并返回一条部分路径，只看 words 会误判为有解）。

于是整句候选的 `consumed_length` 仍是 0，**全仓「码表候选 consumed_length 恒 0」的约定
未被打破**，清空守护 / 词频记账 / 自动造词缓冲 / 混输回捞四处都不用改。
分段上屏（真正会打破约定的那一步）留到后续阶段。

同理 `boundary` 也留 0：它是**音节**边界（拼音域），码表码没有音节语义。填编码单元的
切分位会让整句被自动造词学进用户词库时带一份假的音节真值。

### 11.6 顶码 / 满码上屏 / 满码空码清空让位给整句

两者抢同一个区间（超码长），而顶码是**自动上屏**——一触发用户根本看不到整句候选。
`handle_top_code` 因此在 `sentence_input` 开启时直接返回 `None`。

判据取「功能是否开启」而非「本次有没有解出整句」：后者会让顶码在同一串码上时灵时不灵
（多打一个字母解出整句就不顶了），是最难排查的那种不一致。

**满码上屏与满码空码清空同样让位**（论坛 t350）。它们不抢超码长区间，而是在**满码那一键**
截断：`trwu`（唯一全码「我们」）当场上屏、`qwrr`（空码）当场清空——而那 4 码往往只是句子
的前几个编码单元，用户只觉得「整句时灵时不灵」。处置：

- `CodeTableEngine::new` 在 `sentence_input` 开时把 `auto_commit_at_full` /
  `clear_on_empty_max` 就地关掉（用户显式开过则 `info!` 一句）。`convert` /
  `should_auto_commit` / `recheck_auto_commit` 与清空资格都读这份 opts，一处覆盖；
  协调器的清空裁决（`clear_blocked_by_candidates`）只在引擎给了 `should_clear` 时才走。
- 协调器的**短语满码上屏**（`phrase_auto_commit`）读的是配置、绕过引擎，另判一次。
- `decide_auto_commit` 还排除 `is_sentence` 候选：整句的 `code` 是整串，超码长时常是唯一
  一条 `code == input`，曾在第 5 码把自己上屏（`trntw` →「我人」）。上面让位后这条已不可达，
  留作纵深。

代价：开了整句的用户单打一个词也要按空格选。整句本身是实验性、出厂关，设置页开关说明写明
「开启后顶码上屏、全码唯一自动上屏、满码空码清空不再生效」。

### 11.7 配置：方案级引擎固定参数，出厂关闭

`[engine.codetable] sentence_input = true`（`CodeTableSpec::sentence_input`）。

**做成固定参数而非可回落全局的行为 tri-state**：一张码表能不能整句取决于它的编码结构
（定长与否、简码体系多深），是方案属性而非用户偏好。因此**不动全局
`schema.codetable`，设置仓与文档站的配置项清单都不受影响**。

出厂方案文件**未开启** —— 五笔 86 的 `.schema.toml` 一行未改。要试的话加上面那行。

### 11.9 ★ 整句词频改从**拼音词库**取（用户提议，实测提升显著）

§6.2 的方案 ③「借道拼音库」原本被判为需要 text 为键的索引而搁置。实测证明它是最优解：

**覆盖率**（码表 8.3 万 text vs 拼音库 60 万 text）：

| | 码表 text 去重 | 拼音库能查到 |
|---|---:|---:|
| 全部 | 83,640 | 66,392（79.4%） |
| 多字词 | 62,635 | 58,890（**94.0%**） |
| 单字 | 21,005 | 7,502（35.7%） |

单字覆盖低是因为码表收了大量生僻字（拼音库字表只有 8105 + 41448 扩展）。
**查不到本身就等于「罕见」**，故兜底 `OOV_FREQ = 1` 而不是中性值——按中位数计价会让
生僻字在整句里与常用字平起平坐。

**效果**：真实词库探针的全码打法 **10/12 → 12/12（满分）**。§11.4 记的错例全部自动消失：

| 对抗 | 码表权重带 | 拼音真实词频 |
|---|---|---|
| 个 vs 修 | 851 vs 2135 ✗ | **215733** vs 5839 ✓ |
| 人 vs 八 | 851 vs 851（并列） | **453337** vs 5129 ✓ |
| 我 vs 特性 | 3371 vs 1812 | **889049** vs 14402 ✓ |
| 一 vs 来来回回 | 2831 vs 1298 | **99581** vs 949 ✓ |

**实现要点**：

- `SentenceFreq`：只保留**码表 text 的交集**（6.6 万条、约 3 MB）。全收 60 万条要 20~30 MB，
  而整句只可能用到码表里有的那些。
- 词库走**约定路径** `pinyin/rime_frost.dict.yaml`，不读拼音方案的 schema：整句要的只是
  「一份带真实词频的中文词表」，读 schema 会让码表方案的行为随另一个方案的配置漂移。
- **两级懒**：构建引擎时只交数据目录（`FreqSource::SchemasDir`），词库到**首次整句解码**
  时才读，词频表再在那之后建。⚠️ 这层懒不能省——混输主引擎同样走码表分支构建，
  但它的整句永远调不到（§11.13），构建期加载等于白读一份 60 万条的词库；纯五笔用户若
  从没用过拼音方案，那次加载还要现场构建 `merged.wdat`，直接体现为「切到五笔卡一下」。
- 那份 `merged.wdat` 正是拼音引擎自己用的同一个文件（`reader_pool` 按路径共享 mmap、
  `file_lock` single-flight）⇒ **装了拼音方案的机器上内存不翻倍**，加载也基本免费。
- ⚠️ **两个 `DICT_TOTAL` 必须分开**（`PINYIN_DICT_TOTAL` 2.4e8 / `CODE_DICT_TOTAL` 7e7）：
  两条词频来源量纲差三个数量级，共用一个基准等于给其中一条平白加减一个**按边数累加**的
  罚（`Σ ln(f/T) = Σ ln(f) − n·ln T`）——影响的是「切几段」的判断，不是整体平移。
- ⚠️ `MAX_HOMOGRAPHS` 2 → **8**：`dm.search(code, N)` 按**码表 weight** 降序取前 N，
  而排序用的是拼音词频。**筛选与排序不在同一量纲上时，筛选口必须放宽**，否则真实高频的
  那条在「码表序」里就被筛掉了，后面用什么打分都救不回来。
- 拿不到拼音词库时退回原方案（简码换全码权重 + `trusted_weight`），功能仍在、准确率下降，
  并 `warn!` 一条。单测 `pinyin_freq_overrides_codetable_weight_bands` 把**两条路径的
  相反结论**都锁住了。

### 11.10 组合区切分显示（`preedit_codetable`）

用户反馈：「当前的输入是完全不知道其拆分的处理的」。一长串码配一句话，切错了也无从判断
错在哪一段。

- 引擎侧 `ConvertResult::preedit_codetable` 给出 `aawtaawt` → `aawt'aawt`。
  数据源是 `ViterbiResult::boundary`（**实际走的**那条路径），不是按词长重猜——
  同一串码可有多种切法，谎报切分是拼音侧记过一次的教训。
- 分隔符字符与拼音的音节分隔显示**共用 `'`**：用户不必为码表另学一套符号。
- 协调器侧按**当前高亮候选**切换（`wants_codetable_split`），与既有三种切法
  （拼音音节 / 全拼降级 / 简拼分段）同一套机制。★ 必须排在
  `preedit_split_body.is_empty()` 那道守卫**之前**——码表方案下拼音拆分形态恒空，
  守卫会直接 return 原始码，后面分支一条都走不到。
- 判据抽成自由函数是为了可测：`effective_preedit_body` 收 `&self`，要构造整个
  Coordinator 才测得到，而真正要锁的只是「有切分串 + 高亮的就是那条整句」两条。

### 11.11 手动分隔符

- **键位与拼音完全共用**：`manual_separator_key`（原 `pinyin_separator_key`，语义扩大后
  改名）只是把第一道守卫从「必须是拼音引擎」放宽到「拼音 或 码表整句」，
  `auto`/`quote`/`backtick` 三种模式与「`'` 被占作选词键时改用反引号」的避让逻辑原样复用。
  用户不该为两个方案记两套键。
- 解码按分隔符切成**硬边界**段，各段独立解码后拼接；`boundary` 左移合并回全串空间。
- ★ **「至少两个词」是整体判据，不是段级判据**：`aa'wt` 每段恰好一个词，正是用户敲分隔符
  时最典型的形态。段级判会把它整个否掉。（无分隔符时两者等价，所以此前放在段级没露馅。）
- 冗余分隔符（首尾、连续）容忍；某段解不出则整体无解——分隔符是用户的明确表态，
  不能悄悄跨段重切。
- **实测消歧效果**（真实词库探针，带前提自检）：

  | 输入 | 结果 |
  |---|---|
  | `qjkhlgw` | 旬\|中国\|人 ✗ |
  | `q'j'khlg'w` | **我是中国人** ✓ |
  | `gwhvbrjfwh` | 一\|修好\|的\|时候 ✗ |
  | `g'wh'vb'r'jfwh` | **一个好的时候** ✓ |

### 11.13 混输方案：整句默认关闭，且当前**不会触发**

**事实**：`MixedEngine::convert` 在 `input_len > max_code_len` 时直接走 `convert_overflow`，
**根本不调 `primary.convert`**。而整句的门槛正是「超码长」⇒

| 输入 | 走哪条路 | 整句 |
|---|---|---|
| 码长内（≤4 码） | `primary.convert` | 门槛不满足 ⇒ 不产 |
| 超码长（>4 码） | `convert_overflow`（拼音 + 码表回捞） | 不经主引擎 ⇒ 不产 |
| 超码长 **且没配 `secondary_schema`** | `convert_overflow` 退化为 `primary.convert(整串)` | **会产** |

**开关**：混输主引擎的 `sentence_input` 取**混输方案自己**的 `[engine.codetable]` 声明，
**不继承 `primary_schema`**（`resolve_sentence_input`，有单测锁）；且**只在没配拼音子引擎
（整句真能触发）时才传真**。整句开着会让顶码 / 满码上屏 / 满码空码清空让位（§11.6），一个
不会触发的整句不该白白关掉它们。`wubi86` 开了整句不代表
`wubi86_pinyin` 也该开——否则就是「配置开着却不生效」这种最难排查的状态。

**告知**：若混输方案自己声明了 `sentence_input` 却又配着拼音子引擎，构建时 `warn!` 一条
说明它不会触发、已忽略（顶码 / 满码上屏 / 满码空码清空照常）。别让人对着一个没反应的配置项干瞪眼。

`MixedEngine::sentence_input_enabled()` 如实转发主引擎状态——让「默认关闭」在外部可观测，
也让退化配置（无 secondary）下的分隔符键能正确放行；配着拼音子引擎时它恒 false，
协调器的短语满码上屏也就不让位。

⇒ **混输下要真正支持整句，需要在 `convert_overflow` 里给码表整句一个位置**，那会引入
「拼音整句 vs 码表整句」的竞争（§7.3），是独立的一步。

### 11.14 ★ 懒加载把 660ms 挪到了按键线程上 —— 必须后台预热

**发现**：词库改成「首次整句解码时才读」之后，那笔开销并没有消失，只是换了个落点——
而新落点恰好是**用户敲下第 5 个码的那一刻**（整句的触发闸门就是「超码长且无精确匹配」）。

实测（`codetable_sentence_latency_probe`，本机、页缓存已热）：

| 项 | 耗时 |
|---|---|
| `ShortCodeIndex::build`：码表全表扫描 | ~30–90 ms |
| 打开 82 MB `rime_frost.merged.wdat` + 全表扫建词频 | ~270–570 ms |
| **首次解码合计** | **~300–660 ms** |
| 其后每次解码 | < 0.2 ms |

冷页缓存下只会更久；`merged.wdat` 过期还要现场重建（数秒）。

**修法**：`CodeTableEngine::prewarm_sentence()` 在引擎组装完毕时把两张表推给后台线程
（`CodeSentenceDecoder::prewarm`）。实测 **301 ms → 0 ms**。

★ **「懒加载」只决定「要不要付」，不决定「在哪条线程上付」——这是两个正交的问题。**
省掉不该付的开销（混输主引擎、没开整句的方案）靠的是 `sentence_on` 这个**判据**，
不是靠推迟时机；判据已经把该省的省了，剩下那笔必然要付的，就该挪出按键线程。

**为什么不会更差**：`OnceLock::get_or_init` 保证两条线程抢到同一份结果。极端情况
（预热没跑完用户就打到超码长）按键线程仍会在 `get_or_init` 上等，但那与「不预热」持平，
不会更差。预热**不改变任何取值**——探针以「两条路径的候选逐字相同」为判据锁住这条。

⚠️ **调用顺序有要求**：必须在所有 `with_*` 之后调用。预热线程读的是那一刻的
`freq_source`，早于 `with_sentence_schemas_dir` 就会白跑一趟没有词频的预热
（且 `OnceLock` 已落定，之后再也纠不回来）。

⚠️ **探针的反向对照不能省**：只断言「预热后很快」是假绿——词库没加载成功时两条路都很快。
故同时断言「不预热那条 ≥100 ms」。

### 11.12 剩余误差的性质：真实歧义，不是选错字

简码打法仍是 10/12，但那两条**都不是缺陷**：

- `qj` 既是二简「旬」，也是一简「我」+「是」——击键串**完全同形**；
- `whvb` 既是词「修好」，也是「个 wh」+「好 vb」，而「一修好的时候」本身是合法中文。

⇒ 打分无从区分，**要么上下文模型，要么用户表态**。前者是 bigram（默认关闭、已评估收益
不显著），后者就是 §11.11 的分隔符——实测两条都能救回。
**这也是「智能容忍 + 显式分隔符」这条路线的完整闭环。**
