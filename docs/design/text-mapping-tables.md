# 文本映射表扩展：内置符号组、用户自定义、多表框架

> 本文是 [`emoji-suggestion.md`](emoji-suggestion.md) 的续篇。那份文档记录**已实现**的
> emoji 追加机制；本文回答「把它变成一个能长期扩展的框架」需要什么，以及**先别做什么**。
> 未实施，所有数字均为本机实测（2026-09-07）。

## 1. 三个诉求与一条机制约束

用户提出三件事：内置「对勾 / 红旗 / 加号」这类符号组、开放自定义、以及泛化到任何
「文字映射表」能表达的功能。

在谈方案之前必须先说清一条**机制固有的约束**，它决定了上面三件事哪些做得成：

> **追加式扩展寄生于宿主候选。宿主词打不出来，扩展就够不着。**

`apply_emoji_suggestions` 查的是**已成形候选的最终文本**（`emoji-suggestion.md` §3.2 论证了
它为什么必须钉在管线最末端）。所以「打 `duigou` 出 ✅」这件事，实际发生的是：

```
duigou → 候选里出现「对勾」这个词 → 查表命中 → 追加 ✅ ✔️ ☑️
         ^^^^^^^^^^^^^^^^^^^^^^^ 这一步不成立，后面全部不发生
```

与之相对的是**入口型**能力（短语 `code → text`、符号码表、引导键特殊模式）：它自带编码入口，
不依赖任何宿主词，但要占编码空间、且绑在方案的编码域上。

| | 追加型（本机制） | 入口型（短语 / 码表） |
|---|---|---|
| 数据 | `text → [text…]` | `code → text` |
| 前提 | 宿主词能打出来且排得够前 | 无 |
| 编码空间 | 不占 | 占 |
| 跨方案 | 自动通用 | 绑编码域 |
| 适合 | 打词过程中顺带发现 | 心里明确知道要什么 |

★ 两者**不互斥**，判据是「用户是在找符号，还是在打字时顺带看见符号」。本文只谈追加型；
真要做「打 `chahao` 直接出 ❌」的直达入口，那是短语系统的活，不要在这里重做。

## 2. 决定性实证（先看数据，再谈设计）

下面每条都会改变设计，不是背景介绍。

### 2.1 ⚠️ 宿主词的词频位次决定可用性

内置符号表初稿 59 个键，在主拼音词库里逐个查「该键在其读音下排第几」：

| 覆盖到第几位 | 键数 | 占比 |
|---|---|---|
| 第 1 位（`max_hosts = 1` 即够） | 46 | 82% |
| 前 2 位 | 50 | 89% |
| 前 3 位 | 53 | 94% |
| 前 5 位 | 56 | 100% |

具体的坏样本（现行默认 `max_hosts = 1` 下**完全够不着**）：

```
叉号  第3位  cha hao    前三名: 查好 插好 叉号
星号  第3位  xing hao   前三名: 型号 幸好 星号
心形  第5位  xin xing   前三名: 新型 新兴 心性
打勾  第2位  da gou     前三名: 大狗 打勾 打钩
```

⇒ **两条设计结论**：

1. 符号表需要比 `emoji_word` 更大的 `max_hosts`（建议 3，覆盖 94%）。这不是配置口味问题：
   符号表的键是精选的低频词，命中即强意图；而 `emoji_word` 有 4657 个键、覆盖日常高频词，
   同样调大就是噪音。**⇒ `max_hosts` 必须能按表设，不能只有一个全局值**（见 §4.2）。
2. 选键时**同义多收**是正确策略，成本只是多几行。实测替代键：

   | 原键 | 位次 | 替代 | 位次 |
   |---|---|---|---|
   | 对勾 | 词库无 | **勾选** | 第 1 |
   | 心形 | 第 5 | **爱心** / 红心 | 第 1 |
   | 乘号 | 第 4 | **乘以** / 相乘 | 第 1 |
   | 贝塔 | 第 4 | **希腊字母**（作组键） | 第 1 |

   ★ 用户点名的「对勾」词库里根本没有，「勾选」既在词库又排第 1 —— 这条只有实测才看得出来。

### 2.2 上游表的覆盖缺口正是用户点名的那几个

在归一前的上游表里直查（上游全繁体，故繁简两形都试）：

```
對勾/对勾  無      紅旗/红旗  無      加號/加号  無      箭頭  無      感嘆號  無
打勾  ✅️           勾  ✅️ ✔️ 🪝        加  ➕️
```

⇒ 用户点名的三个叫法上游一个都没有，只有单字形态的「勾」「加」。而**单字键默认被
`min_word_chars = 2` 挡掉**（该默认值是对的，「一 → 1️⃣」噪音最大）。两层原因叠加，
表现就是「对勾、红旗、加号都打不出来」。这正是需要内置补充表的直接理由。

### 2.3 ⚠️ U+FE0F 归一缺失：一个**现存**缺陷

上游 6597 个符号里 **53% 带尾随 U+FE0F**（`✅️` 而非 `✅`，`©️` 而非 `©`）。而
`plan_emoji_insertions` 的 `seen` 去重集按**精确字符串**匹配：

```rust
if seen.insert(e.to_string()) { picked.push(e.to_string()); }
```

`✅` 与 `✅️` 是不同的字符串 ⇒ 去不掉。**这不是将来的问题，现在就在发生**：开了分类表
（`categories = true`）后，`emoji_word` × `emoji_category` 的 14 个交集键里有 3 个当场出重复：

| 键 | 现在用户看到（`max_per_word=3` 截断后） | 应为 |
|---|---|---|
| 奖项 | 🏅️ **🏅** 🎖️ | 🏅️ 🎖️ 🥇 |
| 车 | 🚗️ **🚗** 🚕 | 🚗️ 🚕 🚙 |
| 面包 | 🍞️ **🍞** 🥐 | 🍞️ 🥐 🥖 |

三个配额位里两个是同一个符号。加入内置符号表后会显著恶化：初稿 59 键与上游撞键 21 个，
其中 **11 个裸去重会出重复**（打勾 → `✅ ✔️ ☑️ ✅️`、版权 → `© ©️`）。

⇒ **去重键必须是「剥掉 FE0F 后的形态」，保留先到者的原形**。保留先到者很重要：FE0F 决定
文本呈现还是 emoji 呈现（`✔` 黑白窄字形 vs `✔️` 彩色全宽），谁排前面谁说了算，而排前面的
是我们自己维护的表 ⇒ **呈现形态由内置表决定**，这是内置表的一项职责，不是副作用。

### 2.4 符号跨三套字体渲染，这是对的

内置表初稿的 90 个符号按 `script.rs` 的分类表落段：

| 落段 | 数量 | 例 | 用哪套字体 |
|---|---|---|---|
| `U+2600..27BF` / `U+2B00..2BFF` / `U+1F000+` | 38 | ✅ ❌ ➕ ⬆️ 🚩 | **emoji 字体**（出厂 Segoe UI Emoji） |
| `U+20F1..25FF` / `U+27C0..2AFF` | 25 | ℃ ™ Ⅰ ① ∑ ≈ ∞ | 默认链 |
| 希腊块 | 9 | α β π Ω | 默认链 |
| 标点段 | 9 | © ® ± × ÷ …… | 默认链（声明 punct 才切走） |
| 全角 / CJK 兼容 | 9 | ＋ ％ ￥ ㎡ ㎏ | CJK 字体 |

★ 这个分裂**是刻意的**，不要「统一」它：`script.rs` 的表头注释写明了整段归 Emoji 的代价
（`① ■ →` 会跟着 emoji 字体跑）。数学符号本来就该用文本字体，emoji 该用 emoji 字体。

⚠️ 但有一条连带依赖：初稿里 **14 个符号带 FE0F**（`✔️ ⚠️ ➡️ ❤️ …`），它们要正确显示，
依赖 §10 刚落地的 `font_runs` 回溯改写（把基字连同 FE0F 整体归入 emoji 段）。**内置符号表
不能早于那个修复发布** —— 否则这 14 个会退化成黑白窄字形或缺字框。

## 3. 内置符号表

### 3.1 放哪、什么格式、许可边界

⛔ **不能放 `data/emoji/`**：该目录整个被 `.gitignore`（上游 rime-emoji 是 LGPL-3.0，我们
原样分发不加工，见 `emoji-suggestion.md` §3.5）。把自己写的表混进去会同时弄脏两件事——
入库规则和许可边界。

仓库既有惯例是 `data/system.*.toml` 为自维护数据（`system.phrases.toml` /
`system.quick.toml` / `system.softkeyboard.toml`）。故取 **`data/system.symbols.toml`**，
MIT，随仓入库。

格式取 TOML 而非上游的 `.txt`，两条理由：

- 上游格式有个只对 opencc 成立的怪癖——**值的首项必须重复键本身**（`勾\t勾 ✅️ ✔️`），
  我们解析时按位置丢弃它。自己维护还要遵守一个对自己无意义的约束，迟早写错。
- 几百条要长期手维护，需要分组、注释、以及给整组标属性的能力。

```toml
# data/system.symbols.toml
[meta]
max_per_word = 5      # 表的固有属性，不进用户配置（理由见 §4.2）
max_hosts = 3
min_chars = 2

[[group]]
name = "标记"
[group.entries]
勾选 = "✅ ✔️ ☑️"
打勾 = "✅ ✔️ ☑️"
对号 = "✅ ✔️ ☑️"
叉号 = "❌ ✖️ ❎"
红旗 = "🚩 🏁 🏴"
加号 = "➕ ＋"
```

代码成本：一个 `parse_symbols_toml(&str) -> Vec<(String, Vec<String>)>`，输出类型与现有
`parse_upstream` 完全相同，直接喂 `write_emoji_wemj`。约 40 行，**不新增任何二进制格式**。

### 3.2 四条编写准则，全部可机器校验

这是本设计最该固化的部分——把「这条键选得好不好」从人工判断变成守门测试：

| 准则 | 判据 | 失败时的表现 |
|---|---|---|
| 1. 键必须在主词库里 | 查 `rime_frost` 合并词表 | 该条永远不触发 |
| 2. 键在其读音下排进前 3 | 按词频位次算 | 用户打了却看不见（§2.1） |
| 3. 键长 ≥ `min_chars` | 字符数 | 被 `min_word_chars` 静默挡掉 |
| 4. 同一符号在表内只出现一次（按剥 FE0F 归一） | 归一后比对 | 挤占 `max_per_word` 配额（§2.3） |

★ 准则 2 需要词库，属于**数据依赖测试**。仓里已有先例，且 `project_build_dev_data_missing`
记着一条坑：缺 `build_dev/data` 时这类测试会**静默跳过、计数照绿**。故该测试必须在缺数据时
**显式失败或显式标记跳过**，不能沉默。

### 3.3 初稿规模与**收窄**

实证草稿是 59 键 / 90 符号，分九组（标记、运算、箭头、单位、希腊字母、数字形式、货币、
版权、其它），词库命中 56/59，缺的三个（除号、拉姆达、欧米伽）按准则 1 剔除或换叫法。

⚠️ **但这九组不是 P1 的范围**。§6.1 查明仓里已有 25 组 `$AA` 字符组覆盖了运算 / 箭头 /
单位 / 数字形式 / 货币，按 §6.3 的判断，P1 只收**两组**：

| 收 | 组 | 理由 |
|---|---|---|
| ✅ | 符号标记（勾选 / 叉号 / 红旗 / 加号…） | `$AA` 里没有这组，且用户点名 |
| ✅ | 希腊字母**逐字**（阿尔法→α） | `$AA` 只能整组浏览，给不出词到单字母 |
| ⏸ | 其余七组 | `$AA` 已覆盖浏览，只剩「打词直达」这点增量，等真机反馈再说 |

★ 草稿全表留在设计讨论里备查，**不要整份落库**——那正是 §6.1 警告的「第二套并存符号组」。

## 4. 多表框架

### 4.1 一类一文件，**不**给 `.wemj` 加类别字段

两条路都能表达「多类映射」：

| | A. 格式加 class 字段 | B. 一类一文件（**取此**） |
|---|---|---|
| 格式 | VERSION 1 → 2，读写两侧都改 | **不动** |
| 开关某类 | 查询期过滤 | 不挂那个 reader |
| 合并顺序 | 建缓存时定死 | 查询期按挂载顺序，**改配置立即生效** |
| 查询成本 | 一次二分 | N 次二分（N ≤ 4，各 O(log n)） |
| 基础设施 | 要改 | **零改动** |

B 之所以零改动，是两处现成的接口恰好已经支持：

- `emojidict::load_or_build(tables: &[PathBuf], …)` 本就收表数组；改成一表一缓存只是调用方
  循环，函数签名不动。
- `reader_pool` 的 `EMOJI_POOL` 是 `HashMap<PathBuf, Entry<T>>`，**按路径分键** ⇒ 多个
  `.wemj` 天然并存、天然共享。

★ B 还顺手消掉了 `emoji-suggestion.md` §8 记录的那个坑：现在翻 `categories` 开关要**重建
`.wemj`**，而 Windows 上 rename 覆盖被映射的文件返回拒绝访问（WinError 5），已经踩过一次
（「打开分类词后 emoji 整个消失」）。表越多，这条路径走得越频繁。一类一文件下，开关只是
挂不挂某个 reader，**永远不重建**。

代价是同键合并从建缓存期挪到查询期。这正好是想要的：合并顺序 = 挂载顺序 = 用户可调，
而 §2.3 的 FE0F 归一去重本来就得在查询期做（`seen` 集合在那里）。

### 4.2 表的固有属性 vs 用户的选择

配置面膨胀是真实成本（4 表 × 4 键 = 16 个新配置键，没人调得动）。判据：

> **改这个值需要理解表里装的是什么吗？需要 ⇒ 属于表；不需要 ⇒ 属于用户。**

- `max_per_word` / `max_hosts` / `min_chars` —— 要理解「这张表的键有多精确、值有多长」
  才调得对（§2.1 已证明符号表与 word 表该取不同值）⇒ **写在表自己的 `[meta]` 里**。
- `enabled` —— 用户唯一真正想控制的 ⇒ 进用户配置。

⇒ 用户配置只增加**每表一个 bool**，其余由表自带、随表升级。

### 4.3 挂载配置：照抄 `[[ui.comment_dicts]]`

仓里已有一模一样的问题被解过——注释库的多表挂载（`data/config.toml:903`）：

```toml
[[ui.comment_dicts]]
id = "emoji"
label = "Emoji 名称"
path = "comments/emoji.dict.yaml"
enabled = true                      # 缺省视为 true
schemas = []                        # 留空 = 全部方案
```

四条可直接继承的决定：**数组顺序即优先级**（正是 §4.1 要的合并顺序）；`enabled` 缺省为
true（「配了没反应」比「多加载一份」难查得多）；`schemas` 限定作用域省无谓开销；
`config_schema` 里登记为 `StructList` 不透明叶子。

出厂形态（三条内置 + 用户表槽位）：

```toml
[[input.emoji.tables]]
id = "symbols";  path = "system.symbols.toml";  enabled = true   # 我们维护，MIT
[[input.emoji.tables]]
id = "word";     path = "emoji/emoji_word.txt"; enabled = true   # 上游，LGPL
[[input.emoji.tables]]
id = "category"; path = "emoji/emoji_category.txt"; enabled = false
```

⚠️ **迁移**：现有 `input.emoji.categories`（bool）要变成 `tables` 里 category 那条的
`enabled`。`project_config_field_type_change_migration` 记着：配置字段改类型**必须加 Value
层迁移**，否则老用户的配置静默回落出厂值。

### 4.4 ⛔ 接点不能挪到 `finalize_candidates`

一个看着很有道理、实际会引爆 `emoji-suggestion.md` §3.2 整张表的建议：
「`finalize_candidates`（`handle_candidate.rs:773`）已经在五条路径上接好了，把追加也挪过去，
顺手覆盖 overlay 路径」。

**不行。两者位置要求相反**：

| | `finalize_candidates` | `apply_emoji_suggestions` |
|---|---|---|
| 干什么 | 把候选值里的 `$AA` / `$CC` / `{..}` 展开 | 按最终文本追加新候选 |
| 必须在加工的 | **之前**（展开出来的候选还要参与去重/过滤/重排） | **之后**（§3.2 论证过，四道加工每道都会咬它一口） |
| 正常路径调用点 | 第 919 行 | 第 1291 行 |

中间隔着的 372 行正是排序、去重、`apply_filter`、`apply_freq_rerank`、`apply_shadow`。
在 919 行追加 emoji ⇒ 参与去重造出假同码、`is_common` 恒 false 被整批静默滤掉、
选一次就永久顶到汉字前、打乱用户的置顶规则。**四个坑一次全踩**。

★ 正确的覆盖办法：**每条路径在自己写入 `state.candidates` 之前各调一次**，因为每条路径的
「加工完成点」在不同位置。overlay 路径（`handle_mode.rs:1789`、`handle_special.rs:378/406`、
`handle_temp.rs:374/1006`）都是直接赋值、没有完整的过滤重排管线，在它们的写入点接是安全的。
判据始终是「在**该路径**的全部加工之后」，不是某个函数名。

## 5. 编辑能力

三种诉求，落点各不相同（`emoji-suggestion.md` §9 已定方向，此处补落点与入口）：

| 诉求 | 例 | 落点 |
|---|---|---|
| 加自己的 | 「猫猫」→ 🐱 | 用户表，挂在 `tables` 最前 |
| 调顺序 | 「开心」下 😊 排 😄 前 | 同上 —— 整行重写一遍即可 |
| 不要某个 | 「一个人」不出 👤 | 用户覆盖层（**不是**改表） |

★ 前两项被同一个机制覆盖：**用户表挂在数组最前 + 合并保序** ⇒ 用户写的既是新增也是排序。
不需要单独的排序数据结构。

「隐藏」必须与表分开：表是全量数据，隐藏是对全量数据的**稀疏否定**。把隐藏写成「把那条从
表里删掉」的话，上游表一升级就全丢。

⛔ **不走 shadow**（置顶/前移/后移那套）：shadow 主键是 `(schema, code, text)`，按输入码落键；
同一个词在五笔和拼音下码不同，规则得写两份，宿主词一换就成孤儿。emoji 的归属是**词**不是码。
这也是为什么 `handle_menu.rs` 与 `candidate_op` 两端各有一道 `is_emoji_suggestion` 守卫。

**入口三处，分工不重叠**：

1. **右键菜单**（就地、单条）：只给「不再显示此符号」与「编辑符号表」两项。⛔ 不要复用
   置顶/前移/后移——那是跨候选的位置语义，符号只在自己那个词的小列表里有序，两套语义
   混在一个菜单里只会误导。
2. **外部编辑对话框**（批量）：⛔ **不要自造两栏映射编辑器** —— wind-setting 是 Rust 原生
   GUI（自研 windui），**没有动态增删行的映射编辑原语**，自造成本远高于复用。字符类已经把
   这套对话框做成了**领域无关的壳**（`wind-setting/src/pages/dict/external_edit.rs`），接入
   只需填一份 `ExternalEditDomain` 描述符（title / probe / export / import / key_param /
   new_label / file_filter / summarize，约 10 行）+ core 侧三个 RPC
   （`emoji.editFile` / `emoji.exportEdit` / `emoji.importFile`）。
   「导出完整视图 → 用户改 → 回读折成 diff → 试算 → 确认才写」整套状态机白拿。
3. **设置页列表**（浏览、撤销）：只做只读列表 + 「已隐藏」的撤销按钮，逐条编辑交给 2。

### 5.1 用户层存 redb，不存文件（⛔ 推翻 `emoji-suggestion.md` §9 的写法）

§9 原本规划 `<userdata>/emoji/emoji_user.txt`。**这条要改**：仓里已经有一模一样的问题被解过
并留下了判据（`wind-store/src/charsets.rs` 模块文档）：

> 用户层曾是 `{user_config}/charsets/` 目录（2026-09-04，未发布即改）。改成表的理由只有
> 一条：**程序和人不能写同一个文件**。设置页改一个开关要重写文件，用户此时若在编辑器里
> 开着那份文件，谁后保存谁赢，另一方的改动静默丢失。

这条**逐字适用**于 emoji 用户表：右键「不再显示此符号」与设置页的两栏编辑器都会写它，
用户也可能同时拿编辑器改导出的副本。⇒ 新建 redb 表 `emoji_user`，与 `charset_user` 完全同型：

```rust
/// key = 宿主词，value = JSON `{added: [符号…], hidden: [符号…]}`。
pub(crate) const EMOJI_USER: TableDefinition<&str, &[u8]> = TableDefinition::new("emoji_user");
```

**按词分行而非整表一行**：右键「不再显示此符号」只改一行，不必读-改-写整份；`charset_user`
的分行粒度也是「一个逻辑单元一行」（一个类一行），此处的逻辑单元就是词。
★ **加表成本≈零**：`init_tables` 在写事务里 `open_table` 即创建；`migration.rs` 至今是空壳、
`CURRENT_VERSION` 仍为 1，后加的三张表（`quick_format` / `common_chars` / `charset_user`）
文档里都写着「新表无需迁移」。

**`added` 与 `hidden` 走两条完全不同的路，这是本节最要紧的一句**：

| | 消费时机 | 理由 |
|---|---|---|
| `added`（加自己的 + 定顺序） | **建缓存期** | 导出成生成文件，作为 `tables` 的第一张传进 `load_or_build`；`write_emoji_wemj` 本就同键合并保序，用户的行排前面自然赢。零新格式 |
| `hidden`（不要某个） | **查询期** | 在 `plan_emoji_insertions` 的 `seen` 集合里预先装入被隐藏的符号，接入一行 |

⚠️ **隐藏绝不能放建缓存期**：右键点一次就要重写文件、重算指纹、重建 `.wemj`、重新 mmap，
还得走「先把旧 Arc 置 None 再 rename」那套（否则 Windows 上 rename 覆盖被映射的文件返回
拒绝访问）。§4.1 的一类一文件刚把 `categories` 那条重建路径消掉，隐藏走构建期等于把它
换个地方请回来。走查询期则右键即时生效、永不重建。

★ 隐藏判定与 §2.3 的剥 FE0F 归一**共用同一个 `seen` 集合与同一套归一**，否则会出现
「隐藏了 ✅ 但 ✅️ 还在」这种两套判据分叉。

**与 `.wemj` 缓存的衔接**：`sync_emoji_dict` 每次把 `added` 导出成
`<cache>/emoji/emoji_user.gen.txt` 再走 `load_or_build`。这层导出**不会引发重建风暴**——
指纹是**内容指纹不是 mtime**（`cache_fp.rs`，当初正是被部署刷 mtime 导致每次重建 300MB
逼出来的），内容没变指纹就没变，缓存照常命中；用户一条都没加时文件不存在也没关系，
`fingerprint` 把 `NotFound` 编码成「稳定地不存在」记 0。
⚠️ 那份生成文件里**不含** `hidden`（它在查询期消费）；导出给用户编辑的交换格式则两段都要有，
解析器须显式跳过 `hidden` 段，否则接手的人会以为漏实现了。

## 6. 泛化：先划线，再谈做什么

### 6.1 ⚠️ 先看清：符号组仓里**已经有了**，25 组

`data/system.phrases.toml:141-261` 有 25 条 `$AA` 字符组，按**编码**触发，
经 `finalize_candidates` 展开，正常 / 特殊模式 / mix / 临拼 / 临英五条路径全部生效：

```toml
code = 'zzys'
text = '$AA("圆圈数字", "①②③④⑤⑥⑦⑧⑨⑩")'
```

覆盖面（实测全表）：标点（含 ± × ÷ ∑ √ ≈ ≠ ≤ ≥ ∞ ℃ ☆ ★ → ← ↑ ↓）、数学符号、
特殊符号、单位 `㎎㎏㎜㎝㎞㎡㏄`、货币 `＄￠￡￥¤`、箭头 `→↑←↓↖↗↘↙`、
罗马数字大小写、希腊字母大小写、俄文大小写、圆圈/括号/点号/中文数字、
上标 `¹²³`、下标 `₁₂₃`、拼音声调、注音、平假名、片假名、偏旁。

⇒ **本文初稿里「数学运算 / 单位计量 / 希腊字母 / 数字形式 / 箭头方向」五类全部已存在**，
不是待做项。⛔ 不划清这条线就会做出第二套并存的符号组，然后开始纠结两边的组名、顺序、
以及用户改了一边为什么另一边不变。

### 6.2 两种触发方式的分工

| | `$AA` 字符组（已有） | 追加式映射（本框架） |
|---|---|---|
| 触发 | 打编码 `zzjt` | 打词，候选里出现「箭头」 |
| 产出 | 整组炸开供浏览 | 该词对应的那几个 |
| 前提 | 记得住编码 | 词打得出来且排得够前 |
| 一句话 | **给我看这一类的全部** | **这个词对应的那几个符号** |

⇒ **判据：用户会用中文词去找它吗？**

- 「阿尔法 → α」：会。而 `$AA` 只能整组浏览希腊字母，给不出单个词到单个字母的映射 ⇒ **本框架有价值**。
- 「上标 ¹²³」：不会有人用中文词找单个上标字符，整组浏览才是对的形态 ⇒ **`$AA` 更合适，不要重做**。
- 「勾选 → ✅✔️☑️」：会，且用户点名了 ⇒ **本框架的主场**。

### 6.3 据此重排的适配清单

| 类别 | 例 | 判断 |
|---|---|---|
| **符号标记** | 勾选→✅✔️☑️、叉号→❌✖️、红旗→🚩 | ✅ **P1 唯一必做**：`$AA` 里没有这组，且用户点名 |
| **希腊字母（单个）** | 阿尔法→α、圆周率→π | ✅ 值得做：`$AA` 只有整组浏览，给不出词到字母 |
| **单位（单个）** | 摄氏度→℃、平方米→㎡ | ⚠️ 边际：`$AA` 的单位组已覆盖浏览，只有「打词直达」这点增量 |
| **数学 / 箭头 / 罗马数字 / 序号** | | ⚠️ 同上，`$AA` 已有整组；除非真机上发现「记不住编码」是主要痛点，否则先不做 |
| **颜文字** | 开心→(^▽^) | ❓ 未定：值是长串，与「一格一符号」的排版假设不同，先在真机上看一行放不放得下 |

### 6.4 ⛔ 不做

| 想法 | 为什么不做 |
|---|---|
| 花体 𝓗𝓮𝓵𝓵𝓸、任意数字转上下标、拼音声调标注 `pin1→pī` | **函数式**：对任意输入按规则变换，键集无法枚举。★ 注意与 `$AA` 的上下标组区分——那是**固定字符集的浏览**（有限、可枚举），不是变换 |
| 打 `alpha` → α、`\sum` → ∑、`:)` → 😊 | **方向反**：`code → text`，属英文方案 / 码表 / 引导键特殊模式 |
| 繁简、地区变体 | 已有专门通路（出口转换 octrie），重做只会分叉 |
| 邮箱、地址、日期模板 | 短语系统已覆盖，且那里能求值（`$Y年$M月`），这里不能 |
| 全角半角互转 | 已有独立开关 |

★ 第一行是最容易被要求、也最该拒绝的一类：看着「也是文字映射」，实际是**变换函数**。
一旦开口子，表格式就要长出「模式匹配」维度，那条路的终点是又一个正则引擎。

## 8. 已知坑

- ⚠️ **内置符号表不能早于 `font_runs` 回溯改写发布**（§2.4）：14 个带 FE0F 的符号依赖它。
- ⚠️ **`max_hosts` 调大会放大所有表的噪音**，不只符号表 ⇒ 必须按表设，别改全局默认。
- ⚠️ **守门测试依赖词库**，缺 `build_dev/data` 时会静默跳过、计数照绿
  （`project_build_dev_data_missing`）⇒ 缺数据必须显式失败。
- ⚠️ **`categories` 改类型须加 Value 层迁移**，否则老用户静默回落出厂值。
- ⚠️ **`reader_pool` 的 `Close` 是配额语义、非幂等**：多表动态挂卸时重复调用会吃掉别人的
  引用计数（这条在单表时已记，多表下触发面变大）。
- ⚠️ **加 redb 表要同改备份还原四处**：`wind-transfer/src/backup.rs` 的 `create_backup` 写入、
  `section_of`、`restore_backup` 的 sections 过滤，以及 `apps/service/src/backup_cli.rs` 的
  `RESTORE_SECTIONS` 白名单。★ 该白名单**现在就是破的**：缺 `common_chars` 与 `charset`，
  而备份侧早已在写这两类，它自己的文档注释写着「白名单须覆盖备份包实际写入的全部 type」
  ⇒ 加表时顺手补上。
- ⚠️ **跨仓**：wind-setting 是 Rust 原生 GUI 不是 Web 前端，新 RPC 要在那边补一条 mock 分支，
  否则 mock 模式下静默返回 null；操作列加按钮必须同步调 `CategorySpec::actions_weight()`，
  否则按钮被静默挤出可视区。
- 符号候选与 emoji 候选共用 `is_emoji_suggestion` 标记位。该位的语义是「这条是扩展来的」这个
  **客观事实**，不编码任何排序或显示决策 —— 加符号表**不需要**给它加值域，四个消费点
  （自动上屏跳过 / 词频排除 / 排序 / UI 标注）对符号的期望与 emoji 完全一致。
  ⛔ 尤其**不要**加第二个 `is_symbol_suggestion`：该位现有 9 个消费点，新类在每一处的行为
  与 emoji 逐字相同，加一位就是 18 处。要区分来源只能挂一个**不参与任何守卫判据**的来源 id，
  仅供菜单显示「来自：符号表」。⛔ 更不要拆成枚举让 9 处各自 match —— 那正是该字段文档里
  列过三次前科（`is_prefix` 被短语借作「非精确层」等）的同一种分叉。
- **菜单端与写端两道守卫必须同时放开**（`handle_menu.rs` 与 `candidate_op`），只放一端就是
  「点得动没反应」或「明明不能用却亮着」。
